# matter-plan-builder

将商定的范围转化为团队真正可以据以执行的结构化事项计划。阶段、工作流、里程碑、依赖关系、责任人分配、事项设置 — 外加使计划在整个执行过程中保持最新的维护架构。

## 本技能的功能

只存在于合伙人脑海中的计划不是计划。它是意图。本技能的功能是让计划显性化：分配归属、排定工作顺序、标记依赖关系，并产出一个其他每一项 LPM 纪律都可以引用的产出。

技能按事项复杂度和规划阶段缩放为五种模式：

**模式 1 — 完整计划。** 从范围到完整计划。事项计划加每个工作流的工作流计划。适用于具有明确团队的中等复杂度事项的默认模式。与计划一并产出事项设置建议。

**模式 2 — 仅事项计划。** 阶段、工作流、里程碑和责任人。工作流计划是工作流负责人的职责 — 技能产出事项计划及他们应遵循的模板。专为大型多辖区项目设计，因为在这种项目中，由中心完成全部工作流规划是不切实际的。

**模式 3 — 工作流计划。** 单一工作流或辖区，细化到任务层面。由工作流负责人持有和维护。

**模式 4 — 滚动波（Rolling wave）。** 完整规划当前阶段；后续阶段仅以里程碑作桩。用于完整范围尚未定义时 — 常见于监管事项、第二阶段范围取决于第一阶段认定的复杂交易，以及动员初期的大型项目。

**模式 5 — 依据往来函件更新计划。** 实践中使用最频繁的模式。接受电子邮件、通话记录或会议记录，并以确认清单的形式提出对现有计划的更新建议。LPM 逐项确认、驳回或编辑。确认后，更新后的计划作为新版本产出。

**模式 5 之所以存在，是因为替代方案 — 请律师直接更新计划 — 行不通。** 律师不会更新计划。信息存在于他们的电子邮件和他们的脑海中。LPM 的工作是从这些来源提取信息。模式 5 消除了人工提取步骤：Claude 读取往来函件、提出更新建议，LPM 的角色从数据录入转变为判断。

## 与其他 LPM 核心技能的关系

本技能位于 LPM Core 架构的中段。它消费 matter-intake-scoping 的范围，并产出下游一切内容所引用的基线：

**matter-intake-scoping** → 范围摘要直接输入计划。模式 2 的输出去向字段按设计映射到计划输入 — 纳入项对应工作流范围，排除项对应 OOS 标记，约束对应阶段时长限制，里程碑对应事项计划里程碑清单。

**scope-change-controller** → 完成的计划是 scope-change-controller 在整个事项中管理的范围基线。经批准的范围变更作为模式 5 触发源回流，产出带版本的计划更新。

**timeline-generator** → 带依赖标记的任务清单（含 FS/FF/SS/SF 标签）是 timeline-generator 进行关键路径计算和假设分析的主要输入。

**status-report-drafter** → 里程碑登记册是报告基线。进度按里程碑报告，而非按任务完成百分比。

**risk-and-issues-manager** → 信息依赖关系和计划假设是事项启动时 RAID 日志的种子条目。

## 输入

- 来自 matter-intake-scoping 的范围摘要（结构化、字段映射）
- 聘用函（Engagement letter）、条款纲要（heads of terms）或等效的范围描述
- 团队名册（或确认姓名待定 TBC — 技能在继续前会询问）
- 可比事项的先前计划（可选，用作规划先例）
- 在 M365 连接模式下：SharePoint 文档、先前事项计划、Outlook 启动往来函件

## 产出

所有产出均以 .docx 生成。每份计划都附有一份结构化数据导出（CSV），用于 SharePoint List 导入 — 这正是使模式 5 更新和连接模式监控成为可能的机制。

- 事项计划（.docx）：事项计划、每个工作流的工作流计划、事项设置建议、RAID 日志开账条目、沟通日程表、跨技能交接提示
- 结构化数据导出（.csv）：所有任务和里程碑条目，含完整字段集
- 计划版本历史：每次更新都会产出一个新的带版本文件 — v1.0、v1.1 等。先前版本作为事项审计轨迹保留
- 工作流负责人模板（模式 2）：负责人为其工作流计划必须遵循的格式

## 标准任务字段

每份计划中的每个任务条目包含 13 个字段：

唯一 ID（事项范围内、稳定、绝不重新分配）| 任务 ID（人类可读、计划内引用）| 任务摘要 | 任务描述 | 责任人 | 截止日期 | 时长（天）| 前置任务 | 依赖类型（FS/FF/SS/SF）| 里程碑 | 状态 | 进度备注 | 任务代码

缺少其中任何字段的计划条目都无法驱动执行、状态报告或升级。它是一份清单，而非计划。

## 事项设置决策

事项设置是本技能的一部分 — 而非计划完成后委托给计费管理的行政任务。事项在计费系统中的配置方式（单一事项 vs 分阶段结构、任务代码设计、计费指令）直接决定您日后能提取哪些数据。设置时出错会让整个项目在整个生命周期内付出代价。本技能与计划一并产出事项设置建议，并在启动时分发计费指令。

## 结构化数据导出与 SharePoint List

每份计划产出都包含一份带完整任务和里程碑字段集的 CSV 导出。这就是 SharePoint List 模式 — 部署本技能的律所应在事项设置时，使用初始计划构建的结构化导出来配置 List。

只以 Word 文档形式存在的计划无法由 Claude 更新。位于 SharePoint List 中的计划可以。结构化导出正是连接两者的桥梁。

## 跨技能交接

- **来自 matter-intake-scoping：** 模式 2/3 范围摘要 — 通过步骤 1 中的字段映射表消费
- **来自 scope-change-controller：** 经批准的范围变更触发模式 5；确认后计划定版
- **至 timeline-generator：** 带 FS/FF/SS/SF 标签的依赖标记任务清单
- **至 scope-change-controller：** 完成的计划作为范围基线传递
- **至 status-report-drafter：** 里程碑登记册和工作流结构作为报告基线
- **至 risk-and-issues-manager：** 信息依赖关系和假设作为 RAID 日志种子条目
- **至 billing-cycle-manager：** 任务代码结构和计费指令

## M365 连接模式

当 M365 MCP 连接器启用时（Claude Team/Enterprise），本技能可以搜索 SharePoint 获取同类型事项的先前计划、提取范围摘要和聘用函、在 Outlook 中搜索启动往来函件、根据事项计划创建启动日历邀请，并将已批准的任务和里程碑推送到 Planner 或 Teams 进行实时跟踪。

无连接器时：通过直接粘贴或上传提供范围摘要、先前计划和往来函件。
