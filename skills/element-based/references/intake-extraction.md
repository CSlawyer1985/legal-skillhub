# 信息取数与要素抽取规范

本文件规定 Agent 在生成要素式诉状前，如何从用户提供的各类材料中系统性地抽取、标注和补充案件信息，确保值表 JSON 完整、准确、无冲突。

---

## 1. 信息来源清单

Agent 应主动识别并利用以下所有信息来源，而非仅依赖用户口述：

| 来源类型 | 描述 | 优先级 |
|---|---|---|
| 本次对话中已陈述的案情 | 用户在当前会话中以自然语言描述的事实、诉求、背景 | 高（但需核对） |
| 过往对话（如有） | 之前会话中用户提供的案件信息（若在上下文窗口内） | 高（但需核对） |
| 旧版/传统诉状 | 用户或律师此前起草的传统格式起诉状，含诉讼请求、事实与理由全文 | 高 |
| 合同/协议/借条/欠条 | 双方签订的书面文件，含条款、金额、时间、违约条款 | 高 |
| 微信/短信/QQ 等聊天记录 | 当事人之间的电子通信记录，常含转账记录、催款记录、承诺等 | 中 |
| 谈话笔录/询问笔录 | 公安、法院、仲裁机构或律师制作的谈话记录 | 中 |
| 证据材料（照片/视频说明/鉴定报告） | 用于证明特定事实的各类证据，提取其中的事实信息 | 中 |
| 已生效判决/裁定/仲裁裁决 | 含已确认的事实和法律关系，可直接引用 | 中 |
| 行政处理决定/通知书 | 行政机关出具的文件，如工商处罚决定、劳动仲裁决定书 | 中 |
| 其他文书（律师函、催款函、保全裁定等） | 可提取时间节点、金额主张、当事人信息等 | 中 |

---

## 2. 各格式材料读取方式

| 格式 | 读取方式 | 注意事项 |
|---|---|---|
| 对话/粘贴文本 | 直接解析，无需额外工具 | 注意用户口述可能有误，需与文件材料交叉核对 |
| `.docx`（Word） | 使用 python-docx 库或 docx 工具读取文本内容 | 注意表格内容需单独读取，不得遗漏 |
| 老式 `.doc`（Word 97-2003） | 先将 `.doc` 转换为 `.docx`（可使用 LibreOffice 命令行或在线转换），再按 `.docx` 读取 | 直接读 `.doc` 容易乱码，必须先转格式 |
| `.pdf`（文本型） | 使用 Read 工具或 pdfminer/pdfplumber 等库解析文本层 | 判断是否为文本型：能选中文字则为文本型 |
| `.pdf`（扫描型） | 无文本层，按图片处理，交由 LLM 视觉 OCR 识别文字 | 识别率取决于扫描质量；关键数字（金额、日期、编号）需用户确认 |
| 图片（JPG/PNG/BMP 等） | 依赖 LLM 多模态视觉能力进行 OCR 识别 | 模糊/手写/斜角拍摄的图片识别率较低，建议请用户提供清晰图片或手动录入关键信息 |
| 截图 | 同图片处理方式 | 聊天截图可能含有用户名、时间戳等有用元数据，需一并提取 |

## 3. 核心抽取要点

对于任何类型的材料，优先抽取以下类别信息：

### 3.1 当事人身份信息

- 自然人：姓名、性别、出生日期、民族、身份证号码、住所/户籍地、经常居住地（如与户籍地不同）、联系方式。
- 法人/非法人组织：完整名称、统一社会信用代码、注册/工商地址、法定代表人/主要负责人姓名及职务、联系电话。
- 委托代理人（如有）：姓名、单位、职务、联系方式、授权范围（一般/特别）。

### 3.2 关键时间节点

- 合同/协议签订日期。
- 履行期限/还款期限/交货期限等约定节点。
- 违约/侵权行为发生日期（催款无果日、拒绝履行日、侵权发生日等）。
- 催款/发函/仲裁申请等维权时间节点。
- 已申请诉前保全的时间（如有）。

### 3.3 金额与标的

- 合同约定金额/借款金额/赔偿金额。
- 已实际支付/收到的金额（含分批付款情况）。
- 尚欠/未付/损失金额。
- 约定利率/违约金率及计算方式。
- 其他可量化损失（律师费、鉴定费等）。

### 3.4 合同或约定内容

- 合同编号、名称、签订主体。
- 合同标的（货物/服务/资金/不动产等）及数量/规格。
- 付款/履行方式与期限。
- 违约责任条款（违约金约定、损失赔偿方式）。
- 纠纷解决方式约定（仲裁条款/协议管辖条款）。
- 利率约定（借贷合同）。

### 3.5 违约/侵权事实

- 被告具体违约行为描述（逾期付款、拒绝交货、擅自解除合同等）。
- 违约行为的持续时间和次数（如有多次）。
- 侵权行为的具体方式、时间、地点、对象（侵权案件）。
- 原告已采取的催告、诉前通知等措施及结果。

### 3.6 已产生的损失

- 直接损失金额（货款损失、本金损失等）。
- 利息损失（含计算起止日、利率）。
- 违约金（含合同依据和计算结果）。
- 其他损失（运费、鉴定费、律师费、误工费、医疗费等，逐项列明）。
- 已保全财产情况（如有诉前保全）。

## 4. 取数流程：汇总 → 标注 → 补缺

### 4.1 汇总

读取用户在本次交互中提供的全部材料，将所有案件信息统一归并到该案由对应的要素 schema（参见 `assets/template_index.json` 中该案由的 `text_keys` 和 `checkbox_groups`）。

操作要点：
- 不遗漏任何已提供的材料，包括附件、截图、长段文字等。
- 对跨多份材料描述同一事实的内容进行合并，提取出最完整的版本。
- 暂不判断正确性，先将所有来源的信息并排记录。

### 4.2 标注

对要素 schema 中的每一个要素字段，根据汇总结果标注其状态：

| 状态 | 含义 | 处理方式 |
|---|---|---|
| **已知** | 从已有材料中可明确获取该要素的值，且各来源一致 | 直接采用，填入值表 |
| **冲突** | 从两个或以上来源获取了该要素的不同取值，存在矛盾 | 列出所有取值和来源，**主动向用户确认**，不擅自取舍 |
| **缺失** | 无法从已有材料中获取该要素的值 | 区分必填/关键 vs. 非必填，仅对前者向用户询问 |

**要素重要性分级**：
- **必填**：`assets/template_index.json` 中标记为 `required: true` 的字段；模板核心要素（当事人身份信息、诉讼请求核心内容、关键事实时间和金额）。
- **关键但非必填**：对诉请成立有实质影响的信息（违约事实具体情节、证据说明等）。
- **非必填/可留空**：与本案无关的要素，或模板说明允许留空的字段。

### 4.3 补缺

仅对仍处于"缺失"状态的**必填和关键**要素向用户提问，遵循以下原则：

- **分批询问**：将需要补充的信息按逻辑区块（当事人信息 → 诉讼请求核心 → 关键事实 → 证据清单）分批次提问，每批不超过5-6个问题，避免一次性列出过长的问题清单令用户感到困扰。
- **优先必填项**：先问当事人基本身份信息，再问诉讼请求的核心金额/标的，最后问细节。
- **不追问无关项**：与本案纠纷类型无关的要素字段，直接填"无"或留空，不向用户询问。
- **示例引导**：对于用户不熟悉的法律概念（如"经常居住地"、"统一社会信用代码"），提供简短的解释和示例，帮助用户准确作答。

## 5. 多源冲突处理

当同一要素在不同来源中呈现不同取值时，不得由 Agent 擅自决定采用哪个值，必须遵循以下流程：

### 5.1 识别冲突

冲突的典型场景：
- 旧诉状中写的借款金额为10万元，但借条原件上写的是9.8万元。
- 合同约定还款日期为2023年6月30日，但用户口述说"7月份到期"。
- 当事人姓名在一份材料中为"王丽"，另一份为"王莉"（同音异字）。
- 两份聊天记录显示利率约定不同（一处3%/月，另一处4%/月）。

### 5.2 汇报冲突

向用户清晰呈现冲突：
- 明确指出哪个字段存在冲突。
- 列出所有不同取值及其来源（"借条原件显示……；旧诉状中写……"）。
- 礼貌但明确地请求用户确认以哪个为准。

示例报告格式：
```
发现信息冲突，需要您确认：

借款金额
- 借条原件（2023年1月5日）：人民币98,000元
- 旧诉状（2024年2月草稿）：人民币100,000元

请问以哪个为准？
```

### 5.3 等待用户确认

收到用户确认后，以用户指定的取值更新值表，同时在自检报告中记录"此处以用户于[日期]确认的[取值]为准"。

---

## 6. 抽取完成后的值表校验

在向模板填充值表之前，执行以下快速校验：

| 校验项 | 方法 |
|---|---|
| 必填字段无空缺 | 对照 `required: true` 字段列表，确认每项均已填值 |
| 金额计算一致 | 本金 + 利息 + 违约金 + 其他损失 = 诉请总额（含误差说明） |
| 时间逻辑无矛盾 | 借款日 < 到期日 < 催款日 < 起诉日；侵权发生日 < 起诉日 |
| 完整表述与要素逐项一致 | 逐条对比诉讼请求的完整表述与逐项要素中的每一条 |
| 当事人名称前后一致 | 各区块中原被告的称谓/姓名/名称一致 |
| 当事人主体类型明确 | 拆分型模板须在 `party_types` 中标明原告、被告为自然人或法人/非法人组织；没有第三人则标明 `第三人: 无`，以便删除不适用表格行 |
| 勾选项无互斥冲突 | 每组互斥勾选项只有一个被选中 |

校验发现的问题，在生成 `.docx` 后的自检报告中向用户如实报告，不得隐瞒或自行修正（除明显笔误外，笔误须注明"已更正为……，请核对"）。
