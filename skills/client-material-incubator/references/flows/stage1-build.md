# 阶段1 · 模板制作（教+做，详细流程）

> 本文件由 SKILL.md 按需加载。适用：律所已备好 DOCX 模板，开始建库。

## 先确认制作模式

> 「贵所希望母版制作在**线上（云文档）**还是**线下（本地）**？
> - **A. 线上（推荐）**：母版上传至云文档模板库（**腾讯文档**或**金山文档**二选一），**所内同事可直接在线查看与复用**，模板成为律所共享资产；生成时通过三步法产出在线文档，交付链接，可在线协作编辑。
>   - **A1 腾讯文档**：需已连接腾讯文档（tencent-docs connector 或 tencent-docs Skill）
>   - **A2 金山文档**：需已连接金山文档（kdocs connector 或 kdocs Skill）
> - **B. 线下**：母版以 DOCX 保存于本机，生成产出本地文件，完全离线；同事复用需自行拷贝。
>
> 两种模式在脱敏、分析、变量化环节流程一致，仅在「入库与生成交付」环节走不同路径；选定后全程按该模式执行，中途可切换。」

## 前置条件检查（选择模式时同步执行）

| 模式 | 前置条件 | 未满足时的处理 |
|------|----------|----------------|
| **A1. 线上（腾讯文档）** | 智能体已连接腾讯文档（connector 已启用），或已加载具备腾讯文档操作能力的 Skill（如 tencent-docs） | 提示客户：① 先完成腾讯文档连接后再继续；② 或切换至金山文档/线下模式继续，流程不受影响 |
| **A2. 线上（金山文档）** | 智能体已连接金山文档（kdocs connector 已启用），或已加载 kdocs Skill | 提示客户：① 先完成金山文档连接后再继续；② 或切换至腾讯文档/线下模式继续，流程不受影响 |
| **B. 线下（本地）** | 本地 Python 环境已安装依赖：`pip install -r requirements.txt`（核心依赖 python-docx、requests） | 引导客户先在 Skill 目录执行安装命令；无 Python 环境时按 `references/teaching/` 准备清单指引安装 |
| 录音通道（阶段2 可选） | 本地 ASR 已安装（faster-whisper） | 引导按 `references/whisper-intro.md` 安装，或改用对话/笔录通道 |

检查逻辑：线上模式被选中时，先验证对应云文档（腾讯文档或金山文档）的连接状态；不可用时如实告知客户并给出其他路径，**不得静默回退或假装可在线**。

## 存储位置确认（按模式，首次入库前执行）

- **线上（云文档）**：与客户确认母版在云文档中的存放位置——推荐为贵所建立专门的「模板库」空间/文件夹（腾讯文档空间或金山文档云盘目录），**全部母版统一存放**，命名 `<文书类型>（母版）`；空间/文件 ID 记录于 manifest 与进度登记；生成时三步法从该位置复制母版，**所内同事可在该空间直接查看与复用**。
- **线下（本地）**：与客户确认母版存储文件夹——推荐新建「母版库」文件夹，**全部母版统一存放**，命名 `<文书类型>（母版）.docx`；文件夹路径记录于 manifest 与进度登记，客户可随时自查；系统不将母版散存于无关目录。

## 批量投喂引导

> 「贵所可将整套材料包的模板**一次性投喂**，支持两种方式：
> ① **直接将 DOCX 文件拖拽到聊天框**（推荐，可一次拖入多份）；
> ② 提供文件路径列表。
> 系统将自动分类并按批次处理；建议一次性投喂整套（3-6 份），便于统一脱敏审核与材料包分组。也可逐份投喂。」
>
> 💡 **精准指令提示**：投喂时顺带说一句「这是哪类文书、用来做什么」（如「这是授权委托书，请识别变量建母版」），分类更准、识别更快——详见 `references/prompt-skills.md`。

## 每份模板六步走

先教后做，每步一句话解释"为什么"再执行；批量投喂时，①-② 按批次合并处理，③-⑥ 逐份执行。

| 步骤 | 教（为什么） | 做（AI 动作） |
|------|-------------|--------------|
| ① 投喂（支持批量） | 哪些文书构成一个委托材料包 | 收文件（原始模板即可，**无需客户手动脱敏**，可一次多份）、**检测文件格式**——收到 .doc 旧格式时主动提示先另存为 .docx（或提供 LibreOffice 命令行转换方案，见 prep-checklist）、按文书类型分类 |
| ② 脱敏审核（批量合并） | 客户信息保护是执业义务；变量化前的模板可能含真实客户信息 | 扫描全部文件敏感信息 → 生成**合并脱敏清单**（按文件分组）→ 客户一次审核确认 → 批量执行脱敏生成各副本 |
| ③ 分析 | 人名/案号/金额/日期都是会变的变量；**模板中的横线（填空线）= 变量位置指示符**，空白横线和带字横线都要识别为变量候选 | 逐份对脱敏副本提取全部变量（含填空横线/下划线填空检测），输出变量清单 |
| ④ 变量化 | 命名规范：`{{全角花括号}}`+中文表意名（见 `teaching/variable-naming.md`）；**横线替换为变量后删除横线，格式型下划线保留（生成时数据带横线）** | 逐份生成变量映射表，用户一次确认 |
| ⑤ 验收 | 格式铁律：只换字、不动格式 | 逐份生成母版 DOCX，展示变量清单+效果预览，按「验收维度」五项逐项核对（含页数基准记录） |
| ⑥ 入库（按模式） | 资产归本所：存律所自己的空间；线上模式还承载"同事可复用" | **线上**：母版上传云文档模板库——腾讯文档（pre_import → PUT → async_import → 移至模板库空间）；金山文档（`upload_file` 上传本地母版 DOCX 至云盘模板库目录）；manifest 登记 file_id；**线下**：母版存入「母版库」文件夹，manifest 登记路径 |

## 模板性质审核（①投喂后、②脱敏前，告知笔录/正文类 DOCX 专项）

> 收到投喂文件后，先判断是否属于委托材料（委托合同/授权委托书/律所函/风险告知书/送达确认书/收款确认等）。**非委托材料** → 按 SKILL.md「本技能不做什么」的超范围失败路径处理，不进入六步流水线。

收到告知笔录 DOCX 后，先判断「有无正文」，再判断「通用 or 特定纠纷」：

1. **判断有无正文**：
   - **无正文模板**（只有头尾基本要素，正文空白待填）→ **通用模板**，只需分析头尾基本要素；
   - **有正文模板**（含问答文本）→ 进入第 2 步判断。

2. **判定性质**（有正文时）：
   - 正文含专属术语（"租赁合同""钢管扣件""工伤""交通事故"等）、特定场景提问（"收发清单由谁填写"等）→ **特定纠纷模板** → 向客户确认：A. 保留为特定纠纷专用模板（**记住该纠纷的提问方式/流程**）；B. 通用化（专属术语替换为通用表述）
   - 正文不含专属术语 → **通用模板**

3. **正文处理铁律（问答三类分类）**：告知笔录正文采用**一问一答**结构，按「问」与「答」是否通用分三类：
   - **通用问 + 通用答 → 整段保留**（固定文本）：问题不涉本案事实、回答是固定口径（如执业规范告知、风险提示标准话术）；
   - **通用问 + 个案答 → 问保留、答留空**：问题通用，但回答是被告知人每案不同的说辞，答清空留横线由本案填写；
   - **个案问 + 个案答 → 整段删除**：问题本身含本案具体事实（如「这 70000 元是怎么构成的」）——这不是通用模板内容，须从母版删除、不放母版。
   - **识别个案问**：问题中含具体数额、具体对象、具体人名/案情等本案事实即属个案问，须删除。

## 分析/变量化关键确认点（第③④步执行时逐项落实）

- **变量语义确认**：授权委托书/律所函的「地址」「电话」栏默认指**受托人（律所/律师）**，用 `{{受托人地址}}`/`{{律师电话}}`，生成前向用户确认归属（委托人信息用 `{{委托人地址}}`/`{{委托人电话}}`）。
- **告知笔录变量化规则（问答三类）**：
  - **头尾基本要素**变量化：告知人、被告知人、告知时间、告知地点、记录人、签署日期 → `{{变量}}`；
  - **正文问答三类处理**：
    1. **通用问 + 通用答** → 整段保留（固定文本）；
    2. **通用问 + 个案答** → 问保留、答清空留横线；
    3. **个案问 + 个案答** → 整段删除（不放母版）；
  - **「答」清空的落地方式**：映射时 old=完整答句原文，new=填空横线「答：＿＿＿＿」——build_master 普通替换即可，**无需新增脚本能力**；变量化前**显式向用户确认**「正文个案问答将删除、个案答句将清空」，避免遗漏；
  - **「整段删除」的落地方式**：映射时 old=整段个案问答原文，new=`""`（空字符串）——build_master 替换后**段落保留、仅文本清空**，母版该位置会残留一个空行（空段落）。这是当前已知行为（保证段落数稳定、避免后续段落偏移错位）；验收时发现空行为正常现象，可接受保留，或在母版生成后手动删除空段落。**不得**用「直接删除整个 `<w:p>` 段落」的方式落地（会导致后续段落偏移、run 绑定校验错位）；
  - 生成时：头尾变量替换成本案值；通用问答照母版保留；通用问照母版保留、答按本案被告知人实际说辞填写。
- **同文件多套文书确认**：分析发现同一 DOCX 内同类文书标题出现 ≥2 次（如已填示例版+空白手填版），**倾向建议「含完整填写内容的示例版做母版、空白版保留原样」**——示例版每个位置都有实际值、能准确识别变量类型；空白版做不满、识别不出完整变量结构。但**最终决断仍须问用户**，不替用户拍板。**多套文书之间是否分页，须先确认模板原排版意图**——有的律所刻意同页编排（如所函+授权委托书同页），不得擅自分页；仅当确需分页且模板当前无分页符时，才调用 `scripts/insert_page_break.py <母版.docx> "第二套文书标题"` 在第二套文书标题前插入分页符，**禁止手工 XML 逐段偏移替换**（偏移错位会截断段落）；脚本自检不通过（段落数变化）视为系统缺陷，不得入库。
- **布局画像**：分析输出标注制表位分栏（has_tab）、填空位下划线（underline），供变量化时保留 tab 与下划线。
- **勾选框层级识别（强制执行）**：法律服务范围等段落的勾选框常为**两层嵌套**（先选大类[民事诉讼/行政诉讼/仲裁/刑事]，再选程序[一审/二审/再审/执行]）。变量化时：
  1. **逐行扫描所有 `□`/`☑`**，每一个勾选框都必须生成 `{{勾选_*}}` 变量，不得遗漏（含模板末尾空白副本）；**排除说明性□**——引导语中仅作示例、非勾选项的□（如委托协议「下列『□』内的法律事务」的□、或「以□表示勾选位」的示意□），**不生成变量、不计入数量**（识别依据：□ 前后为引号 / 说明文字、上下文无备选项，则为说明性□）；
  2. **保留层级**：大类 `{{勾选_民事诉讼}}`/`{{勾选_行政诉讼}}`/`{{勾选_仲裁}}`，子类 `{{勾选_一审}}`/`{{勾选_二审}}`/`{{勾选_申请再审}}`/`{{勾选_申请执行}}`；
  3. **生成时逻辑**：先定大类勾选，再定该类子类；未选大类下的子类一律 `□`；
  4. **验收时核对**：母版 `{{勾选_*}}` 数量必须与原始模板**实际可勾选的** `□`/`☑` 数量一致（**已排除说明性□**）；严格比对误报 FAIL 时，先复核是否误把说明性□ 算入。
- **所内固定值确认**：律所名称/注册地址/办公地址/电话（合同用）/管辖法院（合同争议）等**全所一致的值**须逐项请客户确认或修改（未确认的留 `{{变量}}` 占位）；**承办律师、告知人、授权书电话是随人随案的值，不进画像固定值**（走终端固定值或生成时确认）。
- **表格密集型文书专项扫描**：送达地址确认书、退费账号确认书等以表格为主的文书，须**逐格扫描**（含空白/占位符单元格——空白格也是变量候选），并逐项向客户确认"此项是否为变量"，不得默认全变量或全固定。
- **同值多语义位置识别**：同一文本值出现在两个不同语义位置（如「告知人：张三」「记录人：张三」同值）时，**不得用裸值做 old**（会被全文替换吞并成一个变量）——须用**上下文前缀区分**：old 写「告知人：张三」「记录人：张三」，分别映射 `{{告知人}}`、`{{记录人}}` 两个独立变量。
- **多人角色单变量**：同一角色的多个主体（如两名被执行人、三名被告）合并为**一个变量**，值内用顿号「、」分隔（`张三、李四、王五`）；**不得**按人数拆成 `{{XX一}}`/`{{XX二}}` 固定变量——人数不定时会造成变量空洞（单人间顿号悬空）或溢出（三人无处填）。映射时把「李建华、朱英丽」整体作 old，new 为单一变量（如 `{{被执行人}}`）。
- **条件联动变量链识别**：送达确认书等存在「A 的取值决定 B」的依赖链（如：与当事人关系[本人/代理人/其他] → 证件类型[身份证/律师证] → 证件号码 → 手机号归属[本人=当事人电话/代理人=律师电话]）。变量化时须识别此类**联动链**，生成时按勾选结果**联动分配**对应变量值，不得各自独立填固定值；生成后自检须核对联动字段与勾选状态一致。

## 验收维度（格式零改动拆解，五项全过才算验收通过）

- ☐ 字体/字号/行距/对齐/边框不变（`build_master.py --verify` 的 T9 覆盖）
- ☐ 下划线覆盖范围正确（run 绑定校验覆盖，`--verify` 第 4 项）
- ☐ 制表位/左右分栏布局保持（分析阶段布局画像标注 has_tab，替换保留 tab）
- ☐ 年月日等填空位单行不拆行（v5 精确区间替换覆盖）
- ☐ **页数基准记录**：用 `scripts/check_pages.py <母版.docx>` 检测分页标记（或用 Word 打开确认），将母版**基准页数**记录到 manifest 的 `page_count` 字段——作为生成成品的页数契约（成品页数不得超过基准页数）
- ☐ **多套文书排版正确**：同文件多套文书（如授权委托书+律所函两套）的排版须**与模板原设计一致**——分页编排的，每套标题在独立页首（套间有分页符/分节符）；**同页编排的（律所刻意为之），不得擅自分页**。判定基准是「模板原排版意图」，而非一律要求分页
- ☐ **分页符插入自检通过**：分页符一律由 `scripts/insert_page_break.py` 插入，输出「段落数不变，三重自检全部通过」；插入后 `w:p` 段落数量与源文件一致，`zipfile.testzip()` 为 None（zip 完整）
- ☐ **落款署名分页正确**：署名区（甲方/乙方/落款/日期）不得与正文分离、不得单独成页。若署名被挤到下一页，须**微调格式让署名上移**（行距缩至 22pt / 微调页边距 / 微调段落间距）与正文同页——**禁止截断正文末段、禁止加分页符强制换页让署名单独成页**

## 批量投喂处理规则

- 一次投喂多份文件后，系统先按文书类型分类（委托合同/授权委托书/笔录/其他），输出分类清单供客户确认；
- 脱敏环节按批次合并：所有文件的敏感信息汇总为一张清单（按文件分组标注），客户一次审核完成全批次脱敏；
- 变量化、验收、入库逐份执行（每份的变量不同，需分别确认），但流程连续推进，无需客户反复发起。

## 脱敏审核环节（第②步标准流程）

- 客户交付原始模板后，系统自动扫描以下敏感信息类型：**姓名、手机号、身份证号、对方当事人名称、银行账号、案号、邮箱**等——这些属于客户个人信息，应脱敏处理；
- **脱敏白名单（默认不脱敏、直接保留）**：以下信息不属于客户敏感信息，为**律所内部分固定值或案件必要信息**，在脱敏清单中不出现、默认保留——
  - 律所名称（如"浙江××律师事务所"）——律所自身信息，非客户数据
  - 律所地址、律所电话——所内固定值，建库时一次性变量化即可
  - 管辖法院——所内通常为固定管辖约定，以 `{{管辖法院}}` 变量化而非脱敏
  - 承办律师姓名——律所内部人员，变量化时转 `{{承办律师}}`
  - 以上四项仅在客户明确要求脱敏时才处理（如跨所共享模板等特殊场景）
- **批量投喂时合并扫描**：所有文件的敏感信息汇总为一张清单，按文件分组标注；**同一敏感实体跨文件出现时须全局归并展示（列出出现文件列表），由客户一次决策（全部脱敏/全部保留）**，避免逐文件处理不一致；
- 生成脱敏清单供客户审核：

```
| 序号 | 位置 | 原文 | 建议替换为 | 信息类型 |
|------|------|------|-----------|----------|
| 1    | 第3段 | 张伟 | 张三       | 姓名     |
| 2    | 第5段 | 13812345678 | 13800000000 | 手机号 |
```

- 客户可选择：全部确认 / 修改个别替换值 / **将白名单保留项（律所名称/地址/管辖法院）主动要求脱敏**（默认不脱敏，除非客户明确要求）；
- 审核确认后执行脱敏，生成**脱敏副本.docx**，后续分析、变量化均基于副本；原件保留于律所本地，资产归所。
- **脱敏修复机制**：若在审核后发现漏检或误检（如律师证号未被第一次扫描命中）：
  1. 客户指出漏检项 → 系统执行二次扫描（仅针对新增敏感类型，不重新扫描已确认的脱敏结果）
  2. 生成**增量脱敏清单**（仅含新增命中的敏感信息）
  3. 客户确认增量清单 → 在脱敏副本上追加执行替换（不覆盖已完成的脱敏）
  4. 已确认的脱敏副本已有内容不受影响——修复过程不退回已审核的脱敏结果

## 材料包分组与案件类型适配

完成多份母版后，AI 建议"这些组成一套委托材料包"，用户确认即登记为 manifest。

| 案件类型 | 典型材料组合 | 说明 |
|----------|-------------|------|
| **民事一审** | 委托合同 + 授权委托书/律所函 + 风险告知书 | 标准组合，最常用 |
| **民事执行** | 执行授权委托书 + 送达地址确认书 + 执行款收款账户确认 | 不需要委托合同（已有判决），需要开户行/账号变量 |
| **行政案件** | 委托合同 + 行政授权委托书 | 授权权限与民事不同 |
| **仲裁案件** | 委托合同 + 仲裁授权委托书 | 管辖约定不同 |
| **刑事案件** | 委托辩护合同/委托书 + 律所函（致案件承办单位）+ 风险告知书 | 律师权限**法定**（刑诉法第 38-43 条）非授权；委托书是"确认委托+指定辩护人"；分阶段（侦查/审查起诉/审判）；收费**省级指导价 + 禁止风险代理**（详见 compliance/ 清单） |

- 同一律师可建多套材料包（民事、执行、行政等），每套独立编排
- 同一材料包内的母版**共享变量字典**——同名变量跨文书一致
- 同族变体（如计件版 vs 风险代理版）保留为同一材料包内的可选变体，仅差异条款不同，共享其余变量
- **收费确认书非标配**：很多律所（尤其计件制收费）没有独立的收费确认单，收费条款直接并入委托合同正文——**材料包是否含收费确认书，以律所实际为准，由律所自行选择**；系统不默认要求每家律所都建这份母版。

## 技术实现

- 分析/母版化复用 `scripts/analyze_templates.py`、`scripts/build_master.py`（本地 XML 替换，格式零损失）
- `analyze_templates.py` 附加能力：疑似变量候选自动提示（案号/日期/金额/手机号/身份证/律师执业证号/统一社会信用代码/法院/律所正则）、**脱敏检查——从外部配置文件 `references/sensitive-words.txt` 读取词表**（本 Skill 分发时为空模板，由各家律所自行填写，不内置任何真实词）、多套文书检测、布局画像、别名归一提示、JSON 结构化输出
- `build_master.py` 为 v5 精确区间替换完整实现：Pass1 单节点替换 → Pass2 长词优先防污染 → Pass3 段落精确区间替换（按映射规则 find 定位 old 区间，起始节点写 new、其余被覆盖节点清空但保留 run 结构含下划线）；内置短数字 old 拦截、映射冲突检测、原子写入、T9 + run 绑定双校验
- 已知坑位：日期跨 t 元素、表格单元格变量、全角/半角括号差异、下划线归属错位（v5 精确区间替换已根治，不用 difflib 模糊对齐——其会把新变量名与原文公共字符误判为 equal 导致替换文本被拆开）
