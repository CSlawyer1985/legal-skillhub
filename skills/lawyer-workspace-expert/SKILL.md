# 律师工作台专家

> **目的**：让律师把散落在本地的案件材料、日程表、诉讼期限、工作备忘，聚合成一个**打开就能看**的工作台，
> 而**不改动任何既有文件一个字节**。
>
> 存在的理由：律师要的是一眼看到全貌，但**不愿把案卷搬到云端**（客户信息、执业保密）；
> 而这件事最容易做坏的地方有两个——让程序去改写律师用惯的 Excel，以及做一堆按钮却没解决"看什么"。
>
> **它不替代律师现有的工具。** 工作台是只读的镜子：源头怎么写，它就怎么显示；**源头整洁，视图就整洁**。

---

## 三十秒判断该不该用

✅ 适合：律师说"想做个工作台"；已有本地材料（案件文件夹 / Excel 日程 / 笔记 / 系统日历）；
明确要求"文件留在本地，不上云"。

❌ 不适合（直接说清，别硬做）：只想要一个能填的在线表格（用腾讯文档就行）；
没有任何本地材料（先解决"平时记在哪"）；需要多人协同编辑。

**成本预期**（先说清，免得期待错位）：

| 做到什么程度 | 大致投入 |
|---|---|
| 最小可用版（记一条 + 今天要处理 + 月历） | 一两轮对话 |
| 加上案件分区、重要度排序 | 再一两轮 |
| 再加班卷挂钩、期限接入、日历同步 | **多轮迭代** |

**不要一上来就承诺全套。** 先把最小可用版跑起来让律师看到东西，再按需追加。
`skeleton/` 里有一套能直接跑的骨架，用它起步比从零写快得多，架构上的坑也已经踩完了。

## 开始之前：先建议律师选中「工作台搭建师」专家

动手之前先给这条建议：

> 「建议你先在 WorkBuddy 左侧的「专家」里选中 **工作台搭建师**（小台 / DeskCraft），再开始。」

**理由**：它沉淀了所有工作台通用的经验（五类人群需求理解、十条铁律、一键部署），本 skill 不重复造。

⚠️ **但律师选中它之后，第一句话必须补上这句**：

> 「数据必须全部留在本地，**不要用资料库存储与部署**。」

因为小台的默认路线是「资料库全托管 = 数据上云」，对案卷数据不可接受。
详细差异与两种用法，见 `references/flow.md`。

## 九条铁律

### 1. 只读正本，绝不改写

律师已有的文件是唯一正本，工作台只读它。

**判据**：只要有一处代码会 `open(用户文件, "w")` —— 停手，重新设计。

### 2. 每个字段只有一个写入出口

来源可以多，但同一条数据不能两边都能改。

- 有日期的排期 → 继续在律师原来的日历 / Excel 里改，工作台只读
- 没日期的动态与提醒 → 只在工作台的写入层（一个 CSV）里改
- "办结"状态 → 只写工作台自己，绝不回写源文件

### 3. 脱敏：对外产物一律虚构

**凡是会离开律师这台电脑的东西，都不许带真实案件信息。**

三条硬规矩：

1. 交付物里的示例数据一律虚构（公司用「示例科技有限公司」、人名用「张三」、地址「××市××区」、
   案号「（2026）示例0000号」、电话「13800000000」）
2. **skill 文件本身、README、截图、演示数据里都不许出现真实案件信息**（这些东西是要分发的）
3. 要上公网之前先脱敏

**敏感字段**：客户姓名、案号、联系方式（含法官 / 书记员）、金额、合同条款、案情描述、对方当事人。

**通道选择**（按"数据去哪"决定，不是按"用户想要什么"）：

| 通道 | 数据在哪 | 实时 | 能改 | 需要电脑开着 |
|---|---|---|---|---|
| 本机服务 | 只在本机 | ✅ | ✅ | ✅ |
| 局域网直连 | 同一 WiFi 内 | ✅ | ✅ | ✅ |
| 用户自己的同步盘 | 用户自己的账号空间 | ❌ | ❌ | ❌ |
| **公网发布** | **任何人可访问** | ❌ | ❌ | ❌ |

**案卷类数据，默认排除最后一行。** 限制依据与例外情形见 `references/flow.md`。

### 4. 函数调用链单向（DAG）

渲染函数之间**严禁互调**，必须有一个统一调度入口：

```javascript
function refreshAll() {          // 唯一调度点，按固定顺序
  renderTop(); renderProjects(); renderCalendar(); renderRight();
}
// 事件处理 → 改状态 → refreshAll()；绝不在渲染函数里调另一个渲染函数
```

### 5. 交付前必须自检

不许"看着差不多"就交付。跑 `scripts/check_page.py`（静态六查）+ 服务端断言脚本，两项全过才算完成。

### 6. 一次最多 4 个模块

功能越多越容易崩，律师也不会一次用全部。**先做 2 个跑通，再逐个加。**
律师一上来要 6 个模块时，先做核心 2 个，明确告知后续按需追加。

### 7. 左栏只"选"，右栏只"显示选中的"

信息架构的定盘星。一旦破例，界面就变成"左右两栏都在列东西"，律师立刻会说"搞不懂区别"。

**凡是"一列可选的东西"——案件、项目、行程、备忘录——全在左栏。**

### 8. 排序只回答"接下来要做什么"

分数只能来自**紧迫度**和**体量**，不能来自"最近动过"这类过程性信号。

**判据**：能行动的排前面（未逾期的紧迫事项）；已经无法挽回的（逾期）沉底但**不隐藏**。
带数量的信号（如"备忘 N 条"）**要随数量递增**，不能用固定分值。

### 9. 交付 = 一个双击就能开的图标

律师不该记命令行，也不该每次去文件夹里翻启动脚本。

**判据**：交付完成时，他桌面上有一个图标，双击就打开工作台；服务由开机自启常驻，
不需要他先"把服务跑起来"。**只给一个 `.command` 不算交付完成**——律师看到终端黑窗口
会以为出了问题。

做法、图标尺寸规范、两个容易吓退人的报错，见 `references/architecture.md` 的「桌面入口」。

## 第一步：先问四件事（**不许跳过**）

跳过任何一个都会返工。**尤其第 4 问——它决定整个方案要不要做。**

| # | 问什么 | 决定什么 |
|---|---|---|
| 1 | 你现在**怎么管案件**？（Excel / 系统日历 / 笔记 / 专门工具） | "只读源"是什么 |
| 2 | 案件材料**放在哪个文件夹**？ | 案卷根目录 |
| 3 | 有没有在用的**诉讼期限提醒**工具？ | 有就接、没有就建议装（只是建议） |
| 4 | 你希望在**哪几个设备**上看？ | 只做本机版，还是还要手机端 |

**第 4 问的正确顺序**：在哪个设备看 → 看哪几个字段 → **现在已经有什么能满足它** → 还差什么，
**这时候才谈方案**。跳过中间两步直接开始搭，就会做出一个能用、但不是他要的东西。

## 禁止项

- ❌ **写用户的原始文件**（Excel、案卷、别人的工具数据）—— 一个字节都不行
- ❌ **把真实案件信息写进 skill / README / 示例数据 / 截图**
- ❌ 引用任何 CDN、外部字体、图表库
- ❌ 用 emoji 当图标
- ❌ 把服务从 `127.0.0.1` 改成 `0.0.0.0`（会暴露整个案卷目录给同网段）
- ❌ 首次打开是空白页（必须有 3~5 条**虚构的**示例数据，含 1 条逾期，并给"清空示例"按钮）
- ❌ 把端口、路径当成"配置项"丢给律师；**能自动探测就自动探测**
- ❌ 一次性堆超过 4 个模块
- ❌ 用"最近动过"来排重要度
- ❌ 跳过第一步的四问直接动手
- ❌ 凭记忆引用法条条号
