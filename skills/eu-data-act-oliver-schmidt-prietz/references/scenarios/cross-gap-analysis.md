# 跨章节差距分析

**锚点：** 任意 × 跨章节 × 差距分析。本卡片构建对组织《数据法》合规状况的多章节合规审查。它对每个涉及的章节执行七步方法，并按照 `references/method/house-style.md` 的"差距分析或合规检查"交付物规范，为每个章节生成结构化的差距分析表。

**路由来源：**

- "我们需要为 [产品/业务线] 做《数据法》就绪评估。"
- "我们在第二、四和六章上的合规差距在哪里？"
- "对我们的 SaaS 联网产品业务做一次《数据法》差距分析。"
- "我们正在为2025年9月12日的适用做准备；我们需要修复什么？"
- "将我们的当前状态与全技术栈上的《数据法》要求进行比较。"

**相邻卡片（如事实表明，请改路由到这些卡片）：**

- 单章节范围界定问题：路由到章节特定卡片（如仅商业秘密问题路由到 `ch2-trade-secret-stages-1-2.md`；第32条请求路由到 `ch7-third-country-request.md`）。
- 问题是"《数据法》是否适用于我们？"而非差距分析：路由到仅范围界定回复。七步方法的第1步即为答案；完整的差距分析属于过度构建。
- 与 GDPR 的边界是主要关切：路由到 `cross-gdpr-boundary.md`。
- 问题涉及《数字综合法案》（Digital Omnibus）将如何改变差距分析：路由到 `cross-omnibus-impact.md`。

---

## 典型事实模式

某组织依第1条第(3)款属于《数据法》适用范围。它是以下一种或多种身份：在欧盟市场上投放联网产品的制造商；相关服务的提供者；数据持有者；数据接收方；数据处理服务的提供者；数据空间（data spaces）的参与者或智能合约（smart contracts）的供应商。该组织此前未完成过《数据法》合规状况审查，或其此前的审查已过时。

交付物是差距分析：组织当前合规状态与《数据法》应有状态之间的差距，附具体行动和责任人。交付物仅供组织内部使用，通常作为整改计划（remediation plan）的输入。

差距分析的范围涵盖组织活动所涉及的章节。带有 SaaS 相关服务的联网产品制造商通常涉及第二章（用户访问）、第四章（数据共享合同中的不公平 B2B 条款）、第六章（SaaS 的切换）和第七章（SaaS 托管的第三国政府访问）。也可能按观察清单方式触及第三章（依其他欧盟法律的强制性 B2B 共享）和第五章（公共部门的例外需要）。

## 关键纪律

这三点区分了有用的《数据法》差距分析与打勾式（checkbox）练习。

- **每次只处理一章。** 每个涉及的章节都有自己独立的七步走、自己的角色映射和自己的差距表。将各章节混入单一矩阵会产生分析错误，因为各章的操作性规则不同。第二章下的发现（"用户未被告知数据访问权利"）与第六章下的发现（"客户在终止时无法取回可导出的数据"）是对不同主体的不同义务，需要单独的整改轨道。
- **按阶段定角色，而非总体定角色。** 组织通常在产品线、客户关系和生命周期阶段中扮演多个《数据法》角色。角色映射记录的是所审查的具体义务下的角色，而非单一的总体角色标签。同一组织是其联网产品的数据持有者、其 SaaS 层的提供者、其云基础设施的客户，并且可能是其从供应商处消费的联网产品的用户。参见 `references/gotchas.md` 第2条（制造商不一定是数据持有者）以及 `references/method/analysis-method.md` 中的角色分叉纪律。
- **现行法律先于提案。** 差距分析以已发布的现行《数据法》评估组织。《数字综合法案》提案（COM(2025) 833 final，2025年11月19日）仅作认知用途，放在单独的"观察清单"列或页脚中。基于拟议修正案构建差距分析，会在提案被修改或撤回时产生可能失效的分析。参见 `references/gotchas.md` 第20条和 `cross-omnibus-impact.md`。

## 七步走（对每个涉及的章节执行）

该方法每个章节执行一次。输出呈现每个章节的七步结果，并整合到差距表中。

### 第1步：范围检查

对每个章节独立执行第1条第(2)、(3)和(6)款的范围测试。章节可能适用（组织在范围内）或不适用（组织属于第1条第(6)款的除外情形，或章节的属人范围条件未满足，或组织没有范围内数据）。

对第二章，另外执行第2条第(5)款的联网产品测试、第2条第(6)款的相关服务测试和第2条第(22)款的"投放欧盟市场"测试。在欧盟境内制造用于出口的联网产品不在范围内；仅在欧盟境内流通的移动产品不构成投放（FAQ Q9）。对第六章，执行第2条第(8)款的数据处理服务测试。对第七章，执行第2条第(8)款加上"在欧盟境内持有的非个人数据"地点测试。

### 第2步：章节识别

确认章节并列明所涉及的操作性条款。第二章下的联网产品差距分析主要涉及第3、4和5条，其中第4条第(2)款的安全保障刹车条款（safety-security handbrake）以及第4条第(6)至(8)款和第5条第(9)至(11)款的商业秘密阶梯为条件性子模块。第六章分析涉及第23至31条，其中第30条的功能等效不对称性（IaaS 与 PaaS/SaaS）和第31条的定制构建除外情形为条件性子模块。第四章分析涉及第13条、第14条（第13条被违反时的单方终止权）、第12条（目的和方式），以及委员会依第41条的不具约束力的示范合同条款。

### 第3步：角色映射

按实体、按阶段将组织映射到每个涉及的章节。以表格呈现。当组织就同一数据集既是制造商、控制者、数据持有者又是商业秘密持有者时，差距分析在表中确认全部四个角色；不将其合并。

| 实体 | 阶段/活动 | 《数据法》角色 | GDPR 角色（如含个人数据） | 其他 |
|--------|-------------------|---------------|------------------------------|-------|
| [组织，业务单元1] | [如联网产品的设计和制造] | 制造商（第1条第(3)款第(a)项）；数据持有者（第2条第(13)款） | 产品所产生个人数据的控制者 | 《欧盟指令 (EU) 2016/943》下的商业秘密持有者 |
| [组织，业务单元2] | [如 SaaS 相关服务运营] | 相关服务提供者；相关服务数据的数据持有者 | 控制者（或处理者，取决于组织是否决定目的和方式） |  |
| [组织，业务单元3] | [如消费 IaaS 用于托管] | 数据处理服务的客户（第2条第(30)款） | 视数据而定为控制者/处理者 |  |
| [客户企业1] | [如使用联网产品的车队运营商] | 用户（第2条第(12)款） | 控制者（依序言第34段，如其不是数据主体） |  |
| [最终用户，自然人] | [如联网车辆的驾驶员] |  | 数据主体 |  |

序言第34段将非数据主体的用户置于控制者角色。当组织向企业客户供应联网产品时，差距分析会标注客户并行的 GDPR 控制者义务，并确认组织在第4条第(12)款和第5条第(7)款下的法律依据控制已考虑到该角色划分。参见 `references/gotchas.md` 第3条。

### 第4步：事实类别分类

按标准维度对范围内的数据进行分类：个人与非个人；原始或预处理与衍生（序言第15段）；产品数据与相关服务数据；随时可得与不可得（第2条第(17)款）；内容与非内容（序言第16段）；商业秘密与非商业秘密。分类表是差距分析交付物的一部分；第5和第6步下的操作性规则依赖于此。

对于多章节差距分析，数据类别表通常出现在交付物开头一次，并从每个章节部分引用。当各章节适用于不同的数据子集时（第二章仅适用于产品/相关服务数据；第六章适用于数据处理服务处理的数据；第七章适用于在欧盟持有的非个人数据），各章节部分会说明涉及哪个子集。

### 第5步：操作性条款的逐项适用

对每个操作性条款执行逐项测试。测试的深度取决于条款的结构：

- **多分支累积测试**（如第2条第(5)款联网产品；第4条第(8)款拒绝；第15条第(1)款第(b)项例外需要；第31条第(1)款定制构建除外）：每个分支独立评估。发现须指明失败的分支。
- **封闭清单式禁止**（第5条第(3)款守门人排除；第6条第(2)款第三方禁止）：逐项评估。封闭清单框架意味着未列出的行为不受该条款禁止（其他欧盟法律仍可能适用）。参见 `references/gotchas.md` 第12条。
- **示例性清单**（序言第31段的客观要素；FAQ Q22a 技术与实际访问要求）：每项作为示例考虑；操作性测试是清单所说明的原则。参见 `references/gotchas.md` 第8条。

差距分析交付物不在文档正文中逐一列举每个分支。正文识别相关条款和发现；逐分支分析放在工作文件中，在分析细节重要处从交付物引用。

### 第6步：跨制度门禁检查

对每个章节执行门禁检查：

- **GDPR 叠加**（`references/gates/gdpr-overlay.md`）：只要范围内含个人数据即始终涉及。门禁向差距表添加发现，通常放在"GDPR 叠加"标题下。
- **《商业秘密指令》叠加**（`references/gates/trade-secrets-directive.md`）：任何数据受商业秘密保护时涉及。差距表中的发现涉及第一阶段保障、元数据中商业秘密的识别、技术和组织措施以及拒绝函准备就绪度。
- **DMA 守门人排除**（`references/gates/dma-gatekeeper.md`）：组织收到第5条第三方请求或依第6条第(2)款第(d)项转交共享数据时涉及。差距表中的发现涉及接收方筛选和合同条款。
- **部门性特别法**（`references/gates/sectoral-lex-specialis.md`）：组织的产品属于受监管行业（车辆、医疗器械、能源、金融服务、AI 系统、eIDAS、NIS2、CRA）时涉及。差距表中的发现标注部门性制度及其与《数据法》的相互作用。
- **成员国实施法律**（`references/gates/member-state.md`）：涉及设立地成员国和客户所在地成员国。差距表中的发现涉及主管机关指定、争议解决机构以及任何国家减损。

### 第7步：现行法律与提案的综合

对每个章节，差距分析以现行法律作为操作性要求。《数字综合法案》提案（COM(2025) 833 final，2025年11月19日）在提案对该章节产生实质性影响处（第4条第(8)款和第5条第(11)款的拒绝事由；第五章第15条的情形；第25条提前终止罚金；第31条定制构建除外；第36条智能合约；合并吸收 DGA、ODD、FFD、P2B）在差距表的"观察清单"列中标注。观察清单条目为风险和时机决策提供信息；它们不改变现行状态的合规性。

## 决策点

对每个章节完成第5和第6步后，差距分析为每个章节生成结构化表格，并生成整合的整改积压清单。交付物的输出结构：

1. **各章节差距表。** 每个涉及的章节一张表，遵循规范风格"差距分析或合规检查"格式。
2. **整合的整改积压清单。** 跨章节优先级排序（严重性、监管风险敞口、对其他行动的依赖）。
3. **观察清单部分。** 《数字综合法案》和其他即将到来的变化（如 EDIB 建议的关于第9条第(5)款补偿和第32条第(3)款条件的指南；委员会依第33条的授权法规；依第35条的协调标准）。
4. **假设部分。** 分析所依据的任何未核实事实（依 `references/method/house-style.md`）。

## 起草者注释

- **每次只处理一章；最后整合。** 抵制在分析过程中将发现合并为跨章节矩阵的诱惑。合并发生在整合的整改积压清单中，且在每个章节的差距表完成后进行。过早合并会产生分析错误，因为各章节的操作性规则不同。
- **责任人写角色，不写个人。** 差距表中的"责任人"列标明职能（DPO、法律、工程、产品、商务、运营、安全）。写个人姓名会使交付物过时并造成人力资源管理噪音。整改计划可以另行将职能映射到个人。
- **截止日期参照《数据法》时间表。** 第50条的截止日期（2025年9月12日一般适用；2026年9月12日第3条第(1)款下的设计义务；2027年9月12日不公平条款适用于遗留合同）是绝对且已知的。内部截止日期应锚定这些日期，而不是容易漂移的抽象"2026年第三季度"标签。
- **观察清单不是整改积压清单。** 《数字综合法案》提案项目属于单独的列或部分。它们为风险和路线图决策提供信息，但不产生现行状态的整改行动，因为现行法律没有变化。参见 `references/gotchas.md` 第20条。

## 关于结构创新的说明

原型卡片（`ch2-trade-secret-stage-3-refusal.md`）是单章节、单场景的。差距分析卡片在结构上不同：它多次运行七步方法（每个涉及的章节一次），并生成结构化的表格交付物，而非拒绝函或备忘录。本卡片保留了原型的十节结构（锚点；路由来源；相邻卡片；典型事实模式；关键纪律；七步走；决策点；输出骨架；需要加载的引用；交叉引用；起草者注释），其中七步走按通用方式（每章）撰写，输出骨架扩展为多章节交付物，并采用 `references/method/house-style.md` 规定的各章节表格格式。"差距表示例"部分是新增的，因为表格格式是操作性输出，经过演练的行让起草者能够校准粒度，而无须每次使用时重新发明格式。
