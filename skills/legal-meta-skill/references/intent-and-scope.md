# 意图与范围

先确认要不要建 Skill，再决定建多大。法律类 Skill 的复杂度应由复用频率、错误代价、输入文件、权限和交付稳定性共同决定。意图画布用于收集建模输入，不替代 `legal-skill-ir/v0.3` 或 `universal-legal-core/v0.1` 的正式能力配置。

## 意图画布

| 字段 | 要回答的问题 |
|---|---|
| Job | 哪个重复出现的法律工作要被稳定完成？任务从哪里开始，到哪里结束？ |
| Users | 谁使用：律师、助理、业务人员、研究员或其他 Agent？谁是实际受众？ |
| Decision | 最终要支持什么决定，由谁作出决定？Skill 是提供信息、比较选项、提出建议，还是执行经授权的可逆动作？ |
| Inputs | 文件、事实、问题、已有规则、项目约束、既有入口和可用工具是什么？哪些输入是必需、可选或待补？ |
| Outputs | 要交付分析、表格、文书、证据包、Skill 包还是评测报告？每类输出的最低字段、格式和落点是什么？ |
| Exclusions | 哪些事明确不做？是否排除最终法律决策、未经复核的正式定稿、自动发信、不可逆提交或远程发布？ |
| Jurisdiction bundle | 涉及哪些实体法、程序法、法院或仲裁机构、监管机关和地域？准据法、争议解决地、冲突规范及强制性规定如何确定？ |
| Temporal bundle | 事实期间和法律核验时点是什么？是否涉及新旧法过渡、持续性事实、诉讼时效、除斥期间或其他程序期限？ |
| Actors | 谁是委托人、代理人、相对方和第三人？各主体的资格、授权、行为能力、程序地位、控制关系和利益冲突如何？ |
| Matter | 专业领域、法律关系、交易或争议对象是什么？事项处于筹备、履行、变更、违约、争议、执行或其他生命周期状态？ |
| Legal profile | 默认法域、适用时点、法律领域、权威来源层级、来源标签和独立核验要求是什么？十二模块中哪些适用、哪些经检查后不适用、哪些因缺口受阻？每个状态的具体理由、最低输出和降级路径是什么？ |
| Evidence | 哪些是原始材料、材料陈述、已确认事实、待证事实、法律评价、程序记录和缺口？结论如何追溯到证据位置？ |
| Workspace | 目标运行环境、`input/scratch/output` 是否适用、用户明确提供的项目约束和既有入口是什么？ |
| Attribution | 新建、改造还是白标？是否保留原作者、许可证及 CSlawyer 来源标识？ |
| Permissions | 是否需要联网、外部 MCP、脚本、写文件、账户或发布权限？哪些动作只读、可逆、不可逆或必须另行授权？ |
| Human control | 谁复核，谁承担最终决定和签发责任？哪些结论、金额、期限、引用或程序动作不得自动定稿？出现哪些事实、法律、来源或权限变化时必须重新核验？ |
| Success | 什么结果才算完成？如何验证触发边界、法律输出、文件落点、权限边界和降级路径？复核周期多长？ |

## 画布收敛规则

1. `Decision` 先于输出形式确定。不能只写“生成报告”，还要说明报告支持谁作出什么决定，以及 Skill 不代替谁作决定。
2. `Jurisdiction bundle` 与 `Temporal bundle` 必须分别记录实体、程序、机构、地域和时间连接点；默认中国大陆不等于可以省略法域与时点判断。
3. `Actors` 与 `Matter` 分开。前者说明主体资格、授权和利益，后者说明法律关系、事项对象与生命周期，不能用文件标题代替法律关系定性。
4. `Human control` 必须落实到具体角色和重新核验触发条件。涉及效力、金额、期限、责任、程序资格、正式提交或对外签发的核心判断，不得仅写“人工复核”。
5. `Legal profile` 同时收集法律分析基线和十二模块状态。权威来源层级、来源标签及独立核验要求必须成为 `authority_and_interpretation` 的建模输入，不能只登记模块状态而省略来源与核验契约。
6. 画布中的缺口会实质改变架构、权限或法律可靠性时再提问；可以通过模块状态、条件化输出或停止路径表达的，不为形式完整反复追问。

## 三层渐进收敛协议

意图阶段的提问按三个逻辑层组织，避免"固定长问卷"和"全凭自由裁量"两个极端：

1. **第 1 层：意图推断**。用户提供名称和基本描述后，据此推断场景原型（八类之一或 `other`）与法律领域，并向用户确认推断；推断会实质改变设计而用户未确认时，必须问，不擅自定。
2. **第 2 层：固定底层问题**。画布九个核心键（job、users、decision、inputs、outputs、exclusions、human_control、success、legal_profile）——与业务类型无关，每个 Skill 都必须实质回答。
3. **第 3 层：路由领域问题**。按确认的原型提出条件键问题（未被原型放宽的键）和该原型的补充提问（见 [法律场景原型](legal-scenario-archetypes.md)）；原型为 `other` 或包内规则对该领域覆盖不足时，按 [同类 Skill 研究来源](skill-research-sources.md) 的"领域方法论研究"一节，经用户授权后从权威法律来源提取该领域应关注的角度与方法，形成第 3 层问题。联网研究只在创建期进行，结果内化进目标包，不得变成运行时依赖；无法联网时如实记录证据缺失，不用模型常识冒充领域方法论。

### 渐进式提问纪律

三层是**逻辑分层，不是三次表单**。实际交互是渐进式的：

- **小批量推进**：每次只提出当前层最关键的少量问题（一般一至三个），获得回答后再决定下一批；不得把画布十五键或某层全部问题一次性甩给用户填表。
- **回答驱动路由**：每一批问题由此前的回答决定——原型确认后才路由该原型的条件键与补充提问；用户回答中暴露的新事实（如"我是被告且已届上诉期"）应立即改变后续问题（跳过请求设计，改问期限与卷宗）。允许随回答新增、合并或消减问题，层与层之间可以回查。
- **轮次不设上限**：交互可能少于或多于三次来回；收敛标准是关键字段获得实质回答，而非走完固定轮次。
- **数量收敛**：只问答案会改变架构、权限或法律可靠性的问题；可用合理默认替代的不问。联网兜底时尤其不得把研究到的所有角度都转成问题——从动态路由退化为动态长问卷是反模式。
- **机检只验终点**：生成器的画布校验约束的是最终 intake 的完整性与具体性，不约束对话路径；对话层的渐进纪律由本文件承担。

## 画布覆盖的机器兜底

`legal-skill-intake/v0.2` 模板包含 `intent_canvas_coverage` 对象，十五个键覆盖画布的信息域（画布表中 `Workspace` 与 `Permissions` 合并为 `workspace_or_permissions` 一键；`Attribution` 由 SKILL.md 的作者标识与传播规则单独处理，不在画布机检范围）。生成器按"核心层 + 原型路由"两层校验：

- **核心键**（job、users、decision、inputs、outputs、exclusions、human_control、success、legal_profile）：与业务类型无关，永远要求实质回答，不接受 `not_needed`。
- **条件键**（jurisdiction_bundle、temporal_bundle、actors、matter、evidence、workspace_or_permissions）：默认要求实质回答；仅当所选场景原型声明放宽时，才允许以 `{"not_needed": "具体理由"}` 声明不适用，理由仍须具体。各原型的放宽集见 [法律场景原型](legal-scenario-archetypes.md)。

空泛回答（"按需""略"等）、缺失键或越权 `not_needed` 会被拒绝生成。意图阶段的提问质量因此有最低机器保障：核心键空泛即意味着存在未澄清问题；条件键的豁免只由原型决定，理由不具体同样打回。

## 不建 Skill 的条件

- 用户只需要一次性法律意见、条款解释、翻译、总结或普通文书草稿。
- 没有重复任务，也没有可复用的输入/输出契约。
- 目标只是临时改变本轮回答风格。
- 关键决定、法域、时点或输出对象缺失，且补充后仍可能完全改变设计。

这时直接完成任务，或交付一个临时检查清单；不要把一次性内容伪装成可复用 Skill。

## 必要澄清

只在答案会改变架构、权限或法律可靠性时提问，例如：

1. 这是法律分析 Skill，还是用于“创建法律 Skill”的元 Skill？
2. 最终要支持谁作出什么决定，哪些内容必须由律师或其他责任人复核、签发？
3. 目标只供个人使用，还是要给团队、其他平台或公开仓库复用？
4. 是否允许联网研究、外部法律数据库、真实案卷夹具或发布动作？

信息足够时直接采用合理默认：中国大陆、个人可安装、数据本地、输入只读、无远程发布、缺失证据显式标记；但准据法、程序地、法律时点、期限和主体资格仍须由目标 Skill 在运行时根据具体材料核验，不能被默认值代替。
