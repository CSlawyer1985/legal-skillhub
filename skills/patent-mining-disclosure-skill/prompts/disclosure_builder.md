# 专利说明书式技术交底书生成模板（Step 7）

本步骤生成的是**面向代理人可继续撰写/上报的专利技术文本**，不是普通项目说明，也不是含“注意事项/联系人/委托确认话术”的空泛交底书。正文只写与发明技术方案相关的内容。

交底书不能只写概念性文字。必须写到代理人和发明人能顺着正文看出“输入是什么、系统怎么处理、输出是什么、异常怎么兜底、哪些字段/模块支撑权利要求”。代码不必逐行公开，但技术链路、关键数据结构、伪代码/处理表、输入输出样例和模块对应关系必须足够具体。

详细章节范例与 **mermaid** 图示模板见同目录 **`template_reference.md`**。落盘前还须遵守 **`versioned_output.md`**：所有用户交付文件写入当前 `vN-说明-时间戳/` 版本目录，根目录只保留 `版本索引.md` 和修订日志。

## 7.1 章节结构（必遵）

正文采用接近专利说明书的结构：

```markdown
# 一种XXX方法、系统、设备及介质

**发明人/发明者**：XXX、XXX

## 技术领域

## 背景技术

## 发明内容

### 要解决的技术问题

### 技术方案

#### 方法方案

#### 系统方案

#### 设备、介质或程序产品方案（可选但建议写）

### 有益效果

## 附图说明

## 具体实施方式

### 实施例一：整体方法流程

### 实施例二：关键子流程/关键算法/关键规则

### 实施例三：系统模块与数据交互

### 可选实施方式与异常分支

## 摘要
```

若用户明确要“交底书”而非“说明书”，仍使用上述技术正文结构；可以省略权利要求书正式编号，但**不得**加入“注意事项”“请代理人确认”“联系人”等非技术正文。

发明人/发明者属于案件元信息，应写在一级标题下方。若用户未提供发明人，不得根据代码提交人、作者名或公司信息猜测；应先询问，或在必须先落盘草稿时写为 `[待填写]`。

## 7.2 正文禁止项

正文不得包含：

- “注意事项”“技术联系人”“请确认文本是否准确无误”“委托人”等流程话术。
- Skill 仓库、示例仓库、Agent、自检清单、生成过程说明。
- “本方案很先进”“效果显著”等无技术支撑的空话。
- 商业秘密点的具体参数表、完整 prompt、真实客户口径、真实映射表、真实训练数据样例；必要时写成“预设规则/预设模板/预设阈值/预设样本集”。

## 7.3 各章节写法

### 技术领域

1 段，明确所属技术方向，例如“自然语言处理、信息检索、数据库问答、Text-to-SQL、向量检索”等。

### 背景技术

写 2-4 段：

- 场景：该技术在什么系统中使用。
- 现有技术路径：至少列出 2 类最接近方案。
- 技术缺陷：必须落到具体技术问题，不写泛泛“效率低、准确率低”。
- 查新来源：若已完成 Step 5 深度查新，写入可核验 URL；若只是轻量初筛，写“初步检索发现…”并提醒正式申请前需深度查新。

### 发明内容

这是核心章节，不能过短。至少包含：

#### 要解决的技术问题

用 3-6 点写清楚，每一点对应背景技术缺陷。

#### 技术方案

必须写成“可转权利要求”的方案，不只写概念。

方法方案至少包含 S1-Sn：

- 每一步写清输入、处理、输出。
- 写关键判断条件、阈值、排序、过滤、映射、重试、回退。
- 写上下游数据如何传递。
- 写端到端闭环：前一步输出如何成为后一步输入，最终产物如何被展示、保存、审计或继续计算。
- 若有模型，写模型输入、输出、约束，不必公开具体 prompt。
- 若有规则，写规则类型、触发条件和处理结果，不公开真实规则表。

系统方案至少包含模块：

- 模块名称与职责。
- 模块间数据流。
- 每个模块对应方法步骤。
- 至少用一段说明“方法步骤 S1-Sn 与系统模块 M1-Mn 的对应关系”，避免方法和系统两张皮。

设备、介质或程序产品方案可用较短段落，但建议保留，便于后续权利要求布局。

#### 有益效果

每条效果必须能对应某个步骤或模块。例如：

- “通过先检索候选再模型重排，减少大模型候选空间并降低幻觉”。
- “通过字段级规则绑定，仅对命中字段改写条件值，降低误改概率”。

### 附图说明

列出每张图：

- 图1是……流程图。
- 图2是……系统结构示意图。
- 图3是……关键子流程示意图。

正文的图示仍先用 fenced **mermaid** 表达；交付 Word 时按用户选择转 PNG、专利附图风格生图提示词，或调用图片接口自动生图并嵌入 Word。

### 具体实施方式

这是最重要的章节，篇幅通常应占全文 40% 以上。必须写到“技术思路和实现颗粒度足够清楚”。

#### 实施例一：整体方法流程

- 按 S1、S2、S3……逐步展开。
- 每一步至少写一段，不得只列一句。
- 对关键步骤写数据结构、字段、变量、阈值、排序依据或判断逻辑。
- 写边界情况：无候选、单候选、多候选、低置信、模型输出不在候选中、规则未命中、执行失败等。

#### 实施例二：关键子流程/关键算法/关键规则

围绕本案最关键的技术点展开，例如：

- 多字段检索与权重排序。
- 样本泛化与训练版本索引构建。
- 标签过滤与候选重排。
- 字段级规则触发与 SQL 条件值替换。
- 失败问题入库与训练样本沉淀。

必须写出可实施细节：

- 字段或表结构示例（可脱敏）。
- 规则类型和处理伪代码或公式。
- 样本构造方式与评分/标签方式。
- 阈值范围或示例值（注明仅为实施例）。
- 异常分支与回退策略。
- 输入样例、处理中间态和输出样例；不公开真实客户数据时，用脱敏/抽象样例。
- 关键算法的伪代码或处理表：字段类型如何分支、规则状态如何判断、版本漂移如何处理、结果如何组装。
- 与项目代码或系统字段的对应关系：例如实体字段、JSON 字段、模块职责、接口输入输出；不得编造不存在的实现，扩展能力要写成“一实施例中可……”。

#### 实施例三：系统模块与数据交互

写模块如何部署、如何调用、如何共享上下文、如何输出结果。

#### 可选实施方式与异常分支

列举可替换实现：

- 本地模型/远程模型/第三方接口。
- 本地向量索引/远程向量库。
- 规则函数/SQL 查找/枚举表映射。
- 阈值、topN、重试次数可配置。

### 摘要

用 150-300 字概括技术领域、核心步骤和主要效果。不要写营销话术。

## 7.4 图示要求

- 至少包含 2 张图：方法流程图、系统结构图。
- 复杂案件建议增加关键子流程图。
- 图示用 **fenced mermaid** 表达，节点标签简短中文。
- Word 交付时，按用户选择转 PNG、生图提示词或自动生图并嵌入 Word。
- 不要 ASCII 文字框图。

## 7.5 公式、参数和表格

若技术方案包含评分、相似度、排序、权重、阈值、过滤条件、损失函数等，必须写公式或参数表。

要求：

- 先定义符号，再写公式。
- 参数表给出含义、取值范围、示例值和作用。
- 示例值应脱敏，可写“例如 0.7”“例如 topN=10”，并注明不限制保护范围。
- 不要为了形式化硬塞公式；没有必要时用伪代码或表格表达。

## 7.6 输出目录与文件命名（用户产出目录，必遵循）

在用户目录写入 `.md`、`.docx` 或 `.pdf` 前，先按 **`versioned_output.md`** 创建或选择本轮版本目录：

```text
{专利组或案件根目录}/
├── 版本索引.md
├── 交底书修订对话记录.md
└── vN-简短说明-YYYYMMDDHHMMSS/
    ├── {标题规范化}_{YYYYMMDDHHmmss}.md
    ├── {标题规范化}_{YYYYMMDDHHmmss}.docx
    ├── {标题规范化}_{YYYYMMDDHHmmss}.pdf
    ├── {项目名}_专利簇通俗说明清单_{YYYYMMDDHHmmss}.md
    ├── mermaid_figures/
    └── math_figures/
```

根目录不得平铺新增定稿文件；多件专利同批次交付时，放入同一个版本目录。

在当前版本目录中，主文件名须体现正文标题，且凡向用户落盘交付的定稿均须带时间戳后缀：

`{标题规范化}_{YYYYMMDDHHmmss}.md`、同名 `.docx` 或同名 `.pdf`

规则：

1. 从一级标题 `# 一种XXX...` 或“案件名称”提取标题。
2. 删除 `[待填写]`、非法路径字符和换行。
3. 文件名建议不超过 80 个字符，超长可截断但保留“方法及系统”等结尾。
4. 不覆盖旧稿；每次交付新时间戳，并更新根目录 `版本索引.md`。
5. 当前版本 Markdown 的图片引用应指向同版本目录内的 `mermaid_figures/`、`math_figures/` 或其他资源目录。

## 7.7 定稿交付：Markdown / Word（二选一，可选 PDF）

交付前确认：

- Markdown 或 Word。
- 若 Word，再确认图示方式：PNG、生图提示词或自动生图。
- 若 Word，再确认是否需要同时导出 PDF；PDF 由生成出的 Word 转换得到，保证内容一致。

### Markdown

交付 `.md`，正文保留 mermaid 源码。

### Word + PNG

运行：

`python3 tools/mermaid_render.py -i <草稿.md> -o "{版本目录}/<标题_YYYYMMDDHHmmSS>.md"`

默认生成同名 `.docx`，Word 中嵌入 PNG。

若用户需要 PDF，追加 `--pdf`：

`python3 tools/mermaid_render.py -i <草稿.md> -o "{版本目录}/<标题_YYYYMMDDHHmmSS>.md" --pdf`

PDF 转换依赖 LibreOffice / soffice。若环境缺失，脚本保留已生成的 Word，并输出手动转换命令；不得因此重写正文或覆盖旧稿。

### Word + 生图提示词

运行：

`python3 tools/mermaid_render.py -i <草稿.md> -o "{版本目录}/<标题_YYYYMMDDHHmmSS>.md" --diagram-mode prompt`

Word 中保留每张图的专利附图风格生图提示词，用户后续用 gpt-image 等工具生成图片替换。

若用户需要 PDF，追加 `--pdf`。

### Word + 自动生图

适用于用户提供 OpenAI-compatible 图片接口站点和 key，或已在环境变量中配置。**生成 Word 前必须先检查环境**；检查失败时只给出设置命令并等待用户补齐，不继续生成文档。

- `OPENAI_API_KEY`：图片接口 key。
- `OPENAI_BASE_URL`：接口站点，由用户提供，不写死。
- `OPENAI_IMAGE_MODEL`：图片模型，默认 `gpt-image-1`。
- `OPENAI_IMAGE_SIZE`：图片尺寸，默认 `1536x1024`。

检查：

`python3 tools/mermaid_render.py --check-image-env`

若检查输出缺少环境变量，按系统提示让用户执行 `export` / PowerShell `$env:` / fish `set -x` 命令，用户补齐后再继续。

运行：

`OPENAI_API_KEY=<key> OPENAI_BASE_URL=<站点> python3 tools/mermaid_render.py -i <草稿.md> -o "{版本目录}/<标题_YYYYMMDDHHmmSS>.md" --diagram-mode image-api`

或使用命令行参数：

`python3 tools/mermaid_render.py -i <草稿.md> -o "{版本目录}/<标题_YYYYMMDDHHmmSS>.md" --diagram-mode image-api --image-api-base <站点> --image-api-key <key> --image-model gpt-image-1`

自动生图模式会把每个 mermaid 图转为专利附图风格提示词，调用图片接口生成 PNG，写入 `mermaid_figures/`，并通过隐藏图片引用嵌入 Word。若某张图调用失败，该处保留 mermaid 源码作为降级，避免整份文档生成中断。

若用户需要 PDF，追加 `--pdf`；PDF 只在 Word 成功后转换。

**安全要求**：优先让用户通过环境变量提供 key；不得把真实 key 写入交底书正文、Markdown、Word、修订日志或最终回复。

## 7.8 生图提示词与自动生图要求

提示词和自动生图的 prompt 须使模型生成符合专利说明书常见附图风格的图：

- 白底，黑色或深灰细线。
- 二维平面线稿，矩形/圆角矩形节点，箭头清晰。
- 简体中文短标签，层级分明，留白充足。
- 禁止照片、3D、渐变、阴影、装饰图标、品牌标识、卡通风格。
- 适合插入 Word/A4 文档。

## 7.9 交付回复：权利要求偏向点（仅对话，不入正文）

每次交付定稿后，在回复中追加简短引导：

用户若希望把正文进一步改成更接近权利要求书的写法，可说明偏向，例如：

- 更偏“方法步骤主权利要求”；
- 更偏“系统模块主权利要求”；
- 更偏“关键子流程从属权利要求”。

Agent 后续按迭代流程写入下一个版本目录，并另存新时间戳文件，不覆盖旧稿。

## 7.10 生成质量硬性要求

生成前自问：

- 发明内容是否已经能直接抽成权利要求 1 的步骤？
- 具体实施方式是否讲清楚每个关键步骤怎么做？
- 方法步骤和系统模块是否能一一对应，整体闭环是否能串起来？
- 是否写了端到端数据流、关键数据结构、输入/处理中间态/输出样例、伪代码或处理表？
- 是否写了参数、阈值、字段、样本、规则、异常分支或替代实现？
- 代理人是否无需阅读源码，也能理解核心技术方案并据此撰写权利要求？
- 是否把商业秘密细节抽象化，而不是泄露具体 prompt/真实规则表？
- 是否删除了注意事项、联系人、委托确认话术等非技术正文？

若任一答案为否，先补正文再交付。
