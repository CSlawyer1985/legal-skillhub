# 专利说明书式技术文本生成后自检（Step 8，内部执行）

自检结果用于**修订正文**，默认**不单独输出自检报告**；用户索要时可单独提供。**不得**将自检清单作为正文一章写入。

## 8.1 说明书式正文结构与技术完整性

- [ ] 正文是否只包含专利技术内容，未出现“注意事项”“技术联系人”“委托确认”“请核对文本”等非技术话术？
- [ ] 标题下是否写明发明人/发明者；若未知，是否仅写 `[待填写]` 且未根据作者、提交人或组织信息猜测？
- [ ] 是否包含：技术领域、背景技术、发明内容、附图说明、具体实施方式、摘要？
- [ ] 发明内容是否写清“要解决的技术问题、技术方案、有益效果”，而不是只写一句概述？
- [ ] 方法方案是否可直接抽象为权利要求步骤，且至少包含 S1-Sn 的实质处理步骤？
- [ ] 系统方案是否列出模块、职责和模块间数据流？
- [ ] 具体实施方式篇幅是否足够，是否覆盖每个核心步骤，而不是重复发明内容？
- [ ] 是否写明关键技术思路：数据结构、字段、参数、阈值、样本、规则、模型输入输出、排序/过滤/映射逻辑？
- [ ] 是否写明端到端闭环：输入数据、处理中间态、输出结果、保存/展示/审计或继续计算路径？
- [ ] 是否提供关键输入输出样例、字段映射表、伪代码或处理表，使代理人无需读源码也能理解方案？
- [ ] 方法步骤与系统模块是否存在明确对应关系，而非各写各的？
- [ ] 是否写了异常分支或回退策略：无候选、单候选、多候选、低置信、模型输出不合规、规则未命中、执行失败等？
- [ ] 是否写了可选实施方式或替代实现：本地/远程模型、本地/远程索引、规则函数/SQL 查找/映射表等？
- [ ] 商业秘密内容是否做了抽象处理，未泄露完整 prompt、真实规则表、真实客户口径、真实训练数据？

## 8.2 逻辑与闭环

- [ ] 技术方案是否形成完整闭环（发现→处理→扩展/输出）？
- [ ] 模块之间关联关系是否清晰？上下游是否衔接？
- [ ] 对多件相关专利，是否能用通俗话说明每件专利的侧重点、交叉点和边界？
- [ ] 分支样本（如边界样本、低置信度样本等）是否有明确处理路径？
- [ ] 依赖项（如类别中心、动态阈值等）是否有来源说明？
- [ ] 发明内容、附图说明和具体实施方式是否相互呼应？

## 8.3 公式与参数一致性

**Step 8 必做（含公式时）**：除符号体例与跨节一致外，须**主动复核公式是否正确、公式逻辑是否与「发明内容」和「具体实施方式」叙述一致**（等同用户会提出的「检查公式和公式逻辑是否有误，有误请调整」）；发现问题**直接改稿**，勿仅提示用户自行修改。

### 符号与体例

- [ ] **符号表**：全文含公式时是否在首次公式前先定义符号（含义、下标、量纲）；式 (1) 及后文每个符号是否均已在表中定义？
- [ ] **维度下标**：是否存在 `^{cpu}`、`^{mem}`、`^{io}` 等 **上标表示维度** 的写法？若有须改为 `b_{i,\mathrm{cpu}}`、`a_{j,\mathrm{mem}}` 等 **下标 + `\mathrm{}`** 形式（见 **`disclosure_builder.md` §7.5**）
- [ ] **字母多义**：同一字母是否兼指任务侧与节点侧等不同对象？若有须拆分符号（如任务用 \(b\)、节点用 \(g\)）
- [ ] **公式表述一致**：同一物理量在不同公式、段落中是否 **同形同义**（如权重公式、调整系数、匹配分 \(M_{ij}\) 等）
- [ ] **LaTeX 体例**：行内/块级分隔符是否全文统一（`\(...\)`/`\[...\]` 或 `$`/`$$` 二选一）；块级公式是否尽量单行；是否避免 `\text{且}` 等易渲染失败写法
- [ ] **参数表与符号表**：参数表「符号」列是否与符号表 **逐字同形**
- [ ] **阈值范围**：与正文一致（如 0.5–1.5、0.8–1.2 等）
- [ ] **参数命名**：全文统一，避免同义不同名混用
- [ ] **实施例数值**：与关键技术参数表对应，不冲突

### 公式正确性与逻辑（必核）

- [ ] **式面正确性**：各式是否无明显笔误（运算符、括号配对、上下标错位、同一式内符号与符号表不符、缺项/多写项、指数或分母写错等）？
- [ ] **约束与不等式方向**：公式中的 `\leq`/`\geq`/正负号是否与文字含义一致（如「饱和度」「有余量」「限频间隔」等）；多条件「且/或」是否与具体实施方式中的流程分支一致？
- [ ] **公式与流程互推**：主公式（含式 (1)）及衍生式，能否与 **方法步骤 S1—Sn**、**系统模块职责** 逐步对应？叙述中的打分、重排、限频、窗口聚合等是否在公式中有体现，**无**「文字一套、公式另一套」？
- [ ] **边界与特殊情形**：空队列、单节点、分母为零、指标缺失、达到上下界等情形，公式或正文是否给出合理处理或说明（至少不与主公式矛盾）？
- [ ] **量纲与取值**：符号表声明的量纲/取值范围是否与公式用法一致（如权重为正、比例在 0—1、计数为非负整数等）？
- [ ] **修订联动**：若修正公式或逻辑，是否已同步改发明内容、具体实施方式、参数表及符号表？

## 8.4 格式与引用

- [ ] **迭代路径**：若本次走 `merger.md` / `correction_handler.md`，对话中是否已含 **`## 合并摘要（留档）`** 或 **`## 纠正摘要（留档）`**（按该 prompt 字数要求）
- [ ] **修订对话记录**：案件目录是否已追加 **`交底书修订对话记录.md`** 一条（含记录时间、用户说明摘要、本轮交付文件名、摘要摘录），见 **`iteration_context.md`**
- [ ] **交付文件名**：凡落盘交付的交底书是否均为 **`{案件名}_{YYYYMMDDHHmmss}.md`**、同名 `.docx` 或同名 `.pdf`（见 `disclosure_builder.md` §7.6，**含首次定稿与迭代**），未无故覆盖旧稿
- [ ] **交付选择**：是否已让用户选择 Markdown / Word；若选择 Word，是否已让用户选择 PNG 图示、生图提示词或自动生图，并确认是否导出 PDF
- [ ] **附图**：至少包含方法流程图和系统结构图；复杂方案是否包含关键子流程图？
- [ ] **系统框图与流程图**：均先用 fenced mermaid 表达结构，**无** ASCII 文字流程图/框图；若 Word+PNG 已用 `mermaid_render.py` 转 PNG；若 Word+生图提示词，提示词是否符合专利附图常见样式并说明由用户自行用 gpt-image 等工具生图；若 Word+自动生图，是否已用 `mermaid_render.py --diagram-mode image-api` 生成 PNG 并确认正文、Markdown、Word、修订日志中未泄露真实 key
- [ ] **附图说明**：是否逐图说明“图1是……流程图；图2是……结构图”？
- [ ] 章节引用须指向真实存在的章节或附图编号。
- [ ] **背景技术/现有技术**：每个方向下列举的专利/文献是否均附有**可访问且与著录项一致**的公开 URL（非编造）；是否与 `prior_art_search.md` 要求自洽；**检索说明**是否**未**出现 `cnipa_epub_search.py`、WebSearch/降级等内部流程用语
- [ ] **查新摘要（国知局）**：凡 **`EPUB_HITS_JSON`** 中带非空 **`abstract`** 的条目，对该条的方案概括与局限**是否体现对摘要的理解**（非仅标题、且不与摘要矛盾）；无 `abstract` 的条目是否在查新路径上已按 `prior_art_search.md` 用其它可核验来源补全理解
- [ ] **文末清洁**：正文**无**技能仓库名、`examples/`、`disclosure_draft` 路径、「教学示例」「虚构」「不构成法律承诺」等**元信息脚注**（若存在则删除）
- [ ] **权利要求偏向点（对话）**：凡**定稿交付**的对话回复，是否已按 **`disclosure_builder.md`** 交付回复要求补充「可选下一步」类建议交互（**仅对话**，不入正文）；其中对举的侧重点是否**源于本稿与已定观点**，**无**凭空捏造

## 处理原则

发现问题则**直接修订正文**后再交付。  
**公式类**：Step 8 须完成「公式正确性与逻辑」核对；有误则改公式并联动修订相关章节，**不要**只向用户报告问题而不改稿（除非缺少必要技术事实、无法从正文与材料推断正确写法）。
