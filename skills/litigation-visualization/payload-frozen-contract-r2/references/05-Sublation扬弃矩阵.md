# Sublation 扬弃协议

Sublation 不是把多个 SKILL.md 拼在一起，而是用真实法律任务验证每项能力后作出有证据的去留决定。

## 决策词

| 决策 | 含义 |
|---|---|
| `保留` | 原能力适配法律任务且边界充分，可直接进入新体系 |
| `强化` | 能力方向正确，但需增加法律、隐私、证据或验收约束 |
| `替换` | 原实现或验证标准不适合，改用新的法律专用机制 |
| `组合` | 两个以上能力结合后产生独立增量 |
| `舍弃` | 价值不足、风险过高、平台绑定或会造成误导 |

每个决定必须有四项：`donor_evidence`、`legal_impact`、`decision_reason`、`regression_test`。缺一项即未完成扬弃。

## 领域基线继承门

新案型不得只写“参考了”已验证 Skill。先为每个 donor 生成稳定 inventory：`donor_id`、版本、冻结哈希和 `required_gate_ids`；再为每个 gate 写且只写一条决策记录。

通过条件是集合严格相等：

```text
{(donor_id, required_gate_id)} == {(donor_id, decision.gate_id)}
```

- 左侧有而右侧没有：遗漏，`HOLD-BASELINE-INHERITANCE`；
- 右侧重复：无法确定真实处置，`HOLD-BASELINE-INHERITANCE`；
- `舍弃` 没有风险解释和防复发测试：未完成扬弃；
- donor 版本或冻结哈希缺失：无法证明继承基线，保持 HOLD。

机器可读模板见 `templates/domain-baseline-inheritance.schema.json` 和对应 example。

## 比较顺序

1. 明确目标任务和受保护边界；
2. 用相同输入运行原创基底与 donor；
3. 比较正确性、可执行性、触发精度、隐私、可审计性和维护成本；
4. 先确定 P0 风险，再比较效率与表达；
5. 对保留/强化/组合项做正向回归；
6. 对替换/舍弃项做防复发测试；
7. 记录尚无证据的未知项，不以推测晋升。

## 本包三方定位

- **原创基底**：提供授权、只读基线、SSOT、答案键隔离、证据/法源门禁、多席验收与冻结控制面。
- **仓颉 donor**：提供全局理解、多镜头候选提取、候选/淘汰轨迹、原子化、链接和触发压力测试的启发。
- **GEO donor**：提供直接回答、结构化表达、查询集、引用忠实度、重复测量和公开优化节奏的启发。

控制面冲突时，以原创基底的隐私、法源、答案键和独立授权门禁为准。

## 禁止的“浅合并”

- 仅改名字或 description；
- 保留 donor 的平台 API 和分数，却没有法律有效性证据；
- 把书摘中的引文当作法律权威；
- 为了提高 GEO 指标删除例外、风险或不确定性；
- 在测试通过后自动安装或发布；
- 用起草者自评代替独立盲测；
- 没有回归样本就宣称“优于原版”。

## 验收

完成矩阵后至少回答：

1. 新包比原创基底多解决了什么真实问题？
2. donor 的哪些能力在法律场景中被改写，而不是照搬？
3. 哪些能力被舍弃，如何防止后续重新引入？
4. 私域案件为何不可能流入 GEO 层？
5. 当前证据能支持“候选完成”还是“正式晋升”？
6. donor inventory 是否 100% 被唯一决策覆盖，是否存在漏项或重复？

本 RC 只能支持本地候选完成，不能自动支持正式安装和外部发布。
