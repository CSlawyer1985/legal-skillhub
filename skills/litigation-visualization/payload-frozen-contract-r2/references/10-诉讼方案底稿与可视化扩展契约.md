# 诉讼方案底稿与可视化扩展契约

## 1. 架构边界

诉讼可视化采用受控 extension contract：

1. 母 Skill 负责蒸馏规则、领域基线继承门和统一契约。
2. 案型子 Skill 负责生成并冻结 `L2-05`，派生 anchor-map 与 handoff。
3. `litigation-visualization-cn` 负责 semantic spec、渲染和输出验证。
4. 下游不得反写 L2、SSOT、九文书、法院提交件或母 Skill。

母 Skill 不内置 renderer、浏览器、字体、图形依赖或第二套事实模型。触发默认为 `on_request`，不得随九文书自动生成。

## 2. 输出配置

诉讼可视化是 `professional_service.litigation_visualization` 子配置，不是新的顶层产物类别。v1 只允许：

- `case_process_flow`
- `claim_evidence_matrix`

`spatial_diagram` 或法院展示用途需要新的 Sublation、格式规则、证据规则、隐私门和真实 E2E。

## 3. L2-05 九个稳定语义区

蒸馏出的案件型 Skill 必须继承：

1. `parties_roles`
2. `contract_chain`
3. `performance_delivery_acceptance`
4. `payment_balance`
5. `notices_objections_termination_limitation`
6. `claim_element_fact_evidence_matrix`
7. `evidence_index`
8. `litigation_stage_plan`
9. `risk_hold_register`

具体标题、允许 locator 和视图角色以 `templates/L2-05-ANCHOR-CONTRACT-v1.json` 为准。每个锚点必须登记为 `present`、`empty_hold` 或 `not_applicable`；不允许因资料不足而省略，也不允许回原始案卷补填冻结 L2 未载事实。

anchor-map 使用 `l2-markdown-paragraph-table-v1`，只保存 `para-N` 或 `cell-A1` 定位及哈希，不复制事实文本。表格行不得同时计入段落块。

## 4. Handoff

handoff 必须符合 `templates/litigation-visualization-handoff-v1.schema.json`，至少绑定：

- 母 Skill、案型 Skill 和下游 Skill 的版本与哈希；
- 冻结 L2 的版本、哈希、相对路径和截止日；
- anchor contract 与 anchor-map 的版本、相对路径和哈希；
- 完整 source ledger；
- 本地隐私授权、法源复核状态和 HOLD 恢复条件；
- 下游 canonical validator 哈希；
- `write_back_allowed=false`。

运行 `scripts/validate_litigation_visualization_handoff.py`。字段、隐私枚举、locator、日期、账本、绑定哈希或绝对路径任一漂移均 fail closed。

## 5. 能力状态与渲染门

新案型 Skill 的 `capability_status` 默认为 `hold`。`render_allowed=true` 仅在以下五门同时为真时成立：

1. `litigation_plan_frozen`
2. `source_ledger_complete`
3. `privacy_authorized`
4. `semantic_spec_valid`
5. `independent_semantic_review_pass`

任一门未闭合，workflow 保持 `hold` 或 `research_draft`。门禁变化通过新的不可变 receipt 表达，不修改上游 L2 或历史 handoff。

## 6. 物理分离与零泄漏

- 用户可见图件：仅包含经授权的事实、流程、诉请、证据和风险表达。
- 治理 sidecar：anchor-map、handoff、验证报告、构建日志、绝对路径、哈希台账和 release receipt。
- 法院提交件：本扩展不得修改，也不得自动附带图件。

治理词、模型信息、构建日志、绝对路径、未授权身份信息和外部资源不得进入用户可见图件。外部处理、上传、外传、发布和法院使用均需单独授权。

## 7. 晋升门

candidate 进入正式母 Skill 前，至少补齐：

1. 母 Skill 到案型子 Skill 的蒸馏继承测试；
2. 当前买卖合同纠纷之外至少一个异案由真实 E2E；
3. 正向例、正确 HOLD 例和 validator-drift 回归；
4. 安装态 dry-run、回滚包与回滚演练；
5. 独立构建、语义、隐私和 artifact QA；
6. 观察窗证据与 root 的明确晋升授权。

候选验证通过只证明可进入独立复核，不等于安装、晋升或发布。
