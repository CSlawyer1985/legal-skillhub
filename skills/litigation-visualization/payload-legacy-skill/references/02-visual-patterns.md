# 可视化模式

本文件统一时间、关系、流向、数据、程序、争点矩阵与空间图的最小语义。`assets/` 中的 Mermaid/CSV 是原创、可编辑骨架，不复制原书图示。模板中只要还存在 `TODO_DO_NOT_DELIVER`，就不得交付。

## 统一记录模型

统一采用“3 个记录主维度 + 独立裁判处理维度 + 1 个规格级工作流门”，不得合并命名，也不得把事实支持、记录性质、生命周期、裁判处理和流程推进塞进同一个字段：

| 维度 | 允许值或示例 | 用途 |
|---|---|---|
| `fact_status` | 仅 `confirmed`、`disputed`、`unknown` | 表示当前材料对该事实记录的支持情况 |
| `record_type` | 仅 `fact`、`source_statement`、`inference`、`legal_rule` | 表示记录是什么，不表示它已被证明 |
| `lifecycle` | 仅 `current`、`superseded`、`not_applicable` | 表示记录在当前版本中的适用状态 |
| 独立 `adjudication_status` | 仅 `not_adjudicated`、`party_admission`、`procedurally_disputed`、`judicially_determined` | 表示当事人或裁判机关如何处理，不是记录主维度 |
| 规格级 `workflow_status` | 仅 `ready`、`research_draft`、`hold` | 顶层唯一工作流门，不下沉为节点状态 |

`fact_status`、`record_type`、`lifecycle` 属于每个规格元素，`adjudication_status` 是独立裁判处理维度；`workflow_status` 属于规格或版本顶层。`legal_review` 是始终存在的 sentinel：无触发内容时 `required=false`、`law_check_status=not_required`；触发法条、法律、管辖、流程图、程序、期限、时效、救济、上诉等内容时 `required=true`，并须人工实质核验。渲染时可以显示这些限制，但不能在图或 render manifest 中另造、覆盖规格值。

强制规则：

- `inference` 是 `record_type`，不是 `fact_status`。推论必须列出前提、推理者、建模假设和反例；模型推断本身不能把记录升级为 `confirmed`。
- `source_statement` 只确认“某主体作出过该陈述/主张”这一记录，不确认陈述内容为真；必须填写 `asserted_by`，图中显示“某方陈述/主张”。
- 每个节点、边、矩阵行或其他规格元素都必须有 `asserted_by`、`verification_basis`、`adjudication_status`、`adjudication_refs`，并保留 `support_refs`、`conflict_refs`、`context_refs` 与 `gap_reason`；`asserted_by` 使用明确的陈述者、记录者或来源角色，不得写 `not_applicable`。
- `superseded` 是 `lifecycle`，不是 `fact_status`。旧版本应留在审计层，不能伪装成“未知事实”。
- `confirmed` 必须有可复核的 `support_refs`；`disputed` 必须并列 `conflict_refs` 或相互冲突的来源；`unknown` 必须写 `gap_reason`。
- 对外显示 `fact_status=confirmed` 时必须写“当前材料支持，非裁判确认”；不得简写为可能被理解为司法认定的标签。
- `context_refs` 只提供背景，不能代替支持来源，也不是一种 `record_type`。无来源或 `fact_status=unknown` 时，不画有方向的事实边；将该项放入待核节点或缺口表。
- 节点颜色只可表达主体角色、对象类别或泳道，不得承接关系边、流向边的 `fact_status`。边状态须逐边写在标签中，并以线型或文字做第二编码。
- 每条关系边、流向边和时间关系边都要逐边记录完整元素字段；不得依靠图例替整张图批量赋值。

## 时间线

输入字段：事件 ID、发生/签署/送达/入账/记载时间、时间精度、主体、行为、对象，以及完整记录字段。时间关系边同样必须逐边记录 `lifecycle`、`verification_basis`、`adjudication_status`、`adjudication_refs` 和来源/冲突/上下文/缺口字段。

规则：

- 先统一时间口径；同一日期在材料中可能代表不同法律或事实时点。
- 日期不确定时写区间或“日期未知”，不要自动补日。
- 日期未知节点保持独立，不得从已知事件向它画“先于”“导致”等先后或因果箭头。
- 即使两个事件日期已知，先后边或因果边仍须有独立来源；时间排序本身不证明因果。
- 并行事件用泳道或分组；阶段变化用分隔带；因果关系与单纯先后关系使用不同的边标签。
- 期限计算必须写明起算点、规则来源、时区/工作日口径、法源效力和核验日期；未核验时进入 HOLD。
- 事件过密时按争点拆图，另附全量事件表。

起始模板：`assets/timeline-template.mmd`。

## 关系图

输入字段：主体 ID、角色、关系动词、方向、形成与终止时间，以及节点和边各自完整的记录字段。

规则：

- 同一主体在一张图中默认只出现一次；别名集中在主体表。
- 箭头必须有事实动词；合同、控制、付款、交付、担保等不同语义不得混成无标签线。
- 名义关系与主张的实际关系分别建边；争议关系并列各方来源，不替裁判者选边。
- 母子公司、项目层级、利益共同体等框架本身是待验证命题，不得仅凭视觉分组当作已证明事实。
- 无来源或方向未知时，不画箭头；在独立待核节点或缺口表中记录 `gap_reason`。
- 节点颜色可区分主体角色，但不得承接关系边的 `fact_status` 或暗示裁判结论。

起始模板：`assets/relationship-map-template.mmd`。

## 资金、货物、票据、股权或文件流向图

输入字段：起点、终点、对象、金额/数量、币种/单位、时间、条件，以及每条边自己的统一记录字段与来源字段。

规则：

- 合同主体和实际履行主体分开；“应当流向”和“实际流向”使用不同 `record_type`，不得在一条边上混写。
- 数量、方向和时点中任一未知且无来源时，不画该方向边；写入缺口表。
- 方向有争议但双方均有来源时，可画并列候选边，并在每条边写清 `conflict_refs`。
- 多笔往来保留稳定交易 ID，并用附表逐笔勾稽；图只承担结构与异常点。
- 线条粗细只有在比例准确、口径一致且有图例时才能代表数量；否则统一线宽。
- 节点颜色不得承接流向边状态。

起始模板：`assets/data-flow-template.mmd`。

## 数据表与对比图

输入字段：指标、主体/期间、数值、单位、计算式、`fact_status`、`record_type`、`lifecycle` 和来源字段。

规则：

- 先核单位、币种、含税/不含税、名义/实际、累计/增量和取数时点。
- 静态数据与动态变化分开；原始值与计算值分开。计算值应保留输入来源和可复算公式。
- 柱状或面积对比从合理基线开始；截断坐标必须醒目标注。
- 多笔款项、工程量或股权变化优先使用可核算表；装饰图不能替代计算链。
- `record_type=inference` 的预测或估算必须展示假设、区间和敏感性，不能用 `fact_status=confirmed` 包装。

## 程序流程与决策树

输入字段：节点、触发条件、必经/可选、期限、裁量、法源和核验日期；规格顶层治理元数据单独记录唯一的 `spec.workflow_status` 与 `legal_review.law_check_status`，不得下沉到各业务节点。

规则：

- `legal_review` sentinel 始终存在；流程图本身即触发 `required=true`。`law_check_status=pending` 时，未核验分支只能进入“停止生成确定路径”治理门，该门不是业务节点状态，也不得为不同节点下沉不同 `workflow_status` 或 `law_check_status`。
- 只有律师实质核验现行法、效力层级、适用身份、前置条件和材料截止点后，才可标 `legal_review.law_check_status=verified`；`legal_review.legal_rule_refs` 必须逐条覆盖每个 `record_type=legal_rule` 的 `support_refs`。只有完全不涉及法条、法律、管辖、程序、流程图、期限、时效、救济或上诉等触发内容时，才可说明理由并标 `required=false`、`not_required`。
- 模板不预填任何期限。期限需逐项记录法源、起算点、送达/知悉口径、自然日/工作日、节假日处理和核验日期。
- 区分“必须”“可以”“通常”“可能”；裁量路径不可画成机械必然。
- 对不同身份、程序阶段和前置条件分支；失败路径和补救路径同时呈现。
- `workflow_status=research_draft` 只能作为研究草案；`workflow_status=ready` 只表示通过当前工作流门槛，不等于法律结论正确，也不自动授权外发。

起始模板：`assets/procedure-flow-template.mmd`。

## 争点—事实—证据矩阵

输入字段：争点、事实命题、主张方、统一记录字段、`support_refs`、`conflict_refs`、`context_refs`、核验责任、`gap_reason`、下一步。

规则：

- 一行只表达一个中性、可判断的事实命题；不得在模板中预填任何像真实案情或证据编号的内容。
- `support_refs` 只放直接支持该命题的定位；`conflict_refs` 放反证或冲突口径；`context_refs` 仅放背景材料；三者不得混用。
- `fact_status=unknown` 时，来源字段可以为空，但必须填写 `gap_reason` 和 `next_step`；不得用推断补齐证据。
- 证据“存在”不等于足以证明；真实性、关联性、合法性、证明力和证明标准留给独立法律判断。
- 同一证据可以支持多个命题，但必须逐行说明支持路径。
- 对缺证、冲突、来源断裂和仅有推论的命题建立待办，不用空白掩盖。

起始模板：`assets/issue-evidence-matrix.csv`。

## 空间图、现场示意与路线/边界图

输入字段：空间对象、几何来源、测量方法、比例尺或坐标系、方向基准、采集日期、数据版本、遮挡、测量误差、投影变形、时间变化、视角偏差、建模假设和完整记录字段。这些内容同时写入顶层 `spatial_review`。

规则：

- 首先说明是示意图、按比例图还是坐标图；无法确认比例时醒目标“非比例示意”。
- 记录坐标系、比例尺、北向/方向基准、测量或采集方式、采集日期和数据版本。
- 把航拍、照片、笔录、地图、测量成果和当事人陈述作为不同来源类型保存，不得无说明拼成一个“客观现场”。
- 每条路线、边界、距离、面积和相对位置都须有可复核来源；无来源时不画断言性线条，只记入缺口表。
- 建模假设必须可见；对遮挡、误差、投影变形、时间变化和视角偏差分别说明。
- 示意图不能替代测绘、现场勘验或鉴定，也不能把视觉接近误写成法律边界、占有范围或因果关系。
- 未授权时不得把精确地址、坐标或敏感现场信息放入外发版本。

起始模板：`assets/spatial-diagram-template.svg`。

## 现有诉讼图的视觉完整性审查

对已有时间线、关系图、流向图、程序图、矩阵、空间图或庭审幻灯片，先枚举可见节点、边、形状、表格/幻灯片元素、箭头、颜色、面积和空间关系，再逐项检查：

- 是否能回链到 SSOT 与来源，现图中的元素 ID 是否稳定；
- 是否遗漏会改变理解的反方事实、反证、冲突、未知项、限定条件或替代路径；
- 是否把先后画成因果、关联画成控制、付款画成合同关系，或用颜色、粗细、面积、距离暗示未建模结论；
- 是否混淆 3 个记录主维度、独立裁判处理维度与规格级工作流门；
- 是否超出受众、渠道、字段白名单或人工放行范围。

输出一致性脚本只能核查可定位元素是否含对应 ID，不能发现未建模断言或判断视觉语义是否忠实；完整性结论必须由人工复核者记录范围、发现和处置。

## 图例规则

默认使用“边线型/符号 + 明文标签”的双编码，颜色仅作辅助并满足可访问性：

| `fact_status` | 边或记录的建议视觉 | 必须出现的文本 |
|---|---|---|
| `confirmed` | 实线；颜色可选 | 当前材料支持，非裁判确认 / `confirmed` |
| `disputed` | 双线、并列边或点划线 | 有争议 / `disputed`，并列冲突来源 |
| `unknown` | 不绘制有方向事实边；放待核节点/表 | 未知 / `unknown` 与缺口原因 |

不得使用“红=违法”“粗线=责任更重”等未经证明的默认含义。`inference` 与 `superseded` 不得出现在状态图例中；前者由 `record_type` 表示，后者由 `lifecycle` 表示。
