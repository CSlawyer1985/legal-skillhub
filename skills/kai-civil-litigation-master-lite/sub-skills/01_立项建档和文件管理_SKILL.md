# 立项建档和文件管理

## 强制约束

1. **在原文件夹内直接改造，全部完成后才重命名主文件夹**。在原文件夹内直接改造（创建子目录、移动文件、重命名），全部完成后才重命名主文件夹。命名格式：`原告名称（或简称）诉被告名称（或简称）案由纠纷案（代理身份）`。当事人名称过长时可使用规范简称。示例：`张三诉李四合同纠纷案（代理原告）`、`甲公司诉乙公司股权转让纠纷案（代理被告）`。**注：本命名规则仅适用于民商事诉讼、仲裁案件。刑事案件及其他非诉专项，按实际项目性质另行命名。**
2. **文件保全：整理完成后，用户提供的所有文件均须能在最终案件文件夹中找到**。保留所有用户提供的原始文件，不删除。查重结果仅记录于办案记录，重复文件不另行创建目录存放。
3. **证据目录及证据材料必须作为整体PDF存放，整体存放**。
4. **OCR 采用「延迟 OCR」模式：核心文件立即处理，非核心文件按需唤醒。** 所有 PDF 的文本层状态必须记录到 `工作底稿/OCR状态.json`；`案件卷宗/` 和 `资料收集/` 下所有 PDF 均可被 AI 读取，但不必在 Step 3 一次性完成全部 OCR。具体分级策略见 Step 3。
5. **确认代理方身份后再执行整理或分析操作**。
7. **后续子技能读取规则：限定 + 兜底扫描 + 用户确认**。01 模块负责为后续模块建立清晰的文件读取指引，避免后续 AI 无差别读取导致信息污染或遗漏。具体规则见 Step 4.1 和 Step 5.2。
8. **会话内文件读取复用规则**：同一案件文件夹中，`案件卷宗/` 和 `工作底稿/` 下的静态文件在同一 AI 会话中只需读取一次。后续子技能可直接复用已提取的文本内容，无需重复读取；但每次启动新任务时，必须先重新读取 `办案记录.md` 和 `OCR状态.json`，确认文件版本和状态未更新。若用户在会话中新增或修改了文件，相关文件必须重新读取。

## 执行前检查

按 `references/执行前强制检查清单.md` 完成基础检查。

**通用行为原则读取（强制）**：
- 读取 `references/通用行为原则.md`，全程遵守事实与观点区分、法律分析不预设立场、观点保持一致性、法条与案例引用先核验、事实一致性优先、风险提示常态化、输出结构化可复核等原则。

补充：
1. **加载本skill**：读取当前 `01_立项建档和文件管理_SKILL.md` 文件，熟悉死刑条款和执行步骤。
2. **🔴 模式检测（强制分流）**：检查案件文件夹是否已存在（含标准文件夹结构）：
   - **案件文件夹不存在** / 无标准结构 → **初始建档模式**：执行完整 Step 1-5
   - **案件文件夹已存在**（含 `案件卷宗/`、`工作底稿/`、`资料收集/`、`办案记录.md`）→ **增量归档模式**：**直接跳至 Step 6**，无需重建文件夹结构
3. **检查偏好**：若存在 `./办案记录.md`，读取其中是否有用户格式/风格偏好声明，以及已归档文件清单。
4. **观点一致性强制检查**：读取 `工作底稿/` 下的过程性文件及 `案件卷宗/` 下的在先生效诉讼文书，掌握既有事实主张、法律观点、数额计算，确保后续输出一致。
5. **确认任务**：确认案件名称、待处理文件位置、归档目标。

## 执行步骤（6 Step 精简结构）

### Step 1：确认基础信息

**1.1 确认代理方身份**
- 主动询问："您代理的是哪一方当事人？"
- 记录到后续生成的 `办案记录.md` 的"我方当事人"栏。

**1.2 确认文件夹路径与处理模式**
- 用户已提供明确文件夹路径 → 直接在目标路径内改造
- 用户未指定或材料分散 → 新建案件文件夹
- **跨文件夹搬运**：用户指定"将某文件夹整理到案件文件夹"时，直接在目标路径内完成分类整理，源文件移动至目标路径对应分类目录

---

### Step 2：预分析与用户确认

**开始正式整理前，必须逐项完成以下预分析，向用户展示检查结果，征得确认后再执行：**

```
□ 统计原始文件总数和类型分布（PDF/DOCX/图片/XLS各多少）
□ 【OCR检测】对PDF进行抽样文本层检测，列出需要OCR的核心文件清单（文件名+优先级+估算页数）
  → P0/P1 文件在 Step 3 立即启动**前台 OCR**（实时显示处理进度）；仅当预计超过30分钟时经用户确认后切换后台；P2/P3/P4 文件标记 pending，由后续子技能按需补漏
□ 【查重检测】对比文件名、页数、前200字文本内容，识别重复件
□ 提出分类方案：哪些归案件卷宗/、哪些归资料收集/、哪些归工作底稿/
    → 标注：案件卷宗文件须规范命名，资料收集文件保留原名
```

**查重规则：**
- 对比文件名相似度（去除日期后）
- 对比页数
- 对比前200字文本内容
- 发现重复 → 在办案记录中标注，保留原件不删除

**分类方案必须经用户确认后方可执行。**

---

### Step 3：OCR 延迟处理（核心文件立即处理，非核心文件按需唤醒）

**本步骤默认前台执行，实时展示进度；仅超长任务（预计>30分钟）经用户确认后切换后台、不阻断建档流程。** 根据文件优先级分级决定立即 OCR 还是延迟 OCR，同时生成 `工作底稿/OCR状态.json` 供后续子技能按需补漏。

> **前台执行反馈要求**：前台 OCR 运行时，应在启动时告知预计处理规模（文件数×页数），完成后立即输出处理结果（成功/失败页数、替换情况），并继续推进后续建档步骤，无需用户中途确认。

#### 3.1 文件 OCR 优先级分级

| 优先级 | 文件类型 | 建档时处理方式 | 后续补漏 |
|:---|:---|:---|:---|
| **P0** | 本案判决书、裁定书、调解书、起诉状、答辩状、上诉状、代理词 | 立即全文 OCR，使用自适应 zoom | 无需补漏 |
| **P1** | 证据目录、证据材料、合同、协议、发票、对账单、鉴定报告、评估报告 | 立即全文 OCR，使用自适应 zoom | 按需补漏 |
| **P2** | 委托手续、法院传票、通知书、立案材料 | 抽样检测 + 轻量读取（首页、目录页、末页、签章页）生成内容摘要，标记 `pending` | 关键页按需补漏 |
| **P3** | 资料收集中的背景材料、第三方报告、关联案件判决书、参考材料 | 抽样检测 + 轻量读取（首页、目录页、末页、签章页）生成内容摘要，标记 `pending` | 后续子技能需要时触发单文件即时 OCR |
| **P4** | 纯图片、照片、手写材料、无法 OCR 的扫描件 | AI 视觉轻量识别关键信息，生成内容摘要，标记 `skipped` | 需要时由 AI 视觉识别或人工处理 |

**动态升级规则**：
- 对 P2/P3 文件轻量读取时，若内容摘要涉及本案核心事实（金额、主体、法律关系、关键时间），立即升级为 P1/P2 并立即处理。
- 对 P4 文件 AI 视觉识别时，若发现涉及核心事实，升级为 P1/P2，由 AI 视觉或人工重点处理。
- 02 案情梳理模块启动时，必须读取 `OCR状态.json` 和 `办案记录.md` 中的文件重要性索引，对涉及核心争点的 P2/P3 文件主动升级。

#### 3.2 抽样检测文本层

不再对每本 PDF 的每一页执行 `get_text()`，而是按以下方式抽样：

- 页数 ≤ 5：全检
- 页数 > 5：检测首页、末页、中间 3 页（共 5 页）
- 若抽样页全部有文本 → 判定整本有文本，标记 `done`
- 若抽样页存在无文本页 → 对可疑区域及相邻页精检，返回 `bad_pages`

#### 3.3 启动 OCR 的方式

**P0/P1 文件**（使用自适应 zoom，无需指定 --quality/--zoom）：
```bash
python3 scripts/pdf_ocr_processor.py <案件卷宗路径> <输出路径> --workers 2 --skip-existing
```

**P2/P3/P4 文件**：
- 仅抽样检测文本层，更新 `OCR状态.json`
- 不启动 OCR，后续子技能读取时按需触发

**按需补漏**（后续子技能需要读取某文件时）：
```bash
python3 scripts/pdf_ocr_processor.py <单文件.pdf> <输出/> --skip-existing
```

#### 3.4 `工作底稿/OCR状态.json` 结构

```json
{
  "status": "processing",
  "updated_at": "2026-07-15T18:00:00",
  "files": {
    "案件卷宗/20250808_民事起诉状_己方.pdf": {
      "status": "done",
      "priority": "P0",
      "pages": 12,
      "bad_pages": [],
      "ocr_at": "2026-07-15T18:05:00"
    },
    "资料收集/关联案件/20240601_民事判决书_关联公司.pdf": {
      "status": "pending",
      "priority": "P3",
      "pages": 8,
      "bad_pages": [3, 4, 5],
      "summary": "关联公司合同纠纷一审判决，涉及违约金计算方式",
      "ocr_at": null
    }
  }
}
```

**状态枚举**：`done` / `processing` / `pending` / `failed` / `skipped`

#### 3.5 OCR 后文件替换规则

- OCR 通过质量检查后，可搜索版本在原路径替换原扫描件，文件名不变
- 替换时机：前台 OCR 完成后立即替换原文件；超长任务切换后台时，完成一个替换一个
- 替换后在 `办案记录.md` 中记录 OCR 处理情况（优先级、处理的页数、质量模式）

### Step 4：文件整理归档

#### 4.1 创建标准文件夹结构
在目标文件夹内创建以下 **3 个顶层文件夹**：

```
案件名称/
├── 案件卷宗/            ← L1 必读：当前审级正式诉讼文书（PDF 定稿），初始建档即创建 5 类标准子文件夹
│   ├── 01_委托手续/
│   ├── 02_己方文件/     ← 己方提交法院的诉讼文书及证据
│   ├── 03_对方文件/     ← 对方提交法院的诉讼文书及证据
│   ├── 04_法院文书/     ← 法院出具的文书
│   └── 05_律师文件/     ← 律所出具的程序性说明、工作文件
├── 工作底稿/            ← L2 按需：律师/团队自制的分析文件（Word、MD 草稿；同内容 PDF 定稿归入案件卷宗）。不含客户提供的原始文件。
│   ├── OCR状态.json
│   ├── 办案记录.md
│   └── 文字转录/
└── 资料收集/            ← L3 触发读取：非当前审级材料、客户/第三方背景文件、尚未正式提交法院的诉前材料。保留原名，按需创建子文件夹
    ├── 一审材料/        ← 仅当当前审级为二审/再审且存在一审材料时创建
    ├── 关联案件/        ← 仅当存在关联案件材料时创建
    └── 执行程序材料/    ← 仅当存在非当前阶段执行程序材料时创建
    （其余文件平铺于资料收集/根目录）
```

**案件卷宗填入标准（正面规则）：**

案件卷宗只存放**已向法院正式提交或法院出具的诉讼文书**。立案前收集的往来函件、背景材料、工商信息、参考文件等，无论发送方是我方还是对方，均归入 `资料收集/`；待正式提交法院后，再按角色转入 `案件卷宗/02_己方文件/` 或 `03_对方文件/`。

**文件夹读取等级（供后续子技能使用）：**

| 读取等级 | 文件夹 | 读取规则 | 风险说明 |
|:---|:---|:---|:---|
| **L1 必读** | `案件卷宗/` | 后续子技能执行时必须读取。按子任务类型读取对应子文件夹，详见后续各子技能规则。 | 若 01 分类错误，后续模块会一错到底。01 必须在 `办案记录.md` 中明确分类说明。 |
| **L2 按需** | `工作底稿/` | 仅读取与当前任务相关的分析文件，如 02 输出的案情分析报告、要件映射表、关键事实基准表等。 | 不应读取全部工作底稿，避免草稿污染定稿。 |
| **L3 触发** | `资料收集/` | 默认不读全文。仅在以下情况触发读取：① 用户明确要求；② `办案记录.md` 文件重要性索引标记为"涉及核心事实：是"；③ 当前任务逻辑上必须参考非当前审级材料（如二审读一审材料）。 | 01 分类错误时可能漏读关键背景材料。 |
| **L4 兜底扫描** | `资料收集/` | 后续子技能读取 L1/L2 后，必须扫描 `资料收集/` 下所有文件的文件名和 01 生成的一句话摘要，判断是否存在明显遗漏。 | 不读全文，只读文件名和摘要，用于提示用户。 |

#### 4.2 文件分类归档规则

**判断依据：来源 + 性质 + 格式。**
- 案件卷宗：当前审级正式诉讼文书的 **PDF 定稿**
- 工作底稿：律师/团队自制的可编辑草稿、分析文件
- 资料收集：非当前审级材料、客户/第三方背景文件，保留原始格式

**主分类表：**

| 文件性质 | 归档位置 | 子文件夹 | 命名后缀 | 格式要求 | 重命名 |
|:---|:---|:---|:---|:---|:---:|
| 本案法院/仲裁文书 | `案件卷宗/` | `04_法院文书/` | `_法院` | PDF | ✅ |
| 已向法院正式提交的己方诉讼文书及证据（起诉状、答辩状、上诉状、代理词、质证意见、证据目录等） | `案件卷宗/` | `02_己方文件/` | `_己方` | PDF | ✅ |
| 已向法院正式提交的对方诉讼文书及证据材料 | `案件卷宗/` | `03_对方文件/` | `_对方` | PDF | ✅ |
| 其他非己方当事人提交的诉讼文书及证据 | `案件卷宗/` | `03_对方文件/` | `_对方` | PDF | ✅ |
| 委托手续（授权委托书、委托代理合同、律师费发票、所函等） | `案件卷宗/` | `01_委托手续/` | `_委托手续` | PDF | ✅ |
| 律师出具的程序性说明、工作文件 | `案件卷宗/` | `05_律师文件/` | `_律师文件` | PDF | ✅ |
| 律师/团队自制分析文件、草稿（Word、MD） | `工作底稿/` | 平铺 | （无统一后缀） | DOCX/MD | ✅ |
| 非当前审级卷宗材料 | `资料收集/` | `一审材料/` / `执行程序材料/` | 保留原名 | 原格式 | ❌ |
| 关联案件判决书、裁定书及材料 | `资料收集/` | `关联案件/` | 保留原名 | 原格式 | ❌ |
| 客户/第三方背景材料（合同、函件、财务表格、会议纪要、企业信用报告等） | `资料收集/` | 平铺 | 保留原名 | 原格式 | ❌ |
| 尚未正式提交法院的诉前材料（往来函件、初步证据、参考资料等） | `资料收集/` | 平铺 | 无身份后缀 | 原格式 | 可辅助命名，不得使用诉讼角色后缀 |

**审级归档规则（强制）：**
- 当前代理审级为二审 → `案件卷宗/` 仅放二审文件 + 一审判决书；一审起诉、证据、法院文书等全部归入 `资料收集/一审材料/`
- 当前代理审级为一审 → `案件卷宗/` 放一审文件；此前关联案件材料归入 `资料收集/关联案件/`
- 当前代理再审 → 案件卷宗放再审文件 + 原审判决书；原审其他材料入 `资料收集/一审材料/` 或对应审级子文件夹
- **关联案件的认定（细化）**：不仅指不同当事人之间的另案，也包括**同一当事人之间、与本案非同一审级链条的前案/另案**（如本案为货款之诉，此前的违约金之诉及其执行程序）。判断标准：凡不属于当前代理案件案号项下程序的诉讼文书、法院文书、执行文书及执行救济材料，一律归入 `资料收集/关联案件/`，不得进入 `案件卷宗/`。

**格式转换规则：**
- 案件卷宗文件原则上为 PDF。DOCX/Word 定稿需转换为 PDF 后归入案件卷宗；原始可编辑文件保留在 `工作底稿/`
- 扫描件/图片经 OCR 后转为 PDF 入案件卷宗；原始图片可保留在 `资料收集/` 或删除（根据用户要求）
- 证据目录及证据材料必须作为整体 PDF 存放，不拆分

#### 4.3 文件处理三步顺序（强制）

```
① 识别内容 → ② 格式转换与重命名（资料收集跳过） → ③ 移动到对应文件夹
```

| 步骤 | 操作 | 说明 |
|:---:|:---|:---|
| **① 识别** | 读取内容明确性质 | 判断文件性质、来源、审级，确定归档位置；已有文本层的 PDF 直接读取，未处理的前台 OCR 处理或后续按需补漏 |
| **② 转换与重命名** | 案件卷宗文件转换为 PDF（如需要）；按 `YYYYMMDD_内容简述_身份后缀` 格式重命名 | 仅案件卷宗、工作底稿文件执行；资料收集文件跳过此步，保留原名 |
| **③ 移动** | 归档到最终位置 | 使用移动（move），不保留原始位置副本 |

**禁止操作：**
- ❌ 先移动再处理
- ❌ 先重命名再识别内容
- ❌ 使用复制（cp）而非移动（mv）
- ❌ 对资料收集文件使用 `_己方` / `_对方` / `_法院` / `_委托手续` / `_律师文件` 等诉讼角色后缀
- ❌ 将 DOCX 直接放入案件卷宗而不转换 PDF

**日期提取规则：**
- 文件名自带日期 → 直接使用
- 文件名无日期但内容有页眉/落款/公告编号 → 从内容中提取
- 提取顺序：文件内公告日期 → 落款日期 → 文件编号日期
- 无法提取 → 按日期前缀规则处理

### Step 5：命名规范与归档确认

#### 5.1 文件重命名规范

> **适用范围**：`案件卷宗/` 和 `工作底稿/` 下的文件必须适用本规范。`资料收集/` 下文件原则上保留原名，可辅助以 `YYYYMMDD_内容简述` 格式命名以便检索，但**不得使用 `_己方` / `_对方` / `_法院` / `_委托手续` / `_律师文件` 等诉讼角色后缀**。

**标准化命名模板：**
```
YYYYMMDD_内容简述[_身份后缀].扩展名
```

**命名要素：**

| 字段 | 说明 | 示例 |
|:---|:---|:---|
| `YYYYMMDD` | 事件发生日期或文件落款日期 | `20250808`、`20240601` |
| `_` | 下划线分隔符 | - |
| `内容简述` | 文件核心内容，简洁明了 | `民事起诉状`、`撤裁初步评估报告` |
| `_` | 下划线分隔符，身份后缀不存在时可省略 | - |
| `[身份后缀]` | （可选）表明文件**角色归属**，使用固定后缀；工作底稿文件可省略 | `_己方`、`_对方`、`_法院`、`_委托手续`、`_律师文件` |

**命名示例：**
- `20250808_民事起诉状_己方.pdf`（己方提交法院的起诉状）
- `20250917_答辩状_对方.pdf`（对方提交的答辩状）
- `20260616_撤裁初步评估报告.pdf`（我方自产工作底稿，无需身份后缀）
- `20260608_裁决书_贸仲G20243315号.pdf`（外机关文书，案号替代身份后缀）
- `20250710_传票_法院.pdf`（法院出具的传票）
- `20250715_授权委托书_委托手续.pdf`（委托手续）

**身份后缀规则：**
- 案件卷宗文件必须使用固定角色后缀：`己方`、`对方`、`法院`、`委托手续`、`律师文件`
- 同一角色后缀全案保持一致
- 法院文书后缀统一为 `_法院`，不再使用具体法院简称（如 `杭州中院`、`拱墅法院`）
- 工作底稿文件可不使用身份后缀，直接以日期+内容简述命名

**日期前缀规则（日期无法精确时）：**
- 8位全可识别 → `YYYYMMDD`（如 `20240326`）
- 仅知年月 → `YYYYMM00`（如 `20240300`）
- 仅知年份 → `YYYY0000`（如 `20240000`）
- 有语义标识无日期 → 按语义加前缀（如 `一证_国有土地使用证.pdf`）
- 完全无法识别 → `00000000` 前缀（如 `00000000_答疑文件.pdf`）

**适用范围：** 本命名规则适用于案件文件夹下的所有子目录及后续模块产物。

| **C（法院短信/送达链接）** | 文本含法院短信或 `https?://` 送达链接 | 法院短信专属处理流程：解析案号/当事人/平台 → API直连或浏览器下载 → 文书解析 → 关键信息提醒 → 标准归档 |
| **D（跨文件夹搬运）** | 用户指定"将XX整理到案件文件夹" | 直接在目标路径内完成分类，源文件移动至目标对应目录 |

**智能检测**：
- 若用户仅说"归档新文件"：自动检查 `待整理文件/`，有文件→模式B；否则询问输入方式
- 若提供文本含链接→自动模式C
- 若提到具体文件夹名称→自动模式D

#### 6.2.C 法院短信/送达链接专属处理流程

> 本流程处理法院短信送达、立案通知、开庭提醒等含送达链接的文本。法院短信处理是 01 模块增量归档的子流程，下载、解析、归档均在本模块内完成。

**C.1 输入解析**

1. **判断输入类型**

| 输入类型 | 特征 | 处理方式 |
|:---|:---|:---|
| 完整短信 | 含法院签名 + 正文 + 链接 | 解析短信文本，提取全部字段 |
| 纯链接 | 用户直接发送送达 URL | 跳过短信文本解析，直接从 URL 提取参数 |

2. **提取关键信息**

| 字段 | 提取方法 | 说明 |
|:---|:---|:---|
| 案号 | 正则匹配标准案号格式 | 示例：`（2025）苏0981民初1234号` |
| 法院名称 | 短信签名或 API 响应中的 `c_fymc` | 短信签名优先作为初步判断 |
| 送达平台 | URL 域名或路径特征 | 见 C.2 平台识别表 |
| 发送时间 | 短信文本或 API 响应中的 `dt_cjsj` | 用于期限计算 |

3. **平台识别**

| 平台 | 域名特征 | 下载方式 | 提取参数 |
|:---|:---|:---|:---|
| 全国法院统一送达平台 | `zxfw.court.gov.cn` | **API 直连（优先）** | `qdbh`, `sdbh`, `sdsin` |
| 广东法院电子送达 | `sd.gdems.com` | Playwright 无头浏览器 | 路径中的送达标识码 |
| 集约送达平台 | `jysd.10102368.com` | Playwright 无头浏览器 | `key` |
| 湖北电子送达 | `dzsd.hbfy.gov.cn` | HTTP API / 浏览器自动化 | `msg` 或账号密码 |
| 司法送达网 | `sfpt.cdfy12368.gov.cn` | Playwright 浏览器自动化 | 手机尾号后6位 / 短信验证码 |
| 未知域名 | 路径匹配已知平台特征 | 按路径识别平台 | 按具体平台规则 |

**C.2 文书下载**

1. 创建临时目录：`mkdir -p /tmp/court-sms-staging/`
2. 按平台顺序尝试下载：
   - **zxfw 平台 API 直连**：
     ```bash
     curl -s -X POST "https://zxfw.court.gov.cn/yzw/yzw-zxfw-sdfw/api/v1/sdfw/getWsListBySdbhNew" \
       -H "Content-Type: application/json" \
       -H "User-Agent: Mozilla/5.0 ..." \
       -d "{\"qdbh\":\"...\",\"sdbh\":\"...\",\"sdsin\":\"...\"}"
     ```
     响应字段：`data[].c_wsmc`（文书名称）、`data[].wjlj`（下载链接）、`data[].c_fymc`（法院名称）、`data[].dt_cjsj`（创建时间）。
   - **降级策略**：API 失败时，按 `Playwright CLI 无头模式 → Playwright MCP 浏览器自动化` 顺序尝试。遇到验证码优先使用手机尾号后6位，其次从短信正文提取。
3. **下载失败兜底**：向用户展示原始链接，提示手动下载后按 6.2.A 模式归档，不阻塞其他流程。

**C.3 文书解析与关键信息提取**

下载完成后，用 `pymupdf` 或 `pdfplumber` 提取首页文本，识别文书类型并提取关键信息：

| 文书类型 | 关键字段 | 提醒 |
|:---|:---|:---|
| 传票/出庭通知书 | 开庭时间、地点、法庭、联系电话 | **高亮提醒** |
| 判决书/裁定书 | 裁判日期、上诉期、上诉法院 | **计算期限** |
| 举证通知书 | 举证期限、证据交换时间 | **期限提醒** |
| 受理通知书/立案通知 | 立案时间、案号、法官/书记员 | 记录时间轴 |
| 诉讼费结算通知书 | 缴费金额、账户、期限 | **高亮缴费提醒** |
| 起诉状/证据目录/对方材料 | 提交方、案号、核心主张 | 按制作主体归档 |

**C.4 标准归档**

1. **确认目标案件目录**：扫描当前工作目录匹配案号；未匹配则新建 `{案号} {当事人简称}/` 并按 Step 4 创建标准结构。
2. **按制作主体分流**：

| 文件制作主体 | 归档位置 | 命名后缀 |
|:---|:---|:---|

| 己方当事人提交的材料（起诉状、答辩状、证据目录等） | `案件卷宗/02_己方文件/` | `_己方` |
| 委托手续（授权委托书、所函、律师费发票等） | `案件卷宗/01_委托手续/` | `_委托手续` |
| 非当前审级法院文书 | `资料收集/一审材料/` 或 `资料收集/执行程序材料/` | 保留原名 |

3. **命名规范**：统一执行 Step 5.1：`YYYYMMDD_内容简述_身份后缀.pdf`。身份后缀使用 `己方` / `对方` / `法院` / `委托手续` / `律师文件`，不再使用具体法院简称。

#### 6.3 文件预处理（复用 Step 2-3 规则，轻量模式）

1. **OCR 处理**（复用延迟 OCR 模式）：
   - 检查 `工作底稿/OCR状态.json` 是否存在，若不存在则新建
   - 对新 PDF 进行抽样文本层检测，按 P0-P4 分级判断处理方式
   - P0/P1 新文件 → 启动**前台**单文件 OCR（实时显示进度）：`python3 scripts/pdf_ocr_processor.py <单文件.pdf> <输出/> --skip-existing`；批量或超长任务（预计>30分钟）经用户确认后可切换后台
   - P2/P3 新文件 → 抽样检测 + 轻量读取（首页、目录页、末页、签章页）生成内容摘要，标记 `pending`，不阻塞归档
   - P4 新文件 → AI 视觉轻量识别关键信息，生成内容摘要，标记 `skipped`，不阻塞归档
   - 手写材料 → 按 P4 处理，AI 视觉识别关键信息，标记 `skipped`
   - OCR 工具不可用时 → AI 直接读取 PDF/图片内容，识别关键信息并记录摘要，不阻塞归档流程
2. **查重检测**（复用 Step 2 规则）：与已归档文件对比文件名、页数、关键段落
   - 重复件 → 在办案记录中标注，保留原件不删除
   - 同一文件不同载体（扫描件+手机拍照）→ 非重复件，分别归档（可放同一子文件夹）
3. **日期提取**（复用 Step 4.3 规则）：文件名无日期时从 PDF 内容中提取

#### 6.5 关键材料文字转录（按需）

> **原则**：PDF OCR 添加文本层是默认做法。独立转录文件仅按需生成，避免 `工作底稿/` 文件过多、过乱。

**触发条件（满足任一即转录）**：
1. 用户明确要求对某份文件全文转录。
2. 后续子技能（如 02 案情梳理、06 质证意见）需要逐段引用原文。
3. 文件版式复杂、手写混排、OCR 文本层可读性差，需要整理成标准文本。
4. 文件属于下列「建议转录」范围且内容对本案有实质影响。

**转录流程**：
1. **内容分析**：优先从已 OCR 的 PDF 提取全文 → 分析核心信息（当事人、金额、日期、法律关系、关键条款）。
   - OCR 不可用 → AI 直接读取图片/PDF，识别关键信息生成摘要。
2. **生成转录文件**：保存至 `工作底稿/文字转录/`，命名 `YYYYMMDD_原文件名_文字转录.md`。
3. **转录文件结构**：
   ```markdown
   # [文件名称] OCR 转录
   ## 文件信息
   - 原文件名 / 页数 / 归档路径 / 转录日期
   ## 核心信息摘要
   - 当事人 / 关键日期 / 金额/标的 / 法律关系 / 对本案的影响
   ## 全文转录
   [逐页转录]
   ```
4. **转录范围**：
   - ✅ **必须转录**：合同、协议、发票、对账单、关键往来函件（直接影响权利义务的原始交易文件）
   - ⚠️ **建议转录**：承诺书、声明、情况说明、律师函、会议纪要、会谈记录（手写除外）
   - ❌ **无需转录**：法院文书（已有标准格式）、纯图片材料、手写材料、程序性申请文件

> **说明**：「必须转录」并非每次归档都自动执行。只有当后续分析需要全文引用，或文件 OCR 层质量不足时，才生成转录文件。归档流程不阻塞。
