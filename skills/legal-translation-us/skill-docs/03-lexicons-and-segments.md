### 步骤 3b：为字符碎片化跟踪更改簇搭建 en_segments — 若源文件有跟踪更改则强制

源语言概念草稿偶尔包含逐字母编写的跟踪更改编辑——单个单词或序数词通过一系列 1-3 字符的 `ins` / `del` 拆分被替换为另一个词。在英文中，正确的编辑几乎总是**整词**替换（例如美式默认变体下“Section 12” → “Section 13”，`--variant uk` 下“Clause 12” → “Clause 13”），而非字符级——因此分段感知的翻译者无法在没有明确指导的情况下针对碎片化源结构产出干净的英文红线。

在起草翻译前运行一次检测器：

```bash
python <skill-path>/scripts/coalesce_fragmented_tcs.py <workdir>/paragraphs.json
```

脚本扫描每个 `has_track_changes: true` 的段落，检测在接受侧和拒绝侧各自重组为连贯单词/序数词的连续字符级 ins/del 簇，并**将预填的 `en_segments` 骨架写入**每个被标记的段落。它**不**修改 `tc_segments`——源 XML 结构仍保留所有字符级 run，因此骨架为每个 `tc_segments` 条目生成一个 `en_segments` 条目。在每个检测到的簇内部，骨架包含：

- 第一个 `ins` 段上的 `<<TRANSLATE: ins='<accepted-word>' (accepted)>>` 占位符，
- 第一个 `del` 段上的 `<<TRANSLATE: del='<rejected-word>' (rejected)>>` 占位符，
- 每个其他段（共同构成碎片化簇的中间 ins、del 和常规 run）上的空字符串 `""`。

簇外部骨架留下 `en: ""`，因此翻译者仍填写正常段落文本。

翻译时（步骤 4），翻译者：

1. 将每个 `<<TRANSLATE: …>>` 占位符替换为最终英文（例如 ins 侧为 `"Clause 13"`，del 侧为 `"Clause 12"`）；
2. 用正常翻译填写周围非簇 `en_segments` 条目；
3. 将簇内的空字符串槽保持**为 `""`**——这些是刻意的“清除此 run”标记，`apply_translations_textmatch.py` 用它清空匹配的源 run，使孤儿源字母不会泄漏进英文红线。

幂等：在已搭建的 paragraphs.json 上重新运行脚本会重新检测相同簇并写入相同骨架。无簇匹配时以 `"No character-fragmented TC clusters detected. Nothing to do."` 干净退出。

理由和典型西班牙语道路使用示例见步骤 4 下“混乱 / 字符碎片化整词编辑”。

如果源文档没有跟踪更改，本步骤为空操作，可跳过。

#### 跟踪更改标记数量在源与输出之间可能有合理差异

三种机制可以减少最终英文文档中的 `<w:ins>` / `<w:del>` 数量而不丢失任何跟踪更改信息：

1. `coalesce_fragmented_tcs.py` 将字符级源编辑折叠为整词英文编辑——例如源编辑 `Duodécima → Decimotercera` 中的五个字符级 ins/del 对在英文中变为单一整词对 `Section 12 → Section 13`（美式默认；英式：`Clause 12 → Clause 13`），因为字符级编辑无法在词级翻译中存活。
2. `strip_noop_tracked_changes.py`（步骤 8 / 应用阶段）移除无操作正字法对——在源中唯一效果是西班牙语重音/标点/变音符号变更、无英文对应的跟踪更改——并剥离遗留的任何空 `<w:ins>` / `<w:del>` 包装。
3. 文本替换后遗留的空 run 包装在应用步骤期间被压缩。

对典型的西班牙语 `.doc → .docx` 红线稿，你应预期 `<w:ins>` 数量下降约 10-25%（插入数量比删除数量缩减更多，因为西班牙语转换痕迹集中在插入侧）。这是质量改进，而非缺陷。如果你将文件交给逐侧比较标记数量的审阅者，请事先提及，以免缩减被误认为内容丢失——接受全部 / 拒绝全部模拟是确认跟踪更改覆盖的正确方式，而非标记算术。
