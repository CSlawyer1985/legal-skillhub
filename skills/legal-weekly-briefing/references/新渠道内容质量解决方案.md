# 新渠道（微信读书）内容质量解决方案 · 新旧渠道对比分析

> 2026-08-01 | 背景：MP 跨号接口关闭（2026-07-29）后，内容发现从「MP API + Agent 手工构建」切换到「微信读书全自动」。全自动跑出现 5 类内容质量问题，本文对比新旧渠道差异并给出系统性方案。

## 一、新旧渠道对比（基于 7-28/7-31/8-01 三期实证）

| 维度 | 旧渠道（7-28，MP API） | 降级模式（7-31，WebSearch） | 新渠道（8-01，微信读书全自动） |
|------|----------------------|---------------------------|------------------------------|
| 数据来源 | fetch_mp_week.py（MP API digest，**质量好但常为空**） | Agent WebSearch 手工构建 | fetch_weread_week.py（微信读书 desc，**质量差**：文末片段/法条段） |
| 摘要（digest） | 空 → Agent 不补或 WebFetch | Agent 写摘要 | 微信读书 desc 直接采用 → 文末投稿声明/法条段（胡尚慧/韩小龙/丈夫借款等 5 条踩坑） |
| 推荐理由 | **Agent 写**（"> 推荐理由：…"格式，有） | **Agent 写**（💡 格式，有） | **无人写**（L1 只有 5 字段）→ 全空 |
| 特征标注（features） | Agent 标注 → 评分可信 | Agent 标注 | **无人标注**（空 {}）→ k-NN 评分失真（"至正之旅"文体新闻得 7.3 分） |
| 内容过滤 | Agent 筛选（人工判断） | Agent 筛选 | 无 → 文体活动/庆祝/会议新闻混入 |
| 跨期去重 | Agent 记忆（人工避重） | 人工 | 无 → 与上期窗口重叠重复 |
| Agent 参与度 | **高**（构建环节全程把关） | **高** | **零**（设计为全自动，构建环节被跳过） |

**结论：新旧渠道的差异不在数据源，而在「候选构建环节是否有人（Agent）把关」。**
旧渠道和降级模式质量好，是因为 Agent 在构建 candidates 时做了 5 件事：内容过滤、跨期避重、摘要修复、推荐理由撰写、特征标注。新渠道把它们全部跳过了，5 类问题随之而来。

## 二、新渠道质量保障方案：恢复 Agent 精修环节，聚焦精选区

**原则**：机器负责"广撒网"（L1/L2/WebSearch 产候选），Agent 负责"精挑"（只精修最终进周报的 ≤10 条）。候选池 20-30 条全量精修成本高，精选区 10 条精修可控。

```
Step 2/2.5（机器）        Step 3（Agent 精修，只做精选区）        Step 4（pipeline）
L1 微信读书抓取  ──────►  ① 内容过滤（文体/庆祝/征稿/会议剔除）   ──►  评分排序 → 精选 10 条
L2 元宝反查      ──────►  ② 跨期去重（上期周报 URL 指纹）        ──►  渲染 MD + HTML
AI 动态 WebSearch ─────►  ③ digest 质量修复（WebFetch 回退）      ──►  交付
                         ④ recommend 撰写（律师视角 ≥30 字）
                         ⑤ features 标注（7 维 / AI 4 维）
```

### 各问题的新渠道解决方案

| # | 问题 | 新渠道方案 | 已落地 |
|---|------|-----------|--------|
| 1 | digest 文末片段/法条段 | 质量判断规则（文末特征词/《开头）→ WebFetch 回退，**只修精选区条目**（≤10 条，每条约 1 分钟） | ✅ SKILL.md 规则 + 本轮 5 条修复 |
| 2 | recommend 缺失 | **Agent 必写**：精选区每条写律师视角推荐理由；写不出 = 不该进精选（天然过滤器） | ✅ SKILL.md 纪律 + 本轮 24 条补写 |
| 3 | features 空 → 评分失真 | **Agent 标注精选区候选**（7 维/AI 4 维）；全自动模式由 Step 2.5 的 Agent 一并标注 | ⚠️ SKILL.md 警示已写，标注落实待自动化流程 |
| 4 | 非实务文章混入 | 内容过滤规则（文体/庆祝/征稿/会议/文化建设类剔除） | ✅ SKILL.md Step 3 |
| 5 | 跨期重复 | 上期周报 URL 指纹去重（__biz/mid/idx/sn） | ✅ SKILL.md Step 3；脚本化待并入 merge_candidates.py |

### 摘要来源优先级（新渠道修订版）

```
L1 digest（微信读书 desc）→ 质量预筛：
   ✅ 正常（案情/问题引入开头）→ 采用
   ❌ 文末特征词开头（来稿/投稿/关注/点击/长按）→ WebFetch 回退
   ❌ 《开头（法条引用段）→ WebFetch 回退
   → WebFetch 取正文开头 150-200 字（案情/内容提要）
```

### 已知边界

- **中国应用法学【法官办案心得】栏目**：文末固定带投稿须知，digest 命中率最高，重点检查
- **山东高法案例类**：法条链接段被抽中概率高（民诉法解释等）
- 精选区外的条目不精修（不展示，成本可控）；若某期精选条目 digest 全部低质，最多 10 次 WebFetch（~10 分钟），可接受

## 三、遗留（后续可工程化）

1. merge_candidates.py 加 `--exclude-prev`：自动读上期周报做指纹去重
2. fetch_weread_week.py 输出加 `digest_quality` 标记（文末/法条特征自动预筛，供 Agent 快速定位）
3. 全自动 automation 的 prompt 显式包含 Step 3 精修职责（内容过滤/去重/摘要/推荐/标注）
