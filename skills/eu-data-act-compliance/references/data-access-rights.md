# 数据访问权——用户访问与第三方共享

## 概述

《数据法》第二章和第三章确立了**用户访问互联产品生成数据的权利**，以及**指示数据持有者将该数据共享给第三方**的权利。

这些是《数据法》运营意义最大的义务之一。

## 用户访问权（第 4 条）

### 范围

用户有权访问互联产品或相关服务使用期间生成或与其使用相关的数据。

**「使用生成的数据」**包括：
- 传感器数据（温度、位置、速度、压力等）
- 运行日志（使用频率、模式、正常运行时间）
- 性能指标（效率、产出、错误）
- 状态和诊断数据
- 运行期间捕获的环境数据

**排除：**
- 制造商专有分析或衍生洞察的结果数据（除非合同或法律承诺）
- 无法关联到特定用户产品的聚合或匿名数据
- 第三方持有、数据持有者无法控制的数据

### 技术要求

数据必须以下列方式提供：

1. **在技术上可行的情况下持续、实时提供**（第 4(1) 条）
   - 「实时」指无不当延迟
   - 「技术上可行」承认约束（如离线产品、批处理架构）
   - 如间歇性连接为产品设计固有，可以接受

2. **免费**（第 4(2) 条）
   - 标准用户访问其自身数据不收费
   - 例外：「频繁或复杂」请求可收取合理费用（第 9 条）——见下文费用结构

3. **易于访问**（第 4(2) 条）
   - 用户友好界面（门户网站、移动应用、带清晰文档的 API）
   - 不要求专门技术知识
   - 可行时向残障人士开放

4. **安全**（第 4(2) 条）
   - 身份验证和授权机制
   - 加密传输（最低 TLS/HTTPS）
   - 访问日志和审计追踪
   - 防止未经授权访问

5. **结构化、常用、机器可读的格式**（第 4(3) 条）
   - JSON、XML、CSV 或领域特定标准（如医疗用 FHIR、电动车充电用 OCPP）
   - 非专有或混淆格式
   - 解释所需的元数据和模式文档随附

### 数据持有者义务

数据持有者**不得将数据用于**用户同意的提供产品/服务之外的其他目的，**除非**用户已同意额外使用（第 4(2) 条第二款）。

**实际影响：**
- 默认：数据仅为产品功能收集和使用
- 如数据持有者想将数据用于分析、产品改进、营销或第三方共享：**须明示同意**
- 涉及个人数据时，同意须符合 GDPR 标准

### 拒绝与限制

数据持有者仅可在以下狭窄事由上**拒绝或限制访问**：

1. **可证明的提供访问所需能力不可用**（第 4(4) 条）
   - 暂时性技术中断、不可抗力
   - 不是永久借口——数据持有者必须补救并提供访问

2. **商业秘密保护**（第 4(5) 条，交叉引用第 5(4) 条）
   - 数据含商业秘密且披露将显著损害数据持有者商业利益时
   - 必须逐案证明并附详细说明
   - 数据持有者必须探索部分访问、聚合或删节是否能在保护秘密的同时实现访问

3. **特定安全或保密风险**（从一般安全义务中隐含）
   - 访问将造成不成比例的安全漏洞时
   - 必须适用限制性最小的替代方案（如经安全 API 访问而非完整数据库导出）

**举证责任：** 数据持有者必须以具体、有记录的理据为拒绝辩护。笼统主张不够。

## 第三方数据共享权（第 5-7 条）

### 用户共享指示（第 5(1) 条）

用户可**指示数据持有者**将数据提供给用户选择的**数据接收者**。

**要点：**
1. 用户发起请求（而非数据接收者单方面）
2. 请求可由用户直接提出，或由经用户授权的数据接收者代为提出
3. 数据持有者必须**及时**遵从
4. 数据可通过以下方式共享：
   - **直接访问**（数据接收者连接数据持有者的 API）
   - **数据副本**（数据持有者向数据接收者提供数据集）

### 数据接收者义务（第 5(1)-(2) 条）

数据接收者必须：

1. **仅按与用户商定的目的使用数据**
   - 在数据共享协议或用户指示中指明
   - 未经进一步用户同意不得二次使用

2. **不得使用数据开发削弱数据持有者在产品市场地位的竞争产品**
   - 反竞争使用限制（第 5(2) 条）
   - 「竞争产品」= 互联产品的直接替代品，非相邻/互补服务
   - 示例：使用诊断数据的售后维修服务**允许**；使用数据逆向工程并制造竞争设备**受限**

3. **处理个人数据时遵守 GDPR**
   - 数据接收者是独立控制者或处理者，取决于与用户的关系
   - 必须有合法依据、尊重数据主体权利、确保安全

### 数据持有者回应义务（第 6 条）

数据持有者必须**及时**提供数据，方式须：
- 安全
- 结构化、常用、机器可读格式
- 随附解释所需的必要元数据和文档

**拒绝事由（第 6(1)-(2) 条）：**

数据持有者仅在以下情形可拒绝第三方共享请求：

1. **可证明的必要能力不可用**（暂时）
2. **特定安全或保密风险**（附理据）
3. **商业秘密保护**（第 6(2) 条）——见下文商业秘密保障
4. **守门人排除（第 6(2)(e) 条）**——不得强制数据持有者向被《数字市场法》指定为守门人的数据接收者提供数据

**拒绝通知：**
- 必须**及时**告知用户和数据接收者
- 必须提供**详细拒绝理由**
- 必须说明拒绝是暂时（附补救时间表）还是永久

### 商业秘密保障（第 6(2)-(5) 条）

数据含**商业秘密**时，数据持有者可拒绝或限制访问，但仅限：

1. **对保护秘密的合法利益成比例**
2. **提供详细说明**，指明：
   - 哪些数据要素包含商业秘密
   - 为何披露将显著损害商业利益
   - 部分访问、聚合或合同保障措施能否降低风险
3. **探索技术和组织措施**：
   - 匿名化或聚合以去除商业秘密要素
   - 限制访问（仅查看、不可下载）
   - 数据持有者与数据接收者之间的保密协议
   - 限时访问
   - 访问限于特定数据字段

**数据接收者保密义务（第 6(3) 条）：**
- 数据接收者不得披露通过《数据法》共享获得的商业秘密
- 必须实施适当的安全和保密措施
- 对未经授权披露或滥用承担责任

**第三方审计与核验（第 6(4) 条）：**
- 商业秘密主张有争议时，独立专家可核验数据是否确实包含可保护秘密
- 专家受保密约束

### 数据持有者的中小企业豁免（第 7(1) 条）

微型和小型企业在作为**数据持有者**行事时，豁免第三方共享制度下的数据提供义务。

**门槛（第 7(1) 条结合《建议书》2003/361/EC 概念）：**
- **微型企业：** 员工少于 10 人且年营业额或资产负债表总额不超过 200 万欧元
- **小型企业：** 员工少于 50 人且年营业额或资产负债表总额不超过 1000 万欧元

**实务关键点：**
- 用户特别要求此处核验的门槛是低端的**微型/小型豁免**：员工少于 10 人且低于 200 万欧元始终在豁免类别内
- 依赖豁免前，仔细核验当前企业分类，包括关联和合伙企业的适用
- 此豁免区别于条例他处的制造商侧简化

**实务评估问题：**
- 该实体是否对所请求数据集扮演**数据持有者**角色？
- 其在集团层面是否符合微型或小型企业资格？
- 分类是否已记录，以便向用户或机关抗辩？

### 费用结构（第 9 条）

**默认：** 第 4 和 5 条下的数据访问**免费**。

**例外：** 数据请求「频繁或复杂」且数据持有者履行请求须付出**非微不足道的努力**时，可收费。

**收费条件：**
1. **合理**——基于成本，而非利润最大化
2. **透明**——费用结构事先公布
3. **无歧视**——可比较请求收费相同

**什么算「频繁或复杂」：**
- **频率：** 每日或每周多次请求、超出标准 API 速率限制的自动轮询
- **复杂性：** 定制数据转换、遗留系统集成、从非自动化来源手工提取

**什么不构成收费理由：**
- 正常使用水平的标准 API 访问
- 一次性或偶尔的用户数据导出
- 属于核心产品/服务功能一部分的数据访问

**GDPR 相互作用：** 涉及个人数据时，GDPR 第 15 条（访问权）禁止对标准请求收费。《数据法》费用不得规避 GDPR 免费访问权。

## 实务实施指引

### API 与接口设计

**最低可行实施：**
1. **用户门户或应用**，带身份验证登录
2. **数据导出功能**——以 JSON/CSV 下载完整数据集的按钮
3. **API 端点**，用于程序化访问（OAuth2 或 API 密钥身份验证）
4. **文档**——哪些数据可用、字段定义、更新频率

**最佳实践实施：**
1. **实时流式 API**（WebSocket、服务器发送事件）用于连续数据
2. **细粒度访问控制**——用户可选择日期范围、数据类型、共享权限
3. **第三方集成市场**——预先授权的数据接收者、一键共享
4. **数据预览与透明仪表板**——用户在请求访问前看到存在哪些数据

### 回应时间表

《数据法》未规定确切时间表，仅规定**「及时」**。

**实务基准（基于 GDPR 第 15 条类比和行业实践）：**
- **简单请求：** 自动化 API 访问在 **48 小时**内
- **标准导出请求：** **5-10 个工作日**内
- **复杂或高量请求：** **30 天**内，如需更多时间则发中期通知

**请求被拒或延迟时：** 在 **7 天**内通知用户和数据接收者并附详细理由。

### 数据格式与标准

存在**领域特定标准**时使用：

| 行业 | 标准/格式 |
|--------|-----------------|
| 汽车 | NGTP、OBD-II、ISO 20078-1 |
| 能源/智能家居 | EEBUS、OCPP（电动车充电）、IEC 61850（智能电网） |
| 医疗保健/医疗器械 | FHIR、DICOM |
| 工业物联网 | OPC UA、MTConnect |
| 通用 | 带文档化模式的 JSON、XML、CSV |

**避免：** 专有格式、PDF（非机器可读）、需要许可软件解析的格式。

## 跨法规相互作用

### GDPR
- 依《数据法》访问的**个人数据**须遵守 GDPR（合法依据、数据主体权利、安全）
- 《数据法》访问权**补充**但不替代 GDPR 第 15 条（访问权）
- 数据既是产品数据又是个人数据时：两种制度都适用

### 《商业秘密指令》（欧盟指令 (EU) 2016/943）
- 《数据法》明确保留商业秘密保护
- 商业秘密必须**实际保密**、具有**商业价值**，并已采取**合理步骤保密**
- 主张商业秘密保护的数据持有者必须达到该门槛——并非所有专有数据都符合

### 网络安全与韧性
- **NIS2 指令**和**《网络弹性法》**要求安全设计和事件响应
- 数据访问 API 是**攻击面**——必须依安全设计原则设计
- 日志记录、监测和事件响应计划为强制要求

## 常见陷阱

1. **把数据访问当作可选或「锦上添花」**
   - 这是法律义务，不是功能请求

2. **笼统的商业秘密主张**
   - 必须具体、有依据，并探索部分访问替代方案

3. **对标准访问收费**
   - 只有「频繁或复杂」请求才可收费；GDPR 个人数据访问始终免费

4. **专有或锁定数据格式**
   - 「机器可读」指无需逆向工程即可程序化解析

5. **无视第三方共享请求**
   - 必须回应，即使是附详细理据的拒绝

6. **未能区分个人与非个人数据**
   - 涉及个人数据时，GDPR 义务叠加其上

## 关键要点

1. **用户访问是默认**——数据持有者必须为任何限制提供理据
2. **实时、免费、安全、机器可读**——这些是不可协商的技术要求
3. **第三方共享由用户控制**——数据持有者按用户指示行事，而非接收者请求
4. **商业秘密受保护但非绝对**——须成比例平衡
5. **费用是例外**——仅针对真正的频繁或复杂请求，且必须合理
6. **实施截止日期：2025 年 9 月 12 日**——系统届时必须投入运行
