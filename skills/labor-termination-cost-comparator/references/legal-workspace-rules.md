# 法律文件与工作空间规则

法律类 Skill 涉及文件、证据或项目材料时采用以下规则。用户明确提供的项目约束可以细化这些要求，但不得放宽法律真实性、隐私和原始材料保护底线。

## 新生成工作区的目录规则

下游法律 Skill 必须根据实际场景选择中文工作流配置，并在工作区根目录生成 `文件夹使用说明.md`。新工作区不得把 `input/`、`scratch/`、`output/` 作为通用默认目录；这些名称仅用于识别历史项目和生成兼容映射报告。

案件分析、尽职调查、合同审查和法律研究分别使用对应的中文工作流配置。目录应区分原始材料、AI 可读材料、事实证据、法律研究、风险条线、人工复核、正式交付和归档，避免把不同证据状态混在同一目录。

## 输入与输出生命周期

仅在识别历史项目时参考三层结构；新项目不再采用：

```text
<project>/input/    原始合同、证据、邮件、PDF；只读
<project>/scratch/  转换包、检索记录、分析草稿、评测结果
<project>/output/   经复核的正式交付物
```

- 发现上述目录时保持原样，只记录其与中文工作流目录的映射关系。
- 不自动迁移、删除、覆盖或重命名历史目录中的材料。
- 经用户明确授权迁移时，先保留原路径、文件哈希和回滚方案。
- 用户指定其他目录结构时，记录映射关系并服从用户当前指令；不得自行创造平行入口。
- 目标 Skill 包不得写入真实密钥、客户身份、私人附件或机器绝对路径。

## PDF 与扫描材料

当目标 Skill 接收法律 PDF、扫描件或证据包时，内置以下最低规则：

1. 先确定材料所属项目和输入清单，再开始转换或分析。
2. 用户要求批量或全量处理时，必须转换全部文件并核对输入/输出数量，不以抽样替代。
3. 优先使用可靠的 PDF 到 Markdown/OCR 工具；资源不足时采用串行或低并发方式，避免因并行造成漏件、错配或内存失控。
4. 每份 PDF 独立形成转换包，至少包含同名 Markdown 与 evidence JSON；保留源文件哈希、页码/坐标、OCR 质量、印章/签名等客观观察和质量警告。
5. 正文与表格分析优先读取 Markdown；证据形式、定位和完整性检查读取 evidence JSON；仅在缺失、哈希不一致、质量失败或需视觉核实时回查原 PDF。
6. 自动检测到的颜色、坐标、印章残片、页面异常或电子签名线索仅作客观观察，不直接认定真伪、原件属性、篡改或证据效力。

## 工具与路径可移植性

- 以能力描述工具，例如“PDF 转 Markdown/OCR 转换器”“法律数据库检索工具”，不要硬编码个人安装路径。
- 确需脚本时，将可复用脚本放在目标 Skill 的 `scripts/`；确需规则时，将规则放在 `references/`。
- 外部工具不可用时，说明缺失能力、允许的降级方案和剩余风险；不得悄悄切换到质量更低且改变证据契约的入口。
- 生成报告只写相对路径；安装说明使用平台标准 Skill 根或用户指定目标，不嵌入创建者机器的绝对路径。

## 修改边界

创建/改造请求只修改目标 Skill 包及用户授权的项目产物；审计/诊断请求保持只读。外部规则系统、记忆、账号、远程仓库和发布渠道必须得到用户单独明确授权。
