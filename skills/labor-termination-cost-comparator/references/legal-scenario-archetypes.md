# 法律场景原型

法律任务类型不同，十二模块的典型状态、专项检查项和评测重点也不同。本文件定义八类场景原型，解决"通用模型贴合争议分析、但对生成型、合规型、检索型和 DOCX 审阅任务只有兜底没有指导"的问题。

使用规则：

1. 创建或改造法律 Skill 时，在 intake 的 `scenario_archetype` 中选择一类（或 `other` 并说明）；原型决定模块状态预设与专项检查清单，生成器把对应清单复制进目标包 `references/`。
2. 预设只是起点：每个模块仍须按 `mandatory-review-conditional-expansion` 逐一检查并记录实际状态；预设 `not_applicable` 的模块如实际适用，必须改为 `active`。
3. 原型专项检查是对 [法律方法核心规则](legal-method-core.md) 的场景化裁剪，与十二模块最低契约叠加，不得互相替代。
4. 跨原型任务（如"为诉讼目的审合同"）选择主原型，并在 `matter.exclusions` 或任务说明中记录次要原型的边界。
5. 原型同时决定意图画布条件键的放宽集（画布十五键中六个条件键仅在被放宽时允许 `not_needed` 加具体理由）：

| 场景原型 | 放宽的画布条件键 |
|---|---|
| 争议解决 / 合同审查 / 证据与文件处理 / `other` | 无（最严默认，十五键全部要求实质回答） |
| 文书起草与生成 | `evidence`（起草时无既有案卷事实） |
| 法律研究与咨询 | `actors`、`evidence`（研究问题可无关个案主体与证据） |
| 合规与监管 | `evidence`（未进入执法调查时无个案证据） |
| 法律检索与知识管理 | `actors`、`evidence`（检索任务无当事人与待证事实） |
| DOCX 审阅、修订与批注 | 无（基准文件、版本、证据和权限均须明确） |

## 1. 争议解决（`dispute_resolution`）

诉讼、仲裁、再审、执行及争议可行性评估。

- **模块预设**：十二模块通常全部 `active`；`proof`、`procedure`、`outcomes_and_enforcement` 是本原型的重心。
- **专项检查**：请求权基础映射链；定性优先与备选定性；对抗预演（对方最强论点、裁判者可能追问及应对）；证明责任双重结构与证明标准二维分层；程序阶段—结论深度耦合（立案/实体/执行/再审）；类案三核验与可适用性论证；执行依据明确性（主体与给付内容明确，执行不解决实体争议）。
- **输出契约要点**：保留"法律关系—请求—要件—事实—证据—抗辩—程序—救济"完整映射；区分"法律上有理"与"法院会支持"（结果公平与制度约束的现实校验）；程序性策略（提交新证据、申请再审）须评估反向副作用。
- **典型失败模式**：阶段错配（立案意见写成胜诉预测）；对全部要件平均用力而不识别实质争点；堆砌站不住脚的凑数论点；只给单一路径无 back-up plan。
- **评测重点**：映射链完整性；阶段—结论匹配；类案引用姿态；对方最强论点是否具体而非陪衬。

## 2. 合同审查（`contract_review`）

合同、协议、交易文件的风险审查与修改建议。

- **模块预设**：`task_context`、`matter`、`actors`、`temporal`、`jurisdiction`、`authority_and_interpretation`、`strategy_and_uncertainty`、`governance` 通常 `active`；`proof`、`procedure`、`outcomes_and_enforcement` 按"以争议解决终局视角审查"的条件展开（评估条款在诉讼中的可执行性时 `active`）。
- **专项检查**：背景目的先行（不问清交易背景与客户立场不审查，信息不全须书面声明审查前提）；双弦结构查漏（正常交易安排 + 意外预防安排）；查漏四法（时间顺序法、办事流程法、权利义务对等法、假设法）；重要性原则（先抓最大风险，反对面面俱到的平庸）；违约条款可执行性终检（违约责任无法在诉讼中落地的条款是废话）；修改建议按风险分级并给可谈判替代方案。
- **输出契约要点**：条款摘要—风险—触发条件—后果—修改—替代方案映射；区分修改建议的必须/建议/可选等级。
- **典型失败模式**：只改"写了什么"不查"缺了什么"；不区分风险等级；修改建议不可谈判或不可执行；忽视交易闭环（付款、交付、验收、解除、争议解决的衔接）。
- **评测重点**：查漏覆盖面；风险分级合理性；修改建议的可执行性与可谈判性。

## 3. 文书起草与生成（`document_drafting`）

合同起草、法律文书生成、条款库组装、模板填充。

- **模块预设**：`task_context`、`matter`、`actors`、`authority_and_interpretation`、`strategy_and_uncertainty`、`governance` 通常 `active`；`proof`、`procedure` 通常 `not_applicable`（无既有争议与程序，理由写法示例："本任务为文书生成，尚无待证事实与程序状态；文书投入使用后另行触发核验"）；`outcomes_and_enforcement` 条件展开为"条款可执行性预检"。
- **专项检查**：条款完备性（按交易闭环与双弦结构核对缺漏）；变量槽位显式化（待填信息全部列出，不留隐藏假设）；谈判立场备选对（关键条款给己方/对方/折中三版）；攻防条款映射（每条核心条款标注其在未来争议中的证明与抗辩功能）；效力阶梯预检（批准、登记、生效条件条款的层级标注）。
- **输出契约要点**：文书正文 + 变量槽位清单 + 条款风险备注 + 使用前提声明；生成物须标注"未经责任人复核不得对外签发"。
- **典型失败模式**：模板化套用不问交易目的；隐藏假设不进槽位清单；只给单一立场版本；把起草任务做成法条综述。
- **评测重点**：完备性（对照交易闭环）；槽位完整性；立场备选的可用性；前提声明存在性。

## 4. 法律研究与咨询（`legal_research`）

法律问题研究、专项法律意见、合规咨询、裁判规则梳理。

- **模块预设**：`task_context`、`jurisdiction`、`temporal`、`matter`、`authority_and_interpretation`、`strategy_and_uncertainty`、`governance` 通常 `active`；`claims_and_elements`、`proof`、`procedure` 视问题是否指向具体争议而条件展开。
- **专项检查**：找法四步（选择→解释→续造→引用）各步留痕；准法源四档分级与引用姿态；规范性质辨识前置；政策时间轴感知（政策敏感领域按时间轴梳理监管演变及其对效力判断的输入）；结论可接受性回检；五种必须充分说理的情形。
- **输出契约要点**：结论先行 + 依据分层 + 适用边界 + 行动路径；关键结论注明核验状态与论证强度；检索失败如实说明缺口。
- **典型失败模式**：只给文义推演不做可接受性回测；把准法源当裁判依据；忽视政策动向与地域/时间差；对开放问题给"综合考虑"式糊涂账而不做类型化。
- **评测重点**：来源分级正确性；核验留痕；回检与说理充分性；结论的适用边界声明。

## 5. 合规与监管（`compliance_regulatory`）

合规义务识别、监管检查应对、整改方案、合规监测与义务追踪。

- **模块预设**：`task_context`、`jurisdiction`、`temporal`、`actors`、`matter`、`authority_and_interpretation`、`outcomes_and_enforcement`、`strategy_and_uncertainty`、`governance` 通常 `active`；`proof`、`procedure` 在涉及执法调查、听证、处罚程序时 `active`。
- **专项检查**：多层级规范叠加（法律、行政法规、部门规章、自律规则、监管政策逐层识别，层级口径不一时显式披露）；存疑从严（规则不明确、监管态度含糊时按从严口径处理并声明）；监管动向跟踪（答记者问、征求意见稿、执法案例的动向感知与知识时点标注）；整改动作可执行性（每项整改落到责任部门、时限、材料、验证方式）；违规后果的效力通道分析（规章违规经公序良俗等通道影响民事效力时须充分说理）。
- **输出契约要点**：义务清单（义务—来源—适用条件—现状—缺口—整改动作）；风险分级与整改优先级；监测类任务须声明监测时点与下次核验触发条件。
- **典型失败模式**：只查法律漏掉监管规则与自律规则；层级冲突时悄悄选用有利口径；整改建议不可落地；把一次性合规意见当作持续监测结论。
- **评测重点**：规范层级覆盖完整性；存疑从严声明；整改动作的具体性；监测时点声明。

## 6. 法律检索与知识管理（`legal_retrieval`）

法规检索、类案检索报告、裁判规则提炼、法律知识库构建。

- **模块预设**：`task_context`、`jurisdiction`、`temporal`、`authority_and_interpretation`、`governance` 通常 `active`；`matter` 条件展开为"检索主题边界"；`claims_and_elements`、`proof`、`procedure` 通常 `not_applicable`（检索本身无请求与证明问题；检索服务于具体案件时回到争议解决原型）。
- **专项检查**：检索质控流程（法条识别 → 效力甄别四问 → 冲突规则 → 双源交叉验证 → 检索留痕）；类案检索报告形式标准（素材三核验：生效/未撤销/全文无不利风险；精选排序五维：层级、地域、时间、程序、背景；同争点 3-5 个为宜；开篇即给检索结论并落到本案建议；不利类案须处理而非隐藏）；来源分级标注纪律。
- **输出契约要点**：检索结论前置 + 检索式与数据库声明 + 命中清单（每项含核验状态）+ 未命中与缺口说明。
- **典型失败模式**：案例堆砌无检索结论；只报有利类案；不声明检索时点与数据库；以检索数量代替相关度。
- **评测重点**：三核验执行；排序理由；结论存在性；不利类案处理。

## 7. 证据与文件处理（`evidence_files`）

案卷整理、PDF 证据处理、证据清单与证据包构建、事实梳理工程。

- **模块预设**：`task_context`、`matter`、`proof`、`governance` 通常 `active`；`temporal`（时间轴）、`actors`（陈述主体对照）条件展开；`claims_and_elements` 在证据按要件分组时 `active`；`procedure` 在涉及举证期限、证据交换程序时 `active`。
- **专项检查**：遵守包内 [法律文件规则](legal-workspace-rules.md) 的全部契约（项目定位、全量转换、`input/` 只读、`scratch/` 映射、Markdown 与 evidence JSON 双文件包、质量警告人工复核）；事实梳理三件套（材料工程化命名、大事记/时间轴、矛盾对照表）；证据组织说服工程（按争议焦点/要件分组而非按材料来源堆砌；证明对象逐项拆解做完整性校验，杜绝要件"裸奔"）；证据链印证结构与来源锚定（编号、页码、段落）。
- **输出契约要点**：证据清单（证据—证明对象—要件—来源位置—质证要点）；事实时间轴；矛盾与缺口清单；质量警告台账。
- **典型失败模式**：按材料来源堆砌而非按证明对象组织；事实主张无证据锚定；质量警告被静默吞掉；材料内容直接当作已确认事实。
- **评测重点**：完整性校验（每个证明对象有证据覆盖）；锚定精度；四层分离遵守；工作空间契约遵守。

## 8. DOCX 审阅、修订与批注（`document_review_redline`）

合同、法律文书和其他 DOCX 的审阅、Track Changes、批注、版本交付与复核留痕。

- **模块预设**：`task_context`、`jurisdiction`、`temporal`、`actors`、`matter`、`authority_and_interpretation`、`proof`、`strategy_and_uncertainty`、`governance` 通常 `active`；`procedure` 和 `outcomes_and_enforcement` 按是否进入争议或签发阶段条件展开。
- **专项检查**：原始基准只读、独立版本副本、修订/批注作者与锚点、中文跨 run 文本、WPS 兼容性、编号与 OOXML 关系、渲染后视觉检查、元数据清理边界。
- **输出契约要点**：基准文件哈希、版本清单、修订和批注统计、法律依据与待确认事项、视觉检查状态、人工签发责任人。
- **典型失败模式**：覆盖原文件、静默接受修订、批注丢锚、跨 run 漏改、只验证 XML 不验证视觉效果、将审阅版本误当最终分发版。
- **评测重点**：基准保护；修订与批注可追溯；OOXML 完整性；视觉限制披露；对外签发门禁。

## 各原型第 3 层补充提问

意图阶段第 3 层在条件键之外，按原型提出下列补充问题；渐进式小批量提出，答案会实质改变设计时才追问，能采用合理默认的不问。

- **争议解决**：委托人处于原告/被告/申请人哪一方，程序已到哪个阶段？期望结果是什么（胜诉、和解、拖延、执行回收），可接受的底线是什么？是否有在审时效、保全或上诉期限等紧急节点？
- **合同审查**：代表哪一方、该方的市场地位与谈判空间如何？交易的商业目的和最大顾虑是什么？哪些条款是不可谈的底线，哪些可以让步？
- **文书起草**：文书的使用场景和签署对象是谁？关键商业条款（价格、期限、交付）是已定还是待谈？是否需要同一条款的多立场备选版本？
- **法律研究与咨询**：研究结论写给谁、支持什么决定？问题的时间敏感性如何（是否涉新旧法衔接或政策窗口）？是否已有内部倾向性结论需要验证或挑战？
- **合规与监管**：适用的监管体系和执法强度如何（行业、地域、监管层级）？整改的资源与时限约束是什么？是一次性评估还是需要持续监测机制？
- **法律检索与知识管理**：检索服务的下游用途是什么（诉讼呈交、内部研究、知识库沉淀）？可访问哪些数据库，检索时点要求是什么？结果需要何种形式（清单、报告、规则提炼）？
- **证据与文件处理**：材料量级、格式与完整性如何？证据组织的下游用途是什么（举证、质证、尽调底稿）？有无举证期限或证据交换节点？
- **其他（`other`）**：先按"该领域最常见的错误是什么、哪个结论出错代价最高、谁复核"三问自行提取领域关注点；必须通过 `domain_supplement` 记录至少一项内部化规则；包内规则不足时，在创建期经用户授权按元技能包内 `references/skill-research-sources.md` 的"领域方法论研究"一节兜底（该文件属于元技能创建期规则，不复制进下游包）。

## 其他（`other`）

不属于以上八类时，在 intake 中写明任务特征，并按 [通用法律能力模型](universal-legal-capability-model.md) 逐模块自行确定状态与专项检查；`other` 不免除任何模块的适用性检查义务，也不降低最低契约。
