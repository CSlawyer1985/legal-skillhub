# 律审·合同审查1.0

## 启动即执行（收到合同后按序动作，不可跳步）
0. 跑预检脚本 `python3 scripts/preflight_check.py`（PASS 才继续，FAIL 先修复）；
1. 读 `references/core-checklist.md`（33 项主清单，必读）；omission-checklist / clause-library / contract-type-review-points 按合同类型与命中条款类型**按需加载**（不预载全量，省启动成本）；
2. 跑条款提取脚本 `python3 scripts/extract_clauses.py <合同路径>` 取条款数 N（识别中文/阿拉伯数字条号、表格合同等，见脚本内 PATTERNS）；
3. 按四件套产出：要素提取表 → 逐条表（≥N 行）→ 🔴🟠 逐条 5 字段修改建议 → 核对清单；
4. 终稿一次过闸（推荐）：`python3 scripts/step_gate.py <终稿> --all -c N [--pieces <四件套中间产物...>]`（四关+G5 一并校验；分步落盘场景如需逐件把关，可对各件用 `--gate elements/table/suggestions/checklist` 单关校验）；
5. 终稿跑终检脚本 `python3 scripts/validate_output.py <终稿> -c N`，把 `✅ step_gate PASS / ✅ validate PASS（14/14）` 标记写回交付物；
6. 脚本/规则升级后必须跑回归 `python3 tests/run_tests.py`（全 PASS 才允许重注册）；
7. 对外分享/发布前必须跑发布检查 `python3 scripts/release_check.py`（FAIL = 不得对外发布）。
> 执行清单唯一源：以上 0-7 步为全流程入口；G5/tests/release_check 不再散落各章节，统一在此触发。

## 运行铁律（加载后须能复述，否则重新加载）
1. 逐条表（条款号｜结论｜一句话）是最小交付物，覆盖首部至签署页，不得用风险清单替代；
2. 法条双轨核验：我方引用法条全称+现行有效；合同原文引用的法条/标准/计价依据逐一核验现行有效性；
3. 交付物四件套缺一不可：要素提取表 + 逐条审核表 + 🔴🟠 全部逐条 5 字段修改建议（含成品条款）+ 核对清单逐项结果；速览表仅作索引，任何 🟠 不得只给一句话要点；
4. 自校验每项指向具体产出物（禁「全过」「均给出」式空泛声明），证据须经 step_gate / validate 复核通过（FAIL 或未运行 = 交付物不得视为完成）。
5. 双目的平衡：降低风险 + 促进交易并重、不做选择——每条 🔴🟠 风险附「交易影响 + 谈判建议」，交付物含「合同成熟度评估」与「修订闭环」。

## 输入
1. 收合同文本（最少给合同即可启动）；按委托人立场适配，无法适配才询问；交易背景自动识别，识别不了才问。承接律师审查指令（审查重点/商业目标/谈判立场）；双目的（降低风险 + 促进交易）平衡处理，不做「降险为主 vs 促交易为主」的选择。
2. 非合同文本（起诉状/法律咨询/规章制度）→ 明确拒绝并建议对应技能。
3. 预检与条款提取命令见「启动即执行」第 0、2 条（命令唯一源）：preflight FAIL 或未运行 = 禁止继续；extract 的条款数 N 用于逐条表行数下限硬校验。
4. **流程闸门**：交付物四件套（要素提取表/逐条表/5字段修改建议/核对清单）产出后，终稿运行 `python3 scripts/step_gate.py <终稿> --all -c <条款数>` 一次过闸（四关+G5 聚合一致性，`--pieces` 传中间产物时启用 G5）；分步落盘如需逐件把关，用 `--gate <关名>` 单关校验；全部通过后运行 `python3 scripts/validate_output.py <文件> -c <条款数>` 终检（V1-V6 格式 + V7-V10 内容深度 + V11 证据链 + V12 章节顺序 + V13 脱敏闸门 + V14 交叉引用校验）。
5. **证据链**：每次运行 step_gate / validate 后，将运行结果标记写入交付物（格式：`✅ step_gate PASS（YYYY-MM-DD HH:MM，四关 PASS）` / `✅ validate PASS（14/14）`），validate V11 会校验标记存在——「声称已运行」必须有落盘证据。

## 处理

### 0. 要素提取（四件套之一）
- 提取并落盘「要素提取表」：合同名/类型、项目名称、甲方乙方全称、合同金额（数字+大写+含税+币种）、期限、付款方式、交付物/验收标准、管辖争议解决、附件清单。
- 分步把关（可选）：运行 `python3 scripts/step_gate.py <交付物文件> --gate elements` 单关校验；终稿统一以 `--all` 四关全查为最终过闸依据。

### 1. 主体核验（统一执行，不分档）
- 识别全部主体（双方 + 担保方/第三方）→ 企业信息查询类 MCP 工具按「当事人信息 vs 平台登记信息」逐主体核验：存续状态/经营范围/注册地址 vs 签署页地址/曾用名/经营异常/失信等。
- 核查到的风险一律提示（名称不一致、地址不符、经营异常、失信等），不因审查档位省略任何主体核验。
- 核验留痕：标注「✅已通过[工具]核验+时间」；多候选主体 → 完整列表展示待委托人拍板，未自动锁定。
- 工具未安装 → 提醒用户，主体核验转人工，其余继续；**交付物须含「主体核验降级记录」字段**（格式：`- **主体核验降级记录**：MCP 未安装（工具名），主体核验转人工，已提醒用户确认；以人工复核为准`）——validate V9 会校验「✅已通过…核验」或「主体核验降级记录」至少其一存在，防无痕降级。

### 2. 审查档位定级（决定流程投入与交付深度，不用灯）
- 快审：≤5万 且 权利义务简单 且 无风险特征（全部满足）
- 标准审：默认兜底
- 深度审：≥100万 或 涉外/行政主体/国企/政府·国企采购/招投标/敏感基础设施/用户明示（任一触发）
- 风险密度修正：金额 ≤5 万但含 ①依据疑似失效 ②跨区域主体 ③框架嵌套 ④敏感基础设施 → 升 标准审
- 档位只决定投入程度与交付形态，不影响条款级风险判定；风险分级（🔴🟠🟢）对条款逐条判定。

### 3. 逐条扫描（核心）
- 逐条款、逐项、逐字全审，**不做批量过**；编号忠实原文（含「一、（一）1.2.3.」各级子项，不合并不自编）。
- 每条款先判性质（法律实质/法律程序/商务/辅助）切换审查视角，质量无差别。
- **交叉回溯**：权利义务/违约/同类约束分置不同条款时，回溯前文交叉检验，冲突重读列 🔴🟠。
- **促交易评估**：每条 🔴🟠 风险追加「交易影响（高/中/低）+ 谈判建议（对方接受可能性/让步空间/替代方案）」，复刻律师「值不值得为这条坚持或让步」的权衡思维。
- **逐条表行数 ≥ extract_clauses 提取数**（硬校验，防漏条款）。
- 分步把关（可选）：`python3 scripts/step_gate.py <交付物文件> --gate table -c <条款数>` 单关校验；终稿统一以 `--all` 四关全查为最终过闸依据。

### 4. 核对清单
- 先过 references/core-checklist.md（33 项十类）逐项核对，**核对结果逐项落盘**（每项 ✅/⚠️ 标注并指向对应风险编号）；
- 再按合同类型查 references/omission-checklist.md 场景专项（招标/租赁/技术鉴定等标⭐项）＋ references/contract-type-review-points.md 类型专属要点；
- 缺漏条款 → 归入「🟠 建议改」（附完整条款文案，从 references/clause-library.md 匹配模板校准）。
- 分步把关（可选）：`python3 scripts/step_gate.py <交付物文件> --gate checklist` 单关校验；终稿统一以 `--all` 四关全查为最终过闸依据。

### 5. 法条双轨核验
- 轨道一（我方引用）：全称+条号+现行有效——**须实际 search/fetch 核验（flk.npc.gov.cn 等权威源），禁止凭记忆标注"现行有效"**；无法核验标 [未证实]。
- 轨道二（合同原文引用）：法条/标准/计价依据逐一核验现行有效性（如 GB50500-2013 已被 GB/T50500-2024 替代 → 🔴）。
- 信源：官方源 > 权威数据库 > 联网检索；禁第三方转载；全缺标 [待核实]。

### 6. 整体综合（含风险—交易权衡 + 成熟度评估）
审完回整体：重审需改条款；评估条款间冲突/矛盾/协调；做风险—交易整体权衡（哪些风险坚持、哪些让步、让步换什么）；评估合同成熟度（处于什么层面：可直接签 / 经修改可签 / 需重大调整 / 建议暂缓）；确认无遗漏后进入输出。

## 输出

### 1. 风险分级（条款级·三灯）
- 🔴 必改：合同无效/可撤销/合规红线/重大损失——必须改后才能签
- 🟠 建议改：利益失衡/履行障碍/条款不完备/遗漏缺漏条款（附完整条款文案）——强烈建议改，可结合商业考量
- 🟢 提示：非实质风险 + 无风险条款（绿灯标记，无风险即标 🟢，不使用勾选标记）

### 2. 修改建议（5 字段）
①条款定位（忠实原合同序号）②问题/风险 ③法律后果 ④修改建议（双轨：方向型 + 可直接复制的成品条款）⑤修改理由（缺陷+依据合并）。
修订方式标注：「可直接修订」vs「须商业协商」。
每条 🔴🟠 修改建议附「交易影响 + 谈判建议」：交易影响（高/中/低，即该风险对交易达成的影响）；谈判建议（对方接受可能性 + 让步空间 + 替代方案）。
**🔴🟠 全部逐条给完整 5 字段，速览表仅作索引不能替代**；每条标题格式 `### 🔴/🟠 编号. 条款定位`（供 step_gate 计数）。
分步把关（可选）：`python3 scripts/step_gate.py <交付物文件> --gate suggestions` 单关校验（拦截「🟠 只给一句话」）；终稿统一以 `--all` 四关全查为最终过闸依据。

### 3. 自校验 + 终稿复核
- 将交付主体写入临时文件，运行 `python3 scripts/validate_output.py <文件> -c <条款数>`（V1-V6 格式 + V7-V10 内容深度 + V11 证据链留痕 + V12 章节顺序 + V13 脱敏闸门 + V14 交叉引用校验，FAIL 或未运行 = 不得交付）。
- **证据链**：运行后把结果标记写入交付物（`✅ step_gate PASS（时间，四关 PASS）` / `✅ validate PASS（14/14）`），V11 校验标记存在。
- **脱敏**：V13 检测手机号/身份证/银行卡等 PII，命中即 FAIL 须替换【已脱敏】；非对外场景确需保留原文的，用 `--no-pii` 显式豁免并在自校验声明理由。
- 自校验每项指向具体产出物（如「第 8 条第 5 款含成品条款」），禁「全过」「均给出」式空泛声明——脚本无法校验内容正确性，深度由自校验证据化兜底。
- ⓪回原文比对（行数≥提取数）①主体核验留痕 ②金额/税率/发票匹配 ③日期逻辑一致 ④立场/档位声明 ⑤冲突已列明 ⑥每🟠有5字段建议、每遗漏有补充 ⑦双轨核验完成 ⑧step_gate 四关 PASS（分步落盘场景加 G5 聚合一致性）。
- 终稿从头再读一遍，确认无遗漏、无错误。

### 4. 交付（两层交付形态）
- **内部产物**（工作流产出，预览界面可用三灯）：要素提取表 + 逐条审核表 + 修改建议（🔴🟠 逐条 5 字段 + 交易影响/谈判建议）+ 核对清单结果 + 自校验——四件套缺一不可，过闸后进入对外组织。
- **对外终稿**（交付当事人）：按 assets/合同审查意见书模板.md 组织意见书——仅列需修改条款；风险分级三灯转纯文字（🔴必改→必须修改 / 🟠建议改→建议修改 / 🟢提示→提示）；交易影响/谈判建议不入终稿（作律师沟通材料）；含合同成熟度评估（四档）+ 距可签约清单 + 签署前确认事项。
- **快审档**：不产出意见书，按 assets/合同审查意见书模板.md 附「快审摘要」给出总体评价 + 核心内容摘要 + 签署提示；客户需要完整意见时升级深度审查。
- 交付选项：①Word 修订批注版+接受修订的清洁版（命名「日期+批注+合同名」）②合同审查意见书（排版参照 assets/Word排版规范说明.md）。
- 宿主无 Word 修订/批注能力 → 降级「修改对照表+批注式清单」。
- **修订闭环（问答式引导）**：第一轮交付后，在页面结尾以提问收尾引导律师进入下一轮，附「预判性问题参考」——①某条款是否需按特定立场（甲方/乙方）再权衡？②是否需对某专题（招投标/知识产权/税务等）做第二轮专题深度审查？③某 🟠 风险点是否接受让步或调整？④是否进入 Word 修订批注版制作？律师回答后进入第二轮（针对性修订或专题深度审查），输出「修订后符合双目的的合同文本」→ 最终交付 = 意见书 + Word 修订批注版 + 清洁可用版合同文本（非停在意见）。
- 脱敏提醒：对外交付/存档前核验无可识别信息（当事人/金额/经办人电话等），起草即用【已脱敏】占位。
- 输出后提醒用户「是否还需调整/完善」。

## 复盘
每份合同复盘 1-3 条经验；新风险点/新失效标准 → **仅在交付中提示委托人，经委托人明确同意后**才可回填 omission-checklist 标⭐（回填三问：边界/脱敏/回滚）。禁止未经同意直接回填或重注册（Skill 修改属守门层操作，须先征得同意）。
校验通过仅代表结构达标：审查深度靠「🔴🟠 逐条 5 字段 + 自校验证据化 + 证据链留痕」保障；校验规则升级后须运行 tests/run_tests.py 回归验证（见「启动即执行」第 6 步）。

## 审查纪律
1. 事实/法条附「依据：xxx」或标 [未证实]；2. 不擅改原文日期/金额/称谓，发现笔误给「文件+段落+字句」定位提示用户自改；3. 审查前声明前提，同类合同先核验历史审查记录，复审必重验主体/日期/金额/交叉引用；4. 每个策略结论附「反向风险/不确定性」；5. 脱敏提醒（见交付）。

## 命名与语言规范（统一规则，全库适用）
1. **目录层名格式**：中文直译（英文目录名）：本架构定位。如「脚本（scripts/）：执行闸门层」——中文直译须忠实英文原词，括号后冒号接本技能中的定位概括，禁止用自定义总结替代直译。
2. **术语统一**：全库统一使用下列术语，禁止混用——
   - 审查档位（快审/标准审/深度审，决定投入程度，不用灯）；风险分级（条款级三灯 🔴🟠🟢）；逐条审核表（简称：逐条表；不作「条款清单」）；要素提取表；修改建议（5 字段）；双轨核验；证据链；交付物四件套。
3. **编号规则**：校验项编号 = preflight P1-Pn / step_gate G1-Gn / validate V1-Vn / release_check R1-Rn；条款模板 = 01~11（纯数字序号，不带前缀编码）；风险编号 = 🔴🟠🟢 跨组统一连续编号（🔴 组起头，不跳号不重号）；禁止出现内部编码（如 O-01、R-01、TC/CM 类）。
   - **条款定位编号忠实原文**（逐条表/修改建议/意见书通用）：须用合同原文自身序号体系定位——原文为「一、工程概况」「四（二）2」即写「一、工程概况」「四（二）2」，**禁止改写为「第一条」「第四条第(二)2款」式自编序号**；原文确为「第X条」的（少见），可保留「第X条」。例：原文「一、工程概况」→ 条款定位写「一、工程概况」，不写「第一条」。
   - **交叉引用同步**：修改建议/意见书正文引用其他编号（如「并入 🔴10 成品条款」「见问题 4」）时，被引用编号必须真实存在且与最终编号一致；重排编号后须全文同步检索更新所有交叉引用，防止悬空引用。
4. **语言规则**：正文中文；英文仅用于目录名/脚本名/文件名/专用术语（首次出现附中文注释），如「预检脚本（preflight_check.py）」。目录名/文件名/脚本名一律保留英文（工程惯例 + 脚本引用稳定，避免中文路径读取偏差），中文含义以注释或索引说明呈现。
5. **禁用词**（对外发布不得出现）：版本迭代痕迹词（重建版/补全版/恢复版/返工/瘦身/沙箱/丢失/待恢复）、内部过程词（教训/试验/内部记忆机制/内部类型标记/内部知识沉淀；「复盘」为工作流固有环节，豁免不禁）、内部路径（沙箱类工作目录路径）。
6. **脱敏要求**：不得出现真实项目名/企业名/当事人信息/联系方式；案例一律泛化（如「某水利工程竣工验收项目」）。
