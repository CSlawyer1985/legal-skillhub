### 步骤 3b：为字符碎片化修订追踪簇搭建 en_segments——如果源文件有 TC 则为强制性

源语言概念草稿偶尔包含逐字母撰写的修订追踪编辑——通过一系列 1-3 字符的 `ins` / `del` 拆分将单个词或序数替换为不同的词。在英文中，正确的编辑几乎总是**整词**替换（如 "Clause 12" → "Clause 13"），而非字符级替换——因此感知片段的译者无法在没有显式指导的情况下针对碎片化的源结构产生干净的英文红线。

在起草翻译之前运行一次检测器：

```bash
python <skill-path>/scripts/coalesce_fragmented_tcs.py <workdir>/paragraphs.json
```

脚本扫描每个 `has_track_changes: true` 的段落，检测在 Accept 和 Reject 两侧各自重新组装为连贯单个词/序数的连续字符级 ins/del 簇，并**向每个标记的段落写入预填充的 `en_segments` 骨架**。它**不**修改 `tc_segments`——源 XML 结构仍保留所有字符级运行，因此骨架为每个 `tc_segments` 条目对应一个 `en_segments` 条目。在每个检测到的簇内，骨架包含：

- 首个 `ins` 片段上的 `<<TRANSLATE: ins='<accepted-word>' (accepted)>>` 占位符，
- 首个 `del` 片段上的 `<<TRANSLATE: del='<rejected-word>' (rejected)>>` 占位符，
- 其余每个片段（共同构成碎片化簇的中间 ins、del 和 regular 运行）上的空字符串 `""`。

簇外骨架留下 `en: ""`，以便译者仍填写正常的段落文本。

在翻译时（步骤 4）译者：

1. 将每个 `<<TRANSLATE: …>>` 占位符替换为最终英文（如 ins 侧为 `"Clause 13"`、del 侧为 `"Clause 12"`）；
2. 用正常翻译填写周围的非簇 `en_segments` 条目；
3. 将簇内的空字符串槽**保持为 `""`**——这些是 `apply_translations_textmatch.py` 用来清空匹配源运行的有意"清除此运行"标记，使孤立的源字母不会泄漏进英文红线。

幂等：在已搭建的 paragraphs.json 上重新运行脚本会重新检测相同的簇并写入相同的骨架。当没有簇匹配时，以 `"No character-fragmented TC clusters detected. Nothing to do."`（未检测到字符碎片化 TC 簇。无事可做。）干净退出。

理由和典型西班牙语道路使用示例见步骤 4 下的"错乱 / 字符碎片化的整词编辑"。

如果源文档没有修订追踪，此步骤是无操作，可以跳过。

#### TC 标记计数在源文和输出之间可能有合理差异

三种机制可以在不丢失任何修订追踪信息的情况下减少最终英文文档中的 `<w:ins>` / `<w:del>` 计数：

1. `coalesce_fragmented_tcs.py` 将字符级源编辑折叠为整词英文编辑——例如源编辑 `Duodécima → Decimotercera` 中的五个字符级 ins/del 对在英文中变为单个整词对 `Clause 12 → Clause 13`，因为字符级编辑无法在词级翻译中存活。
2. `strip_noop_tracked_changes.py`（步骤 8 / 应用阶段）移除无操作正字法对——在源文中唯一效果是西班牙语重音 / 标点 / 变音符号变化且无英文对应物的修订追踪——并剥离其后留下的任何空 `<w:ins>` / `<w:del>` 包装器。
3. 文本替换后留下的空运行包装器在应用步骤期间被压缩掉。

在典型的西班牙语 `.doc → .docx` 红线上，你应预期 `<w:ins>` 计数下降约 10-25%（插入计数比删除计数缩水更多，因为西班牙语转换伪影集中在插入侧）。这是质量改进，而非缺陷。如果你将文件交给会并排比较标记计数的审阅者，提前说明这一点，以免减少被误认为内容丢失——接受全部 / 拒绝全部模拟是确认 TC 覆盖的正确方式，而非标记算术。
