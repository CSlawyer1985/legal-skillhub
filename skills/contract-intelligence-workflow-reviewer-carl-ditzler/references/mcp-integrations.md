# MCP 集成

本文件管辖如何在合同审查中使用连接器或 MCP 支持的数据源。

## 适用性

MCP 或连接器集成可用于：

- 从经批准的云盘拉取合同
- 检索剧本、模板、条款库和过往交易
- 加载审批政策或内部文档
- 在工作流系统中创建审批任务
- 跨系统追踪当前谈判文件包
- 更新经批准的合同系统中的工作流状态
- 向经批准的下游工具交付机器可读的行动包

## 要捕获的设置数据

设置期间，向用户询问：

- 经批准连接器的名称
- 每个来源的人类友好别名
- 每个来源内经批准的位置
- 每个来源被允许提供什么
- 是否允许本地下载
- 该来源可否用于先例，还是仅用于当前合同
- 该来源可否提供主导性剧本文件
- 是否可保存从该来源提取的 Markdown 和规范化 YAML
- 经批准的范围是文件级、文件夹级还是更广
- 是否禁止宽泛的驱动器或站点访问

将其保存到 `.contract-review/connectors.yaml`。
将操作路由工具和权限保存到 `.contract-review/workflow-tools.yaml`。

## 推荐的连接器类别

- 云存储：Google Drive、Dropbox、Box、OneDrive、SharePoint
- 知识来源：内部维基、政策库、条款库、剧本库
- 工作流工具：工单、审批或收件系统
- CLM 或电子签名系统：协议状态、附件、审批历史
- 经批准用于摘要或审批包的消息或通知目的地，如 Slack 或邮件系统

## 审批人目录与消息规则

- 如连接器可暴露用户目录、团队名册或身份选择器，技能仅在该连接器经批准时可用它解析审批人身份。
- 如 Slack 或消息连接器未配置或不暴露用户查找，手动收集审批人姓名、电子邮件、Slack 句柄或 Slack 用户 ID。
- 不要仅因 Slack 已连接就假定 Slack 工作区或频道已获批准。
- 仅当连接器和目的地均在 `.contract-review/workflow-tools.yaml` 中获批准时，才将自动通知视为可用。
- 如平台无法直接发送通知，仍准备审批包和收件人清单，以便用户手动发送。

## 来源控制规则

- 绝不查询未经用户批准的连接器。
- 绝不因连接器存在就假定文件夹、驱动器、站点或集合已获批准。
- 优先特定文件或狭窄文件夹，而非完整驱动器、站点或工作区。
- 将宽泛连接器范围视为明确例外，需要用户确认安全风险增加。
- 在合同文件中记录审查中使用的每份外部来源文档的来源。
- 如所需文档无法通过连接器获得，请用户上传或分享许可链接。
- 如来源用于剧本，同时记录来源文件标识符和衍生剧本产物的位置。

## 远程 MCP 信任规则

- 除非用户确认服务器可信或经组织批准，否则不使用自定义或远程 MCP 服务器。
- 如服务器是第三方或新引入的，警告提供者保障并非万无一失，且工具行为可能在技能控制之外变化。
- 优先组织管理的或供应商官方的连接器，而非未知第三方服务器。

## 来源记录

对使用的每个外部来源，在 `contract.yaml` 或 `document-map.md` 中记录：

- 来源别名
- 连接器类型
- 路径或标识符
- 使用目的
- 是作为合同、剧本、先例还是政策输入使用

对剧本文件，还记录：

- 来源是否成为主导性剧本
- 提取的 Markdown 保存位置
- 规范化的 YAML 保存位置
- 提取信心

## 连接器冲突规则

如两个连接器来源冲突：

- 优先 `.contract-review/config.yaml` 中保存的来源顺序
- 如未保存优先级，询问用户哪个来源主导
- 不要静默合并矛盾的版本

## 输出要求

如 MCP 来源实质性影响了审查，在审查状态中说明：

- 使用了哪些来源
- 缺少哪些来源
- 是否有任何不可用来源降低了信心

如使用了工作流工具或准备了下一步，包括：

- 目的地别名
- 行动类型
- 是否仍需人工审批
- 系统是从连接器解析了具名收件人，还是使用已保存的手动联系人
