# ISO/IEC 42001:2023——附录 A 控制措施（全部 38 项）

ISO/IEC 42001:2023 附录 A 包含**38 项控制措施**，组织在 **9 个控制领域**（A.2–A.10）之下。在每个领域内，.1 子条款包含领域目标声明——编号控制从 .2 开始（A.6 的两个子目标为 .1.2 / .2.2）。附录 B 为每项控制提供实施指引。

> **使用方式：** 控制措施根据组织角色（提供者、使用者或两者）、人工智能系统影响级别和风险评估结果进行选择。不适用的控制措施必须在适用性声明（SoA）中说明理由。

---

## A.2——与人工智能相关的政策（3 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.2.2 | 人工智能政策 | 提供者 + 使用者 | 应制定、记录并传达正式的人工智能政策。政策应包括组织对负责任的人工智能开发或使用的承诺、与组织价值观和法律义务的一致性，以及设定人工智能目标的框架。由最高管理层签署。 |
| A.2.3 | 与其他组织政策的一致性 | 提供者 + 使用者 | 人工智能特定要求应纳入现有组织政策（如人力资源、采购、IT、数据治理、信息安全），只要这些政策影响或受人工智能系统影响。 |
| A.2.4 | 人工智能政策审查 | 提供者 + 使用者 | 应按计划间隔以及发生重大变化时审查人工智能政策，以确保其持续适宜、充分和有效。 |

**常见缺口：** 人工智能政策存在但缺乏具体的负责任人工智能承诺；其他组织政策未更新以应对人工智能；政策审查周期未定义。

## A.3——内部组织（2 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.3.2 | 人工智能角色与职责 | 提供者 + 使用者 | 应定义、分配、传达并记录人工智能治理的角色和职责。这包括对个别人工智能系统、数据治理和 AIMS 监督的问责。建议使用 RACI 矩阵或等效工具。 |
| A.3.3 | 关切报告 | 提供者 + 使用者 | 应建立人员就人工智能系统提出关切的机制——包括伦理关切、偏见观察、意外输出或政策不合规——且无需担心报复。 |

**常见缺口：** 人工智能所有权非正式或分散在团队之间而无明确问责；没有员工报告人工智能关切的渠道。

## A.4——人工智能系统资源（5 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.4.2 | 资源文档 | 提供者 + 使用者 | 应识别并记录开发、部署、运营和维护人工智能系统所需的资源，包括计算、数据、工具和人力资源。 |
| A.4.3 | 数据资源 | 提供者 | 政策和控制应管辖人工智能系统中使用的数据资源的获取、管理和质量保证——涵盖训练、验证和测试数据。 |
| A.4.4 | 工具资源 | 提供者 | 控制应管辖人工智能工具的选择、采购和管理——包括开发框架、模型库和评估平台。 |
| A.4.5 | 系统与计算资源 | 提供者 | 控制应管辖用于人工智能开发和部署的计算基础设施：配置、访问控制、容量管理和退役。 |
| A.4.6 | 人力资源 | 提供者 + 使用者 | 应记录人工智能特定能力要求。应为人工智能开发者、运营者和业务用户建立培训计划。应为所有与人工智能交互或受人工智能影响的员工维持意识计划。 |

**常见缺口：** 没有人工智能特定能力框架；员工人工智能意识培训缺失；第三方人工智能工具未盘点；数据资源治理未记录。

## A.5——评估人工智能系统的影响（4 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.5.2 | 人工智能系统影响评估流程 | 提供者 + 使用者 | 应建立并维持评估人工智能系统影响的记录在案流程。流程应定义范围、方法、评估频率、角色，以及评估结果如何为控制选择和处理决策提供信息。 |
| A.5.3 | 人工智能系统影响评估文档 | 提供者 + 使用者 | 人工智能系统影响评估的结果应记录、保留，并在人工智能系统或其运行情境发生重大变化时更新。 |
| A.5.4 | 评估人工智能系统对个人或群体个人的影响 | 提供者 + 使用者 | 影响评估应评估人工智能系统输出如何可能影响个人权利、福祉和自主权。这包括歧视风险、画像、无有意义人工审查的自动化决策，以及对弱势个人或群体的不成比例影响。 |
| A.5.5 | 评估人工智能系统的社会影响 | 提供者 + 使用者 | 影响评估应评估更广泛的社会影响：错误信息生成的潜力、劳动力市场影响、人工智能计算的环境影响、大规模系统性偏见的强化，以及人类自主权的侵蚀。 |

**常见缺口：** 影响评估在部署时执行一次但从未重新审视；跳过社会影响维度；没有记录在案的流程——评估为临时进行。

## A.6——人工智能系统生命周期（9 项控制）

A.6 分为两个子目标：**A.6.1 管理指引**和**A.6.2 人工智能系统生命周期**。每组中的 .1 子条款包含目标声明；控制从 .2 开始。

### A.6.1——管理指引（2 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.6.1.2 | 负责任开发人工智能系统的目标 | 提供者 | 应建立、记录并监控负责任人工智能开发的具体、可测量目标。这些目标应与人工智能政策和负责任人工智能原则（公平、透明、问责、安全、可靠）保持一致。 |
| A.6.1.3 | 负责任人工智能系统设计与开发的流程 | 提供者 | 正式流程应管辖人工智能系统设计和开发，以嵌入负责任人工智能原则：公平意识设计、设计决策的记录、与人工智能影响级别相称的可解释性要求，以及关键开发关卡的人工监督。 |

### A.6.2——人工智能系统生命周期（7 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.6.2.2 | 人工智能系统需求与规格 | 提供者 | 应记录每个人工智能系统的需求，包括预期用途、性能标准、运行条件、输入/输出规格以及适用的约束（法律、伦理、技术）。 |
| A.6.2.3 | 人工智能系统设计与开发文档 | 提供者 | 应记录设计决策、架构选择、模型版本、超参数和开发理由，以支持可复现性、可审计性和问责性。 |
| A.6.2.4 | 人工智能系统验证与确认 | 提供者 | 部署前应应用测试协议：性能基准测试、跨人口统计群体的公平性和偏见测试、对抗性测试、边缘案例验证，以及放行/不放行授权标准。 |
| A.6.2.5 | 人工智能系统部署 | 提供者 | 受控部署流程应管辖人工智能系统发布：分阶段推出、部署授权、风险和影响评估签署，以及回滚程序。 |
| A.6.2.6 | 人工智能系统运营与监控 | 提供者 + 使用者 | 对生产环境中的人工智能系统进行持续监控，以检测性能漂移、输出质量退化和偏见。应定义警报阈值和补救流程。 |
| A.6.2.7 | 人工智能系统技术文档 | 提供者 + 使用者 | 应为每个人工智能系统维护全面的技术文档：规格、预期用途、已知局限性、性能数据和失效模式。这支持透明度义务和第三方评估。 |
| A.6.2.8 | 人工智能系统事件日志记录 | 提供者 + 使用者 | 人工智能系统应记录足以支持事件调查、审计、性能监控和问责的事件日志。应定义日志保留期限和访问控制。 |

**常见缺口：** 没有模型版本控制或可复现性控制；偏见测试未记录；没有用于模型漂移的生产监控；部署缺乏正式授权流程；事件日志未保留或未针对人工智能系统界定范围。

## A.7——人工智能系统数据（5 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.7.2 | 用于开发和增强人工智能系统的数据 | 提供者 | 治理框架应定义数据在整个人工智能数据生命周期中的管理方式：获取、质量保证、标注、版本控制、偏见测试、保留和安全删除。 |
| A.7.3 | 数据获取 | 提供者 | 控制应管辖训练、验证和测试数据的来源：数据使用的法律依据、适用时的同意要求、来源文档，以及禁止使用非法获取的数据。 |
| A.7.4 | 人工智能系统数据质量 | 提供者 | 应为训练、验证和测试数据定义数据质量标准——涵盖完整性、准确性、代表性和时效性——并在数据用于人工智能开发前进行测试。 |
| A.7.5 | 数据来源追溯 | 提供者 | 人工智能系统中使用的数据的来源、保管链和转换历史应记录并可追溯。这支持问责性、偏见识别和监管合规。 |
| A.7.6 | 数据准备 | 提供者 | 数据清洗、转换、标注和注释流程应包括质量控制：标注数据的人工审查、标注者间一致性检查，以及识别和补救准备步骤中引入的偏见。 |

**常见缺口：** 训练数据来源未记录；没有数据质量标准或测试；标注流程不可审计；来源追溯缺失；数据准备偏见控制缺失。

## A.8——人工智能系统利益相关方信息（4 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.8.2 | 面向用户的系统文档和信息 | 提供者 + 使用者 | 应向用户和其他利益相关方提供关于人工智能系统的文档和信息，详细程度与人工智能系统的影响相称。这包括预期用途、已知局限性以及如何解读人工智能输出。 |
| A.8.3 | 外部报告 | 提供者 + 使用者 | 组织应定义关于人工智能系统的信息在外部报告什么、向谁报告、多久报告一次以及通过什么机制——包括监管披露、透明度报告和面向公众的人工智能披露。 |
| A.8.4 | 事件沟通 | 提供者 + 使用者 | 应建立人工智能特定事件沟通流程：内部升级、在要求时通知受影响个人、监管报告（如根据部门特定人工智能或数据保护法律），以及事件后审查和披露。 |
| A.8.5 | 利益相关方信息 | 提供者 + 使用者 | 应告知利益相关方——包括客户、员工、监管机构和公众——其权利以及对人工智能系统的预期。沟通计划应解决沟通什么、何时以及通过哪个渠道。 |

**常见缺口：** 未向用户披露人工智能参与决策；事件报告流程未扩展到人工智能特定场景；没有外部透明度报告；利益相关方沟通计划缺失。

## A.9——人工智能系统的使用（3 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.9.2 | 负责任使用人工智能系统的流程 | 使用者（主要） | 正式流程应管辖组织如何负责任地使用人工智能系统，包括可接受使用标准、对人工智能输出的人工监督，以及升级或推翻人工智能决策的程序。 |
| A.9.3 | 负责任使用人工智能系统的目标 | 使用者（主要） | 应建立并监控负责任人工智能使用的可测量目标，与人工智能政策和负责任人工智能原则保持一致。这些目标推动人工智能使用实践的持续改进。 |
| A.9.4 | 人工智能系统的预期用途 | 提供者 + 使用者 | 应记录、传达并执行每个人工智能系统的预期用途。超出已记录预期用途的使用应被识别、评估和控制。 |

**常见缺口：** 没有人工智能可接受使用政策；员工在预期范围之外使用人工智能工具；没有负责任人工智能使用的正式目标；人工监督程序未记录。

## A.10——第三方与客户关系（3 项控制）

| 控制 ID | 控制名称 | 适用对象 | 描述 |
|-----------|-------------|-----------|-------------|
| A.10.2 | 职责分配 | 提供者 + 使用者 | 当人工智能系统涉及多方（提供者、使用者、客户、合作伙伴）时，负责任人工智能治理的职责应明确分配并记录——包括谁负责影响评估、监控和事件响应。 |
| A.10.3 | 供应商 | 提供者 + 使用者 | 人工智能供应链风险管理应管辖第三方人工智能提供者：按风险分级、尽职调查问卷、合同性人工智能特定条款（包括数据处理、偏见控制和审计权），以及持续供应商绩效监控。 |
| A.10.4 | 客户 | 提供者 | 当人工智能系统部署给客户时，组织应定义客户收到关于人工智能系统能力和局限性的哪些信息、客户在负责任使用中负有哪些义务，以及客户反馈和事件如何管理。 |

**常见缺口：** 没有人工智能特定供应商尽职调查问卷；与关键人工智能供应商没有合同性人工智能条款；提供者与使用者之间的职责未正式分配；没有面向客户的一个人工智能使用义务。
