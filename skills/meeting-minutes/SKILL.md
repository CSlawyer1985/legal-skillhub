# 会议纪要

## 硬性规则（违反即视为任务失败）

1. **只能通过 `docfmt` MCP 的 `create_minutes` 工具生成文档。**
2. **禁止自行编写任何排版代码。** 不许用 python-docx、pandoc 或任何其他方式
   生成或修改 .docx。
3. **禁止手工设置任何格式参数。** 字体、字号、缩进、编号全部由工具内部的
   规范表决定，工具也没有开放任何格式参数给你。
4. **绝对不要自己写标题序号。** 这一条最容易犯——写 `# 1. 项目背景` 会变成
   「1. 1. 项目背景」，因为序号是 Word 自动编号生成的。只写 `# 项目背景`。

第 4 条与公文格式 skill（`gongwen-docx`）的做法**正好相反**，那边要你把序号
写进标题文字里。两者不要混。判断依据很简单：

- 序号形如 `一、`／`（一）`／`1.` → 公文格式，序号自己写
- 序号形如 `1.`／`1.1`／`1.1.1` → 会议纪要，序号交给 Word

## 工作流

1. 需要确认规范细节时，调用 `get_minutes_spec`。
2. 从用户给的材料里提取四项必填事项：题名、主题、时间、参会人员。
   **缺任何一项工具会直接报错**——这是纪要的基本要素，缺了不成立。
   材料里找不到就问用户，不要编。
3. 组织正文，写成下面规定的受限 Markdown。
4. 调用 `create_minutes(title=..., topic=..., time=..., attendees=[...], markdown=..., output_path=..., lead=...)`。
   - `output_path` 用**绝对路径**。文件已存在时工具会报错，先问用户是覆盖还是换名。
5. 用户想核对已有纪要的格式时，调用 `check_minutes(path)`。它认得所里旧模板的
   样式名（0A / A- / A+ / B / C），能直接体检存量文档。只报告、不改文件。

## 四项必填事项怎么填

| 字段 | 说明 | 例子 |
|---|---|---|
| `title` | 题名，居中加粗单独成行 | `会议纪要` |
| `topic` | 会议主题，排成「主题：xxx」 | `广本数据流通会议纪要` |
| `time` | 会议时间，排成「时间：xxx」 | `2026/7/7 13:50-14:20` |
| `attendees` | 参会人员，**每个单位一行** | `["广本：张三、李四；", "北京大成（杭州）律师事务所：王五。"]` |

`lead` 是可选的导语段，放在「会议内容总结：」下面，用一段话概括本次会议
讨论了什么。有材料就写，没有就留空。

## 正文怎么写

`markdown` 参数只认四种结构：

```
# 项目背景与业务场景        ← 一级标题，Word 自动编号成「1.」
## 战败线索数据交换设想      ← 二级标题，自动编号成「1.1」
### 协议层面的限制          ← 三级标题，自动编号成「1.1.1」
普通文字就是正文条目。       ← 正文（楷体小四，无首行缩进）
```

- **段落之间必须空一行**，否则相邻两行会被拼成同一段。
- **标题里不要写序号**（见上面第 4 条）。
- 正文条目可以写成 Markdown 列表（`- xxx`），工具会把每项排成独立一段——
  纪要的正文本来就是一条一段的形态，这样写是自然的，不会有警告。
- 不要用 `**加粗**` 等行内标记，正文的字体粗细是固定的。
- 层级最多三级，写第四级会被降到第三级并给出警告。

## 语体

纪要是记录，不是文章。每条写成一个完整的陈述句，交代清楚「谁提出了什么、
理由是什么、结论或待办是什么」。不要用「我们认为」「笔者」这类口吻，
也不要替参会人补充他没说过的判断——纪要的价值在于可追溯。

## 常见误区

- ❌ 「标题写成 `# 1. 项目背景`」——会变成「1. 1. 项目背景」。
- ❌ 「材料里没说会议时间，我先填个大概」——必填项缺失要问用户，不要编。
- ❌ 「用户要加个表格，我用 python-docx 补一下」——本规范不含表格格式，
  应告知用户当前不支持，问他是否接受改写成文字表述。
- ❌ 「这份纪要格式不对，我打开改一下」——只能重新生成，或者用
  `check_minutes` 报出问题让用户决定。
