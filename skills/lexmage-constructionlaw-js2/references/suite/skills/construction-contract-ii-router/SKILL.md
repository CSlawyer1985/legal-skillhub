# 《建工解释二》总控

## 核心任务

先分诊，再调度，最后合并。不要把总控变成第七种重复审查模式。

## 开始前必须读取

1. 读取 [共同审查协议](references/common-protocol.md)。
2. 读取 [技能路由表](references/suite-map.md)。
3. 读取 [用户接收与交付协议](references/intake-and-delivery.md)。
4. 读取 [知识库边界](references/knowledge-base/00-知识库导航与使用边界.md)。
5. 对规范内容作任何判断前，读取 [总论](references/knowledge-base/01-总论-到底改了什么.md) 和与问题对应的专题或逐条精解。
6. 需要逐字引用条文时，只从 `references/knowledge-base/official/01-法释2026-12号全文.md` 提取。

## 分诊流程

### 第一步：识别输入

用户无需知道技能名称或预先选择模式。先提取并明确：

- 材料类型；
- 文件是否完整可读，是否为长材料或多份材料；
- 使用者角色；
- 希望得到的交付物；
- 一审受理时间或其他程序阶段；
- 主体链、合同链、施工链和资金链；
- 是否存在紧急期限、退场、保全、质量安全或工资风险。

长材料或多份材料按 [用户接收与交付协议](references/intake-and-delivery.md) 建立稳定定位、材料登记和统一时间轴。

信息不足时先基于已知材料给出初步方向，再从 [决定性问题卡](references/issue-question-cards.md) 中选择最多5个问题。不要把长问卷当作答案。

### 第二步：选择模式

遵守以下原则：

- 用户明确点名某一模式时，以该模式为主；
- 用户未点名时，选择一个主模式，必要时增加不超过两个辅助模式；
- 同一材料需要“发现问题+直接修改”时，组合快速扫描与对应修改技能；
- 需要形成完整诉讼判断时，以深度审查为主，角色策略为辅；
- 不为显示全面而机械调用全部模式。

### 第三步：加载执行技能

按 [技能路由表](references/suite-map.md) 中的路径完整读取所选内部工作流的 `SKILL.md`，严格执行其工作流和输出格式。总控不得凭记忆模拟子技能。

### 第四步：合并结论

统一处理：

1. 删除重复问题；
2. 发现结论冲突时回到官方条文和事实前提复核；
3. 将“规范结论、事实判断、证据判断、策略建议”分开；
4. 将风险等级与结论标签分开；
5. 以用户最需要的交付物为主体，调度说明保持简短。
6. 为重大结论保留“事实—证据—法条—结论—行动”追溯链。

### 第五步：终检

完整执行 [最终质量门](references/final-quality-gate.md)。未通过的项目先修正再交付。

## 总控输出

先按用户需要的一屏版、标准版或正式版给出实质结果。仅在有助于理解时，再用一段简短说明写明：

- 主模式及辅助模式；
- 选择原因；
- 审查基准日；
- 是否存在因事实不足或裁判发展而保留的结论。

不得让用户先理解技能体系才能获得答案，也不得只报告“已经调用哪些技能”而不完成实际任务。

## 法律护栏

- 先审第23条时间效力。
- 不以“实际施工人”标签代替具体身份和请求权。
- 不把关键词命中写成法律要件已经满足。
- 不披露内部研究材料名称或来源。
- 对外法源只使用可核验的法律法规、最高人民法院正式材料及其他权威来源。
- 现行法、后续案例或地方规则可能变化时，先检索核验再形成正式结论。
- 事实不足时使用“明确命中、可能命中、证据不足、不适用、待裁判发展”标签。

## 维护入口

用户要求检查或更新本技能时，完整读取并执行本一体化 Skill 根目录下的 `references/update-policy.md`，不要把更新任务路由到六种法律审查模式。SkillHub 版本不得运行来源不明的自更新脚本，也不得静默覆盖本地文件。
