# 变更日志

本文档记录 One-Contract 的重要变更。


## [3.2.0-preview.1] - 2026-09-18

来源：一份真实合同（睡眠监测运营服务合作协议·甲方视角）的**三次独立审查**——
我一次、两位互不通气的冷启动审查者各一次。三次比对出的差集，就是本版的主要内容。

**本版两条主线**：① 修工具链缺陷（会让产物出错的那类）；② 把"只活在审查者判断里"的规则写进库并接上执行点。

### 知识库：第一层新增五组规则（均可直接落笔）

- **3.4.1 组织／协调角色与第三方专业服务的责任隔离**——三段式（角色限定／身份否定／责任归属）；
  硬边界：不得写成免责条款（民法典 506）、**不得对抗第三人**（465）、我方实际控制度高时会被穿透；
- **3.5.1 责任限制（赔偿上限）**——先判方向（我方是被索赔方→落笔设限；我方是索赔方→只提示），
  再定基数（引发责任的那一单）、倍数（1×）与必写例外（故意／重大过失、人身损害不适用）；
- **3.5.2 保险安排**——**只加对方义务**（让实际控制标的与作业的一方投保，我方列为共同被保险人／受益人），
  五要素缺一即空转；保额写口径不写金额；
- **§八 履约链条上的十四类典型缺口（8.1–8.14）**——对账默认确认、"有效完成"在客户原因下的认定、
  第三方延误顺延、对外担责追偿、现场核查权、隐蔽瑕疵检验期、赔偿不得归零、逾期占用成本、
  **不可抗力三项义务**、质量标准与检验期两部分俱全、终止后清算清单、违约金三件套、
  送达视为规则、附件引用对应与效力顺位。每条含触发、风险、可直接落笔的措辞与边界。
  体例说明：**"必须补什么"要写成清单，不要埋在硬边界里**——8.9 就是从硬边界挪出来、
  三次审查中前两次都漏、第三次才被抓住的那一条。
- **四之二 主体与资信核查只进报告、不落批注**——审阅件是给对方看的文本工作件。

### 口径（写作规则）

- **1.5 命中明确规则就落笔**：判据从"是不是商务条款"换成"有没有明确规则可依"；**1.5.1** 说明
  这条落在**证据状态的定性**上（文档管不住字段）；**1.6 填数三条线**：天数与比例可填并注明可调整，
  具体金额留 `【待填：金额】`；
- **十一 审查人回复口径**：不写"采纳／同意／接受／认可"（那是当事人表态），只写核对结论。

### 契约与机制

- `review_plan.schema.json` 正式纳入 `responses`、`linkage_checklist`、`rule_hit`、`direction_clear`
  （**均为可选，不新增必填**）；契约层与运行时同判，由 `test_review_plan_schema.py` 钉住；
- 联动必检清单**增第六组**"角色边界与第三方专业服务"；
- 执行器新增三条软检查：`amount_guard`（具体金额）、`subject_check_guard`（主体核查误落批注）、
  `insurance_burden_guard`（我方被加投保义务）；措辞越界是**硬校验**；
- `rule_hit` + `direction_clear=true` 时**不得记 `major_choice`**（否则执行器会把它降级成仅批注——
  这条机制就是为"规则写了却不生效"设的）。



### 修复：交付物正确性

- **修订后文本保真**（会造成可见错误的一处）：`_get_accepted_text()` 递归段落全部子元素，
  把 `w:pPr/w:tabs/w:tab`（制表位**定义**）读成正文制表符，段落重写时又写回正文——
  任何**带制表位定义**的段落被修订都会在段首多出制表符，"拒绝全部修订"视图因此与原稿不一致。
  现在文本抽取整棵跳过段落/字符属性与批注锚点（`_NON_CONTENT_ELEMENT_TAGS`），
  整段重写保留首个正文 run 的字符格式。回归：`test_revision_text_fidelity.py`
  （拒绝视图逐字等于原件、批注锚点数量不变、字符格式不丢）。
- **报告输出「审查依据与覆盖层级」**：该节为 `SKILL.md` §1 与报告模板所要求，但
  `scripts/report/reporting.py` 此前**没有任何实现**，也没有测试会发现"文档要求 ≠ 实现"。
  现按 `meta.classification_provenance` 渲染审查深度（三档）、生效资产、空壳议题；
  取不到 `coverage_level` 时如实写「未记录」并计入完整性错误。
  新增**报告章节契约** `scripts/report/report-sections.json`，生成器逐节自检，**缺节即报错**。
- **`report_bucket=tax` 的 finding 不再被误判"缺少审查意见"**：
  `_resolve_review_direction()` 增加 `tax_advice` 键。
- **运行态配置默认隔离**：`apply_review_plan.py` 在导入运行期模块前，把
  `CONTRACT_COPILOT_CONFIG_DIR` 默认指向本轮归档目录的 `runtime-config/`
  （此前未显式设置时会把审查人自述与审查记忆写进**冻结的 Skill 副本**）。

### 新增：源文档批注的回复与处置

- **`plan.responses`：逐条回复源批注**（执行器调用引擎既有的 `reply_to_comment`，
  形成 Word 线程化回复）。门禁：`stance=already_present` 必须带 `evidence`
  —— 防止把"现稿本来就有的内容"写成"已采纳"这类**事实错误**。
- **`--orphan-comments {quarantine,strip,reject}`**：悬空批注（正文中无锚点、Word 里不可见）
  此前只有检出没有出口。默认 `quarantine`：原样导出 `orphan-comments.json` 后从工作底稿移除，
  内容留痕、锚点干净。
- **引擎补 `update_comment()` / `delete_comment()`**：此前批注只能"加"和"回复"，
  措辞写错只能做 XML 级手工清理（实测中手工清理漏掉 `commentReference` run，被质量门拦下）。
- 报告新增「源文档批注意见处理」一节（可选节，仅在有回复或悬空批注时出现）。

### 新增：流程性门禁

- **`plan.linkage_checklist`：条款联动必检清单**（五组，缺一组不得出报告）。
  依据 `review-doctrine` 六与 `modular-knowledge-routing`「联动组」。
  动因是一次实测漏检：把"要不要投保是商务取舍"（动作判断）当成"不必检查保险安排"（识别），
  整组被漏掉——**动作判断不得提前当作识别筛子**。
- **`legal-citations.json`**：每轮汇总引用到的法条，供具备数据库的使用方逐条复核现行有效性；
  `SKILL.md` 增补中性口径：本库条文于建库时核验（随文标注日期），核验结论是**冻结时点**的。

### 文档

- `references/redline-comment-policy.md` 新增「十一、审查人回复口径」：
  **审查人不写"采纳"**（那是当事人表态）；说"现稿已体现"必须先核对并给出条文号；
  无锚点批注回复不了，不得假装回复。
- `SKILL.md` §1 增两节（源批注处理、联动必检清单），§6 增悬空批注与法条复核口径。

### 契约：`responses` / `linkage_checklist` 正式入 schema（产品负责人授权）

`assets/knowledge_v2/schemas/review_plan.schema.json` 新增两个**可选**字段（不新增必填项，
历史 plan 继续可用）：

- `responses`：源批注回复；`stance=already_present` 时 `evidence` 必填（契约层与运行时同判）；
- `linkage_checklist`：五组必检；`not_applicable` 必带 `reason`；组内结构不合规直接拒绝。

两层校验口径由 `scripts/tests/test_review_plan_schema.py` 钉住（同一份 plan，
JSON Schema 与 `plan_loader.validate_plan` 结论必须一致）。

**后果（必须知情）**：该文件是公共资产，改动会改变公共指纹；绑定旧指纹的**客户快照将 fail closed**
（行为由 `test_data006_public_fingerprint_mismatch_fails_closed` 钉住）→ 需重新发布快照。
影响面待评估，见 `qa/rule-studio/adr-proposal-review-plan-extension.md`。

### 口径：命中明确规则要落笔；填数守三条线

- **1.5 命中明确规则时落笔**：风险点命中三层架构中的明确规则、方向明确时，直接修订 + 批注，
  **不因条款属"商务"而退化为仅批注**（动因：保险安排被处理成"建议投保"的批注）。
  仍只批注的是**没有规则可依**的纯商业取舍与事实/授权不足事项。
- **1.6 填数三条线**：**天数与期限、比例（含以金额为基数的比例）可直接填入**并批注注明可调整；
  **具体金额不填数字**，正文写 `【待填：金额】`、批注给出计算口径。能写成比例就不写金额。
- 执行器新增**软检查** `amount_guard`：新增文本里出现具体金额且未标待填时打印提示并记入执行日志
  （只提示、不阻断——这是写作者自己的护栏）。

## [3.1.0-preview.2] - 2026-09-17

本版是 3.1.0-preview.1 的发布收口版，不新增法律知识正文，重点修复规则路由、可视化唯一定位、Agent 调用与发布说明的一致性。

- 分类交叉检验改为 fail closed：路由器已有 `medium/high` 结论且与 AI 归类不一致时，返回 `needs_human_review`（退出码 2）；只有人工复核后显式传入 `--human-confirmed` 才可继续。
- 修正可路由类型清单：系统运维的原则卡与五个模块仍为 `candidate / inactive`，因此从 `routable_types` 移除；当前正式可路由类型为 **92**，另有 9 类已建候选资产。
- Rule Studio 的类型原则节点使用 `doctrine_id::type_id` 唯一定位，解决同一可复用原则服务多个合同类型时详情、提案只命中第一条的问题；运行时规则身份仍保留原 `doctrine_id`。
- 生效规则载荷保留 `content_status`，使客户规则解析路径也能识别并披露空壳模块。
- Agent API 补齐 CSRF 与同源请求头，支持受保护的写操作；`stop` 改走本地认证接口，服务不可达时不再按过期 PID 强制发送终止信号。所有 Agent HTTP 请求显式绕过系统代理且限定为本机回环地址，避免企业代理环境下的 502/超时。
- 删除未被消费的 URL fragment secret 表述与死代码；页面继续通过同源 bootstrap 取得短时会话凭据。
- 同步 README、Skill 版本、OpenAI 展示名与知识资产状态说明。

### 发布风险接受

为满足当前可用版本的交付安排，产品负责人决定九张大类卡与 17 个本轮修改模块继续保持启用，不等待本轮补充律师复核。该决定已在 README 与资产状态说明中显式记录；不得将其解释为已经完成更新后律师逐条审批，实际合同输出仍须律师终审。

### 一条实务规则修订：管辖地点可落笔争取

原规则「原文管辖合法即不改变归属、只做明确化、改归属须客户明确指示」，在逐条对照中被 6 章独立质疑。
经与律师讨论后改为**分三档**：

- 原文**无有效协议管辖**（如「向有管辖权的法院起诉」——**这不是协议管辖**）→ **落笔新增**；
- 原文有合法管辖**但对我方不利** → **落笔改**，并在意见书首部「改变了权利归属的条款」显著列明；
- 原文有合法管辖且对我方无不利 → 只明确化，不改归属。

**三项约束**：① **限定在管辖，不外推**（违约金、责任封顶等商业取舍仍只批注、由客户决策；
理由是管辖的方向单边、商业取舍是双向判断）；② 落笔必须带不可忽略的说明，**不得闷头改**；
③ **方向要判断**——我方常被诉争取我方所在地、常主动起诉争取原告住所地，
原文已是「原告住所地」且我方常为原告的不该动。

同款表述已同步修订至 `SKILL.md` 与 `doctrine-goods-transaction-control`（EC-02-002）。

### 全库自我纠错：我方自身缺陷九处

逐条对照同时暴露了本库自身的错误，已全部修正（所引条文均经元典核验现行有效）：

- **流押／流质定性写错**（会给出错结论的一处）：原写「条款无效、担保实现受阻」，
  而民法典 401／428 条现行原文是「**只能依法就抵押／质押财产优先受偿**」——是**效力限缩**、非无效，
  担保实现**不受阻**。已改正定性，动作层不变；
- 赠与族：`mod-gift-revocation` 补法定撤销三项事由与一年除斥期间；5 个模块回填 657–665 条号；
  2 个模块修正瑕疵担保与附义务的责任分层；
- 担保制度解释**第 7／9／10 条**（法定代表人越权担保、上市公司披露、一人公司）补入资产；
- 运输 5 件回填 825–837 条号，并**成对补上检查点**（832 三项法定免责、833 赔偿额顺序、
  836 留置权、829 托运人变更权、837 提存）；
- 中介（963／964）、出资（公司法 51／52）、承揽（772／773）等空壳模块用真实条文填充；
- 融资租赁卡补「买卖合同与融资租赁合同互洽」等检查项；
- `domain-layer-status.md` 的历史快照就地加现行值标注；
- `review-doctrine.md` 九「来源」节一处**与实测不符的自称**已更正（原称"整体无效情形已并入本库"，
  实测为零；第五章补齐后该声称方成立）。

### 新增「空壳资产」识别机制

核查时发现 **54 个条款模块（全部 active）是模板生成的空壳**——每个字段都是同一句套话套上议题名，
**模块只有标题、没有检查项**，分布在 58 个类型中。这类模块会让审查报告**高估覆盖深度**。

- 已全部标记 `content_status = stub_placeholder_pending_content`，**校验器强制该标记双向一致**
  （标了就必须只有一条检查项；只有占位句就必须标记）；
- 审查意见书的「审查依据与覆盖层级」**须逐项列出空壳模块的议题**，作为"本类型下暂无具体检查项的议题"；
- 若某类型生效模块**全部**为空壳，覆盖深度按 `domain_only` 写。

### 来源追溯：登记 `src-skill1` 并如实标注

- 该素材为正式出版物，**版权状态：已授权**（产品负责人明示）；
- 库内以内部代号 **`skill1`** 指代，**交付包不出现原作品名称与作者名**；
- 第一层三份方法文档标到**条目级**（逐项列在文档末尾「来源标注」节）；
