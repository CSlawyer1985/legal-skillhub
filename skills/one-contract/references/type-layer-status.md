## 二、为什么保留空壳而不一次填满

**有意为之，不是遗漏。** 理由：

1. **填满 113 个类型会产生大量重复规则**——本库明令"不做重复的两条规则"（见 `knowledge-asset-governance.md`）；
2. **多数空壳类型可由既有类型 + 第一层通用规则覆盖**（下节 B 类），强行建卡是凑数；
3. **保留空壳使版本迭代可见**：每个版本补上若干类型，是产品能力的可验证增长；
4. **空壳是诚实状态**：与其写一张内容空泛的卡，不如明确"这里还没有"。

## 三之二、**空壳模块**：类型已建、但检查项为空

与上面的"空壳类型"不同——这些类型的卡与模块**存在且已 active**，但模块内容是**模板生成的套话**：

| 字段 | 内容 |
|---|---|
| `review_checks` | 「应明确对象、条件、程序、期限和后果」 |
| `recommended_actions` | 「双方应就**{clause_group}**的对象、触发条件、程序、期限及责任作出明确约定。」 |
| `failure_mode` | 「P1：**{clause_group}**缺失或与相邻条款不一致——核心履行机制无法闭环」 |
| `legal_basis_notes` | 「经批准的类型原则与当前可核验法条」 |

**即：模块只有标题，没有具体检查项。**

| | 数量 |
|---|---:|
| 空壳模块（全部 `active`） | **54** |
| 涉及类型 | **60** |
| 全部模块皆空壳的类型 | **0**（每个受影响类型至少有一个真模块，最差 3/5） |

**标记**：这类模块的 `content_status` 为 **`stub_placeholder_pending_content`**。
该标记由 `validate_assets.py` **强制双向一致**（标记了就必须只有 1 条检查项；只有占位句就必须标记），
故它是可机器检索的**唯一真值来源**，不做启发式判断。

**运行时影响**：选择器返回的模块对象**已含 `content_status`**，审查时可据此识别。
`SKILL.md` 要求：报告的「审查依据与覆盖层级」一节**须逐项列出空壳模块的 `clause_group`**，
作为"本类型下暂无具体检查项的议题"；若某类型生效模块**全部**为空壳，覆盖深度按 `domain_only` 写。

**待办**：其余 **52 个**待填（2026-09-17 已填充 2 个真空壳：`mod-brokerage-duties`、`mod-brokerage-tail`）。
填充时须按语义补入实际检查项与条号，**不得再用套话**。

> **与「名实不符」的区别**：另有 2 个模块（`mod-work-subcontract`、`mod-contribution-default-loss`）**不是空壳**——它们有真实检查项，但没有一条对应自己的 `clause_group`（议题在字段名上、内容在别处）。这是**名实不符**，不是内容为空。
> 二者都要修，但**判据不同**：
> - **空壳**：`review_checks` 是否只有那句占位套话；
> - **名实不符**：`review_checks` 是否覆盖了 `clause_group` 声明的事项。
