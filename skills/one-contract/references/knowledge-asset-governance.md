# 知识资产治理与隐私边界

## 状态机

知识资产只能按以下顺序流转：

`candidate → lawyer_approved → regression_passed → active → deprecated`

只有 `active` 可进入正式审查。状态变化必须有审核人、审核时间、法律核验时间和回归证据；不得由运行时脚本自行晋级。类型、大类原则卡、具体类型原则卡、条款模块、联动组、触发器、经验卡和 DOCX 母版分别管理状态；激活某一层不得自动激活其他层或任何辅助资产。

大类原则卡的正式选择器只可展示候选卡的 ID、领域、覆盖等级、覆盖数量、来源数量和状态，不得展示 `candidate` 正文。离线评估入口位于 `scripts/tests/`，不进入对外导出包。EC-10 缺口卡不得激活，直至形成实质规则、有效来源并完成独立批准与回归。

v1 归档提炼的任何内容必须新建为 `candidate`，不得就地改写正在运行的 `active` 资产。本项目由用户逐项确认迁移候选；确认后回写 `reviewer`、`reviewed_at` 和 `lawyer_approved`，再进入回归测试，不因用户确认而跳过 `regression_passed` 门。

## 本地与 Skill 边界

原始合同、条款全文、客户信息、原始路径、合同族标识和原件哈希只保留在本地敏感数据区。Skill 只能保存脱敏、提炼并批准的知识资产以及公开来源的必要元数据。

候选 Skill 发布前扫描：

- 用户主目录绝对路径；
- 合同族标识和长哈希；
- 客户名称、项目名称和未脱敏主体名称；
- 原合同条款的大段逐字文本；
- 未获批准的来源或模块。

发现任一项即阻断安装。

## 来源层级

优先使用现行有效的法律法规、司法解释和官方典型案例；其次使用可核验的高质量律师实务文章、真实历史修订和失败案例。文章只提炼观点与判断方法，不整篇打包。

每项来源至少记录：来源 ID、作者或发布机关、标题、来源链接或本地登记、法域、发布日期、核验日期、来源状态和律师批准状态。知识性质标记为 `legal_boundary`、`judicial_tendency`、`risk_control`、`negotiation` 或 `client_policy`。

仅通过搜索结果确认标题、账号或摘要的微信公众号文章须标为 `wechat_practice_article_discovery`，只能作为后续取证线索。未取得并核验正文前，不得进入原则卡、模块或触发器的 `source_ids`，不得支持法律结论。

## 代表合同与母版

代表合同适格度自动分值仅用于缩小人工审阅范围。法律明显过时、文本不可可靠提取、内部冲突、无法脱敏、来源不明或只有签署扫描件且无可编辑版本的，均不得进入母版。

每类3至8个批准合同族分别承担基础骨架、我方强保护、对方强保护、平衡、特殊场景和反例。完整 DOCX 最多三份，其他差异进入条款模块。内部批准合同族少于三个的类型保持暂行、未激活。

## skill1 来源与规则号标注（2026-09-17 建立）

**背景**：本库部分内容提炼自用户提供的合同审查技能包。该素材为**正式出版物**，
用户已明示**版权已授权**，但要求**交付包与对外文件中不得出现原作品名称或作者名**。
因此该来源在库内以内部代号 **`skill1`** 指代。

**来源登记**：`source_catalog.json` 中的 `src-skill1`

| 字段 | 值 |
|---|---|
| `source_id` | `src-skill1` |
| `title` | `skill1`（**不写书名**） |
| `source_kind` | `user_provided_skill_package` |
| `access_scope` | `user_provided_licensed`（**版权状态：已授权**） |
| `approval_status` | 随引用它的资产状态而定（见下） |

**规则号标注约定**：

- 资产的 `source_ids` 加入 `"src-skill1"`；
- **规则号写在 `source_family_ids`**（该字段在本库此前全为空，现约定用于承载来源条目号）；
- 格式：`skill1:<规则号>`，规则号沿用素材原有编号体系（`R-`／`S-`／`C-` 加章-序，如 `R-07-01`）。

> ⚠️ **粒度不统一是如实记录，不是遗漏**：
> - **第一层三份方法文档**（`review-doctrine.md` 第九节、`redline-comment-policy.md` 第一节、
>   `common-clause-doctrine.md` 第三节）标到**条目级**，逐项见各文档末尾的「来源标注」节；
> - **第三层新增类型卡与模块**标到**章节级**（`skill1:第15章` 等）——本批建卡时**未逐条记录条目号**，
>   **不得事后补造看起来精确的编号**。如需条目级，须重新对照素材逐条建立。

**`approval_status` 的规则**（校验器强制）：来源的 `approval_status` 取决于**引用它的资产是否 active**——
被 active 资产引用的来源必须为 `active`，否则必须为 `candidate`。
故 `src-skill1` 当前为 `candidate`（引用它的资产尚为 candidate）；
**版权授权不是 `approval_status`，而是 `access_scope`**，二者不要混同。

**交付边界**：导出包的内容巡检须确认——**不出现原作品名称、作者名、原书页码**。
规则号（`R-07-01` 形式）不构成书名披露，可以保留用于溯源。

### 导出前巡检（**执行要求**）

```bash
python scripts/knowledge/scan_export_boundary.py
```

**任一次导出前必须运行，且退出码须为 0。**

| 退出码 | `status` | 含义与处置 |
|---|---|---|
| `0` | `pass` | 全部检查已执行且无命中 → 可导出 |
| `1` | `fail` | 发现命中 → **阻断导出**，逐条处理 `findings` 后重跑 |
| `2` | `incomplete` | **有检查项未执行**（如禁词表缺失）→ **不得视为通过**，补齐后重跑 |

**禁词表在包外**：`<仓库根>/.local_data/export-boundary-denylist.txt`（该目录已在 `.gitignore` 中）。
**为什么外置**——巡检脚本会随技能包交付，若把不得外泄的原作品名称、作者名写在脚本里，
**脚本自身即成泄漏源**。同一考虑也适用于既有代码：`validate_assets.py` 对用户路径采用
`"/" + "Users/"` 的拼接写法，就是为了让完整字面量不出现在源码中。

**禁词表格式**：每行一词，`#` 开头为注释，空行忽略。新增不得外泄的名称时追加即可，
**不得把禁词写进技能包内任何文件**（本治理文档、`type-layer-status.md` 等一律以 `skill1` 指代）。

**巡检覆盖**：
- 外部禁词表逐词匹配（原作品名称、作者名等）；
- 原书页码模式（三类，均以占位符表述，避免本文档自身触发）：
  ① 字母 `P` + 2–3 位数字 + 连接号；② `第` + 数字 + `页`；③ `p.` + 数字。
- 绝对用户路径、合同族 ID、长哈希（与 `validate_assets.py` 同类模式）。

**配套回归**：`scripts/tests/test_export_boundary_scan.py` 六项用例——含**反向补丁重放**
（注入禁词与页码必须被发现）与**失败开放检查**（禁词表缺失时 `status` 不得为 `pass`）。

## 类型原则卡的 ID 不是唯一键（重要）

**一张类型原则卡可以服务多个合同类型，实现方式是按类型各存一份副本，共用同一个 `doctrine_id`。**
这不是数据重复错误，是设计：`taxonomy_v2.json` 的 `routable_types[].required_doctrines` 显式声明了哪些类型需要同一张卡
（例如 EC-02-001／002／003／005 四类均声明 `doctrine-goods-transaction-control`）。
当前共 **21 个 `doctrine_id` 被多张卡共用，涉及 55 张卡**，其中 20 个组的副本内容完全一致。

**由此产生的三条纪律**：

1. **不得按 `doctrine_id` 取卡**——同 ID 有多份副本，取到哪一份取决于遍历顺序。
   要定位某类型的卡，**只能用 `type_id` 或 `type_code`**。（2026-09-17 修订管辖规则时实际踩过：
   按 ID 取卡取到了另一类型的副本。）
2. **共用 ID 的多份副本，实质内容必须一致**——否则同一 doctrine 在不同类型下给出不同规则。
   当前**有且仅有一组例外**：`doctrine-goods-transaction-control`，
   其中 EC-02-002（设备、原材料采购）是 18 条默认倾向的深化卡，其余三张是 3 条的基线卡。
   **该例外是否为有意，待产品负责人确认**；确认前不得据以推断其他组的做法。
3. **`doctrine_id` 的集合语义**：`asset_manifest.json` 的 `active_doctrine_ids` 与校验器中的
   `principle_ids` 都是**集合**，同 ID 多份副本在此塌缩。因此这两处**不能**用来判断卡的份数。
