# 企业合同分类体系 v2

## 分类结构

正式主类固定为：

| 主类 | 范围 |
|---|---|
| EC-01 | 公司治理、投资与股权 |
| EC-02 | 买卖、采购与供应 |
| EC-03 | 租赁与资产使用 |
| EC-04 | 服务、委托与专业支持 |
| EC-05 | 技术、数据与知识产权 |
| EC-06 | 劳动、人事与用工 |
| EC-07 | 融资、借贷与担保 |
| EC-08 | 建设工程与房地产 |
| EC-09 | 合作、经销与营销 |
| EC-10 | 结算、履约与通用配套 |

主类和展示编码用于人读；机器接口始终使用永久不复用的 `type_id`。行业、我方角色、交易阶段、文书性质和业务场景只能作为独立标签，不能塞回类型编码。

## V2 类型目录

当前 214 个类型及永久 ID 以 `assets/knowledge_v2/taxonomy_v2.json` 为唯一机器来源。九类 `active` 类型可进入正式专项路由：股权转让、设备/原材料采购、员工保密、竞业限制、协商解除劳动关系、综合咨询服务、房屋/场地租赁、商品房现售和商品房预售。`pilot_types` 只保留为历史首批20类基线；运行时使用 `routable_types`，不再以“试点”命名决定资产是否可用。其余类型保持非 `active`，须另经回归和激活决定后才可运行。

## 分类确认门

统一输出：

```json
{
  "primary_type_id": "...",
  "secondary_type_ids": [],
  "document_kind": "...",
  "our_role": "...",
  "scene_tags": [],
  "classification_status": "high|medium|low",
  "evidence": [],
  "required_doctrines": [],
  "required_modules": [],
  "human_confirmation_required": false
}
```

自动路由同时要求：

1. 标题具有明确类型证据；
2. 交易结构与主类型一致；
3. 当事人角色和我方角色明确且不冲突；
4. 没有同分或近分的混合类型；
5. `classification_status=high`。

任一条件不满足，`human_confirmation_required=true`。不得用旧分类、文件夹名或单一关键词覆盖交易实质。

## 主辅类型

主类型决定交易骨架、核心原则卡和主要模块。辅类型只补充确实存在的配套机制，例如采购主合同中的软件许可、合作协议中的数据处理或借款合同中的保证。不得为“看起来相关”而堆叠辅类型。
