# 法务标书全套生成（legal-bid-pipeline）

## 概述

本技能将投标文档制作从"人工逐章拼凑"升级为**多Agent协作自动化流水线**。核心思路：**投标可行性预评估 → 总调度拆解（含模板自动识别+自定义废标条款提取+风险库扫描） → IMA知识库检索 → N个Agent并行写（知识库优先+法务专用指南引导）→ 人工确认AI生成内容 → 模板/自由双轨合稿 → 八道硬门槛质检（含模板对齐+风险库复检+格式类自动修复） → 五维评审 → 评分项闭环补强（PDCA-Act，自动落稿） → 修改迭代 → PDF拼合交付组装**。全流程共**6个人工确认点**，其余阶段完全自动化。

覆盖六大管控维度：**政策合规**、**技术匹配**、**商务匹配**、**格式检查**、**模板对齐**、**废标风险**。

**三类材料三轨映射（v3.6 用户产品愿景：素材一股脑进，一键出 Word，确认后出 PDF）**：

| 材料类型 | 处理轨 | 规则落点 |
|---------|--------|---------|
| ① 招标方模板文件 | 模板轨：逐字填空，四步拷贝法 | 阶段三·轨道A |
| ② 服务方案 | 方案轨：按招标服务内容与评分细则生成，事实从源头取值 | 阶段二 + 阶段三·轨道B |
| ③ 业绩/证件/身份证等 | 图片轨：首页+末页双读分类建清单，扫描件压缩后以图片内插 Word | 阶段三·同类项目一览表规则 + `extended-references/delivery_pipeline.md` |

素材无需用户预分类（模板识别规则A-D + 首页OCR分类自动分轨），但四样必须用户给：**报价金额、授权代表人选、团队成员名单、投/不投决策**。素材统一放一个文件夹（如 `素材/`），不与输出物混放（实战教训：同名新旧两版标书文件混放导致评审险些拿错版本）。

> 版本演进与历次实战复盘原始记录见 [CHANGELOG.md](CHANGELOG.md)。最新规则已直接写入下文各阶段正文（四步拷贝法→阶段三轨道A、残留块检查→阶段四门槛8、封面字号层级→阶段三封面表、精准修改轨→阶段七、报价校验脚本→阶段四门槛6、页码脚本→阶段三合稿、自动修复脚本→阶段四路径A、md→docx脚本→阶段三轨道B），此处不再重复。

## 第一性原理：模板 vs 自由（P0 级核心规则）

> **本规则优先级高于 Skill 内其他所有章节。** 这是从实战中标书 v1→v2→v3 三次迭代中提炼的根本性教训。

### 为什么这条规则是 P0

招标文件第二章·（六）·8 明确规定：**「响应文件未按磋商文件规定的格式、内容和要求填写制作的，属于无效响应」**。

这不是"建议"，这是废标条款。而且是**29项废标情形**之一。

### 两分法

| 维度 | 有模板的章节 | 无模板的章节 |
|------|------------|------------|
| **本质** | 招标方给了"答题卡"，你在上面填空 | 招标方给了"作文题"，你写文章 |
| **判断标准** | 招标文件第五章中给出了固定格式（表格列数、占位符文字、签章空位） | 招标文件只给了章节标题，没有给出内容格式 |
| **典型章节** | 磋商申请及声明、授权书、磋商一览表、细目报价表、承诺书、偏离表、类似业绩表（格式三）、人员配置表（格式十） | 服务方案、质量保证措施、律所简介 |
| **处理方式** | **逐字逐格填空**：模板原文一字不改，占位符处填入数据，签章行保留空白 | **自由编写**：按评分标准要点逐条响应，自主设计章节结构 |
| **底线** | 表格列数、标点符号、空格缩进、段落顺序——一模一样。**改一个字都有风险** | 无格式约束，但内容必须覆盖评分项 |
| **对应Skill** | `bid-template-filler` 精神 | 自由编写模式 |

### 对抗性审查清单（合稿后必查）

从评标专家的视角，打开招标文件第五章和响应文件，逐项比对：

| 序号 | 审查点 | 示例（某真实标书的错误） | 后果 |
|:---:|--------|--------------------------|------|
| 1 | 表格列数一致 | 细目报价表模板6列（序号\|名称\|数量\|单位\|单价\|合价），v1版本只做了5列，漏了"单价" | 废标风险 |
| 2 | 标点符号一致 | 磋商申请及声明模板"5、一旦我方成交"，v1/v2写成"5. 一旦我方成交"（英文句号代替中文顿号） | 评委一眼看出不一致 |
| 3 | 承诺书文字逐字一致 | 格式一/格式二的空格、缩进、"日      期"（中间有空格） | 格式偏差 → 可能被认定为"未按格式制作" |
| 4 | 偏离表包含"偏离情况"列 | 模板5列含"偏离情况"，v1只做了4列 | 漏列废标 |
| 5 | 类似业绩表列数 | 格式三8列完整版，不可简化为5列 | 格式不符 |
| 6 | 签章行留白 | 模板中"供应商授权代表姓名（签字）：         "有空白——这是给手签的，不是给你填名字的 | 填了名字不给手签空间 |
| 7 | 模板原文一字不改 | 磋商申请"我们的总报价为（大写）         元人民币"，不要改写成"采购包1总价...采购包2总价..." | 句式被改写 |

> **关键教训**：v1 版本用 AI 直接生成全文（add_paragraph），把模板文字重写了一遍，导致大量微小偏差。v3 版本改为对照模板逐行编写，每个段落都来自模板原文。

### 阶段一中新增的模板识别步骤

在 MECE 拆解时，对招标文件第五章的每一项标注类型：

```
- 章节一·磋商申请及声明 → [模板] 按 P371-P393 原文填空
- 章节二·法定代表人授权书 → [模板] 按 P395-P408 原文填空
- 章节三·磋商一览表 → [模板] 3列表格
- 章节四·细目报价表 → [模板] 6列表格
- 章节五·资格证明文件 → [模板] 含格式一/二承诺书
- 章节六·补充证明文件 → [模板] 格式三8列表格
- 章节七/八·偏离表 → [模板] 5列表格含偏离情况
- 章节九·服务方案 → [自由] 自主编写
- 章节十·人员配置 → [模板] 格式十8列表格
- 章节十一·质量保证 → [自由] 自主编写
- 章节十二·其他 → [自由] 自主编写
```



## 多Agent角色分工

| 角色 | 类型 | 数量 | 职责 |
|------|------|------|------|
| 总调度（Dispatcher） | 主Agent | 1人 | 解析招标文件→MECE拆解→生成章节Brief→启动后续Agent |
| 章节编写（Writer） | 子Agent | N人（1章/人） | 基于Brief独立上下文编写各章节，加载对应reference |
| 合稿（Compiler） | 主Agent（v2.2起，不再用子Agent） | — | 模板/自由双轨合稿：模板轨逐字填空（四步拷贝法）、自由轨 python-docx 直接生成 DOCX（不经过 HTML） |
| 质检（QA） | 子Agent | 1人 | 执行八道硬门槛检查（含风险库复检，「与」关系，一道不过即打回） |
| 评审（Reviewer） | 子Agent | 5人（A~E） | 五维并行评审→P0/P1/P2分级→加权总分 |
| 修改（Reviser） | 子Agent | 1人 | 合并评审意见→逐条修改→输出vN+1 |

## 触发场景

- 用户上传或提供招标文件，要求生成标书初稿
- 用户需要撰写技术方案、商务方案、项目实施计划
- 用户需要进行招标文件解析、提取关键要求
- 用户需要生成响应矩阵（Compliance Matrix）和偏离表
- 用户需要对已完成标书进行质量检查和合规审查
- 触发词示例：「帮我写投标文件」「生成技术方案」「分析这份招标文件」「检查标书格式」

## 输入要求

**推荐模型**：DeepSeek V4 Pro 及以上。本技能涉及 N 个编写 Agent + 5 个评审 Agent 的并行编排、招标文件与素材库的长上下文读取、以及大量格式硬规则的同时遵守——低规格模型容易丢规则、丢上下文，导致模板错位和事实幻觉（内部复盘的多起事故与模型遵循度直接相关）。

1. **必需**：招标文件（PDF/DOCX/Markdown/纯文本）
2. **推荐**：公司简介、资质证书清单、成功案例库
3. **可选**：产品资料、技术白皮书、历史投标文件、报价策略
4. **素材组织约定（v3.6）**：素材（招标材料、资质证书、业绩合同、简历等）放入单一文件夹一次性提供即可，无需预分类（流水线自动分轨）；勿与输出物（标书_vN.docx 等）混放
5. **知识库（推荐）**：接入IMA知识库（`ima-mcp` 连接器），将公司资料、资质证书、案例、技术方案等上传至IMA，阶段二中将自动检索并优先使用知识库中的真实素材

## 阶段〇：投标可行性预评估（v3.0 新增，v3.2 强化不可跳过约束）

> **核心价值**：决定"要不要投"比"怎么写"更重要。5分钟出结论，避免花两天写完全文才发现资质不够。

**⚠️ v3.2 硬约束（不可跳过）**：
- 即使用户开场指令是"帮我做一套投标材料"（隐含决定要投），**也必须先跑阶段〇**并输出 `00_投标可行性预评估报告.md`，由用户明确确认「继续投标」后才能进入阶段一后续流程
- 理由：用户的"决定"可能基于不完整信息——可能没注意到某个一票否决条款、可能时间不够、可能团队配置不符。阶段〇的作用是**让用户的决定基于完整信息**
- 唯一例外：用户明确说"阶段〇跳过，我已经评估过了"——此时记录用户指令后继续，但保留评估骨架在最终交付物中

**执行者**：主Agent，在解析招标文件后立即执行，不另启子Agent。

**执行时机**：阶段一·步骤2（解析提取）完成后，在进入MECE拆解之前。

**输入**：阶段一的 `01_招标要素清单.md` 中的资格条件部分 + 评分标准部分 + 时间节点部分。

**评估维度**：

| 维度 | 评估内容 | 数据来源 |
|------|---------|---------|
| **资质匹配度** | 营业执照范围是否覆盖、专业资质是否齐全、类似业绩数量是否达标、人员资格是否满足 | IMA知识库中的律所资质资料 + 用户确认 |
| **废标风险初筛** | 是否存在"一票否决"条款（如★号资格条款缺失、业绩门槛不达标等），加载 `extended-references/risk_library.md` 中的「投标准入类」模式进行比对 | 招标要素清单 + 风险库 |
| **时间压力** | 投标截止日距今的日历天数、答疑截止时间、保证金到账时限 | 招标要素清单·时间节点 |
| **竞争态势** | 评分标准中价格分占比（价格战风险）、技术分/方案分的区分度（是否有明显加分点） | 招标要素清单·评分标准 |
| **投标建议** | 综合以上四维，给出三档建议 | 主Agent综合分析 |

**三档建议**：

| 建议 | 标志 | 含义 |
|------|------|------|
| 🟢 **建议投标** | 资质全匹配 + 无硬性废标风险 + 时间充裕 + 有明确竞争优势 | 进入阶段一后续流程 |
| 🟡 **谨慎投标** | 部分资质需补充或有时间压力，但无致命风险 | 提示风险点，用户自行决定 |
| 🔴 **建议放弃** | 存在一票否决条款无法满足、或资质严重不匹配 | 列出不可逾越的障碍，节约后续投入 |

**输出产物**：`00_投标可行性预评估报告.md`，包含：
- 资质匹配矩阵（招标要求 vs 我方资质，逐项 ✅/⚠️/❌）
- 废标风险初筛结果（命中的风险模式编号 + 风险等级）
- 时间压力评估（关键节点倒计时）
- 竞争优势分析（评分标准的加减分预判）
- 最终建议及理由

**⚠️ 人工确认点 #0**：将 `00_投标可行性预评估报告.md` 呈现给用户。用户决定：
- 「继续投标」→ 进入阶段一后续流程（MECE拆解）
- 「放弃」→ 终止流程，保存预评估报告备查

> 如果用户选择「放弃」，这是**成功的放弃**——比花了两个工作日写完全文再发现废标条款有意义得多。

## 分阶段多Agent工作流

> 阶段编号说明：全流程实际为 阶段〇 → 一 → 二 → 三 → 四 → 五 → 五·B → 七 → 八 → 九（**无阶段六**，为历史版本留号；五·B 是评审后的补强子阶段；阶段九是交付后的客户档案归档）。

严格按照以下阶段流程执行，不可跳过或颠倒顺序。每个阶段的子Agent使用 `Agent` 工具（`subagent_type: "general-purpose"`）启动。

---

### 阶段一：招标解析与框架生成（总调度 Agent）

**执行者**：主Agent（当前Skill的调用者），不另启子Agent

**步骤**：

0. **读取本所专属字段（启动必做）**：在解析招标文件之前，先读取 `private/MEMORY.md`（若存在），获取：
   - 律所全称、统一社会信用代码、律所地址
   - 经办人姓名、身份证号、执业证号
   - 常用投标团队成员库（姓名 + 执业证号）
   - 历史合作但非团队成员的误放黑名单
   - 常见客户类型

   **使用规则**：
   - 上述字段优先使用本文件的值，用户当次指令覆盖本文件时以用户为准
   - 人员配置表中每位律师 ↔ 附件执业证复印件必须一一对应；黑名单内律师证书不得放入附件
   - 本文件只存本地，`private/` 目录已被 skillhub CLI 排除，发布时不会泄露
   - 如果用户明确告知"换律所"或"本次团队成员是 X、Y、Z"，相应更新本文件后继续

1. **读取招标文件**：若用户未提供，主动询问。支持 PDF/DOCX/Markdown/纯文本。
2. **解析提取**：输出结构化的「招标要素清单」，包含：
   - 资格条件：营业执照、资质证书、业绩要求、人员要求、财务要求
   - 技术参数：产品/服务的技术指标、性能要求、标准规范
   - 商务条款：付款方式、交付期限、质保要求、知识产权、违约责任
   - 评分标准：技术分/商务分/价格分权重、各评分项及分值（此为后续章节Brief核心输入）
   - 提交要求：文件组成、格式规范、装订要求、电子版要求
   - 时间节点：投标截止时间、答疑时间、开标时间、保证金截止时间
   - 实质性条款：标注★号条款或"必须满足"条款
   - **v3.1新增：自定义废标条款**：从招标文件中提取所有含"无效""废标""否决""不予受理""不通过"等关键词的条款原文，作为风险库的补充输入
3. **模板自动识别（v3.1新增）**：在人工标注 [模板]/[自由] 之前，先执行自动化规则扫描：
   - **规则A：表格特征检测** — 扫描招标文件中所有含表格的页面，提取表格列数和表头文字。如果一个页面包含 ≥3 列且表头含"序号/名称/..."等关键字，标记为候选 [模板] 章节
   - **规则B：签章空位检测** — 扫描含"（签字）""（盖章）""（签字或盖章）""授权代表"等关键字的段落，标记所在章节为候选 [模板] 章节
   - **规则C：承诺书/声明类检测** — 扫描含"我方承诺""郑重承诺""特此声明""郑重声明"等固定句式开头的段落，标记所在章节为候选 [模板] 章节
   - **规则D：偏离表检测** — 扫描含"偏离情况""偏离说明""正偏离/负偏离"等偏离表专用列的表格，标记为候选 [模板] 章节
   - 自动检测完成后，输出「模板自动识别结果」供人工确认（标注置信度：高/中/低）。**置信度为"高"的自动标注，人工仅需审核"中"和"低"的候选**
4. **加载 `references/policy_checklist.md`**，执行政策合规预检，输出「政策合规检查报告」（通过/不通过/需补充 + 修复建议）。
5. **加载 `extended-references/risk_library.md`**（v3.0新增），执行法务废标风险初筛：
   - 解析招标文件中的形式要件（签字/盖章/密封/装订/正副本/电子版/授权）
   - 逐条比对风险库中的法务/服务类废标模式
   - **v3.1新增：合并步骤2提取的自定义废标条款**，将其作为风险扫描的补充范围（冠以 "CUSTOM-" 编号前缀以区分风险库内置模式）
   - 输出「废标风险初筛报告」（风险命中清单 + 规避建议），嵌入 `02_政策合规检查报告.md` 末尾
6. **MECE拆解**：按评分标准将标书拆解为N个独立章节（1章 = 1个评分维度的完整响应），确保章节间无重叠、无遗漏。**v3.1更新：合并人工标注与自动识别结果，对每个章节标注类型 [模板] 或 [自由]**
7. **生成章节Brief**：每个章节一份Brief，包含：
   - **章节类型标注**（[模板] 或 [自由]，标注来源：人工/自动-高置信度/自动-未确认）
   - 本章覆盖的招标条款编号及原文
   - 本章在评分体系中的分值及权重
   - **[模板]章节**：列出模板段落范围（如 P371-P393）、表格列数（如 6列）、签章空位要求
   - **[自由]章节**：必须产出的内容要素（字数下限 + 图表要求 + 表格要求 + 事实/数据引用点）
   - 需要加载的reference文件名
8. **生成响应矩阵草稿**：条款→响应章节映射，标注各条款类型（强制性/推荐性/隐含性）。

**阶段一产出物**：
- `01_招标要素清单.md`
- `02_政策合规检查报告.md`
- `03_章节Brief汇总.md`（含N个章节Brief）
- `04_响应矩阵草稿.md`

**⚠️ 人工确认点 #1**：阶段一完成后，必须将以上4个文件呈现给用户审核，等待用户确认「y 继续」或「n 修改框架」后再进入阶段二。框架确认前不得启动任何章节编写。

### 阶段二：知识库驱动并行章节编写（4个子阶段）

阶段二从「纯AI凭空生成」升级为「IMA知识库优先 → AI补全 → 人工确认」三阶梯模式。分为 A/B/C/D 四个子阶段。

#### 前置条件

**IMA知识库连接器**（`ima-mcp`）需在 WorkBuddy 中连接并授权。若未连接，阶段二·A 将自动回退为「全量AI生成 + 人工确认」模式。

**相关工具（连接后可用）**：
- `mcp__ima-mcp__search_knowledge`：按关键词搜索知识库中的文档/条目
- `mcp__ima-mcp__get_document`：获取知识库中某篇文档的完整内容
- `mcp__lexiang__search_kb_search`（乐享知识库，备选）：当 IMA 不可用时尝试使用乐享知识库

---

#### 阶段二·A：IMA知识库预检索（主Agent）

**执行者**：主Agent（不另启子Agent）

**目的**：在启动章节编写Agent前，先对每个章节Brief的关键词在IMA知识库中检索，获取已有的公司资料、技术方案、案例等真实素材。

**步骤**：

1. **提取检索关键词**：从每个章节Brief中提取3~5组检索关键词。
   - 示例：章节"MES系统详细技术方案" → 关键词：「MES 制造执行系统」「某制造企业」「数字化车间」「电子制造MES」「生产排程 APS」
2. **并行检索**：对每个章节的每组关键词，调用IMA知识库搜索工具。
   - 若 `ima-mcp` 已连接：使用 `mcp__ima-mcp__search_knowledge` 搜索
   - 若 `ima-mcp` 未连接：尝试使用 `mcp__lexiang__search_kb_search`（乐享知识库作为备选）
   - 若两者均不可用：标记为「知识库不可用，全部内容将由AI生成」
3. **结果归类**：将检索结果按章节归类，标注每条结果的来源（IMA/乐享/无）、相关度（高/中/低）、内容摘要。
4. **生成检索报告**：输出 `05_IMA检索结果汇总.md`，包含：
   - 每个章节的检索关键词
   - 每类关键词的命中数量
   - 每条命中结果的内容摘要与来源链接
   - **内容覆盖度评估**：该章节已有知识的覆盖率（高≥70% / 中40~70% / 低<40%）

**阶段二·A产出物**：`05_IMA检索结果汇总.md`

**回退逻辑**：
- 若 IMA/乐享均不可用 → 该报告中标注「知识库不可用，全部内容由AI生成」
- 若部分章节有命中、部分无 → 各章节分别标注，命中章节优先使用知识库素材，未命中章节AI全量生成

---

#### 阶段二·B：知识库优先的并行章节编写（N个章节编写 Agent）

**执行者**：N个子Agent，使用 `Agent` 工具并行启动

**编排规则**：
- 每个章节一个Agent，所有Agent并行启动
- 每个Agent的prompt必须包含：该章节的完整Brief + IMA检索结果 + 指定加载的reference文件路径 + 公司/项目上下文
- 总调度需创建N个 `TaskCreate` 追踪每个章节进度

**Agent Prompt 模板**：见 `extended-references/agent_prompts.md` 之「阶段二·B 章节编写 Agent」。

**编写质量标准**（每个章节Agent必须遵守）：
- **字数底线**：每个章节正文≥3000字（纯中文文字，不含代码块和图表）
- **图表要求**：每个章节至少1张 Excalidraw 图
- **表格要求**：每个章节至少1张表格
- **事实引用**：每个技术/商务论点必须有数据/标准/案例支撑，优先引用IMA素材
- **逐条响应**：Brief中的每条招标条款必须有独立段落响应
- **溯源标记**：所有AI生成段落必须用 `<!-- AI_GENERATED: ... -->` 标记

**阶段二·B产出物**：N个 `ch_N_章节名.md` 文件（含AI_GENERATED标记）

---

#### 阶段二·C：AI生成内容清单与人工确认

**执行者**：主Agent

**目的**：将每个章节中所有 `<!-- AI_GENERATED -->` 标记的段落汇总成清单，提交用户审核。这是阶段二内部的人工确认点。

**步骤**：

1. **扫描提取**：遍历所有 `ch_N_章节名.md` 文件，提取所有 `<!-- AI_GENERATED: ... -->` 标记段落。
2. **生成清单**：输出 `06_AI生成内容清单.md`，包含：
   - 总体统计：总段落数 / IMA命中段落数 / AI生成段落数 / AI生成占比
   - 按章节逐个列出AI生成段落：
     - 所在章节及行号
     - 段落主题
     - 生成依据（从标记中提取）
     - 段落前100字预览
     - 置信度评估（高/中/低）
   - 风险提示：标注哪些AI生成段落属于P0/P1级别（涉及核心技术参数、公司数据、报价等）
3. **输出内容覆盖率报告**：

| 章节 | IMA命中率 | AI生成占比 | P0级AI段落 | 风险等级 |
|------|:--------:|:--------:|:---------:|:------:|
| 章节一 | 45% | 55% | 2 | ⚠️ 中 |
| ... | ... | ... | ... | ... |

**⚠️ 人工确认点 #1.5**（阶段二内部）：将 `06_AI生成内容清单.md` 呈现给用户。用户审核后：
- 「全部确认」→ 移除所有 `<!-- AI_GENERATED -->` 标记，进入阶段二·D 定稿
- 「指定修改」→ 用户指出需要修改的具体段落编号，主Agent重新生成这些段落（仅重新生成指定段落，已确认段落保留）
- 「全部重写」→ 用户提供补充资料后，重新执行阶段二·B

**阶段二·C产出物**：`06_AI生成内容清单.md`

---

#### 阶段二·D：定稿输出

**执行者**：主Agent

**步骤**：
1. 用户确认所有AI生成段落后，移除所有章节文件中的 `<!-- AI_GENERATED: ... -->` 标记
2. 更新 `05_IMA检索结果汇总.md`，在每条检索结果的末尾标注「已采用至第X章第Y节」
3. 生成最终章节文件（命名格式统一为 `章节N_标题.md`）

**阶段二·D产出物**：
- N个 `章节N_标题.md`（定稿版，已移除所有AI_GENERATED标记）
- `05_IMA检索结果汇总.md`（更新版，含采用追踪）

---

#### IMA不可用时的完整回退流程

当 `ima-mcp` 和 `mcp__lexiang__*` 均不可用时：

1. **阶段二·A** 直接输出 `05_IMA检索结果汇总.md`，标注「知识库不可用，全部内容由AI生成」
2. **阶段二·B** 正常启动N个章节编写Agent，所有段落均标记为 `<!-- AI_GENERATED: 知识库不可用时AI全量生成 -->`
3. **阶段二·C** 的 `06_AI生成内容清单.md` 将显示 **AI生成占比100%**，逐章列出所有段落等待确认
4. **阶段二·D** 同样执行——用户确认所有段落后移除标记，定稿输出

> **注意**：IMA不可用时，人工确认的工作量会显著增加（因为100%内容都需审核）。建议用户尽量在投标前将公司资料（简介、资质、案例、技术白皮书等）上传至IMA知识库，以降低AI生成比例。

### 阶段三：模板/自由双轨合稿（主Agent 执行）

**v2.2 重要变更**：阶段三不再由单独的子Agent执行，**由主Agent直接执行**。原因：模板填空需要精确对照招标文件原文，子Agent的独立上下文会丢失模板细节。主Agent持有完整的招标文件解析结果，可以逐字逐格对齐。

**执行者**：主Agent

**双轨合稿规则**：

```
对每个章节，根据阶段一标注的 [模板] / [自由] 类型，走不同轨道：

轨道A [模板] 章节：
  0. ⚠️ v3.7.3 前置分支：四步拷贝法的前提是招标方提供了**可编辑 docx / 文本型 PDF** 模板。
     若模板只有扫描件 PDF（无文本层）→ 先用 OCR 重建模板文本，再走下述流程；
     重建的模板必须人工逐字核对原文后方可作为填空基准（OCR 错字=填空基准就错了）。
  1. 从招标文件第五章提取该章节的模板原文（段落、表格结构、签章空位）
  2. 将模板原文作为基准，不在上面"重写"——只做"填空"
  3. ⚠️ v3.4 硬约束：模板原文进入标书**唯一的**技术路径是【四步拷贝法】。
     禁止 add_paragraph 仿写模板（必丢格式），禁止裸 deepcopy（编号消失、字体回退）。
     ⚠️ v3.7.2 起，**必须调用 `scripts/clone_template_section.py` 执行四步拷贝**（段落 deepcopy、numbering remap、字体扁平化、pStyle 清理均由脚本完成，特征句唯一性校验防拷错），禁止临场写 Python 代码替代。算法细节见该脚本 docstring 和 references/docx_engineering.md 第五节。
  4. 占位符替换：把（供应商名称）、（项目名称）、（大写）等替换为实际数据
  5. 签章行留白：供应商签字、法定代表人签字、日期——全部保留空白供手签
  6. 表格复制：模板几列就是几列，模板什么表头就是什么表头
  7. 标点符号：保留模板中的中文标点（、。「」），不得替换为英文标点
  8. 填空完成后必须重新渲染该章节逐页目检（占位空格按空白设计，填实数据会折行断字）

轨道B [自由] 章节：
  1. 从阶段二·D产出的《章节N_标题.md》中读取内容
  2. ⚠️ v3.8.0 起，**必须调用 `scripts/md_to_docx.py` 执行 Markdown→DOCX 转换**（pandoc 结构转换 + python-docx 后处理统一宋体小四/1.5倍行距），禁止临场写 pandoc/python 代码替代。支持批量单命令转换多文件
  3. 流程图/架构图通过 `excalidraw-diagram` skill 生成 PNG 后插入 .docx
  4. 字体统一为小四宋体、1.5倍行距
```

**合稿顺序与目录结构规则（v3.6 重写——优先级链）**：

1. **招标文件规定了响应文件组成与顺序** → 严格按它（合规优先，废标条款常挂在这）
2. 未规定组成顺序但**有评分标准** → 技术文件部分按评分标准评分项顺序组织（方便评委对照打分）；资格证明、投标函等非评分项仍按常规顺序置前——"按评分标准建目录"仅适用于技术文件部分
3. 两者都无 → 借用招标文件中任何像目录的结构线索；用户提供的参考目录（如历史项目目录）仅作参考，一律以当次招标文件为准
4. 优先级：合规 > 评委友好 > 参考模板。评委便利永远不能凌驾于格式合规

**章节合并与子标题规则（v3.2 新增）**：
- 含多类业务的章节（如"为选聘方提供法律服务情况"含诉讼 + 常法 + 专项），必须用三级子标题区分业务类型（Heading 3：诉讼代理 / 常年法律顾问 / 专项法律服务）

### 同类项目一览表处理规则（v3.2 新增）

> **背景**：法务标书实战中发现，同类项目一览表是评分项（通常 ≥ 9 分），但业绩合同扫描件的处理方式有两种路径。

**两路径判断**：

| 条件 | 路径 | 操作 |
|------|------|------|
| 用户已提供同类项目一览表扫描件（PDF） | **路径A：直接插入** | 将 PDF 扫描件直接插入对应章节，不做额外处理 |
| 用户未提供一览表，但有业绩合同 PDF | **路径B：从合同首页提取** | 读取每份合同的第一页，提取关键信息，按标准表格呈现 |

**路径B 详细操作**：

1. **首页+末页双读（v3.6 修正）**：对每份业绩合同 PDF，打开第 1 页（判类型、合同名称、甲方）**和最后 1 页**（签订时间、盖章完整性几乎必在末页签章处——评分细则"时间以合同签订时间为准"，只读首页抓不到），提取文本内容
2. **提取关键字段**：
   - 合同名称（通常出现在合同标题位置）
   - 合同甲方（委托方/采购方名称）
   - 合同签订时间（签署日期）
   - 合同主要内容（合同第一条/服务范围段落）
3. **生成表格**，按以下表头排列：

| 序号 | 合同名称 | 合同甲方 | 合同时间 | 合同主要内容 |
|:---:|------|--------|----------|------------|
| 1 | {提取的合同名称} | {甲方名称} | {签署日期} | {服务范围摘要} |
| ... | ... | ... | ... | ... |

4. **信息不确定标记**：如果某个字段无法从合同首页确认（如甲方名称不明确、日期格式异常等），在单元格中标注 `⚠️ 需人工确认`，不猜测填写
5. **如合同扫描件不清晰导致无法识别文字**：用 PyMuPDF (fitz) 渲染首页为高 DPI 图片供人工查看，不强行提取
6. **表格后留空行**：「注：以上业绩信息来源于合同首页，详细信息以合同全文为准。」

**注意事项**：
- 同类项目一览表的目标是**让评委快速核对业绩数量和内容**，不要过度提取（≥5 个字段会导致表格太宽看不清）
- 合同首页提取优先使用 PyMuPDF 读取文本层；无文本层（扫描件）时使用 `pdf-add-text-layer` skill 先 OCR 再提取
- 如果提取的合同名称与招标文件要求的"同类项目"定义不符，标注 `⚠️ 需确认是否为同类业绩`

**执行者**：1个子Agent，使用 `Agent` 工具启动

**八道硬门槛一览**（详细检查标准由质检Agent加载 `references/format_checklist.md` 获取）：

字数≥3000/章 · 图表每章≥1（Excalidraw） · 表格每章≥1 · 事实核查零模糊词 · 格式规范 · 废标风险库复检 · 业务结构与团队边界 · 文档块唯一性与目录纯净度

**打回处理流程**（v3.1更新：增加自动修复能力）：

质检不通过时，按问题类别分两条路径处理：

**路径A：自动修复（格式类风险，v3.1新增）**

以下类别的风险命中，由主Agent自动修复而非打回阶段二：

| 风险类别 | 自动修复方式 | 示例 |
|---------|------------|------|
| 表格列数偏差（B13） | 使用 python-docx 重写表格，严格按模板列数生成 | 偏离表5列→自动补齐到5列 |
| 标点符号替换（B14） | 全文查找替换：英文标点→中文标点（仅限模板章节） | "5." → "5、"、"——"→"——" |

| 签章行预填（B07/E01-E05） | 清空签章行文本，保留空白供手签 | 删除预填文字 |

**自动修复流程**：
1. 质检 Agent 输出 `质检报告.md` 时，对可自动修复项标注 `[AUTO-FIX]` 标记
2. ⚠️ v3.8.0 起，**必须调用 `scripts/auto_fixer.py` 执行全部自动修复**（8 项修复由脚本统一执行，支持 `--dry-run` 预览 + `--all` 一键跑），禁止主Agent逐项临场写 Python 代码
3. 修复后的标书另存为 `标书_v1_fixed.docx`，附带自动修复报告
4. 主Agent对修复后的标书重新执行阶段四质检（仅检查不可自动修复的门槛：门槛1/4 中不可量化部分）

**路径B：人工修复（内容类风险，走传统打回流程）**

| 风险类别 | 原因不自动修复 | 修复方式 |
|---------|------------|---------|
| 承诺书文字被改写（B15） | 涉及语义，AI 无法判断原文 | 打回阶段二，人工对照模板逐字修改 |
| **报价类风险（D01-D06）** | 数值人工定 / 格式 Agent 适配 / 一致性机器审 | ⚠️ v3.7.2 价格处理三段铁律：① **数值由用户人工确定**——DATA 字典里的总价、分项金额、限价对照值全部由用户在投标启动时亲自录入，Agent 不得改数值；② **格式由 Agent 按招标文件要求适配**——如招标要求"大小写并列"就组装成「人民币壹拾万元整（¥100000.00）」、要求 2 位小数就补齐、要求标注币种就加；③ **适配完成后必须调用 `scripts/price_validator.py` 审一遍**——覆盖 D01 大小写一致、D02 分项合计=总价、D03 不超限价、D04 单位一致、D05 小数位、D06 币种标注。**审出的不一致问题 Agent 不得自动修复，必须把报告提交用户确认后再改** |
| 资质证书过期（C01-C06） | 涉及真实业务状态 | 标记风险，用户自行确认和补充 |
| 内容类覆盖不足 | 需要新增章节和内容 | 打回阶段二·B，对应章节Agent重写 |

### 阶段五：五维并行评审（评审Agent A~E，v3.2 强化不可省略约束）

**⚡ 自动执行原则（v3.6.1）**：质检通过即自动进入评审，**无需用户指令**；任何标书类交付物（初稿/修改稿/大修后版本）提交用户前必须已过质检+评审。若本轮对话对交付版做了实质修改而未重审，主Agent交付前必须**主动说明并补跑**——用户没想起来，不是不跑的理由；正确做法是先跑再交，或明确告知"本次修改尚未重审，是否现在补跑"。

**⚠️ v3.2 硬约束（不可省略）**：
- 交付 PDF 前**必须**跑完五维并行评审，输出 5 份评审报告 + 加权总分 + P0/P1/P2 问题清单
- **用户不得承担评审Agent的职责**——不能靠用户的对抗性反馈来替代系统化评审
- 理由（来自 v3.2 实战教训）：本次实战跳过阶段五，靠用户逐条指出"目录没页码""诉讼常法混了""误放张景旭证书""服务方案过短"——这些问题本该由评审 A（完整性）和评审 E（评分博弈）提前发现。跳过阶段五的代价是用户时间成本 + 9 轮迭代 + 用户体验极差
- 评分细则未公开时：评审 E 改为"按公告侧重推断评分维度"模式，不可跳过；评审 A/B/C/D 不依赖评分细则，必须正常跑
- 唯一例外：用户明确说"阶段五跳过，我自己审"——此时记录用户指令后继续，但不作为默认行为

**执行者**：5个子Agent（评审A~E），使用 `Agent` 工具**并行启动**

**前置条件**：阶段四质检通过

**评审角色定义**：

| 评审 | 视角 | 权重 | 核心审查内容 |
|------|------|------|-------------|
| **评审A** | 完整性评审 | 20% | 招标文件每条要求是否被覆盖、章节是否遗漏、响应矩阵是否完整 |
| **评审B** | 技术深度评审 | 25% | 技术方案专业性、架构合理性、参数响应准确性、创新性与差异化 |
| **评审C** | 商务竞争力评审 | 15% | 报价竞争力、商务条款合理性、售后承诺可靠性、业绩匹配度 |
| **评审D** | 语言与规范评审 | 10% | 文字表达规范性、逻辑清晰度、专业术语准确性、排版一致性 |
| **评审E** | 评分博弈评审 | 30% | 从评委视角模拟打分：逐条按评分标准打分，识别失分风险和加分机会 |

**评审Agent Prompt 模板**：见 `extended-references/agent_prompts.md` 之「阶段五 评审 Agent」。

**各评审Agent均需加载**：`extended-references/review_checklist.md`（评审标准与得分规则）

**评审产出物**：
- `评审A_完整性评审报告.md`
- `评审B_技术深度评审报告.md`
- `评审C_商务竞争力评审报告.md`
- `评审D_语言规范评审报告.md`
- `评审E_评分博弈评审报告.md`

**加权总分计算**：
```
总分 = 评审A得分×20% + 评审B得分×25% + 评审C得分×15% + 评审D得分×10% + 评审E得分×30%
```

**P0/P1/P2分级汇总**：主Agent汇总5份评审报告中所有问题，合并去重，按P0/P1/P2分级列出。

**⚠️ 人工确认点 #2**：阶段五完成后，将5份评审报告+加权总分+P0/P1/P2问题清单呈现给用户。用户决定：

### 阶段五·B：评分项闭环补强 PDCA-Act（v3.0 新增）

> **核心理念**：竞品（红点智标、数匠云、钛投标）的"闭环整改"停在输出整改方案，本工具直接把补强段落落稿——PDCA 的 Act 不够，才是真的闭环。

**执行者**：主Agent（不另启子Agent）。原因：补强段落的注入需要精确知道每个章节的原始位置，子Agent的独立上下文无法做到。

**前置条件**：阶段五评审完成，用户选择「n 再改」或加权总分 < 95。

**执行流程**：

#### 步骤 1：评分项覆盖度诊断

对每个评分项，检查其在生成稿中的覆盖状态：

| 覆盖状态 | 判断标准 | 处理方式 |
|---------|---------|---------|
| ✅ 已覆盖 | 成稿中有独立章节/段落明确响应，且内容充分（≥300字/评分项） | 跳过，标注"已充分响应" |
| ⚠️ 弱覆盖 | 成稿中有响应但内容单薄（<300字/评分项），或仅一笔带过 | **自动生成补强段落** |
| ❌ 未覆盖 | 成稿中无任何响应 | **自动生成补强段落**（最高优先级） |

**重要排除规则**：以下两张"元表格"不计入覆盖度判断，避免干扰：
- 「评分项响应保障表」（阶段三合稿生成的附录表）
- 「资质业绩响应表」（资格证明章节）

#### 步骤 2：补强段落生成

对弱覆盖/未覆盖的评分项，按类别消费知识库生成补强段落：

| 评分项类别 | 补强素材来源 | 示例（法务标书） |
|-----------|------------|----------------|
| 业绩类 | IMA知识库：律所类似项目案例 | "我方过去三年为 XX 家政府单位提供法律顾问服务，近三年处理行政诉讼案件 XX 件..." |
| 人员类 | IMA知识库：律师简历/CV | "张律师具有 XX 年执业经验，曾代理 XX 案件..." |
| 资质类 | IMA知识库：律所资质证书 | "本所持有 XX 资质，具备 XX 领域专业服务能力..." |
| 方案类 | AI生成 + 行业知识 | 补充服务方案中缺失的子模块（如"信息化管理方案"） |
| 服务承诺类 | AI生成 + 报价数据 | 补充响应时间承诺、服务质量指标等量化数据 |

**补强段落质量要求**：
- 每段 ≥ 200字，有量化数据支撑（禁用"可能""大概""也许"）
- 与原始成稿风格一致（保持章节语言风格和编号体系）
- 标注来源：`<!-- REINFORCE: 基于IMA素材「{来源文档名}」生成 -->` 或 `<!-- REINFORCE: AI辅助生成，基于{行业/领域}知识，需人工确认 -->`

#### 步骤 3：补强段落注入成稿

1. 将每个补强段落插入到对应章节中评分项响应位置的末尾
2. 在docx中使用「修订模式」标记新注入内容（蓝色文字 + 批注标注来源），方便人工识别审阅
3. 为每个注入的段落保留 `<!-- REINFORCE: ... -->` 标记，与阶段二的 `<!-- AI_GENERATED: ... -->` 标记格式一致

#### 步骤 4：生成补强闭环审计报告

产出 `评分项补强闭环报告.md`，包含：

| 评分项编号 | 原始覆盖状态 | 补强后状态 | 补强段落字数 | 素材来源 | 置信度 |
|:---:|:---:|:---:|:---:|------|:---:|
| 技术分-1 | ⚠️ 弱覆盖 | ✅ 已补强 | 350字 | IMA-案例库 | 高 |
| 技术分-3 | ❌ 未覆盖 | ✅ 已补强 | 420字 | AI生成 | 中 |
| ... | ... | ... | ... | ... | ... |

以及：
- **补强前后评分预估对比**：模拟补强前得分 vs 补强后预估得分
- **零遗漏审计结论**：所有评分项是否均已覆盖（已覆盖/已补强覆盖/仍待人工补充）
- **⚠️ 需人工确认的补强段落清单**（置信度 ≤ 中 的段落）

#### 步骤 5：补强后稿输出

输出 `标书_v1_reinforced.docx`（含修订模式标记的补强段落）。

**⚠️ 人工确认点 #2.5**：将「评分项补强闭环报告」呈现给用户。用户审核每个补强段落：
- 「全部接受」→ 移除修订标记 + AI标记 → 进入阶段七
- 「逐条审核」→ 用户逐条确认/修改补强段落 → 进入阶段七
- 「仅接受高置信度」→ 自动接受置信度为"高"的段落，其余进入阶段七人工修改

**阶段五·B产出物**：
- `标书_v1_reinforced.docx`（含修订标记的补强版）
- `评分项补强闭环报告.md`
- `07_补强后评分项覆盖矩阵.md`（score-response matrix，所有评分项 × 覆盖状态）

### 阶段七：修改与迭代（修改 Agent）

**执行者**：1个子Agent，使用 `Agent` 工具启动

**Agent Prompt 模板**：见 `extended-references/agent_prompts.md` 之「阶段七 修改 Agent」。

**迭代循环规则**：
1. 阶段七输出 `标书_vN.docx`（N=当前轮数+1）
2. 新版本重新进入阶段四（质检）→ 阶段五（评审）→ 阶段五·B（补强）
3. 迭代最多**3轮**（即最多输出v4）

**已合稿 docx 的精准修改轨（v3.4 新增）**：

用户对手头这份 docx 提的局部修改（改封面、换投标函、调某个章节），**不得重新生成全文**——重新生成会丢失用户在 Word 里的手工调整和既往修复。标准操作轨：

1. **备份**：`cp 标书_交付版.docx 备份_时间戳.docx`
2. **定位**：用特征句全文搜索定位目标块（确认唯一，警惕残留旧块）
3. **精准修补**：python-docx 按段落/run 级修改；涉及跨文档拷模板内容时**必须调用 `scripts/clone_template_section.py`**（同阶段三轨道A，禁止临场写代码）
4. **渲染验证**：LibreOffice 转 PDF 逐页目检改动区域（LibreOffice 仅作目检，不作交付转换器）
5. **只交付 docx**，等用户确认后才出 PDF（Word-first 铁律对迭代同样适用）

**阶段七产出物**：`标书_vN.docx`（N≥2）

## 迭代终止逻辑

满足以下**任一**条件即终止迭代，输出最终交付版：

| 条件 | 说明 |
|------|------|
| 加权总分 ≥ 95分 | 质量达标，直接交付 |

## 质量标准（全流程守则）

- **零遗漏**：响应矩阵必须覆盖招标文件每一条要求
- **零模糊**：禁用"可能""大概""也许""应该""左右"等不确定用语
- **零雷同**：严禁使用通用模板直接套用，必须贴合客户行业和具体需求
- **零幻觉**：事实性内容（资质、业绩、时限、数据、案例）**必须**来自源头（素材库/简历/招标文件），优先从IMA知识库检索；论述性内容（方案结构阐述、差异化卖点表达）允许 AI 生成但**必须**标注「AI辅助生成，需人工核实」，阶段二·C中集中审核确认
- **必确认**：证书编号、报价金额、签章要求、授权有效期、案例合同号——标注「⚠️ 需人工确认」
- **可视化**：流程/架构图用 Excalidraw 生成，进度计划用甘特图，数据对比用表格
- **一致性**：同一数据在全文中出现必须一致（报价、人员姓名、时间、编号）
- **事实源唯一（v3.5.1）**：人员资质必须逐字来自其简历/人员档案（正文描述 ⊆ 简历），时限/频次等叙述性事实从 facts 字典取值；模板数据与正文事实分开建典，质检执行程序化交叉验证（见 format_checklist.md 门槛4）
- **修改后必重审（v3.5.1）**：任何对交付版的实质修改（换章节、改数据）完成后，必须重跑阶段四质检+阶段五评审；精准修补不等于免检——曾发生修补后未重审，授权代表口径、资质矛盾等问题直到用户质疑才暴露

## 执行注意事项

### 并行编排规则
- **阶段二**：N个章节编写Agent必须**同时并行启动**（一次 `Agent` 工具调用中发送N个），不得串行逐个启动
- **阶段五**：5个评审Agent必须**同时并行启动**，不得串行逐个启动
- 启动前确保所有前置文件已就绪，避免Agent之间的文件依赖

#### 并发限流降级（429 fallback，v3.2.1 新增）
**并行是首选**——能力足够的模型/套餐都能跑满并行。但当底层模型 API 对单账号同一时刻的并发推理请求有限额时，一次性发起多个 subagent 会触发 **HTTP 429 Too Many Requests**。注意区分错误来源：
- 若 Agent 工具返回的是业务上限错误（如"超过最大并发数"）→ 那是 Agent 工具层的硬限制，按提示的限额执行
- 若返回的是 **429** → 来自底层模型 API 的速率限制，不是 Agent 工具禁止并行；此时按下面的降级策略处理

**降级策略（自动，无需询问用户）**：
1. 第一次尝试：按原计划**全部并行启动**（阶段二 N 个 / 阶段五 5 个）
2. 收到 429 → **分批降级**：先启动前 4 个并行，等这批完成后启动剩余的（每批 ≤ 4 个并发）
3. 分批仍 429 → **全串行**：一次只启动一个 Agent，完成后再启动下一个
4. 不要因为一次 429 就默认改为串行写进 skill——并行是默认推荐，降级只在实战遇到限流时触发

这条规则适用于所有需要并行启动多个 Agent 的阶段（阶段二、阶段五、阶段九）。

### Agent上下文管理
- 每个章节编写Agent拥有独立上下文，互不干扰
- 编写Agent不依赖其他章节内容，完全基于本章Brief工作
- 合稿Agent负责解决章节间的交叉引用和一致性

### 错误处理
- 任一章节编写Agent超时或失败 → 重新启动该Agent（不重跑成功的Agent）
- 阶段四质检不通过 → 仅打回不通过的章节编写Agent，通过的保留
- 连续2次打回同一章节 → 主Agent介入分析原因，调整Brief后重试

### 资源加载
- 各Agent按需加载references/下的参考文档，不提前全量加载
- **阶段〇**：加载 `extended-references/risk_library.md` 中的「投标准入类」模式（v3.0新增）
- **阶段一·步骤4**：加载 `extended-references/risk_library.md` 全量模式库（v3.0新增）
- **阶段二·A前**：主Agent需先检查 `ima-mcp` 连接状态。若已连接，使用 `mcp__ima-mcp__*` 系列工具检索知识库；若未连接，尝试 `mcp__lexiang__*` 作为备选
- **阶段二·B**（v3.1新增）：法务标书时，章节编写Agent加载 `extended-references/legal_service_proposal_guide.md` 对应模块作为编写规范
- **合稿（主Agent，阶段三）**：加载 `references/docx_engineering.md` + `references/format_checklist.md`；结构参考已废除（标书结构以当次招标文件为准）

## 快速启动示例

用户说「帮我写XX项目的投标文件」，主Agent的执行序列：

1. 确认招标文件已提供
2. **执行阶段〇**（v3.0新增）：解析招标文件 → 资质匹配预检 + 风险初筛 → 输出 `00_投标可行性预评估报告.md` → 等待用户确认「继续」/「放弃」
3. 用户确认继续 → 执行阶段一（招标解析+政策预检+风险库扫描+MECE拆解+章节Brief）
4. 输出4份文件 → 等待用户确认（确认点#1）
5. 用户确认后 → 执行阶段二·A（IMA知识库预检索）→ 输出 `05_IMA检索结果汇总.md`
6. 并行启动N个章节编写Agent（阶段二·B，知识库优先）→ 输出含溯源标记的章节初稿
7. 扫描提取所有AI生成段落 → 生成 `06_AI生成内容清单.md` → 等待用户确认（确认点#1.5）
8. 用户确认后 → 移除AI标记 → 定稿章节文件（阶段二·D）
9. 执行阶段三（模板/自由双轨合稿）→ 输出标书v1
10. **自动流转，不等用户指令**：合稿完成 → 自动质检（八道硬门槛，含风险库复检）→ 质检通过自动并行启动5个评审Agent（阶段五）→ 加权计分
11. 输出评审汇总 → 等待用户确认（确认点#2）
12. 用户选择「交付」→ 格式终审 → 输出交付版
13. 用户选择「再改」→ **进入阶段五·B（v3.0新增）：评分项闭环补强PDCA-Act** → 诊断覆盖度 → 生成补强段落 → 修订模式注入成稿 → 输出补强闭环报告 → 等待用户确认（确认点#2.5）
14. 进入阶段七（修改迭代）→ 回到步骤10
15. **执行阶段八（v3.1新增）：PDF拼合与交付组装** → 生成插入清单JSON → DOCX转PDF → 按目录拼合 → 页码校验 → 等待用户确认（确认点#3）→ 输出 `投标文件_完整版.pdf`
16. **执行阶段九（v3.2新增）：客户档案沉淀（必做）** → 更新 `private/clients/{客户名}.md` + 索引（见下）

### 阶段九：客户档案沉淀（v3.2 新增）

**定位**：投标项目交付后，把本次积累的客户情报、招标偏好、服务方案匹配点、踩过的坑全部沉淀到 `private/clients/` 目录，形成**可复利的客户资产**。

**核心理念**（第一性原理）：每次投标不应该从零开始。同一个客户下次再招标、同类客户横向迁移，都应该站在上次肩膀上。把"投标过的客户"变成资产，让"投标次数"产生复利。

**执行者**：主Agent（当前Skill的调用者）

**前置条件**：阶段八已交付最终 PDF，用户确认项目完结。

### 步骤 1：读取或新建客户档案

```
private/clients/
├── _index.md              # 客户索引（按客户类型分组）
└── {客户简称}.md          # 每个客户一个档案
```

- 若 `private/clients/{客户名}.md` 已存在 → 读取已有档案，本次内容并入（追加历史投标记录、更新偏好、补充注意事项）
- 若不存在 → 新建客户档案，按下方模板填充

### 步骤 2：客户档案六要素

每个客户档案必须包含以下六部分：

#### 一、基础画像
- 客户全称、类型（政府机关 / 国企 / 跨境电商 / 外商投资 / 其他）
- 主管单位、所在地、主要职能
- 招标频率（如"法律顾问单位公开选聘每 1-2 年一次"）

#### 二、招标偏好（从本次招标文件提炼）
- 评分维度权重（技术分 / 商务分 / 价格分占比）
- 看重的特殊要求（如涉外能力、本地响应、团队能力）
- 公告关键要件（响应文件、服务方案、资质、团队、业绩、报价等）

#### 三、历史投标记录（表格）
| 时间 | 项目 | 我方团队 | 结果 | 关键文件 |

#### 四、服务方案要点（本次侧重）
- 服务模块结构（适配本客户的模块设计）
- 匹配点（本所强项如何呼应客户需求）

#### 五、注意事项 / 踩过的坑
- ✅ 本次做对的（下次保持）
- ⚠️ 本次踩的坑（下次规避）
- 💡 下次可改进的

#### 六、档案维护记录
- 每次更新时间 + 更新内容简要

### 步骤 3：更新客户索引

更新 `private/clients/_index.md`：
- 新客户 → 在对应类型分类下添加一行
- 已有客户 → 更新"最近投标"时间

### 步骤 4：提示用户确认

向用户展示更新后的客户档案，提示：
> 已把本次项目情报沉淀到 `private/clients/{客户名}.md`。下次为同一客户或同类客户投标时，阶段一会自动读取这份档案，直接复用偏好分析和方案要点。

**不需要人工确认点**（这是事后归档，不影响交付物），但应告知用户档案已更新。

### 阶段九的隐性收益

- **同客户复聘**：年度续约时直接拿上次的偏好分析 + 踩坑记录，少走 80% 弯路
- **同类横向迁移**：搜索 `private/clients/_index.md` 中同类客户（如"政府机关"分类下的所有档案），把成功经验迁移到新客户
- **团队能力地图**：长期积累后，"历史投标记录"自动汇总成团队履历库，可从中挑选最适合的人选
- **踩坑清单**：每个客户的"⚠️ 本次踩的坑"形成本所私域知识库，新人入职即可学习
