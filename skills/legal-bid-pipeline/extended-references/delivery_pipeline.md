### 步骤 2：服务方案 DOCX → PDF

**执行者**：主Agent

**⚠️ 转换引擎选择（v3.2 关键修正 — 来自贸促会投标实战教训）**：

| 引擎 | 是否更新 TOC 域 | 中文路径 | 推荐度 | 备注 |
|------|:-------------:|:--------:|:------:|------|
| **docx2pdf** | ✅ 是（基于 Word AppleScript） | ⚠️ 中文路径报错 | ⭐⭐⭐ | 默认首选，需本机装 Microsoft Word |
| **AppleScript 原生调 Word** | ✅ 是 | ✅ 支持 | ⭐⭐⭐⭐ | docx2pdf 报错时的 fallback，最稳定 |
| LibreOffice headless | ❌ **否** | ✅ 支持 | ❌ 禁用 | 目录页码与正文脱节，**不可用** |

**为什么 LibreOffice 不行**：
LibreOffice headless 转换 PDF 时**不会更新 Word 的 TOC 域**，导致目录中显示的页码是上次保存时的旧值，与正文实际页码严重脱节。生成的 PDF 目录页码全是错的，评委会无法按目录检索。

**推荐方案：docx2pdf**

```bash
# 优先方案（需先 pip install docx2pdf）
python3 -c "from docx2pdf import convert; convert('标书_vN.docx', 'output/标书_vN.pdf')"
```

**Fallback：AppleScript 原生调用 Word**（docx2pdf 中文路径报错时用）

### 步骤 2.5：展示性材料处理（v3.2 新增 — 替代"PDF 后拼合"思路）

**核心理念**：展示性材料（证件扫描件、业绩合同复印件、裁决书等）**不要在 PDF 阶段拼合**，而是**先转 JPEG 图片，在 Word 正文对应章节位置内插**。这样做的三个理由：

1. **目录页码准确**：Word 内插后，目录会自动反映附件的真实页数；PDF 后拼合则目录显示的附件页码与实际页码脱节
2. **签章位置稳定**：图片锚定在段落中，不会因后续编辑漂移
3. **打印所见即所得**：打印 PDF 时附件就在正确位置，无需人工拼合

**展示性材料 vs 字段抽取材料的分类处理**：

| 材料类型 | 典型文档 | 处理方式 | 工具 |
|---------|---------|---------|------|
| **展示性材料** | 执业证复印件、营业执照、业绩合同、裁决书、获奖证书 | 转 JPEG → PIL 压缩 → Word 正文内插 | PyMuPDF（PDF→图）+ PIL（压缩）+ python-docx（插入） |
| **字段抽取材料** | 执照编号、统一信用代码、人员证号 | OCR 提取字段 → 填入正文占位符 | OCR（见步骤 2.6） |

**⚠️ 图片体积控制硬规则**：
- 插入 Word 前**必须**用 PIL 压缩（PNG→JPG quality=85）
- 单张图片 > 2MB 必须先压缩再插入
- 本次实战教训：63 张图未压缩 = 96MB docx → Word 直接卡死无法打开；压缩后 2.7MB → 正常

**⚠️ 占位文字清理**：
找到 `本处插入XX复印件` 这类占位段落后，**删除占位文字**（图片已就位就不需要文字提示），再插入图片。否则会出现"本处插入XX复印件"+ 图片的双层冗余。

### 步骤 2.6：OCR 字段抽取（v3.2 新增 — 最小代价分类法）

**最小代价分类原则（来自贸促会投标实战教训）**：

❌ 错误做法：对所有 PDF 文件循环 OCR 全文，然后基于全文内容分类。这会导致循环依赖（分类需要 OCR，OCR 需要先分类决定处理方式）。

✅ 正确做法：**OCR 首页+末页双读（v3.6 修正）**做最小代价分类——首页判类型/名称/甲方，末页抓签订时间与盖章完整性（评分常"以合同签订时间为准"，签订日期几乎必在末页签章处，只读首页会丢关键字段）。

### 步骤 3：PDF 合并（仅合并独立 PDF 文件）

**执行者**：主Agent（使用 PyMuPDF / pypdf）

**v3.2 关键变更**：展示性材料已在步骤 2.5 以图片形式内插到 Word 正文，**不再需要在 PDF 阶段拼合**。此步骤仅处理仍需作为独立 PDF 保留的材料（如完整的业绩合同原件 PDF，部分评委可能要求查阅完整件）。

```bash
python3 scripts/pdf_assembler.py --manifest 08_插入清单.json --output 投标文件_完整版.pdf
```

`pdf_assembler.py` 的实现逻辑（v3.2 简化版）：
1. 读取 `08_插入清单.json` 中的 `toc_order`
2. 主文档 `标书_vN.pdf`（已含所有展示性材料的图片版本）作为主体
3. 如有独立 PDF 附件（可选），按 toc_order 顺序 append 到主文档后
4. 校验总页数与目录一致性

**⚠️ PyMuPDF 拼合注意**：
- `output_pdf.insert_pdf(input_pdf)` 直接嵌入，**不要**先转图片再插入（体积会暴涨，实战中曾出现 505MB 的 PDF）
- 处理 PDF 旋转方向：`page.set_rotation(0)` 确保所有页面方向一致

**产出物**：`投标文件_完整版.pdf`

### 步骤 4：页码与目录校验

**执行者**：主Agent

1. 打开 `投标文件_完整版.pdf`，核对总页数
2. 逐章核对页码范围是否与插入清单一致
3. 核对：封面无页码、目录页使用独立页码、正文从第1页开始

**产出物**：`页码校验报告.md`

### 步骤 5：最终完整性检查

对照风险库做最后一轮完整性扫描：
- 文件清单是否齐全（对照 `04_响应矩阵草稿.md` 的附件清单）
- 签章页是否均在位（无遗漏、无错位）
- 证明材料是否全部插入（对照 `08_插入清单.json` 的 scan_files 列表）

**⚠️ 人工确认点 #3**（v3.1新增）：将 `投标文件_完整版.pdf` + `页码校验报告.md` 呈现给用户。用户审核后：
- 「确认交付」→ 输出最终交付版
- 「调整拼合」→ 修改 `08_插入清单.json`，重新执行步骤 3-4

**阶段八产出物**：

### 阶段八的技术边界

| Skill 做的事 | Skill 不做的事 |
|-------------|---------------|
| ✅ 生成结构化插入清单（JSON） | ❌ 物理打印（激光/喷墨打印） |
| ✅ DOCX → PDF 自动转换 | ❌ 盖章（物理印章） |
| ✅ 按目录顺序程序化拼合 PDF | ❌ 手签字 |
| ✅ 自动生成目录页 | ❌ 装订（胶装/线装） |
| ✅ 页码自动编排 | ❌ 密封 |
| ✅ 证明材料完整性校验 | ❌ 快递/递交 |

> **原因**：盖章、签字、装订、密封是法律要求的物理操作，无法被代码替代。阶段八的目标是把到达装订台之前的所有编排工作自动化，人工拿到 `投标文件_完整版.pdf` 后只需要打印→盖章→签字→装订→密封五步物理操作。
