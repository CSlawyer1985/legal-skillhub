# W2 预选与大纲（法律层起点 · Gate1 + Gate2）

> 本文件定义工作流第二阶段：从 W1 事实笔记出发，先完成预选报告（Gate1），再展开并冻结审查大纲（Gate2），构成"法律层起点"的双闸门。W2 跨越事实层 → 规范层；大纲冻结后 W3 不可再调整结构。
>
> **上游**：[`./1-case-intake.md`](./1-case-intake.md) 输出的事实笔记与预识别行政行为类型
> **下游**：[`./3-drafting.md`](./3-drafting.md) 并行写作（仅在大纲冻结后启动）
> **引擎调用**：[`../methodology/legality-examination-engine/pipeline.md`](../methodology/legality-examination-engine/pipeline.md)、[`../methodology/legality-examination-engine/admissibility-screening.md`](../methodology/legality-examination-engine/admissibility-screening.md)
> **行政行为路由**：[`../methodology/case-router.md`](../methodology/case-router.md)
> **六要素合法性审查子骨架**：[`../methodology/legality-examination-engine/framework.md`](../methodology/legality-examination-engine/framework.md)

---

## 阶段定位

W2 由两个独立闸门串联组成：

| 闸门 | 任务 | 产出 |
|------|------|------|
| **Gate1 预选** | 双维度路由 + 8 闸门预判 + 程式候选清单 | 预选报告 |
| **Gate2 大纲** | 闸门展开 + 审查骨架嵌入 + 争议标记 + 字数预算 + 各节点待审问题 | 冻结大纲（结构+问题，不含结论） |

**确认规则（条件性）**：默认模式下 Gate1 与 Gate2 的用户确认**不得合并**为一次。每个闸门必须独立向用户复述要点并取得独立确认；确认未通过不得跨闸门推进。**例外——简单案件快速通道**：当案件同时满足以下全部条件时，Gate1 与 Gate2 可合并为一次确认：① 单一诉讼请求（无备位请求）；② 单一行政行为单元；③ 无复议维持/共同被告情形；④ 8 闸门预判中无"不通过"项。合并确认时须将 Gate1 路由要点（诉讼类型 + 被告 + 行政行为实质类型 + 8 闸门预判）与 Gate2 大纲要点（闸门展开 + 六要素嵌入 + 争议标记）同时呈现，用户一次确认即视为双闸均通过。

## 一、Gate1 — 双维度路由 + 候选清单

### 1.1 维度 A：诉讼请求类型识别

对每项诉请逐一识别诉讼类型，复合诉请显式拆分；备位请求显式标记主位与激活条件。

类型清单（与 [`pipeline.md`](../methodology/legality-examination-engine/pipeline.md) § 一权威 5 类决策树一致）：

| 主类型（5 类） | 子类型（识别时显式标注） |
|----------------|------------------------|
| 撤销之诉 | — |
| 履职之诉 | 含针对不作为之诉 |
| 给付之诉 | 含行政赔偿之诉（违法行为致害）、行政补偿之诉（合法行为致特别牺牲）、法定给付/协议给付 |
| 确认之诉 | 确认违法之诉 / 确认无效之诉（重大且明显违法） |
| 特殊之诉 | 行政协议之诉 / 规范性文件附带审查 / 复议机关共同被告 / 行政公益诉讼 |

识别流程详见 [`pipeline.md`](../methodology/legality-examination-engine/pipeline.md)（5 类型决策树 + 7 步识别）。

```yaml
诉讼请求清单:
  R1_main:
    类型: 撤销之诉
    原话: "请求撤销 XX 处罚决定"
    状态: 主请求
  R2_subsidiary:
    类型: 确认违法之诉
    原话: "若撤销不能，请求确认该处罚决定违法"
    条件: R1_main 结论 = "行政行为已不具有可撤销性"
    激活规则: R1_main 失败时自动激活
```

### 1.2 维度 B：行政行为实质类型正式识别

在维度 A 之后**同步**正式识别行政行为实质类型，与诉讼类型构成"双维度路由"：

1. 复核 W1 的预识别结果，确认或修正每个行为单元的实质类型；
2. 对照 [`case-router.md`](../methodology/case-router.md) §2.1 速查表与 §2.2 详表，确定每个行为单元对应的专属审查要点清单；
3. 在预选报告中明确标注："本案行政行为类型 = [类型]，专属审查要点 = [要点清单]"。

### 1.3 双维度叠加规则

| 维度 | 决策作用 |
|------|---------|
| 诉讼请求类型（撤销/履职/给付/确认/特殊） | 决定可证立性审查的程序骨架 |
| 行政行为实质类型（9 类高频） | 决定六要素合法性审查骨架中需叠加的专属要点 |

详见 [`case-router.md`](../methodology/case-router.md) §2.3。

### 1.4 被告识别（含场景套色分支）

进入本步骤前先读取 `.user-config.md` 的 `scenario` 字段：

- `academic` / `litigation`：依"被告资格"条款——复议维持 → 原机关 + 复议机关共同被告；复议改变 → 仅复议机关；未经复议 → 作出行政行为的行政机关。
- `pre-enforcement`：本步骤替换为"拟行为相对人识别"——列出本机关拟作出行政行为的相对人全称、利害关系人，以及可能据以申请复议/起诉的潜在原告。此分支下，§1.5 可受理性 8 闸门预判随之替换为"相对人救济可能性预判"（参见 W4 §五场景分支表）。

### 1.4-bis 代理人站位识别（litigation 场景专属）

仅当 `scenario = litigation` 时启用本步骤；`academic`（学术研习取第三方评价立场）与 `pre-enforcement`（机关内部自审）均跳过。

律师/法务的报告视角对 W3 写作语气、风险清单视角与 W4 终稿模板均产生联动差异，须在 Gate1 阶段显式锚定三态之一并写入 `.user-config.md` 的 `stance` 字段：

| 站位 | `stance` 取值 | W3 §五写作语气 | 风险清单视角 | W4 §五终稿模板 |
|------|--------------|---------------|-------------|--------------|
| 代理行政相对人（原告） | `plaintiff` | 攻击面优先：以可撤销/可确认违法的理由强度作主线，结论段末附 `**[诉讼策略提示]**` 指向"主张顺位 + 证据准备" | 攻击面清单为主，防守弱项作辅 | 行政诉讼风险评估意见书（攻击面分栏） |
| 代理行政机关（被告） | `defendant` | 防守面优先：以抗辩可立点与证据保全空间作主线，结论段末附 `**[抗辩策略提示]**` 指向"证据补强 + 程序救济" | 防守弱项清单为主，对方可能攻击面作辅 | 行政诉讼应诉意见书（防守面分栏） |
| 第三方中立评估 | `neutral` | 双向对照式：每要素结论段同时列"原告可主张 / 被告可抗辩"二段，附 `**[策略对照提示]**` | 攻防对照表（两栏并列） | 行政诉讼风险评估意见书（攻防对照式） |

**识别问句（在 Gate1 末尾询问）**：
> 本案律师/法务的代理身份是？
> ① 代理行政相对人（原告） → `plaintiff`
> ② 代理行政机关（被告） → `defendant`
> ③ 非代理身份，仅做中立风险评估（如客户合规研判、内部立项审议） → `neutral`

**默认值**：用户未明示且无法从输入材料识别时，默认 `neutral`，并在预选报告末段标注"代理人站位：neutral（默认）"提示用户确认。

**联动写入**：本字段与 §3.3.1 场景套色矩阵正交叠加——`stance = defendant` 时将 §3.3.1 矩阵中"程序/证据/裁量"的 ⭐ 偏置部分降为 🔍（避免站在攻方放大被告自身瑕疵），同时把"起诉期限抗辩 / 复议前置抗辩 / 信赖保护"由 🔍 提升为 ⭐。`stance = plaintiff` 时矩阵保持 §3.3.1 默认；`stance = neutral` 时矩阵保持 §3.3.1 默认，但 W3 写作语气切换为双向对照。

### 1.5 可受理性 8 闸门预判

对 8 闸门逐项给出"通过 / 不通过 / 待查"初步判断，每项配一句话理由。8 闸门清单参见 [`../methodology/legality-examination-engine/admissibility-screening.md`](../methodology/legality-examination-engine/admissibility-screening.md)。

**铁律**：若任一闸门确定不通过，Gate2 仅展开该闸门分析，不进入可证立性。

### 1.6 候选程式清单组装

依诉讼类型 × 行政行为类型 × 规范属性组装：

- 撤销之诉 → A 轨 · 六要素合法性审查骨架（见 [`framework.md`](../methodology/legality-examination-engine/framework.md)）
- 履职之诉 → B 轨 · 请求权基础骨架
- 给付之诉 → B 轨 · 给付请求权骨架（含行政赔偿/补偿）
- 确认之诉 → A 轨 · 违法性/无效性审查骨架
- 特殊之诉 → 依子型选程式：行政协议四阶（C 轨） / 规范性文件附带审查（叠加主诉所在轨） / 复议共同被告（叠加主诉所在轨） / 行政公益诉讼（叠加诉前程序要件）

## 二、Gate1 用户确认要点

在 Gate1 末尾，须向用户复述以下要点并请其确认。**复杂案件**下本次确认须**单独**进行，不得与 Gate2 合并；**简单案件**快速通道下，以下要点可与 Gate2 确认要点合并为一次展示：

- [ ] 诉讼请求拆分是否准确（含备位关系是否符合用户原意）
- [ ] 被告识别是否正确（特别是复议维持/改变情形）
- [ ] 行政行为实质类型识别是否准确（双维度路由的 B 维度）
- [ ] 专属审查要点清单是否完整（对照 case-router.md 详表）
- [ ] 8 闸门预判是否合理（特别是判定为"不通过"的闸门）
- [ ] 候选程式清单是否齐备

用户回应分支：**准确** → 进入 Gate2；**需修订** → 修订对应项后重新请求 Gate1 确认；**回退 W1** → 补全事实后重启 W2。

## 三、Gate2 — 要件拆解 + 大纲骨架 + 审查骨架嵌入

> **核心纪律：大纲冻结结构，不冻结结论。** Gate2 的产出是"审查路线图"——确认要审查什么、按什么顺序、争议级别多高——而非"结论框架"。每个待审查节点的结论必须留待 W3 涵摄阶段从事实与规范的交互中**自然得出**。大纲中的条目应使用"待审查问题"或"审查方向"的形式呈现，禁止在 Gate2 阶段预写结论语句。Gate2 确认通过意味着用户认可"按这个路线图审查"，不意味着认可任何实体结论。

### 3.1 可受理性闸门详细展开

对 Gate1 标注为"待查"的闸门完整跑涵摄四步法：**总起句 → 定义 → 归入 → 结论**。重点闸门：

- G2（原告适格）须显式套用保护规范理论；
- G6（复议前置）须区分复议前置与选择复议；
- G7（起诉期限）须计算多标准（一般起诉期限六个月、复议后起诉期限 15 日、最长保护期）。

### 3.2 六要素合法性审查子骨架嵌入

撤销之诉的可证立性审查骨架由 [`framework.md`](../methodology/legality-examination-engine/framework.md) 提供的六要素合法性审查子骨架直接嵌入大纲：

1. 主体要素（职权依据）
2. 程序要素
3. 事实证据要件
4. 法律适用要素
5. 裁量要素
6. 处理结果适当性要件

依 Gate1 识别出的行政行为实质类型，按 [`case-router.md`](../methodology/case-router.md) §2.2 在对应要素下**叠加**专属要点。

### 3.3 大纲格式与争议标记

9 级标题精确矩阵（H1-H9），涵摄四步法落在 H4 或 H6；默认字数上限 30000 字（含目录），按争议级别分配预算。

| 标记 | 含义 | 字数预算 |
|------|------|---------|
| ⭐ | 核心争议 | 600-1500 字 |
| 🔍 | 合理争议 | 200-400 字 |
| 无标记 | 明显/无争议 | 50-100 字 |

**轻量模式分支**（W1 §五触发条件全部满足时）：取消 🔍 中间档，争议级别仅保留 ⭐ 与无标记两级；字数上限 5000 字；本表的预算列按比例下调。轻量模式下 Gate2 大纲确认仍不可省略。

#### 3.3.1 场景套色：默认标记预置规则

在为大纲条目分配 ⭐/🔍/无标记之前，先按 `.user-config.md` 的 `scenario` 字段执行场景套色预置（依据 [`../methodology/case-router.md`](../methodology/case-router.md) §3.1 矩阵）：

| 场景 | 六要素子骨架默认前推（⭐） | 默认次级关注（🔍） |
|------|------------------------|---------------------|
| `academic` | 不偏置；按案件自然争议分布 | 自然分布 |
| `litigation` | 程序要素（听证/告知/送达）、事实证据要件中的证据缺陷、裁量要素、主体要素 | 法律适用要素、起诉期限抗辩、信赖保护 |
| `pre-enforcement` | 主体要素（职权依据）、程序要素（论证/公告/听证/告知前置）、裁量基准内部一致性、规范性文件合法性体检 | 事实证据闭环、文书送达、救济告知 |

**预置流程**：
1. 完成 §3.2 六要素子骨架嵌入与专属要点叠加；
2. 依本表为对应要素自动预填 ⭐/🔍 默认标记；案件证据明显推翻默认值时（如 `litigation` 场景但程序证据完整无瑕疵），可降为无标记并附"程序无瑕疵"短结论；
3. 在 Gate2 用户确认环节复述本次预置结果，由用户最终覆写或确认。

**轻量模式叠加**：轻量模式下 🔍 中间档已被取消，本表"默认次级关注"自动降为无标记。

**`pre-enforcement` 专属**：可受理性层在 §3.1 已替换为"相对人救济可能性预判"；六要素层新增"规范性文件合法性体检"为独立 H3 节点（位于第六要素"处理结果适当性要件"之后）。

### 3.4 大纲输出示例

> **注意**：大纲中的每一项条目仅标注审查节点名称、争议级别和具体待审查问题。**不得预写结论**。结论在 W3 涵摄阶段首次出现。

```markdown
# 审查大纲

## 诉讼请求类型：撤销之诉（六要素合法性审查骨架）
## 行政行为实质类型：行政处罚（叠加专属要点）

### 一、可受理性
#### （一）行政诉讼受案范围 [无标记]
#### （二）原告适格 [🔍]
> **待审查**：原告主张的利益是否落入被诉行政行为所依据法律规范的保护范围？需套用保护规范理论。
#### （三）被告适格 [无标记]
#### （四）诉讼请求具体 [无标记]
#### （五）管辖 [无标记]
#### （六）复议前置 [无标记]
#### （七）起诉期限 [🔍]
> **待审查**：起诉是否在法定期限内（一般期限/复议后期限/最长保护期）？
#### （八）其他法定要件 [无标记]

### 二、可证立性（六要素合法性审查）
#### （一）主体要素（职权依据）[无标记]
#### （二）程序要素 [⭐]
> **待审查**：是否履行了听证告知义务？送达程序是否合规？
> **叠加专属要点**：行政处罚听证程序
#### （三）事实证据要件 [🔍]
> **待审查**：主观过错认定是否有充分证据支持？
#### （四）法律适用要素 [⭐]
> **待审查**：是否存在一事不再罚的违反？裁量基准的适用是否正确？
#### （五）裁量要素 [🔍]
> **待审查**：处罚种类与幅度是否在法定裁量范围内？
#### （六）处理结果适当性要件 [无标记]

### 三、缺陷分级与判决类型预判
> **待审查**：依前述审查结论进行缺陷分级，映射判决类型。

### 四、全案结论
> **待审查**：汇总各项审查结论，形成全案结论。
```

## 四、Gate2 用户确认要点

在 Gate2 末尾，须向用户复述以下要点并请其确认。**复杂案件**下本次确认与 Gate1 确认**严格分离**，不得合并；**简单案件**快速通道下，以下要点可与 Gate1 确认要点合并为一次展示：

- [ ] 闸门展开是否覆盖所有"待查"项
- [ ] 审查骨架是否完整嵌入，专属要点是否正确叠加至相应要素
- [ ] 争议三级标记（⭐ / 🔍 / 无）是否合理
- [ ] 场景套色默认标记（§3.3.1）已复述，用户已选择保留或覆写
- [ ] 字数预算是否合宜（与争议级别匹配，总量 ≤ 30000）
- [ ] 大纲条目层级是否齐全（H1-H9 矩阵无断层）
- [ ] **大纲中不含实体结论——每个节点仅有"待审查问题"，结论留待 W3 涵摄产生**

用户回应分支：**准确** → 大纲冻结，进入 [`./3-drafting.md`](./3-drafting.md)；**需修订** → 调整后重新请求 Gate2 确认；**回退 Gate1** → 重做预选；**回退 W1** → 补全事实。冻结后 W3 不可再调整结构，但**结论仍从零开始——W3 不得预设结论方向，不得将 Gate2 大纲中的审查问题解读为结论倾向**。

## 五、W2 阀门约束

### 5.1 条文号首次出现规则

任何条文在 W2 文本中**首次出现**必须采用 SKILL.md §6.5 法条锚定表登记的语义名称（形如 `[行政诉讼受案范围条款]`、`[处罚听证条款]`），后续在同段内可简写。具体条号一律由 §6.5 锚定表运行时映射，MCP 校验失败时切回锚定表最近一次成功核验的版本。

### 5.2 MCP 双层校验

所有条文号在 Gate1 与 Gate2 输出前均须经 MCP 双层校验：

1. **形式校验**：法条编号语法正确（条/款/项三级清晰）；
2. **现行有效性校验**：通过法律检索后端核验条文版本，未通过则软标注 `[待核验]`，禁止直接采用。

### 5.3 综合门禁清单（进入 W3 之前须全部满足）

- [ ] 双维度路由完成（诉讼类型 + 行政行为实质类型，且专属要点已叠加）
- [ ] 场景套色已按 case-router.md §三 执行（`scenario` 字段读取 → 默认 ⭐/🔍 预置 → 用户确认）
- [ ] 8 闸门预判完成，判定"不通过"的闸门已被 Gate2 单独展开
- [ ] 备位请求已显式标记主位/备位关系与激活规则
- [ ] 所有法条编号已 MCP 双层校验（或软标注 `[待核验]`）
- [ ] G2 原告适格已结合保护规范理论给出初判
- [ ] 六要素合法性审查子骨架已完整嵌入，叠加要点定位准确
- [ ] 大纲条目齐全、争议标记合理、字数预算合宜
- [ ] **Gate1 用户确认通过**（简单案件可与 Gate2 合并确认）
- [ ] **Gate2 用户确认通过**（简单案件可与 Gate1 合并确认；复杂案件须与 Gate1 分离取得）

### 5.4 W2 落盘指令

Gate1 + Gate2 确认通过（独立或合并）、综合门禁清单全部满足后，agent **必须**将冻结大纲写入工作目录的 `outline.md`，作为 W3/W4 全程的大纲权威源。

```bash
# 落盘路径示意（实际路径由用户工作目录决定）
{工作目录}/outline.md
```

落盘内容须包含：(1) Gate1 预选报告（诉讼类型清单 + 被告 + 行政行为实质类型 + 8 闸门预判 + 候选程式清单）；(2) Gate2 冻结大纲（H1-H9 完整层级 + 审查骨架嵌入 + 争议三级标记 + 字数预算 + 各节点待审查问题，不含实体结论）；(3) Gate1 / Gate2 用户确认时间戳。

仅在确认通过（独立或合并）且 `outline.md` 落盘完成后，方可进入 [`./3-drafting.md`](./3-drafting.md)。
