# 合法性审查引擎目录导览（OVERVIEW）

> 本文件是 `legality-examination-engine/` 目录的入口与索引，说明引擎三个核心子文件如何协同、SOP 编号如何映射、各文件在 W1→W2→W3 工作流中的加载时点与下游消费方。
>
> **使用规则**：写作 agent 加载本目录时，先读 OVERVIEW.md 建立索引，再按需进入具体子文件。

---

## 一、目录结构与 SOP 编号映射

| 文件 | SOP 编号 | 定位 | 文件大小（参考） |
|------|---------|------|----------------|
| `admissibility-screening.md` | **SOP-2** | 可受理性 8 闸门筛查（前置决策树） | ~7.4 KB |
| `pipeline.md` | **SOP-1 / SOP-3 / SOP-4 / SOP-5** | 主流水线：诉讼类型识别 → 行政行为定性 → 规范属性分类 → 程式组装与要件拆解 | ~14.6 KB |
| `framework.md` | （子骨架） | 六要素通用合法性审查骨架 + 缺陷分级 + 概念纪律 | ~22.6 KB |

**SOP 编号约定**：

- **SOP-1（诉讼类型识别）**：`pipeline.md` § 一
- **SOP-2（可受理性 8 闸门）**：`admissibility-screening.md` 全文
- **SOP-3（行政行为定性）**：`pipeline.md` § 二
- **SOP-4（规范属性 10 类分类）**：`pipeline.md` § 三
- **SOP-5（程式组装与要件拆解）**：`pipeline.md` § 四
- **六要素子骨架**：`framework.md` 不单独编号，作为 SOP-5 的可证立性层内嵌模板

SOP-1 与 SOP-2 在 W1/W2a 阶段并行（前者驱动诉讼类型路由、后者驱动可受理性闸门）；SOP-3/4/5 在 W2b 大纲冻结阶段顺序展开；`framework.md` 在 W2b → W3 写作阶段被反复调用。

## 二、文件协作链路（端到端流水线）

```
原告诉讼请求原话
   │
   ├──► [SOP-1] pipeline.md § 一  诉讼类型识别（5 类决策树 + 主从诉拆解 + 备位请求建模）
   │           │
   │           ├──► YAML 清单（诉讼类型/主从关系/复议关系/原告身份/备位条件）
   │           │
   │           ├──► [SOP-2] admissibility-screening.md  可受理性 8 闸门逐项筛查
   │           │           │
   │           │           └──► 分项闸门报告（通过项 → 进入可证立性；否定项 → 不予受理）
   │           │
   │           └──► [SOP-3] pipeline.md § 二  行政行为定性（12 类标签 + 适用法律体系）
   │                       │
   │                       └──► [SOP-4] pipeline.md § 三  规范属性 10 类分类
   │                                   │
   │                                   └──► [SOP-5] pipeline.md § 四  程式组装与要件拆解
   │                                               │
   │                                               ├──► 调取 suit-types/*.md 主骨架
   │                                               │
   │                                               └──► framework.md 六要素子骨架（撤销/确认违法/确认无效/赔偿之诉）
   │                                                            │
   │                                                            └──► 可证立性大纲（含每个最小涵摄单元）
   │
   └──► W3 写作阶段：按大纲驱动正文涵摄四步法（总起句 → 定义 → 归入 → 结论）
```

**关键路径说明**：

- SOP-1 是路由器：诉讼类型错配 → 骨架错配 → 整篇报告失效。
- SOP-2 是前置闸门：8 项独立闸门任一不通过则该诉讼请求项裁定不予受理/驳回起诉，逐项对每个诉讼请求单独筛查。
- SOP-3/4/5 是流水线主轴：行政行为定性 → 规范属性 → 程式组装是不可跳跃的顺序流。
- `framework.md` 是子骨架而非独立工作流：仅作为可证立性层的内嵌模板使用，前序闸门与双维度路由不得跳过。

## 三、W1 → W2 → W3 工作流加载时点

| 工作流阶段 | 加载文件 | 用途 |
|-----------|---------|------|
| **W1 案件输入** | OVERVIEW.md（本文件） | 建立引擎索引；不展开实质分析 |
| **W2a 双维度路由** | `pipeline.md` § 一 + § 二 | 诉讼类型识别 + 行政行为定性；产出 YAML 清单 |
| **W2a 可受理性** | `admissibility-screening.md` | 8 闸门逐项筛查；产出分项闸门报告 |
| **W2b 大纲生成** | `pipeline.md` § 三 + § 四 | 规范属性分类 + 程式组装与要件拆解；产出可证立性大纲 |
| **W2b 大纲生成** | `framework.md`（仅撤销/确认违法/确认无效/赔偿之诉） | 六要素子骨架内嵌；产出最小涵摄单元 |

| **W4 三维核验** | OVERVIEW.md + 全部子文件 | 校验 SOP 流水线无跳跃、子骨架未独立使用、大纲与正文一致 |

## 五、上游与下游接口

### 5.1 上游输入

- **W1 案件输入物**：原告诉讼请求原话、被诉行政行为名称与文号、当事人列表、复议关系、原告与第三人身份等。
- **方法论支撑**：`../interpretation-toolkit.md`（保护规范理论、举证责任分配、法律解释方法、下位法抵触判断等）。

| 下游模块 | 接收文件 | 接收数据 |
|---------|---------|---------|
| `../proportionality-and-discretion.md` | SOP-5 输出的"裁量授权规范"要件 | 比例原则四阶段 + 裁量瑕疵三类 |

## 六、铁律提示

1. **三层约束不可松动**：可受理性筛查（SOP-2）→ 双维度路由（SOP-1 + SOP-3）→ 程式组装（SOP-4 + SOP-5），任一层跳过即整篇报告失效。
2. **framework.md 不可独立使用**：六要素子骨架仅作为 W2b/W3 阶段的可证立性层内嵌模板，前置 SOP-1/SOP-2/SOP-3 不得跳过。
3. **多诉讼请求逐项分析**：SOP-2 的 8 闸门对每个诉讼请求项单独筛查；SOP-5 的程式组装对主诉与从诉分别调取骨架并列。
4. **法条解耦原则**：本目录所有方法论文件原则上不出现具体条文编号，语义概念与具体条号的映射统一登记在 `../../SKILL.md §6.5 法条锚定表`，由 MCP 运行时核验。
5. **校验尾标统一以 `../../format/format-and-template.md` §五 为唯一真相源**。

## 七、快速调用清单

写作 agent 加载本目录后，按以下顺序进入子文件：

1. **第一步**：读 `pipeline.md` § 一，输出诉讼类型 YAML 清单；
2. **第二步**：读 `admissibility-screening.md` 全文，逐项产出 8 闸门报告；
3. **第三步**：读 `pipeline.md` § 二 + § 三，完成行政行为定性 + 规范属性分类；
4. **第四步**：读 `pipeline.md` § 四，组装候选骨架并拆解最小涵摄单元；
5. **第五步**：若主诉为撤销/确认违法/确认无效/赔偿之诉 → 读 `framework.md` 全文，将六要素子骨架嵌入可证立性层；
6. **第六步**：将大纲交付给 W3 写作阶段（`../../workflow/3-drafting.md`）。
