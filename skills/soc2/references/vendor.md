## 供应商风险计划概述

SOC 2 CC9.2 要求组织评估和管理来自可访问系统或数据、或组织关键服务所依赖的供应商和业务合作伙伴的风险。

### 审计员关注什么：
1. 存在**供应商清单**并持续维护
2. 供应商按**风险分级**并据此评估
3. 关键供应商入驻前执行了**尽职调查**
4. 供应商评估**至少每年复审**
5. **合同**包含适当的安全和数据保护要求
6. 识别并处理供应商 SOC 2 报告中的**CUEC**

## 供应商清单模板

为每个供应商维护电子表格或 GRC 工具记录：

| 字段 | 描述 |
|---|---|
| 供应商名称 | 法人实体名称 |
| 所提供服务 | 他们为你做什么 |
| 风险等级 | 关键 / 高 / 中 / 低 |
| 数据访问 | 他们可访问的数据类型（PII、机密、无） |
| 系统访问 | 生产 / 预发布 / 无 |
| 有 SOC 2？ | 是 / 否 / 进行中 |
| 上次评估日期 | 最近一次尽职调查的日期 |
| 下次复审到期 | 按等级节奏 |
| 合同到期 | 日期 |
| 已签 DPA？ | 是 / 否 / 不适用 |
| 有安全增补？ | 是 / 否 / 不适用 |
| 主要联系人 | 供应商安全/法律联系人 |
| 负责人 | 拥有该关系的内部利益相关者 |

### 风险等级定义

**关键：** 供应商可访问生产系统，或处理/存储客户 PII。示例：AWS、Azure、GCP、Salesforce、Snowflake、Stripe、数据库供应商。
- 要求：SOC 2 报告审查或完整问卷 + 年度重新评估
- 合同必须包括：DPA、安全增补、72 小时内泄露通知、审计权

**高：** 供应商处理敏感业务数据或运营关键。示例：人力资源系统（Workday、Rippling）、GitHub、Slack、身份提供者。
- 要求：年度 SOC 2 报告或问卷
- 合同必须包括：DPA（如涉个人数据）、安全要求

**中：** 数据暴露有限，有一定运营依赖。示例：项目管理工具、设计工具、分析平台。
- 要求：入驻时安全问卷或 SOC 2 审查 + 每两年复审
- 合同应包括：可接受使用和数据处置条款

**低：** 无实质数据访问，运营风险低。示例：办公用品供应商、无数据访问的大多数 SaaS 点解决方案。
- 要求：轻量入驻检查（他们是否有安全计划？）
- 标准合同条款即可

## 供应商风险问卷

对没有 SOC 2 报告的高/关键供应商使用本问卷，或用于补充 SOC 2 报告。根据供应商的服务类型定制。

---

### 第 1 节：公司与安全计划

1. 贵组织是否有文档化的信息安全政策？如有，上次审查是什么时候？

2. 贵组织是否有专职安全职能（例如 CISO、安全团队）？请描述其结构。

3. 贵组织在过去 12 个月内是否接受过任何第三方安全评估？（SOC 2、ISO 27001、渗透测试等）如有，请提供最近报告或高管摘要。

4. 贵组织是否投保网络安全保险？请提供保额。

5. 贵组织在过去 24 个月内是否经历过影响客户的安全事件或数据泄露？如有，请描述。

---

### 第 2 节：访问控制

6. 贵组织是否对处理我们数据的系统访问强制执行多因素认证（MFA）？哪些系统要求 MFA？

7. 贵组织如何管理特权/管理员访问？是否使用特权访问管理（PAM）解决方案？

8. 离职员工账户的取消配置速度如何？您的离职流程是什么？

9. 贵组织是否执行定期访问审查？频率如何？

10. 客户数据的访问是否限于其职责所需的人员（最小权限）？

---

### 第 3 节：数据保护

11. 贵组织代表我们收集、处理或存储哪些数据？请提供数据清单或数据流图。

12. 数据是否静态加密？如有，使用什么加密标准？

13. 数据是否传输中加密？强制执行什么 TLS 版本？

14. 我们的数据如何与其他客户的数据在逻辑上隔离（多租户）？

15. 贵组织的数据保留政策是什么？合同结束时我们的数据如何及何时被删除？

16. 贵组织是否有再处理者/再分包商清单？在引入新再处理者之前会通知我们吗？

---

### 第 4 节：事件响应

17. 贵组织是否有文档化的事件响应计划？上次测试是什么时候？

18. 贵组织通知客户影响其数据的安全事件的流程和时间线是什么？

19. 贵组织是否维护安全日志？日志保留多长时间？

20. 贵组织是否部署 SIEM 或安全监测解决方案？

---

### 第 5 节：漏洞管理

21. 贵组织对处理我们数据的系统执行漏洞扫描的频率如何？

22. 贵组织对严重和高危漏洞修复的 SLA 是什么？

23. 贵组织执行渗透测试的频率如何？由谁执行（内部还是第三方）？

24. 贵组织是否有补丁管理计划？补丁节奏是什么？

---

### 第 6 节：业务连续性

25. 贵组织是否有业务连续性计划（BCP）和灾难恢复计划（DRP）？

26. 对我们所依赖的系统，贵组织的 RTO（恢复时间目标）和 RPO（恢复点目标）是什么？

27. 贵组织测试 DR 计划的频率如何？上次测试是什么时候？

28. 贵组织是否有冗余基础设施（例如多区域、高可用性配置）？

---

### 第 7 节：合规与法律

29. 贵组织是否受任何行业特定合规要求约束（HIPAA、PCI-DSS、GDPR 等）？目前是否合规？

30. 贵组织是否愿意与我们的组织签署数据处理协议（DPA）？

31. 贵组织是否会在知悉涉及我们数据的泄露后 72 小时内通知我们？

32. 贵组织是否有响应数据主体请求（DSR）的流程，这些请求需要对其代表我们处理的数据采取行动？

---

### 评分指引

对每个问题评分：
- **2**——完全到位且有证据可用
- **1**——部分到位，或控制存在但未完全文档化/测试
- **0**——未到位

| 分数范围 | 风险等级 | 建议 |
|---|---|---|
| 45–64 | 低风险 | 继续；标准合同条款 |
| 30–44 | 中风险 | 附 DPA 继续；年度复审 |
| 15–29 | 高风险 | 需要安全增补；CISO 接受风险 |
| 0–14 | 严重风险 | 升级至领导层；考虑替代供应商 |

## 审查供应商的 SOC 2 报告

供应商提供其 SOC 2 报告时，审查以下内容：

### 1. 报告基础
- **报告类型：** 是类型 1（仅设计）还是类型 2（运行有效性）？优先类型 2。
- **审计期间：** 是否覆盖近期期间？超过 12 个月的报告已过时。
- **范围内的标准：** 报告是否包含与你的用例相关的标准？（例如，如果你关心可用性，可用性是否在范围内？）
- **审计师：** 会计师事务所是否信誉良好？（大型事务所：Deloitte、KPMG、EY、PwC、Grant Thornton 等）

### 2. 审计师意见
- **无保留（干净）意见：** 无重大例外。
- **保留意见：** 一项或多项标准未满足——标记待审查。
- **否定意见：** 多项失败——升级，这是重大红旗。

### 3. 例外与偏离
- 仔细阅读"控制测试结果"部分。
- 任何**例外**（审计期间的控制失败）都必须评估：
  - 我们依赖的控制是否正是出现例外的控制？
  - 供应商的补救计划是什么？
  - 是否已解决（查看管理层回应）？

### 4. 互补用户实体控制（CUEC）
- 查找"互补用户实体控制"或类似标题的章节。
- 这些是供应商*要求你运行*的控制，其控制才能有效。
- 你必须处理每一项适用的 CUEC（见下文 [CUEC 管理](#cuec-management)）。

### 5. 系统描述
- 描述是否与你实际使用的服务匹配？
- 你所依赖的系统和基础设施是否在范围内？

### 审查日志条目

记录每份供应商 SOC 2 审查：
```
供应商：            [名称]
报告类型：        类型 1 / 类型 2
审计期间：        [起] – [止]
审查日期：        [日期]
审查人：          [姓名 / 职务]
意见：            无保留 / 保留 / 否定
显著例外：        [无 / 描述]
识别的 CUEC：    [无 / 清单]
CUEC 处理情况：  [是 / 部分 / 否 — 附详情]
风险评级：        低 / 中 / 高
行动事项：        [任何需要的后续]
```

## CUEC 管理

CUEC（互补用户实体控制）是供应商假定*你*已部署的控制。如果你没有它们，供应商的控制可能无法完全保护你的环境。

### 常见 CUEC 与典型回应

| 常见 CUEC | 典型供应商（示例） | 你相应的控制 |
|---|---|---|
| "用户实体使用供应商的访问控制功能限制对服务的访问" | AWS、Salesforce | 访问控制政策；MFA 强制执行；基于角色的访问 |
| "用户实体负责使用访问日志监测未经授权的访问" | AWS CloudTrail、Okta | SIEM 摄入供应商日志；对可疑登录发出告警 |
| "用户实体使用提供的功能配置数据加密" | AWS S3、RDS | 静态加密已启用；记录在系统配置中 |
| "用户实体对其用户的凭据负责" | 任何 SaaS | 密码政策；MFA 政策；离职流程 |
| "用户实体将任何人事变动通知供应商" | 托管服务提供商 | 离职 SOP 包括通知关键供应商 |
| "用户实体进行自己的风险评估" | 大多数供应商 | 年度风险评估流程（CC3） |

### CUEC 跟踪电子表格字段

| CUEC # | 供应商 | CUEC 描述 | 适用？ | 相应控制 | 证据 | 负责人 | 状态 |
|---|---|---|---|---|---|---|---|
| 1 | AWS | 用户通过 IAM 限制访问 | 是 | 访问控制政策 + IAM 审查 | 季度 IAM 审查记录 | DevOps | 已满足 |
| 2 | Salesforce | 用户监测登录活动 | 是 | SIEM 摄入 Salesforce 日志 | SIEM 截图 | 安全 | 已满足 |

## 供应商入驻检查清单

入驻新的关键或高级供应商之前：

- [ ] 基于数据访问和运营依赖分配风险等级
- [ ] 发送安全问卷（或索取 SOC 2 报告）
- [ ] 审查并评分问卷/报告
- [ ] 如分数为中/高，记录风险接受
- [ ] 签署数据处理协议（DPA）（如涉 PII）
- [ ] 签署安全增补（关键供应商）
- [ ] 合同包括：72 小时内泄露通知、终止时数据删除、审计权
- [ ] 识别 CUEC 并映射到内部控制
- [ ] 将供应商加入清单并附下次复审日期
- [ ] 入驻经 CISO 或安全负责人批准
