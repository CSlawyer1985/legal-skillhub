# 参考——文档结构、条款库、写作技巧及多语言/从右到左（RTL）

> 本文件是输出的骨干：推荐的章节顺序、可组装的模块化条款、须强制执行的平实语言规则、须避免的版本陷阱，以及阿拉伯语/RTL 构建规则。每条条款背后的*法律要求*存在于 `jurisdictions-*` 和 `platform-cookies-ai` 文件中。

---

## 1. 推荐目录（最佳实践顺序）
前置身份 + 目的 + 权利（EDPB WP260 第 36 段说这三者应放在第一层），然后遵循自然的"谁 → 什么 → 为什么 → 与谁共享 → 保留多久 → 你的控制权 → 杂项"流程。

0. **TL;DR /"简而言之"摘要**（平实语言概述——设计最佳实践，非法定字段）
1. **我们是谁** —— 控制者身份、地址、联系方式；代表（如位于欧盟/英国以外）；**DPO**（如有）
2. **我们收集什么数据** —— 类别；对间接获得的数据，注明**来源**（GDPR 第 14 条）
3. **我们为何使用（目的）+ 法律依据** —— 每项目的具体说明；每项目的第 6 条依据；如使用合法利益须指明
4. **Cookie 与跟踪** —— 内嵌或交叉链接至 Cookie 政策；同意机制；GPC/DNT
5. **我们与谁共享** —— 接收方/类别（要具体）；"可应要求提供完整清单"
6. **国际转移** —— 第三国 + 机制（充分性/SCC/DPF/IDTA）+ 如何获取副本
7. **我们保留多久（保留期限）** —— 期限或标准，尽可能按类别
8. **你的权利 + 如何行使** —— 列出适用的权利；反对权须**清晰且单独**展示；渠道 + 响应时间 + 免费 + 验证
9. **向监管机构投诉的权利** —— 点名/链接相关机构
10. **自动化决策/AI** —— 存在 + 逻辑/重要性/后果；AI 子处理者；训练姿态；聊天机器人披露
11. **儿童** —— 年龄门槛 + 父母同意（或否定式"我们不会故意收集 13 岁以下儿童数据"条款）
12. **安全** —— 一般保障措施 +"没有系统是 100% 安全的"+ 违规承诺
13. **本政策的变更** —— 生效/最近更新日期 + 重大变更如何通知（而非"请定期查看本页面"）
14. **联系/如何联系我们** —— 用于隐私问题和权利请求的重复渠道
15. **特定辖区章节** —— 如"您的加州隐私权利"（附 Do-Not-Sell-or-Share 和 Limit-SPI 链接）、"您的欧洲经济区/英国权利"等
16. **免责声明** ——"仅供参考/模板，非法律意见；不构成律师-客户关系"

## 2. 模块化条款库——推荐表述（应做）与禁用表述（不应做）

**核心原则（首要指令）：** 仅当存在确认性的信息收集答复时，才生成条款。只陈述用户确认其实际做的事情。绝不默认加入讨好的事实性表述。

**应做——具体、确定性的表述：**
- "我们基于 [指名的第 6 条依据] 为 [具体目的] 处理 [X 数据]。"
- "我们的合法利益是 [具体利益，如防止欺诈]。您可以反对——见[您的权利]。"
- "我们与以下方共享数据：[指名类别——如我们的支付处理商 Stripe、我们的托管提供商 AWS]。可应要求提供完整接收方清单。"
- "我们将 [数据] 保留 [期限] / 至 [事件]，之后删除或匿名化。"
- "我们使用 [机制] 将数据转移至 [国家]；请联系 [联系渠道] 索取保障措施副本。"
- "您可以随时通过 [方式] 撤回同意；这不影响此前的合法处理。"
- "您可以向 [指名机构] 投诉，见 [链接]。"
- "我们实施合理的行政、技术和物理保障措施……没有任何方法是 100% 安全的。"

**不应做——禁用表述（这些是已记录在案的透明度失败）：**
- 隐藏可确定事实的开放式限定词：*may、might、possibly、such as、including but not limited to、from time to time、where appropriate*（可能、或许、诸如、包括但不限于、不时、适当时）。
- "我们**可能共享**您的数据给**合作伙伴 / 关联公司 / 第三方**"（未指名类别）。
- "我们使用您的数据**改进我们的服务 / 用于业务目的 / 用于研究**"（无具体内容）。
- "**使用本网站即表示您同意**我们的隐私政策"（同意 ≠ 告知；无效捆绑）。
- 安全最高级表述：*military-grade、bank-grade、100% secure、fully secure、guaranteed、fully compliant*（军事级、银行级、100% 安全、完全安全、有保证、完全合规）。
- "**请定期查看本页面以了解变更**"作为*唯一*变更机制——WP260 认为这"不仅不充分，而且不公平"。须配以带日期的变更日志 + 主动的重大变更通知。

**WP260 工作示例：** 差 = "我们可能使用您的个人数据提供个性化服务"；好 = "我们将记录您点击过的文章，并据此投放与您兴趣相关的定向广告。"

## 3. 写作技巧（在输出上强制执行）
- **阅读水平：** 面向广泛消费者受众的目标约为**八年级**水平（NN/g）；面向专业受众最高至十二年级。书写水平要比受众的正规教育水平低几级。
- **句子：** 短句；**平均约 20 词**，**每句一个想法**（联邦平实语言指南）。
- **主动语态**、平实词汇、无多余名词、无法律行话（GDPR 第 12 条 + WP260）。
- **具体且确定性**，绝不抽象或模棱两可。避免对冲限定词（见禁用清单）。
- **可扫读性：** 对"数据类别 × 目的 × 法律依据 × 保留期限"使用**表格**（ICO 自身使用的格式）；项目符号列表；关键词加粗；句子式大小写（而非全大写）；为不可避免的术语提供简短词汇表。NN/g：简洁 + 可扫读 + 客观的写作使可用性提升 124%。
- **内联或简短词汇表定义术语**；在不可避免的法律行话旁附平实语言摘要。

## 4. 分层通知、仪表盘、图标
- **分层通知：** 第一层 = 控制者身份 + 目的 + 权利（+ 任何高影响/意外的处理）；更深的细节放在可展开部分/"了解更多"之后。各层不得是"多次点击才能找到真实信息"（Google/CNIL 的失败点），也不得相互冲突。
- 在收集点提供**即时（just-in-time）**情境通知；用于偏好管理的**隐私仪表盘**；用于有意义概览的**标准化图标**（GDPR 第 12 条第 7 款允许）。
- 隐私"营养成分标签"（苹果应用商店风格）是良好的概览格式——但标签的诚实程度取决于其背后的实践（CMU 发现许多标签不准确）。

## 5. 版本与维护（头号法律陷阱）
- **始终与实践匹配。** 政策是一组可执行的陈述（FTC 第 5 条；OkCupid/Match 2026）。说的比做的多 = 欺骗。技能必须将每条条款与确认的答复进行核对。
- **未经同意不得追溯性重大变更。** *Gateway Learning*（FTC 2004）："你可以改变规则，但不能在比赛结束后。"通过悄悄修改政策开始对已收集数据进行 AI 训练是不公平/欺骗性的（FTC 2024）。
- **带日期 + 变更通知。** 显示醒目的"最近更新"日期 + 变更摘要；考虑公开变更日志（37signals/Basecamp 在 GitHub 上对其政策进行版本管理）。通过专门渠道（电子邮件/弹窗）传达**重大**变更——不要与营销捆绑。"请定期查看"单独使用不合规。

## 6. 关联文件——什么属于哪里
- **隐私政策** = 所有数据处理（什么/为什么/依据/共享/转移/保留/权利/投诉）。
- **Cookie 政策** = 仅 Cookie/跟踪器（类别、目的、如何给予/拒绝/撤回同意）。可以是隐私政策内的一节，也可以是单独的链接文档 + 同意横幅。
- **服务条款/EULA** = 规范*使用*的合同（可接受使用、知识产权/许可、责任、争议）——不是数据处理文件。
- **DPA（数据处理协议）** = 控制者与处理者之间的 B2B *合同*（GDPR 第 28 条）——不面向消费者。不要将 DPA 条款并入公开政策。
- **员工/求职者通知** = 单独的通知（依据不同；雇佣关系中同意通常无效）。不要将人力资源数据并入消费者政策。

## 7. 多语言与阿拉伯语/RTL 构建规则（面向中东北非/多语言受众）
GDPR 透明度要求使用受众的语言；沙特/阿联酋本土公司期望阿拉伯语。阿拉伯语 RTL 政策的关键规则（因为法律文本将 RTL 阿拉伯语与 LTR 品牌名称、URL、电子邮件、引文、日期、数字混合，是困难情形）：
- 用 **`<html lang="ar" dir="rtl">`** 设置基础方向（用属性，而非 CSS `direction`），使其在阅读模式、电子邮件和 PDF 中都能保持。`lang` 与 `dir` 分别声明。
- 使用 **CSS 逻辑属性**（`margin-inline-start`、`text-align: start`）——绝不用物理 `left/right`——使一个样式表同时服务 LTR 和 RTL 版本。
- **隔离每个内嵌的 LTR 片段**（品牌名称、URL、电子邮件、电话/账号、日期、法规引文），用 `<span dir="ltr">`（已知方向）或 `<bdi>` / `dir="auto"`（动态）——否则标点、括号和数字会重排。在纯文本/属性语境中使用 Unicode 隔离符（RLI/LRI/PDI，U+2066-2069），绝不使用旧的嵌入控制符（U+202A/B）。
- **不用大小写强调**（阿拉伯语没有大小写）——使用粗细/字号/颜色和真正的阿拉伯语网络字体（如 Noto Kufi Arabic），配真正的粗体；绝不用伪粗体。为变音符号/下行字母留出充足的 `line-height`（约 1.6-1.8）。
- 避免朴素的 `justify`（网页不支持 kashida）——使用 `text-align: start`。
- **数字：** 海湾/黎凡特用东阿拉伯-印度数字（٠١٢٣），马格里布/泛中东北非数字默认用西方数字（0123）；保持一致；数字片段保持隔离。
- 表格镜像：第一列在右侧，单元格右对齐——镜像后核查列顺序。
- **双向文本（bidi）在 PDF 导出处最容易出错** ——使用支持 UBA 的引擎并单独校对 PDF。
- 添加**主导语言条款**（冲突时以哪个语言版本为准），并让具备法律素养的阿拉伯语母语者审查渲染页面 + PDF。
- 标注法律文件的机器翻译必须经人工审查。
