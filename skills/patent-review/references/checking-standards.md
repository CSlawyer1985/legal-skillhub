# 专利核稿详细核查标准

## 1. 权利要求引用链体系——贯穿全文核查的基本原则

⚠️ 本原则是权利要求书核查的基石，所有涉及从属权利要求的核查环节均须遵循，后续不再重复陈述。

### 1.1 特征总和原则

从属权利要求N的完整技术方案 = 特征(N) ∪ 特征(Cp) ∪ … ∪ 特征(C1)，其中 N → Cp → … → C1 为引用路径，C1 为独立权利要求。特征包含具有传递性：若C引用B、B引用A，则C包含三者全部特征。

多项从属权利要求因引用多个上位权利要求而产生多条路径，每条路径对应一种独立法律解读。

对路径 P = [N → Cp → … → C1]，定义其累积特征集：

S(P) = Features(C1) ∪ Features(C2) ∪ … ∪ Features(Cp)

即路径上除N之外所有节点引入的特征并集。S(P) 是判定N中进一步限定的特征「所述X」是否具有引用基础的检验集合：X ∈ S(P) 则有引用基础，X ∉ S(P) 则缺乏引用基础。

### 1.2 四步核查法

**步骤一：路径穷举**

对进一步限定特征「所述X」的权利要求N，穷举其到独立权利要求的所有完整引用路径。多项引用产生多条路径分支；每条分支递归回溯至独立权利要求。

**步骤二：路径特征累积**

对每条路径P，计算累积特征集 S(P)，S(P)中必须加入路径P的独立权利要求的全部特征。

**步骤三：逐路径判定**

对每条路径P，判断 X ∈ S(P) 是否成立：
- X ∈ S(P) → 该路径具有引用基础 ✓
- X ∉ S(P) → 该路径缺乏引用基础 ✗

**步骤四：精确报告**

仅报告实际缺乏引用基础的特定路径，指明是哪个特征在哪条路径上缺失。全部路径均有引用基础的特征不报告问题。

### 1.3 验证示例（内嵌少样本范例，供推理模式校准）

给定权利要求集：

| 权利要求 | 引用关系 | 自身引入的新特征 |
|----------|----------|------------------|
| 权1（独立） | — | a, b, c |
| 权2 | 引用权1 | d |
| 权3 | 引用权2 | e |
| 权4 | 引用权2或权3（多项从属） | f |

**示例一：权3中"所述a"——传递性验证**

权3仅有一条路径：3→2→1。

| 路径 | 累积特征集 S(P) | a ∈ S(P)? |
|------|------------------|-----------|
| 3→2→1 | {a,b,c,d} | ✓ |

关键点：特征a由权1引入，权2自身仅引入d，但a通过权1传递进入累积特征集。不得因"权2未显式引入a"而判定缺乏引用基础。

**示例二：权4中"所述a, 所述d"——多路径全部通过**

| 路径 | 累积特征集 S(P) | a,d ∈ S(P)? |
|------|------------------|-------------|
| 4→2→1 | {a,b,c,d} | ✓ |
| 4→3→2→1 | {a,b,c,d,e} | ✓ |

结论：两条路径均有引用基础，无问题。

**示例三：权4中"所述e"——部分路径未通过**

| 路径 | 累积特征集 S(P) | e ∈ S(P)? | 缺失 |
|------|------------------|-----------|------|
| 4→2→1 | {a,b,c,d} | ✗ | e |
| 4→3→2→1 | {a,b,c,d,e} | ✓ | — |

结论：路径4→2→1中特征e缺乏引用基础。报告应精确指出该路径及缺失特征，而非笼统判定"权4缺乏引用基础"。

### 1.4 禁止的错误模式

| 模式 | 说明 | 标记 |
|------|------|------|
| 逐节点孤立检查 | 检查路径上每个中间节点是否单独包含特征X，若某中间节点未显式包含即判定缺乏引用基础。此模式忽略了特征通过更上游节点传递继承的事实。 | ❌ 严禁 |
| 仅检查直接引用节点 | 权N引用权A时，仅检查权A自身文本是否包含X，不回溯权A的上游权利要求。 | ❌ 严禁 |
| 跨路径混合判定 | 将不同路径的特征集混合为一个总集合后统一判断，导致路径级别的缺陷被掩盖。 | ❌ 严禁 |
| 路径累积检查（正确） | 计算整条路径的累积特征集（并集），判断X是否存在于此并集中，逐路径独立判定。 | ✓ 遵循 |

### 1.5 边界规则

1. 若特征X仅在权利要求N自身中首次出现，而N的所有上游路径的累积特征集S(P) 中均不包含X，则X是N首次引入的新特征，N中首次出现不应使用「所述X」，应使用无定冠词形式，再次出现则可使用「所述X」。

    ⚠️ **操作澄清：同一权利要求内部「所述X」回指不适用四步核查法**
    当特征X在权N第一句首次出现（无"所述"），在**同一权N后续句子**中以"所述X"回指时，属于同一权利要求内部回指，**无需检查上游累积特征集S(P)**，应直接判定为正确。四步核查法仅适用于检查**引用他权利要求的权利要求**中「所述X」是否在引用路径上具有引用基础，不适用于同一权利要求内部的回指检查。

    ⚠️ **操作澄清：「所述[已知主体]的[新属性]」结构不适用四步核查法**
    当权利要求N中出现「所述A的B」结构，其中A是已在S(P)中引入的已知主体（如"第一终端设备"），B是A的一个属性特征且在S(P)中首次出现（如"标识信息"），此时「所述」的语法限定对象是已知主体A而非属性B。此种情形下B是作为A的属性自然引入，**无需单独检查B是否在S(P)中具有引用基础**，应直接判定为具有引用基础。禁止将此情形判定为"缺乏引用基础"或"不应使用所述"。
    
    示例：「所述第一终端设备的标识信息」——"第一终端设备"已在S(P)中引入，"标识信息"作为第一终端设备的属性首次出现，写法合规。
    
    例外：若B本身是一个独立可分离的技术实体（而非A的固有属性），如「所述数据网络的服务器」——"服务器"是可独立存在的实体，此情形仍需按四步核查法逐路径检查"服务器"是否在S(P)中具有引用基础。

2. 权利要求不可引用自身。若遇到此情况，应作为格式错误单独报告。
3. 多项从属权利要求引用另一多项从属权利要求的情况，应按第2.4-C条款作为形式错误处理。

    ⚠️ **操作澄清：产品通过方法限定（product-by-process）权利要求的特征传递规则**
    当产品权利要求M采用"使用权利要求X-Y任一项所述的制备方法制备得到"的product-by-process表述时，该产品权利要求所定义的产品**通过所述制备方法的全部步骤特征来限定**。因此，在执行四步核查法计算产品权利要求引用链的累积特征集S(P)时：
    
    (a) 对于直接引用该产品权利要求M的从属权利要求N，路径N→M的累积特征集S(P)应包含**M自身显式陈述的结构特征**与**M所引用的制备方法权利要求链的全部步骤特征**的并集。
    
    (b) 换言之，product-by-process产品权利要求的有效特征 = 产品权利要求显式结构特征 ∪ 所引用制备方法的全部步骤特征。
    
    (c) 示例：权6"使用权利要求1-5任一项所述的制备方法制备得到，包含无机颜料核心颗粒，所述无机颜料核心颗粒包覆二氧化硅壳层"，权8引用权6并涉及"所述含芳基的三烷氧基硅烷"。路径8→6的S(P)包含权6的显式特征{无机颜料核心颗粒，二氧化硅壳层}以及权1的全部方法特征{含芳基的三烷氧基硅烷，含环氧基的三烷氧基硅烷，…}，"含芳基的三烷氧基硅烷"∈ S(P)，具有引用基础。✓
    
    (d) 虽然引用基础合规，但仍建议在product-by-process产品权利要求中显式陈述关键结构特征（如"所述无机颜料核心颗粒表面接枝有含芳基和含环氧基的双硅烷偶联层"），以提高权利要求的清楚性和自足性。此建议属撰写优化项（★），非引用基础缺陷。
    
    (e) 若从属权利要求N引用product-by-process产品权利要求M，且N"所述X"中X既不在M的显式结构特征中、也不在M所引用方法权利要求的全部步骤特征中，则按常规四步核查法判定缺乏引用基础。

## 2. 阶段1：权利要求书核查

### 2.1 独立权利要求实质内容核查

**A. 核心技术问题识别：**
- 核心技术问题是否清晰、具体
- 是否与背景技术中的缺陷形成逻辑对应
- 多个核心技术问题时是否明确主次关系

**B. 发明目的可实现性：**
- 独立权利要求的技术方案能否实现发明内容中声称的发明目的
- 保护主题（产品/方法/用途）是否与发明本身要保护的主题一致且合适
- 注：发明目的是指独立权利要求的技术方案能达到的发明目的（此定义贯穿全文）

**C. 必要技术特征审查（实施细则第23条第2款）：**
- 每一技术特征是否均为解决核心技术问题所必需
- 是否存在非必要技术特征被误纳入，导致保护范围不合理缩小
- 判断时应从技术问题及发明目的出发，结合说明书整体内容，不应将实施例特征直接认定为必要技术特征

**D. 上位概括合理性：**
- 上位后的技术特征是否仍能解决核心技术问题
- 实施例公开的技术方案是否被独立权利要求字面覆盖
- 过度上位 → 可能无法解决技术问题或丧失新颖性；上位不足 → 保护范围过窄

**E. 独立权利要求布局合理性：**
- 产业链布局原则：芯片/器件→单板/模块→设备→系统→网络及相应方法、用途、制造工艺/设备、测试方法/设备
- 制造侵权优先原则：优先撰写装置权利要求以形成制造侵权；方法发明应同时构建产品或虚拟装置权利要求
- 方法与装置并重原则：独权体系是否包括必要的方法、系统、关键装置和/或关键部件的独权
- 优先级排序：权利要求1是否为与核心技术问题关联度最高的独立权利要求

**F. 单一性：**
- 多个独立权利要求间是否存在相同或相应的特定技术特征
- 如存在单一性问题且各方案均重要，提示用户分案申请

### 2.2 从属权利要求实质内容核查

本节全部核查严格遵循第1节原则。

**A. 引用关系正确性：**
- 引用的权利要求编号是否正确
- 排列顺序：每条从属权利要求应紧随其所引用的上位权利要求

**B. 特征引用逻辑闭合性：**
- 按第1节四步核查法逐路径检查每条从属权利要求中「所述」引用的特征
- 如存在路径缺乏引用基础，须构思上位权利要求的补充或引用关系的调整方案

**C. 完整性与最少原则：**
- 每条从属权利要求应包含实现其有益效果的所有必要技术特征
- 在满足技术方案完整的前提下，新增特征越少越好
- 检查是否存在可拆分为多条的合写情况

**D. 创新点相关性与优先级：**
- 是否优先布局与核心创新关联度高的非必要技术特征
- 是否充分限定说明书中的优选实施方式

### 2.3 特殊权利要求类型核查

**A. 方法权利要求：**
- 检查是否在步骤前加上不必要的执行主体（除非区别技术特征仅在于执行主体）
- 检查是否存在不必要的逻辑顺序限制（除非区别仅在于步骤次序）
- 若基于前述产品权利要求，是否在开头明确「使用权利要求X-Y任一项所述的{产品名称}」

**B. 产品与方法的撰写风格区分：**
- 产品权利要求：关注组成部件及部件间关系
- 方法权利要求：关注为达到发明目的必需做的步骤

**C. 用途权利要求：**
- 是否采用标准表述「……在……中的应用」
- 严禁「……中的至少一种应用」等口语化表达

**D. 功能性限定核查：**
- 产品权利要求应尽量避免功能特征限定
- 可使用功能性限定的情形：(a) 限定对象是现有技术；(b) 限定对象是发明点且说明书有实施例支撑，功能性限定优于技术特征限定；(c) 技术特征无法用结构特征恰当限定

### 2.4 权利要求书形式核查

**A.** 数量与类型：权利要求总数是否合理；是否包含不同类型（产品、方法、用途等）

**B.** 禁止在权利要求中使用表格

**C.** 多项引用多项的禁止：一项引用两项以上权利要求的多项从属权利要求不得作为另一项多项从属权利要求的引用基础

**D.** 形式从属实质独立的权利要求：从属权利要求若既非补充也非进一步限定，建议改为独立权利要求

**E.** 附图标记规范：标记应用括号括起来，放在相应技术特征后面

**F.** 发明主题禁用词：「算法、程序、商业方法、数据结构、信令（格式）、帧（结构）」——在中国不直接提供保护，出现于主题中可能被驳回

### 2.5 权利要求书文字规范核查

**A. 禁用词汇核查：**

| 类别 | 禁用词示例 |
|------|-----------|
| 强硬词汇 | 只有、就是、仅仅、最好是、核心思想、必要、唯一 |
| 模糊/歧义词 | 例如、最好是、尤其是、必要时 |
| 一般不得使用 | 约、接近、等、大部分、或类似物 |

注：此禁用词表同样适用于说明书实施例（后续不再重复列举）。

**B. 其他文字规范：**
- 百分比：是否明确单位（wt%/v/v）；多组分范围核验须满足以下两条数学约束：

  设各组分 i 的百分比范围为 [Lᵢ, Uᵢ]，则对任意组分 j 须同时满足：

  **约束①（上限约束）：当 j 取上限 Uⱼ 时，其余组分均取下限，总和 ≤ 100%**
  
  表达式：Uⱼ + Σᵢ≠ⱼ Lᵢ ≤ 100%
  
  含义：最「拥挤」场景——某一组分最多、其余组分最少时，总和不超100%，确保总量不溢出。

  **约束②（下限约束）：当 j 取下限 Lⱼ 时，其余组分均取上限，总和 ≥ 100%**
  
  表达式：Lⱼ + Σᵢ≠ⱼ Uᵢ ≥ 100%
  
  含义：最「松散」场景——某一组分最少、其余组分最多时，总和至少100%，确保没有必须由未限定组分填补的缺口。

  违反约束① → 范围取值的上限组合可能超出100%，属于数学不自洽。
  违反约束② → 范围取值的下限组合不足100%，需由其他未限定组分填补（若权利要求明确「还包括」其他组分，则此约束可放宽；若仅限定两个组分且声称即由二者组成，则此约束为硬性要求）。
- 命名一致性：产品/层/模块命名全文统一
- 技术效果描述合规性：权利要求中不应存在纯粹技术效果描述（应改为技术特征限定）
- 错别字及形式缺陷全文检查
- 歧义表述：识别可能导致两种解读的表述
- 清楚性：短句为主，用语通俗易懂

## 3. 阶段2：说明书核查

### 3.1 发明名称核查

- 是否清楚、简要、全面反映保护主题和类型
- 是否与各独立权利要求的主题和类型对应
- 不超过25字（化学领域允许最多40字）
- 不能包含：过小的技术应用领域、具体发明点、不清楚词语、英文名称、人名/地名/商标/型号/商品名称、商业性宣传用语

### 3.2 技术领域核查

- 结构：「本申请涉及X领域，具体涉及{题目内容}」
- 不能包含发明点

### 3.3 背景技术核查

**A. 段落结构与逻辑递进：**
- 第1段现有技术综述 → 第2段改进方向/技术问题阐述 → 第3段明确核心技术问题
- 各段递进关系自然流畅

**B. 严禁事项：**
- 严禁包含发明点（将意味着自认为现有技术，在美国尤为严重）
- 严禁包含本发明不能解决的现有技术问题

### 3.4 发明内容核查

**A. 发明目的：**
- 格式：「为了解决{核心技术问题}，本申请提供了{题目内容}」

**B. 从属权利要求内容的处理：**
- 是否按权利要求顺序依次描述
- 每条从属权利要求描述是否包含：附加技术特征的技术效果、优选方案、可选范围、原料来源/商品名、具体数值点值列举等

**C. 技术效果描述：**
- 技术效果是由技术特征直接带来或必然产生的
- 是否清晰阐述：什么技术特征→解决什么问题→达到什么效果
- 术语是否与权利要求、实施例保持一致
- 有益效果描述必须完整覆盖发明目的

**D. 格式规范：**
- 不得出现「如权利要求……所述…」和「其特征在于」（此类用语仅限权利要求书使用，此规则同样适用于实施例部分）

### 3.5 实施例核查 — 第26条第3款（充分公开）

法定锚点：说明书应当对发明作出清楚、完整的说明，以所属技术领域的技术人员能够实现为准。

判断主体：本领域技术人员（具有该领域公知常识的假想人）。

核心判据：无需创造性劳动，无需过度实验，即可实施。

| 条款 | 核查要点 | 具体标准 |
|------|----------|----------|
| A | 可实现性（核心条款） | 每个实施例是否记载了使本领域技术人员再现该技术方案所需的全部必要信息，包括但不限于：关键结构/步骤、工艺参数及其取值范围、材料选型依据、部件间的连接与协作关系。判断标准：本领域技术人员阅读该实施例后，能否在不付出创造性劳动、不进行过度实验的前提下实施该方案。若需依赖说明书未公开的信息方可实施，则不满足本条。 |
| B | 完整性 | ① 技术方案的全部必要技术特征是否均在实施例中有具体体现，而非仅描述优选方案或局部方案；② 关键步骤或关键部件之间是否存在逻辑跳跃（即从步骤 n 到步骤 n+1 之间缺少本领域技术人员无法自行补充的中间环节）；③ 涉及数值范围的发明，端点值及代表性中间值是否有充分说明或实验验证。 |
| C | 技术效果可验证性 | 实施例是否包含能够证实所声称技术效果的验证数据或验证方法。按技术领域区分：（i）不可预测领域（化学、生物、材料）——应提供实验数据、对比实验或验证测试结果；（ii）可预测领域（机械、电路）——可通过技术原理的逻辑推演替代实验数据，但推演过程必须清楚。若技术效果仅有断言而无任何验证路径，则不满足本条。 |
| D | 概括范围的可实现性 | 当权利要求采用上位概念、功能性限定或较宽数值范围时，核查实施例（群）是否足以使本领域技术人员合理预见：该概括范围内的其他具体实施方式同样可以实现。具体而言：① 实施例的数量与分布是否与概括范围的宽度及技术领域的可预测程度相匹配；② 实施例之间是否体现了技术方案的变化逻辑（而非仅仅是参数的简单替换）。注意：本条判断标准严格限于"能否实现"（26.3），不得滑向"是否支持"（26.4），二者的法律后果和审查逻辑不同。 |
| E | 清楚性 | ① 实施例描述是否存在歧义、自相矛盾或与附图标记不一致之处；② 技术术语的使用是否符合本领域的通常含义，自定义术语是否有明确释义；③ 实施例的描述顺序是否与技术方案的逻辑结构一致（先原理后实施、先整体后局部、先结构后动作）。 |

#### 26.3 与 26.4 边界备注

在实施例核查中，以下两个问题形似而质异，必须区分：

|  | 第26条第3款 | 第26条第4款 |
|------|------------|------------|
| 核心问题 | 本领域技术人员能否实现说明书公开的发明？ | 权利要求是否以说明书为依据？ |
| 判断主语 | 本领域技术人员 | 权利要求书 |
| 判断方向 | 说明书 → 实施（从文本到实践） | 权利要求 → 说明书（从权利到文本） |
| 实施例核查的着眼点 | 实施例是否公开充分，使人能做出来 | 权利要求的每个技术特征是否能在说明书中找到依据 |

原版C条（"逐条检查权利要求是否在实施例中有对应描述"）应归入26.4的核查清单，不在本节范围之内。

### 3.6 对比例核查（如适用）

- 对比例是否缺少权利要求1的至少一项必要技术特征
- 与实施例1的区别是否清晰
- 能否有效突出本发明技术效果
- 测试方法是否清晰、可操作，是否符合行业/国标
- 数据完整性与准确性；是否对比分析性能偏差

## 4. 阶段3：全文交叉验证

### 4.1 权利要求书与说明书的一致性验证

- 技术方案一致性：权利要求1与发明内容第一方面描述是否完全一致
- 术语全文一致性：全文无同物异名或异物同名
- 权利要求的实施例支持度：逐条检查技术特征是否有实施例支持；上位范围是否超出支持

### 4.2 技术效果的逻辑闭环验证

验证完整逻辑链是否自洽：

背景技术提出的问题 → 发明内容声称的解决方案 → 权利要求定义的技术方案 → 实施例/对比例的数据验证

- 是否存在背景技术提出问题但实施例未验证
- 是否存在实施例验证效果但权利要求未覆盖相关特征
- 是否存在权利要求特征但发明内容未阐述技术效果

### 4.3 引用链体系的全文一致性验证

基于阶段1构建的引用关系图，按第1节四步核查法对全部从属权利要求重新执行特征引用基础验证。

### 4.4 综合汇总

合并三阶段问题，按严重程度排序，输出最终综合评审。
