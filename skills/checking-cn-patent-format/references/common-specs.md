# 通用规范（所有审查 Agent 共用）

> 以下规范适用于所有审查Agent。每个审查Agent在执行任务前必须先读取本文档内容并严格遵守。主Agent的query中应告知子Agent读取本文件。

---

## 0. 核心行为约束

**0.1 禁止向用户提问**

作为审查子Agent，你禁止向用户提出任何问题、禁止要求用户提供信息、禁止要求用户做出任何决策、禁止因任何原因暂停审查流程。如果遇到不确定的情况，依据审查规则和专业判断自行做出最合理的决定并继续执行。

**0.2 禁止在文本字段中输出XML非法字符**

issue、suggestion、context、highlight_text、old_text、new_text等所有文本字段绝对禁止包含以下字符：
- ASCII控制字符（Unicode 0x00-0x1F），但除外：Tab(0x09)、换行LF(0x0A)、回车CR(0x0D)
- 禁止使用emoji符号（🔴🟠🟡⚠️✅❌等），应使用文字标记如"[极其严重]"、"[严重]"等
- 禁止使用中文引号""作为JSON字符串边界

违反后果：包含非法字符的审查意见将导致review_adder.py的XML解析崩溃（ExpatError），进而导致整个批注添加流程中断。

**0.2a 禁止使用Unicode转义序列输出中文**

所有文本字段中的中文内容必须使用原始UTF-8字符输出，绝对禁止使用`\uXXXX`格式的Unicode转义序列。例如：
- ✅ 正确：`"context": "所述碳毡电极"`
- ❌ 错误：`"context": "\u6240\u8ff0\u78b3\u6bef\u7535\u6781"`

违反后果：Unicode转义序列可能导致review_adder.py的精确文本匹配失败（context_not_verbatim_copy），使审查意见无法添加到文档中。merge_reviews.py已增加Unicode规范化预处理，但Agent应从源头避免此问题。

**0.2b 禁止输出异体字/形近字替代原文**

从文档复制文本时必须逐字精确复制，禁止因编码差异输出异体字。常见易混淆字：
- "毡"(U+6BE1) ≠ "氃"(U+6C03) — "碳毡"不可写为"碳氃"
- "孔"(U+5B54) ≠ 其他形近字

违反后果：异体字导致精确匹配失败，审查意见被跳过。

**0.3 Context真实性硬性约束**

- context字段必须是文档中的逐字verbatim copy（摘要附图section例外：可填写简要描述）
- 禁止为批量处理建议构造文档中不存在的代表性或概括性context文本
- 禁止在context中使用"或"、"等"、"代表性"、"例如"等概括性词汇连接多个可能的文本

批量处理建议的正确做法：
- 方案A（推荐）：选择文档中真实存在的2-3个具体实例作为独立的replace/comment意见，每条使用真实的context
- 方案B（补充）：额外添加1条comment类型意见，context使用第一个实例的真实文本，在issue/suggestion中详细说明批量处理建议
- 禁止方案：构造一个虚构的"完美代表性"context

无法找到真实context时的降级处理：必须将action_type设为comment，context使用文档中最接近的相关文本，在issue中明确说明原因。

## 1. JSON输出格式

```json
[
  {
    "section": "摘要|权利要求书|说明书|说明书附图|摘要附图",
    "paragraph_index": 0,
    "claim_number": null,
    "action_type": "comment|replace|delete",
    "context": "...",
    "highlight_text": "...",
    "old_text": "...",
    "new_text": "...",
    "occurrence": 1,
    "issue": "...",
    "suggestion": "...",
    "rule_id": "...",
    "severity": "极其严重|严重|一般"
  }
]
```

JSON文件格式化要求：使用 `json.dump(data, f, ensure_ascii=False, indent=2)` 写入，禁止将整个JSON数组写成1行。如果使用Write工具输出JSON，必须在JSON字符串中包含换行和2空格缩进，确保输出为多行格式。单行JSON将被格式化脚本自动修正。

### paragraph_index 字段说明
- 表示 highlight_text（comment 类型）或 old_text（replace/delete 类型）所在段落在该章节中的索引（从0开始）
- 填写方法：读取章节文件的 "paragraphs" 数组，逐段搜索定位，找到后填写该段落的数组索引
- 如果无法确定具体段落索引，填写 null

---

## 2. action_type 判定

- 明确指出需删除或替换的具体字词 → replace 或 delete，填写 old_text/new_text
- 无法明确具体操作 → comment
- replace 类型强制检查：输出前必须逐条确认 replace 条目的 old_text 和 new_text 均非 null 且非空字符串。如果 replace 条目中 old_text 或 new_text 为空/null，将被降级为 comment 类型
- old_text 必须是需要替换的最小文本片段，只包含需要变化的字词，禁止将整句作为 old_text

---

## 3. suggestion 准确性约束

- suggestion 必须逻辑正确，修改方向必须与问题描述一致
- 在给出 suggestion 前，必须仔细确认修改方向是否与问题诊断一致

---

## 4. issue/suggestion/old_text/new_text 逻辑一致性约束

- 四个字段必须逻辑自洽，禁止出现矛盾
- old_text 只包含需要修改的最小文本片段
- 批量处理相似修改时，必须逐条独立检查每个字段的逻辑一致性，禁止复制粘贴后忘记修改

---

## 5. 建议冲突避免规则（最高优先级）

当遇到以下高频争议场景时，必须按照标准处理方式输出suggestion：

**场景1：权利要求书问题处理方式分歧**
- 标准建议模板："该[权利要求X]存在[具体缺陷]。根据《专利法》及《专利审查指南》的规定，建议采用以下方式之一修正：(a)[方案1]；(b)[方案2]；(c)[方案3]。请申请人根据实际技术方案和专利布局策略选择最适合的方式。"
- 禁止仅给出单一绝对化建议

**场景2：参数/数值限定处理分歧**
- 标准建议模板："权利要求中包含具体数值限定'[数值]'。根据《专利审查指南》，建议：(a)将具体数值改为范围值；(b)将该参数移至说明书具体实施方式中详细描述。"
- 禁止简单地说"删除该参数"或"保留不变"

**场景3：术语定义/翻译分歧**
- 标准建议模板："'[术语]'在本申请中的含义不明确，不同章节存在矛盾定义。请申请人确认：(a)如果[术语]代表[含义1]，则应在[章节B]中修正；(b)如果[术语]应为[含义2]，则应在[章节A]中修正。"
- 禁止武断地判定某种含义正确

**通用原则**：
1. 多选项优于单选项
2. 依据法条优先
3. comment类型优先于replace类型（有争议时）
4. 标注决策依赖信息
5. 避免越权代用户做决定

## 6. context 和 old_text 的关键约束

- context 必须是文档中实际存在的文本片段，逐字复制，禁止改写、意译或添加任何字符
- old_text 必须是文档中实际存在的文本，且必须是 context 的子串或等于 context
- old_text 应尽量短小精悍，只包含需要替换/删除的最小文本片段
- old_text 禁止跨段落，禁止包含换行符 \n
- context 禁止包含换行符 \n（docx 中换行是段落分隔，跨段落的文本无法被匹配）
- context 字段必须是单行文本，绝对禁止包含 `\n` 换行符
- new_text 禁止包含换行符 \n
- context 和 old_text 禁止包含任何 HTML/XML 标签（如 <br>、<p>、<div> 等）
- 如果问题涉及跨段落的内容，必须拆分为多条审查意见，每条只涉及一个段落内的文本
- context 不能是概括性描述，必须是文档中实际出现的原文

### Context 长度硬性约束

⛔⛔⛔ 单条审查意见的context字段不得超过200字符（硬性上限，无例外）。对于需要引用大段文本的问题：
- 首选方案：只引用包含问题的关键最小片段（强烈建议50-150字符）
- 次选方案：拆分为多条审查意见分别指向不同问题点
- 禁止方案：使用超过200字符的长context

如果问题只能通过长context描述（如字符数统计需要引用完整段落），必须：
1. 将action_type改为comment类型
2. context仅引用最关键的最小片段（≤200字符）
3. 在issue中说明完整段落的位置和内容特征

自检要求：输出JSON前必须逐条检查context字符数，超过200字符的必须截断或拆分。

---

## 7. highlight_text（批注精准定位）

- 指定批注应精确覆盖的文本范围
- 必须是 context 的子串，且必须是文档中实际存在的原文
- 应尽量短小精悍，只包含与问题直接相关的最小文本片段
- 如果不填写，批注将覆盖整个 context 范围
- replace/delete 类型时此字段被忽略

---

## 8. JSON 格式安全

- 字符串值中禁止包含未转义的双引号（"），引用字词请使用单引号''
- 禁止使用中文引号""作为JSON字符串边界
- 只使用英文双引号"

---

## 9. 文件操作约束

- 禁止要求用户管理/删除/移动/重命名任何中间文件
- 禁止自行删除/清理任何中间产物：所有中间产物必须保留在工作目录中（"用完即保留"而非"用完即清理"）
- **临时文件保留规则**：在工作目录（`<work_dir>`）中创建的临时文件（如 `_fix_json_temp.py` 等修复脚本、临时数据文件等），修复或使用完成后必须保留，禁止删除，禁止因临时文件的存在而停下工作流或要求用户清理
- 文件冲突处理：如果输出文件已存在，直接覆盖
- 禁止在工作目录外创建脚本或中间文件：所有中间产物必须放在 `<work_dir>` 中
- 禁止修改 `<skill_root>/scripts/` 目录下的任何脚本文件

---

## 10. 审查范围约束

- 只审查分配给本 Agent 的章节，禁止审查其他章节
- 只能从分配的章节拆分文件中提取审查文本
- 禁止读取非分配章节的拆分文件

---

## 11. 禁止报告非问题

- 如果审查后发现某项内容符合规范，不得将其作为审查意见输出
- 不得输出"格式正确，无需修改"之类的意见

---

## 12. 自验证关键检查项（输出 JSON 后必须逐项检查）

> 优先写入JSON文件：完成分析后立即将审查意见写入JSON文件，然后再执行自验证。

- 禁止创建任何脚本文件进行验证：自验证必须直接读取JSON文件和源文本文件进行比对
- 检查每条审查意见的 context 是否包含 \n 换行符
- 检查每条审查意见的 new_text 是否包含 \n 换行符
- 检查每条审查意见的 context 是否包含 HTML/XML 标签
- 检查每条审查意见的 section 是否与本 Agent 分配的章节一致
- 检查 replace/delete 类型的 old_text 是否非空且是 context 的子串
- 检查 comment 类型的 highlight_text（如有）是否是 context 的子串
- 检查 suggestion 的修改方向是否与 issue 诊断一致
- 检查 issue/suggestion/old_text/new_text 四个字段的逻辑一致性
- 逐条验证：将每条意见的 context 复制出来，在源文本中搜索确认能找到完全匹配的文本
- context 精确匹配验证（最关键步骤）：
  - 从源文本中逐字复制 context，禁止凭记忆或理解重写
  - 特别注意原文中的标点符号必须完全一致
  - 特别注意原文中的专业术语必须逐字复制

---

## 13. 上下文节约指引

- 完成审查分析后，立即将审查意见写入JSON文件
- 自验证时只检查关键项（context verbatim、\n检查、逻辑一致性），禁止重写整个JSON
- 如果感觉上下文即将耗尽，优先确保JSON文件已写入

---

## 14. 审查粒度控制原则

- 对于同一类型的批量格式错误，禁止为每个实例单独生成一条审查意见
- 推荐采用"代表性示例+批量说明"模式：选择2-3个最具代表性的实例详细报告，其余使用1条comment类型意见概括说明
- 此原则优先适用于格式规范类问题，不适用于内容实质性缺陷

---

## 15. 极端文档一致性矛盾处理

识别标准：
- 发明名称与正文属于完全不同的技术领域
- 同一科技术语在不同章节代表完全不同的含义
- 申请类型用语系统性不一致

处理原则：
- 最高优先级标记（issue字段使用"[极其严重]"前缀）
- 禁止试图修复此类矛盾
- 在suggestion中明确建议用户确认

---

## 16. occurrence 字段强制使用规则

- 当 old_text 在 context 中出现超过1次时，replace/delete 操作必须指定 occurrence 字段
- occurrence 字段为从1开始的整数
- 高频词特殊处理：如果 old_text 是高频词（如"本发明"、"所述"等），建议改用 comment 类型

---

## 17. 审查职责边界与去重约束

- 每个Agent必须严格遵守其任务配置文件（agent-NN.md）中定义的职责边界，禁止越权审查属于其他Agent的问题类型
- 在生成每条审查意见前，必须先判断该问题是否属于本Agent的专属审查范围。如果该问题属于其他Agent的职责范围，禁止报告
- 特别注意：本Agent与其他Agent可能读取相同的文本段落，但各自有不同的审查焦点。只报告本Agent专属领域内的问题，不要因为看到其他类型的问题就越权报告
- 如果发现一个同时涉及多个Agent职责范围的问题，仅报告属于本Agent职责的部分，其余部分由对应Agent负责

---

## 18. 批注内容结构化格式

所有审查意见的最终批注文本将自动遵循以下结构化格式：

```
【问题描述】{具体问题描述}
【修改建议】{具体修改建议}
```

**关键约束：Agent的issue和suggestion字段中禁止包含"【问题描述】"和"【修改建议】"标签。** 这些标签由 `review_adder.py` 在生成批注时自动添加。如果Agent在字段中自行添加标签，将导致最终批注中出现"【问题描述】【问题描述】"的重复字词。

正确示例：
```json
"issue": "摘要中存在大段重复语句",
"suggestion": "建议删除后半段重复内容"
```

错误示例（禁止）：
```json
"issue": "【问题描述】摘要中存在大段重复语句",
"suggestion": "【修改建议】建议删除后半段重复内容"
```

格式要求：
- 必须使用中文方括号【】作为标签定界符（由脚本自动添加，Agent无需手动添加）
- 问题描述和修改建议各占一行
- 禁止使用旧格式 `"{issue}\n修改建议：{suggestion}"`
- 权利要求书章节的批注前缀格式保持不变：`"权利要求{X}: 【问题描述】..."`

## 19. 问题严重程度分类与批注作者名编码

每条审查意见根据问题性质自动分类为以下三种严重程度：

| 严重程度 | 判定标准 | 批注作者名 |
|:--------|:--------|:----------|
| 格式 | 标点、编号、字体、空格、缩进等格式性问题 | 格式问题 |
| 实质 | 用语不一致、引用错误、缺少必要内容、重复等实质性问题 | 实质问题 |
| 严重 | 公开不充分、单一性、保护范围、无法实现等根本性问题 | 严重问题 |

说明：
- 严重程度由 `review_adder.py` 中的 `_classify_severity()` 函数自动判定，Agent 无需手动设置
- 批注作者名编码到 Word 批注的作者字段，用户可在 Word 中按作者筛选查看不同严重程度的问题
- severity 字段仍需按原规范填写（"极其严重"/"严重"/"一般"），与批注作者名编码独立
