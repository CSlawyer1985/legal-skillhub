# 构建规范：OOXML 细节与字体度量

> **这是"系统怎么工作"的知识**，从 SKILL.md 下沉到这里。
> SKILL.md 只留"要做什么 + 用哪个脚本"；具体怎么写、为什么这么写，查这里。

## 一、段落与字符

1. **中文避让字体归属**：run 的 `w:rFonts` 必须**同时**设 `ascii` / `hAnsi`（西文）+ `eastAsia`（中文）+ `cs`。
   只设 eastAsia 会导致标点、数字走另一套字体，字宽与换行全变。
2. **⚠️ ASCII 字体决定下划线的纵向位置**：`_` 走 ascii 分支。

   | 字体 | `_` 墨迹中心相对基线 | 15pt 时 |
   |---|---|---|
   | 方正楷体简体 | +0.0485 em | 0.73 pt |
   | **Times New Roman** | **+0.1952 em** | **2.93 pt** |

   律协案原件实测下沉 **0.135 em**。用楷体 `_` 时重建下划线比原件**高 2.19~2.44pt**（两个样本一致），
   换 TNR 后残差降到 **0.62~1.25pt**。两款 `_` 的 advance 都是 0.500em、墨迹 0.517em，
   **换字体不改变填空线长度**，纯粹修正纵向位置。这也是公文经典配置（eastAsia=中文，ascii=TNR）。
3. **关闭中英自动间距**：`<w:autoSpaceDE w:val="0"/>`、`<w:autoSpaceDN w:val="0"/>`。
   否则"月"与"2025"之间会凭空多出空隙。
4. **固定行距**：`w:line` = pt×20（twips），`w:lineRule="exact"`。
   用"单倍行距"会让 Word 与 LibreOffice 算出的行高不一致，校对失去意义。
5. **长填空线必须手动断行 + 每行留 ≈8pt 余量**：连续 `_` 在 Word/LO 眼里是**一个西文单词**，
   放不下就**整串挪到下一行**。用段内 `<w:br/>` 在原件的换行位置切开，
   并且**每行宽度比可用宽度少留 8pt**，给 1~2 个 `_` 的估算误差兜底。
   手动断行后第 2 行起自动顶格、不再吃首行缩进——这正是原件的样子。
6. **行末下划线会消失**：行末空格被引擎当尾随空格修剪（连带吃掉其下划线）。
   解法：行末改用 `U+00A0` 不换行空格；或直接用 `_` 字符而非"空格+下划线格式"。
7. **关避头尾**：`<w:kinsoku w:val="0"/>`、`<w:wordWrap w:val="0"/>`。
   ⚠️ **LibreOffice 会忽略这两项**，所以第 5 条的"手动断行 + 留余量"才是真正保命的。

## 二、文档网格 `w:docGrid`（最容易吃暗亏的一条）

**规则：照抄原件；或给每一段都设显式 `w:line`+`lineRule="exact"`；绝不能"删掉网格 + 留几段没有行距"。**

- 律协案原件 `docGrid type="lines" linePitch="312"`（= 15.6pt 行网格）。
- **反证实测**：把原件的 `docGrid` 删掉再渲染，表格横线从 **197.4pt → 160.9pt（位移 36.5pt）**。
- 机制：没有显式行距的段落（如标题、居中的说明行）行高由网格决定；删了网格，行高改成按字体自然行距算。
- 旧版本技能曾写"取消文档网格：删掉 `w:docGrid`"，理由是"方便 LibreOffice 校对"——
  **那是让工具倒逼内容**，代价 36.5pt。已废除。

## 三、字号与字符缩放

`w:sz` 以**半磅**为单位（值 = pt×2），只能表示 0.5pt 的整数倍。
要更细的精度用 **`w:w`（字符缩放，整数百分比）**：

```python
SCALE = {15.0: 102}   # 15.0×102% = 15.30pt（目标 15.318）
_W_SUCC = ('w:kern','w:position','w:sz','w:szCs','w:highlight','w:u','w:effect',
           'w:bdr','w:shd','w:fitText','w:vertAlign','w:rtl','w:cs','w:em',
           'w:lang','w:eastAsianLayout','w:specVanish','w:oMath')
e = OxmlElement("w:w"); e.set(qn("w:val"), "102")
rPr.insert_element_before(e, *_W_SUCC)   # w:w 的合法位置：紧跟 w:spacing
```

- **只在过了 SKILL.md 的三道闸门后用**（先取整档 / ≥3 样本一致 / 有原件照抄）。
- 若渲染器忽略 `w:w`，退化为 15.0pt——**安全兜底，不会失控**。
- **别用一个统一缩放**，每个字号各自定标、各自过闸门。

## 四、表格

1. **`w:tblPr` 的子元素顺序在 ECMA-376 里是强制的**，乱序会被渲染器静默忽略：
   `tblW → jc → tblCellSpacing → tblInd → tblBorders → shd → tblLayout → tblCellMar → tblLook`。
   乱序实测后果：表格整体右移 4pt。同理 `w:pPr`、`w:rPr`、`w:tcPr`、`w:trPr` 都**必须按规范顺序**插入。
2. **表格可以比文本列宽**：原件靠 `jc=center` 居中、两边对称溢出。
   律协案：表格宽 481.5pt / 文本列 415.3pt，溢出 **+66.2pt**。
   **不要去改页边距迁就表格**（我曾把左边距从 90pt 改成 56.17pt，错）。
3. **单元格边距用原件的值**：律协案是 **108 dxa = 5.4pt（Word 默认）**。
   我曾压到 1.4pt 防"表头折行"——那是 LibreOffice 字体回退造成的假象，原文在 Word 里本就 3 行。
4. **边框粗细**：`w:sz` 单位 **1/8pt**。律协案原件 **sz=4（0.5pt）**；我用了 sz=6（0.75pt），偏粗。
5. **列宽必须逐列给**（`w:tblGrid/w:gridCol`，单位 twips），别均分；行高用 `w:trHeight` + `hRule="exact"`。
6. **合并单元格靠"缺线"反推**：某段网格线缺失 ⇒ `w:gridSpan`（横合并）或 `w:vMerge`（纵合并）。
   这是最容易错的一步，错一格整表歪。**未实测**。
7. **跨页表头重复**：表头行要设 `w:tblHeader`。**未实测**。

## 五、参数驱动的构建姿态

`scripts/build_table_docx.py` 的设计立场：**脚本不猜任何参数**。
字体/字号/列宽/行高/边距一律由调用方（JSON spec）给出——参数从哪来（原件，还是像素反推）由人决定。

为什么拆这么开：2026-09-12 复盘证实 **构建环节零缺陷**（同参数 → 与原件的渲染逐条 Δ=0.00pt），
21 项里那 17 项错**全部出在"参数获取与判断"**。所以技能把力气花在参数验证上，构建交给脚本。

spec 结构见 `table-spec-模板.json`；唯一经原件核对的样例见 `table-spec-律协附件3.json`。
**spec 必填 `_sources`**（每个参数的来源等级：原件/实测/反推/先验）。
