# 解析非结构化输入

本技能最理想的情形是 `ambiguity-stress-test` 的结构化输出——每个场景带标签字段的 Markdown。真实用户不一定总能提供这样的输入。本文件描述如何处理更杂乱的情形。

## 三种输入特征

**特征 A——完全结构化。** 带 `### S-N — Title` 标题和标签字段的 Markdown：
```
### S-1 — Title

*Narrative:* ...
*Anchors:* ...
*Family:* ...
*Weak point:* ...
*Likely outcome:* ...
*Redraft:* ...
```
或者使用**粗体标签**而非斜体的变体。两种都常见。直接映射到标准规范字段：
- `Title` → `title`
- `Narrative` 或 `Situation` → `situation`
- `Anchors` → `anchors`（解析逗号分隔的 ID）
- `Family` 或 `Defect family` → `families`（按斜杠或"+"拆分）
- `Weak point` → `weak_point`
- `Likely outcome` → `likely_outcome`
- `Redraft` → `redraft`

叙述部分可能已经内嵌了两个立场——如"公诉方主张……居民主张……"这样的句子。提取它们：
- 查找"The [actor] argues" / "The [actor] contends" / "[Actor] argues" / "[Actor] says"。
- 拆分为两个带 `actor` 和 `argument` 的 `positions` 对象。
- 其余句子（通常是铺垫事实的前 1-2 句）成为 `situation`。
- 如果叙述确实是一个没有明确立场的整体，请用户指明两个对立的主体。

**特征 B——半结构化。** 散文形式的编号场景，每个场景一两段但没有标签字段。有时提到改写文本或"可能结果"但没有标注。应用下面的提取启发式方法。

**特征 C——原始散文。** 提到歧义点但未将其分离出来的备忘录、简报或记录。技能必须做更多工作：识别候选歧义点、提出场景结构、与用户确认。

## 特征 B 和 C 的提取启发式方法

**识别场景。** 寻找以下结构线索：
- 编号或带标签的列表（"First, …"、"Second, …"、"Issue #1: …"）。
- 重复的段落开头（"Another ambiguity arises when…"、"A second problem is…"）。
- 话题转换信号（破折号、项目符号、过渡短语）。

不确定时询问用户："我看到您识别了 [N] 个独立的歧义点——我应该把每个都作为单独的场景处理，还是合并一些？"不要静默合并或拆分。

**识别锚点。** 寻找引文模式：
- 法规：`§ 7.2`、`(b)(3)`、`subsection (a)`、`Section 7.1`。
- 合同：`Section X`、`Clause Y`、`paragraph Z`。
- 规章：`Rule X.Y`、`§ XXX.YY(a)`。
- 意见书：`holding`、`paragraph N`、`the rule of X v. Y`。
如果引用的单元不在 `source.sections` 中，要么添加它（如果它在源文本中但尚未解析），要么标记此不匹配。

**识别缺陷类别。** 阅读散文并分类：
- 讨论*词语的含义* → `vague` 或 `def`。
- 讨论*规则是否触及某主体* → `scope`。
- 讨论*谁的意图重要*或对主观状态的沉默 → `mensrea`。
- 讨论*两条条款指向不同方向* → `conflict`。
- 讨论*某种解读引发合宪性疑虑* → `conlaw`。
- 讨论*无标准的单方权力* → `discretion`。

如果类别确实不清楚，询问。如果多个适用，全部列出。

**识别立场。** 即使在原始散文中，真实的争议也有双方。寻找：
- 对抗性框架（"原告会主张……被告会回应……"）。
- 保守的不确定性表达（"一种解读……另一种解读……"）。
- 政府对公民的模式、买方对卖方的模式、监管者对被监管者的模式。

当散文只勾勒了一方时，**根据文本可能支持的内容构建最强版本的另一方**。然后向用户展示你所做的："我根据您提供的文本勾勒了[对方]的立场——请确认或修改。"

**识别弱点和可能结果。** 这些在非结构化输入中往往留作隐含。可以推断：
- "弱点"是一句描述文本未能说明之处的话。
- "可能结果"是关于争议在相关解释规则或普通法原则下如何解决的保守预测。

如果输入确实两者皆无，技能仍可以仅用情境和立场渲染场景——但分析层会明显单薄。向用户标记此情况并提供补全选项（或请其补全）。

**识别改写文本。** 改写文本是文本上的治疗方案。如果输入没有提出改写，技能可以：
- 基于弱点提出一个（默认行为）。
- 将该字段留空并标记为"由起草人提出"。
- 询问用户偏好哪种。

默认提出改写文本。起草人可以覆盖；空白的改写文本在渲染输出中会显得突兀。

## 源文本解析

规范中的 `source` 块要求将受审文本拆分为可寻址单元。如果输入包含完整源文本，解析它：

**法规。** 对分项标记使用正则表达式——`Sec.`、`§`、`(a)`、`(b)(1)`、`(b)(1)(A)`。构建树：顶层条款是章节标题的子节点；子条款作为 `subprovisions` 嵌套。通过去除括号并拼接来分配 ID：`(b)(6)(B)` → `b6B`。

**合同。** 标题通常带编号（1、2、2.1、2.1(a)）。按层级解析。ID：`s2_1_a`。

**规章。** 与法规类似，但注意渲染器应作为标题处理的"Subpart"和"Part"分组。

**意见书。** 段落可寻址但大多数意见书中没有标签。要么按顺序给段落编号（`p1`、`p2`、……），要么在存在时使用法院自己的编号。"holding"通常可识别；将其标记为顶层章节。

如果解析不确定——编号方案重叠、分项含糊——先生成草稿树并展示给用户更正，然后再构建场景。

## 源文本未提供时怎么办

场景引用的锚点 ID 在渲染器可见的任何地方都不存在。网站/文档会显得损坏：无目标的锚点标签、显示"[source not provided]"的法规页面。

两个选项：
1. **请求源文本。** 几乎总是正确做法。即使粘贴相关章节一次也足够。
2. **以"仅场景"模式渲染。** 跳过网站上的法规面板；跳过 docx/LaTeX 中的法规块。结果可作为备忘录使用，但缺少本技能设计的骨架。仅在源文本确实不可用时使用。

## 展示推断出的内容

解析后，向用户展示提取内容与推断内容的简要摘要：

```
Parsed input:
  - Identified 4 scenarios.
  - Anchored to source sections (a), (b)(2), (b)(7), (c).
  - Inferred defect families for 3 of 4 scenarios; scenario 2 was explicit.
  - Constructed Position B for scenarios 1 and 3 (input had only Position A).
  - Proposed redrafts for all 4; user supplied redrafts for scenarios 2 and 4.

Want me to render this, or do you want to revise first?
```

这可以防止静默过度推断。用户可以在产生任何输出之前更正。
