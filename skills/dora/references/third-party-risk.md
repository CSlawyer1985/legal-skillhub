# DORA——ICT 第三方风险管理参考

第五章，第 28-44 条，《欧盟条例 (EU) 2022/2554》。
关键实施细则：CDR (EU) 2024/1773、CIR (EU) 2024/2956、CDR (EU) 2025/532、CDR (EU) 2024/1502、CDR (EU) 2024/1505、CDR (EU) 2025/295、CDR (EU) 2025/420。

---

## 概述：双轨结构

第五章沿两条平行轨道运行：

**轨道 1——实体层面义务（第 28-30 条）：**
每个金融实体都必须管理自身的 ICT 第三方风险——无论其 ICT 第三方服务提供者（TPSP）是否被指定为关键。

**轨道 2——对被指定关键第三方服务提供者（CTPP）的系统性监督（第 31-44 条）：**
欧洲监管机构（ESAs）指定并监督对欧盟金融部门具有系统重要性的 ICT 第三方服务提供者。这是监管制度，而非实体层面的合规任务。

---

## 第 28 条——ICT 第三方风险的一般原则

### 第 28 条第(1)款——ICT 第三方风险政策
每个金融实体必须通过、定期审查并更新**ICT 第三方风险政策**，涵盖：
- 管理 ICT 第三方风险的目标和原则
- 识别关键与重要功能（CIF）与非关键功能的标准
- 缔约前尽职调查要求
- 合同全生命周期管理（准入、监测、退出）
- ICT 集中度风险管理
- 治理角色与责任

**关键监管技术标准（RTS）：** CDR (EU) 2024/1773 第 1-12 条（政策内容细则）

### 第 28 条第(2)款——维护信息登记册
金融实体必须维护并更新**信息登记册（RoI）**，涵盖**所有** ICT 服务安排（不仅是支持关键功能的安排）。完整字段详情见下文"信息登记册"部分。

### 第 28 条第(3)款——信息登记册年度提交
RoI 必须**至少每年**提交给主管机关，并应具体请求提交。提交格式遵循 CIR (EU) 2024/2956 模板。

### 第 28 条第(4)款——缔约前尽职调查
在签订任何支持关键或重要功能的新 ICT 服务安排之前，金融实体必须：
- **(a)** 评估该 ICT 服务安排是否支持关键或重要功能
- **(b)** 评估安排的风险，包括 ICT 集中度风险
- **(c)** 对拟议的 ICT 第三方服务提供者进行适当尽职调查

尽职调查必须形成文件，并与功能的关键程度相称。

### 第 28 条第(5)款——对 ICT 第三方服务提供者的持续监测
- 在合同全生命周期内监测 ICT 第三方服务提供者的绩效、安全态势和合规情况
- 定期审查，与合同条款和风险状况保持一致
- 核实 ICT 第三方服务提供者持续满足约定的服务水平和安全标准

### 第 28 条第(6)款——ICT 集中度风险评估
金融实体必须：
- 评估因关键功能依赖单一或数量有限的 ICT 第三方服务提供者而产生的**集中度风险**
- 确定任何第三方服务提供者的失败或不可用是否会威胁实体维持关键功能的能力
- 将这一评估形成文件，并将其纳入风险偏好和战略

**常见场景：** 银行将核心银行、资金管理和欺诈检测全部依赖单一超大规模服务商（如一家主要云服务商），即使该服务商未被指定为关键，也会产生高集中度风险。

### 第 28 条第(7)款——退出策略
对于支持关键或重要功能的每项 ICT 安排，金融实体必须：
- 制定并维护**退出策略**，涵盖：
  - 退出的条件和触发点
  - 迁移服务所需的最短通知期
  - 数据可移植性和返还程序
  - 退出的第三方服务提供者的迁移协助义务
- 定期测试退出策略（频率：基于风险）

---

## 第 29 条——ICT 集中度风险初步评估

在签订会导致实体对单一第三方服务提供者的关键功能集中度上升的新安排之前：
- 进行专门的**集中度风险评估**
- 将评估结果和风险缓解措施（如有）形成文件
- 考虑集中依赖的服务商若失败可能产生的系统性影响

这是交易特定义务（由签订新安排触发），而非持续监测义务（由第 28 条第(6)款涵盖）。

## 第 30 条——关键合同条款

### 适用范围：第 30 条第(2)款何时适用？

第 30 条第(2)款适用于支持**关键或重要功能**的 ICT 服务合同。非关键安排适用较宽松的条款组合（第 30 条第(3)款）。

### 关键或重要功能（CIF）

一项功能在以下情形属于关键或重要：其中断会：
- 实质性损害金融实体履行法定义务的能力
- 实质性损害其财务业绩，或
- 实质性损害其服务的稳健性或连续性

识别 CIF 的标准在 CDR (EU) 2024/1773 中有进一步规定。

### 强制性合同条款——第 30 条第(2)款(a)-(i)项

| 条款 | DORA 要求 |
|-----------|-----------------|
| **(a)** 服务描述 | 对将提供的 ICT 服务的清晰完整描述 |
| **(b)** 数据位置 | 提供服务和数据存储/处理的地点，包括位置变更的通知义务 |
| **(c)** 数据保护 | 确保数据保护的条款；遵守适用的数据保护法律（适用时为 GDPR） |
| **(d)** 可用性、真实性、完整性、安全性 | 服务水平规格；安全标准；第三方服务提供者的事件响应义务 |
| **(e)** 审计与访问权 | 金融实体、其主管机关（包括对重要机构而言的欧洲央行 ECB）和处置机关享有**全面且不受限制的审计权**——包括在第三方服务提供者场所进行现场检查的权利 |
| **(f)** 终止权 | 金融实体可终止的条件；最短通知期；第三方服务提供者提供过渡服务的义务 |
| **(g)** 报告与监测 | 第三方服务提供者向金融实体报告 ICT 事件；绩效监测；定期服务审查 |
| **(h)** 数据可移植性与迁移 | 终止时，第三方服务提供者必须提供机器可读格式的全部数据；迁移协助；数据删除认证 |
| **(i)** 分包 | 第三方服务提供者可分包 ICT 服务的条件；事先书面同意要求；子处理者合同中同等合同条款；审计子处理者的权利 |

**关键 RTS：** CDR (EU) 2024/1773 规定了每项条款的详细内容。
**关键 RTS：** CDR (EU) 2025/532 详细规定了分包条款。

### 审计权问题（第 30 条第(2)款(e)项）

最常见的合同缺口：大型云服务商只提供第三方审计报告（如 SOC 2、ISO 27001 证书），而非直接审计权。DORA 第 30 条第(2)款(e)项要求：
- 金融实体享有**全面且不受限制**的审计权
- **主管机关的访问权**——包括检查第三方服务提供者场所的权利

欧洲监管机构（ESA）指引已澄清：
- 在超大规模第三方服务提供者处直接审计确实不可行的情形下，汇总审计或第三方审计（SOC 2、ISO 27001 认证）可部分满足**实体自身的审计权**——但前提是实体以书面记录直接审计为何不可行，并确认汇总审计成果有意义且充分
- 金融实体仍必须记录其对为何可接受汇总审计的评估，并确保获得有意义的、实体特定的成果
- **主管机关（和处置机关）依第 30 条第(2)款(e)项的现场检查权不可放弃。** 即使实体接受汇总审计，合同也必须包含明确、无条件的条款，保留主管机关直接检查第三方服务提供者场所的权利。将机关访问权导向第三方服务提供者第三方审计计划的条款**不满足**第 30 条第(2)款(e)项。这是标准云服务商合同中的常见缺陷。
- 接受汇总审计必须以书面风险接受记录，并由适当治理层级（如 CRO 或董事会）批准

### 非关键安排的宽松条款（第 30 条第(3)款）

对于不支持关键或重要功能的 ICT 服务安排：
- 服务描述
- 数据位置
- 基本可用性和安全承诺
- 事件通知义务
- 退出/终止条款

不要求完整的第 30 条第(2)款条款。

### 第 30 条第(4)款——续约前审查

在续约任何支持关键功能的 ICT 服务合同之前，金融实体必须审查：
- 服务水平是否仍然充分
- 审计和访问权是否仍然可行使
- 退出策略是否仍然可行
- 是否出现新风险（集中度、可替代性）

## 信息登记册——完整字段参考（CIR (EU) 2024/2956）

### 何时维护与提交

- **持续维护：** 订立、修改或终止新安排时更新；子处理者变更时；数据位置变更时
- **年度提交：** 至少每年向主管机关提交一次
- **按需提交：** 应主管机关或 ESA 的具体请求提交（针对第 31 条下 CTPP 的监督框架）

### 信息登记册——要点

1. **所有安排，而非仅关键安排。** RoI 涵盖每项 ICT 服务安排，不仅限于支持关键或重要功能的安排。关键程度标志（字段 12）在登记册内对其进行区分。

2. **必须捕捉子处理者。** 对每项安排，必须识别完整的子处理者链条（字段 22-24）。实践中这一项经常不完整。

3. **不是静态文件。** RoI 必须在全年随安排变化而更新；年度提交是对当前状态的快照。

4. **LEI 是强制性的。** 报告主体和所有第三方服务提供者都必须有 LEI。第三方服务提供者没有 LEI 时，实体应记录这一点，并以该服务商的国家商业登记号作为替代。

## ICT 集中度风险——实务评估

### DORA 下的集中度风险是什么？

**横向集中：** 多个关键功能由单一第三方服务提供者支持（如核心银行、欺诈检测和反洗钱都在同一云服务商上）。

**行业性集中：** 欧盟内许多金融实体对关键功能使用同一第三方服务提供者——即使每个实体自身的依赖看似可控，也会产生系统性风险。

**地域集中：** 所有数据和计算都在单一地理区域或数据中心集群，产生关联失效风险。

### 集中度风险评估模板

对支持关键功能的每个第三方服务提供者，评估：

| 评估领域 | 问题 | 评级（高/中/低） |
|----------------|----------|----------------|
| 依赖深度 | 多少个关键功能依赖该第三方服务提供者？ | |
| 可替代性 | 该服务能否在实体的恢复时间目标内被替换？ | |
| 合同退出 | 是否存在通知期和数据可移植性充分、可行的退出路径？ | |
| 财务稳定性 | 第三方服务提供者破产或停止服务的重大风险是否存在？ | |
| 地域多元化 | 服务是否由地域多元化的基础设施提供？ | |
| 监管可执行性 | 审计和主管机关访问权是否实际可行使？ | |

在任何两个或以上领域被评为高的第三方服务提供者，应视为集中度风险关切，需要采取缓解行动。

## 关键 ICT 第三方服务提供者的监督框架（第 31-44 条）

### 关键 ICT 第三方服务提供者的指定（第 31 条）

欧洲监管机构（EBA、ESMA、EIOPA）依据 CDR (EU) 2024/1502 的标准联合将 ICT 第三方服务提供者指定为**关键**。指定流程：

1. 金融实体每年提交其 RoI
2. ESAs 汇总 RoI 数据，绘制欧盟金融部门对第三方服务提供者的依赖图谱
3. ESAs 应用 CDR 2024/1502 标准评估系统性重要性
4. 被指定的 CTPP 得到通知并公布
5. 为欧盟金融实体服务但未在欧盟设立的 ICT 第三方服务提供者，必须指定一名在欧盟设立的法律代表（第 31 条第(11)款）

### 牵头监督机构分配（第 32 条）

每个被指定的 CTPSP 被分配一名**牵头监督机构**——EBA、ESMA 或 EIOPA 之一——基于其所服务金融实体的主导类型。牵头监督机构通过**联合监督网络（JON）**与其他 ESAs 协调。

**联合检查小组（JET）：** 依据 CDR (EU) 2025/420，JET 由牵头监督机构和国家机关人员组成，对 CTPP 进行现场和非现场检查。

### 监督权力（第 33-38 条）

| 权力 | 说明 |
|-------|-------------|
| 第 33 条——信息请求 | 牵头监督机构可要求 CTTPS 提供信息、数据和文件 |
| 第 34 条——一般调查 | 包括访谈、文件审查 |
| 第 35 条——现场检查 | 对 CTPSP 场所和系统的实体检查 |
| 第 36 条——建议 | 牵头监督机构就改进提出建议 |
| 第 37 条——跟进 | 跟进建议和可能的升级 |
| 第 38 条——监督费用 | 依据 CDR (EU) 2024/1505 的年度费用 |

### CTPSP 指定对金融实体的意义

- 其第三方服务提供者被指定为关键时，金融实体的**直接义务没有变化**——实体在第 28-30 条下的义务无论如何都适用
- 牵头监督机构与 **CTPSP 直接**互动
- 金融实体必须配合牵头监督机构就其使用被指定 CTPP 的信息请求（第 40 条）
- 金融实体应注意，对 CTPSP 的监督建议可能导致服务条款变更——需监测这一点
