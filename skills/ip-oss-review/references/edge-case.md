# 边界样例：AGPL组件在微服务架构中的信息网络传播权触发

## 输入

用户提交一个Python项目的requirements.txt，项目为微服务架构SaaS部署模式。其中一个微服务嵌入了AGPL-3.0许可的组件，其他微服务通过REST API与其通信。

依赖清单包含：
- django (BSD-3-Clause)
- celery (BSD-3-Clause)
- redis-py (MIT)
- mongodb (Apache-2.0)
- aGPL-component (AGPL-3.0) — 一个在关键微服务中使用的图数据库连接库

## 期望行为

1. 加载团队实务配置文件，确认实务画像和OSS策略
2. 识别审查范围为"依赖清单"，部署模式为"SaaS"
3. 逐包分类许可证：
   - django → 宽松型 (BSD-3-Clause)
   - celery → 宽松型 (BSD-3-Clause)
   - redis-py → 宽松型 (MIT)
   - mongodb → 宽松型 (Apache-2.0)
   - aGPL-component → 强copyleft (AGPL-3.0)
4. **关键分析：AGPL网络触发与中国法信息网络传播权的对应**
   - AGPL-3.0第13条：若用户通过网络与修改后的版本交互，须提供源代码
   - 中国法下分析：SaaS部署中，用户通过网络访问包含AGPL组件的服务，此行为是否落入"信息网络传播权"的行使范围？
   - 标记为律师审查——此问题在中国法下尚未经司法确认 `[模型知识 — 需核验]`
   - 列出双方因素：
     - 支持触发的因素：AGPL的合同条款明确要求网络交互时提供源代码；罗盒案确认开源许可证具有合同约束力；SaaS使用可被视为信息网络传播行为
     - 反对触发的因素：信息网络传播权的客体是"作品"本身，而非使用作品的服务；微服务API通信可能不构成"向公众提供作品"；AGPL的网络条款是否属于中国法下著作权人可行使的权利范围存疑
5. **链接分析**：
   - aGPL-component是否静态链接/编译到微服务中？若是 → 强信号表明AGPL触发
   - 其他微服务通过REST API通信 → 子进程/IPC模式，通常不构成演绎作品
   - 但AGPL的网络交互条款独立于链接分析
6. 标记风险级别：
   - aGPL-component → 严重（强copyleft + SaaS部署 + 网络交互条款）
7. **应停止并标记为律师审查**，而非默认为"AGPL触发"或"AGPL不触发"
8. 输出备忘录，包含：
   - 底线结论：**不可发布**，AGPL组件在SaaS微服务架构中的义务触发需律师审查
   - 中国法域注释：详细分析AGPL网络触发与信息网络传播权的对应关系
   - 监管合规：若涉及关键信息基础设施，额外标记
   - 审批路由：自动上报至知识产权律师

## 期望输出要点

- 底线结论明确标注：**不可发布**，AGPL组件需律师审查后再决定
- AGPL分析不给出确定结论，而是列出双方因素供律师判断
- 中国法域注释包含：
  - 信息网络传播权与AGPL网络触发的对应分析
  - 罗盒案对开源许可证合同约束力的确认
  - 明确标注`[模型知识 — 需核验]`
- 监管合规章节评估
- 审批路由明确指向知识产权律师

## 应触发的人工gate或来源标签

- **律师审查gate**：AGPL网络触发的法域分析必须由律师确认，技能不给出确定结论
- `[模型知识 — 需核验]`：AGPL网络触发与信息网络传播权的对应关系
- `[中国裁判文书网]`：罗盒案引用
- `[国家法律法规数据库]`：著作权法第10条引用
- **停止gate**：不可默认为"AGPL触发"或"AGPL不触发"——决策姿态要求争议问题标记为律师审查
- **决策姿态一致性**：此为原版decision posture要求的行为——"over-flagging is a two-way door; under-classifying is a one-way door"
