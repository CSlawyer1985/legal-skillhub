# 合同智囊 v3.4.1 · Contract Advisor

## 概述

本 Skill 提供合同全生命周期管理能力，包含四大核心流程 + 三项平台化增强能力：

1. **审核流程（Review）**：全量审核（传 docx/pdf）+ 增量审核（截图/片段），含五步审查框架（1234法→3D框架→4维标准→9步法→60要点），双版本示范条款自动生成
2. **起草流程（Draft）**：从零起草，支持「深度定制」（逐章确认）和「快速生成」（一键出稿）两种模式，覆盖 21 种合同类型
3. **比对流程（Diff）**：对比 AB 两个版本，识别增删改 + 条款效力影响分析
4. **修订流程（Revise）**：四段式修订版（原条款→简版→全版→理由），支持原生 OOXML Track Changes 写入原文件
5. **平台化增强**：①反馈闭环（定稿处置持久化、反哺 rule-pack）②批量/组合审查（同质合同汇总、主合同+补充协议一致性）③质控指标看板（审查次数/风险分布/误报率），详见「平台化增强能力」章节

## 🔗 外部技能集成地图

本 Skill 集成了清华团队（THUYRan/Legal-Skills-Chinese）和杨卫薪律师（cat-xierluo/legal-skills）的开源法律技能，在以下环节增强合同审查能力。

### 集成架构

```
合同智囊工作流              外部增强技能
───────────────────────    ─────────────────
A1 合同解析与结构拆解  →    legal-element-extraction（九类法律要素提取）
                        →    structured-element-extraction（结构化要素拆分）

A4 风险审核（五步框架） →    legal-risk-assessment（四维度风险评估）
                        →    dispute-issue-identification（争议焦点预判）
                        →    conflict-resolution（多来源条款冲突消解）

A7 示范条款生成         →    legal-interpretation-argument（法条解释论证）
                        →    argument-strength-evaluation（论证质量自评）

A8 输出完整审核报告     →    argument-chain-construction（完整论证链构建）
                        →    legal-norm-validity-check（法条有效性核验）
```

### 各技能接入详解

| 增强点 | 外部技能 | 来源 | 接入方式 | 解决的问题 |
|--------|---------|------|---------|-----------|
| **A1 解析增强** | `legal-element-extraction` | 清华 | 在 A1.2-A1.6 之前调用，将合同全文按「九类事实单元」自动打标（主体→行为→时间→地点→对象→结果→因果关系→主观→程序），输出结构化要素 JSON | 替换手写的 6 个子步骤，将「查找主体」「提取金额」等任务自动化，并标注可能涉及的证据来源 |
| **A1 解析增强** | `structured-element-extraction` | 清华 | 对条款文本做「法律要素→事实→结论」的三层结构化拆分，识别每个条款中的义务-权利-救济链条 | 补上「每项义务→违约责任」的手工匹配短板，自动检测义务条款是否有对应救济 |
| **A4 风险复核** | `legal-risk-assessment` | 清华 | 在五步框架完成后，从「行政许可、监管法规、历史处罚、制度合规」四个维度做系统性风险复核 | 你的 checklist 主要覆盖合同内部，这个补充外部监管和行政合规维度 |
| **A4 争议预判** | `dispute-issue-identification` | 清华 | 对高管用风险条款，预判「将来可能引发的争议焦点、对方可能的抗辩策略」 | 把「这个条款有风险」升级为「这个条款将来可能在 X 场景下引发 Y 争议」 |
| **A4 冲突消解** | `conflict-resolution` | 清华 | 三层比选发现多来源模板条款冲突时，给出采信逻辑和消解建议 | 目前仅有比选矩阵没有冲突消解机制 |
| **A7 论证加强** | `legal-interpretation-argument` | 清华 | 对引用法律依据的条款，按照文义→体系→目的三阶段做深度解释论证 | 审核报告中的法律引用目前只是「引用法条号」，缺少规范解释 |
| **A7 论证自评** | `argument-strength-evaluation` | 清华 | 对高风险条款的论证链做自我评估，从「逻辑完整性、证据支撑度、规范对应度、反方可攻击点」四个维度打分 | 输出前自我质量控制 |
| **A8 报告升级** | `argument-chain-construction` | 清华 | 高风险条款增加完整规范论证段：法律规范→合同事实→论证推理→审查结论 | 审核报告从「发现问题+给建议」升级为「发现问题+论证为什么这是问题+给建议」 |

### 贯穿规则（审核和起草模式全场景强制执行）

1. **"每项义务→对应违约责任"原则**：合同中每发现一条对方应履行的义务，必须检查是否设置了对应违约责任条款。未设置的，报告中标记为缺失风险项。
2. **量化表述检查**：所有使用"合理""适当""及时""必要""重大"等模糊词汇的条款，必须提示风险并给出具体量化建议。
3. **"如果-那么"闭环测试**：每个关键条款用"如果发生X，那么会怎样"的逻辑反推，检查条款是否形成完整保护链。
4. **付款条款保护优先**：站在付款方视角，检查预付款比例是否过高、付款节点是否与履约成果挂钩、是否有拒付权/暂付权。
5. **管辖条款倾向己方**：争议解决条款必须明确唯一管辖机构，优先推荐己方所在地法院。
6. **合同目的明确性检查**：检查鉴于条款是否清晰描述了交易背景和目的，这关联后续的法定解除权。
7. **示范条款可直接使用**：每个简洁版和全面版示范条款必须做到「无需补充即可复制粘贴到合同中使用」。简洁版必须以「本合同第 X 条……」或完整法律句式开头；全面版必须是分款分项的标准合同条款格式。缺失条款的示范条款同样适用此规则。**禁止**以「建议补充XX」「应考虑约定XX」「需要增加XX条款」等方向性概括或审查意见替代完整的示范条款文本。变量值用 `___` 占位，保留填充空间但不缺失核心法律要件。

违反以上任一规则 = Skill 执行失败，用户有权要求重新执行。

### 模式 A：全量审核模式（推荐）

**触发条件**：用户上传完整 docx/pdf 文件。

**核心原则**：全文一次性解析 → 全章交叉对照 → 一次性完整报告 → 避免碎片化遗漏。

#### A0：DOCX 读取与解析

| 子步骤 | 操作 | 工具/方法 |
|--------|------|-----------|
| A0.1 段落提取 | 读取所有段落文本（含标题、正文、签章区） | `python-docx` `doc.paragraphs` |
| A0.2 表格提取 | 提取所有表格的行列内容（含合同标的清单、价格表、验收清单） | `doc.tables` |
| A0.3 Track Changes 提取 | 解析 `<w:ins>`（新增内容）和 `<w:del>`（删除内容），获取对方已做的历史修改 | lxml + OOXML XML 命名空间 `w:` |
| A0.4 结构化拼接 | 将段落、表格、修订标记按原文顺序重组为结构化全文 | 保留原名/表名/修订标记 |

> ⚠️ python-docx 的 `.text` 属性不包含 Track Changes 中修订内容，必须 XML 解析。

#### A1：合同解析与结构拆解

> 🔗 **外部增强可用**：在执行 A1 手写解析前，可先调用 `legal-element-extraction` 将合同全文按九类法律事实单元自动打标（主体/行为/时间/地点/对象/结果/因果关系/主观/程序），再调用 `structured-element-extraction` 识别条款义务-权利-救济链条，输出结果作为 A1.1-A1.6 的输入。说 `--skip-external` 可跳过，使用纯本地解析。

| 子步骤 | 提取内容 | 输出 |

| A1.1 基本信息 | 合同标题、签约日期、合同编号、签署地点 | 基本信息卡片 |
| A1.2 主体信息 | 甲方/乙方全称、法定代表人、地址、联系方式、统一社会信用代码 | 主体清单 |
| A1.3 合同标的 | 标的物/服务的名称、规格、数量、质量标准 | 标的信息 |
| A1.4 金额条款 | 合同总价、计价方式、付款节点、发票要求 | 金额结构 |

#### A2：类型识别 + 法规规则加载

基于合同标题 + 鉴于条款 + 标的条款做语义匹配，识别 21 种合同类型之一。自动加载 `references/rule-packs/{合同类型}/legal_rules.json`，获取必备条款清单、法条锚点（civil_code_chapter / 各规则项的 legal_basis）、强制性规定要点。

按协议锁要求执行：
1. 搜索三个核心 IMA 知识库（合同范本库 + 合同大全3000+ 用于模板比对，法务工作及合同审查用于方法论参考）
2. 大结果抽样（合同大全 3000+ 几乎必然截断）
3. 三层比选矩阵输出（当搜到多份模板时）
4. 全面覆盖提炼：共性条款 + 特色条款，漏缺提醒

#### A3.2：IMA 模板溯源与条款借鉴（协议锁级别强制）

> IMA 搜索和本地模板的价值不只在「找到了什么」，更在于**这些模板中的条款文本直接作为示范条款的写作基础**。以下规则确保模板借鉴的每个环节都可追溯。

**一、每个示范条款必须标注借鉴来源**

无论简洁版还是全面版，每个示范条款末尾必须附加 `📎 借鉴来源` 标注，格式如下：

```
📎 借鉴来源
  · 基础来源：[来源库名/文件名] — [条款名称/位置] — [借鉴方式：完整搬运 / 核心框架 / 关键表述]
  · 补充来源：[来源库名/文件名] — [借鉴的具体表述]
  · 本地融合：[本地参考文件描述，如无可写「无」]
```

借鉴方式说明：
- **完整搬运**：模板条款结构完整、适配度高，原文直接作为基础（★★★★★来源适用）
- **核心框架**：保留模板的条款框架（定义→义务→标准→违约→解约），填充本案具体内容
- **关键表述**：仅提取模板中的特定句式/法律术语/结构设计（如「甲方有权从应付乙方的款项中直接扣除」）

**二、模板条款文本应直接保留为条款基座**

三层比选后确定的 ★★★★★ 来源条款，其成熟的法律表述应**直接保留**在示范条款中：
- 模板中的违约金计算方式、解约程序、通知期限等标准化表述 → 直接搬运
- 仅将变量（人名、金额、日期、地点等）替换为 `___` 占位符
- 禁止将模板条款「用自己的话重写一遍」——导致丢失成熟的法律表述和条款结构

**三、禁止架空编造——示范条款必须有根有据**

```
每个示范条款的产生路径：
  模板条款（IMA/本地）→ 按审查结论调整 → 标准化格式 → 输出
         ↑                                          ↓
  不是：凭空构思方向 → 用通用法律常识填空 → 输出（❌ 禁止）
```

**四、借鉴来源的质量标准**

- 每个示范条款至少标注 **1 个基础来源**（可以是 IMA 模板、本地文件或 rule-pack 法条）
- 缺失条款的示范条款尤其必须标注模板来源（既然缺失，必然是借鉴模板）
- 来源标注不得模糊（禁止「参考了多个模板」「行业通行做法」——必须写出具体库名+条款名）

#### A4：风险审核（五步框架贯穿执行）

> 🔗 **外部增强可用**：五步框架执行完后，可依次调用 `legal-risk-assessment`（行政许可+监管法规+历史处罚+制度合规四维复核）、`dispute-issue-identification`（对高风险条款预判将来争议焦点）、`conflict-resolution`（三层比选发现冲突时消解）。说 `--skip-external` 可跳过。

必须按以下顺序完整执行 5 套审查框架，**不可跳过任何一步**。

**框架①：1234法（审查定位）**

| 层次 | 内容 | 本次审查对应操作 |
|------|------|----------------|
| 1 个中心 | 以委托人为中心 | 明确「我在为谁审？甲方还是乙方？」 |
| 2 个目的 | 防风险 + 促交易 | 区分「纯风险防控」还是「促成签约优先」 |
| 3 个步骤 | 审前沟通→正式审查→交付成果 | 第一次用需沟通；复购场景跳过审前 |
| 4 大重点 | 主体→内容→方式→争议处理 | 四块逐项检查 |

**框架②：3D 框架（三层递进审查）**

| 维度 | 检查项 | 执行要点 |
|------|--------|---------|
| **合法性** | 合同整体是否合法有效？ | 主体资质/签约权限/信用；是否有违法无效内容（民法典 497 条）；必备条款是否齐备（民法典 470 条）；交易目的是否合法 |
| **合规性** | 是否符合公司制度？ | 项目审批流程是否走完；合作方遴选是否合规；与前期文件是否有矛盾；用印签署程序 |
| **合理性** | 条款是否公平可落地？ | 权责对等性；付款节奏合理否；验收标准是否量化；违约责任全覆盖；知识产权/保密/质保完整 |

**框架③：4 维标准（通用风险扫描）**

| 维度 | 逐项打勾清单 | 适用范围 |
|------|------------|---------|
| **法律** | 合同目的合法→主体有资质→条款齐备→损失量化→无违法无效条款 | 所有合同 |
| **制度** | 内部决策完成→供应商选定合规→审核合规 | 企业场景 |
| **国资** | 国资报批→资产评估备案→无代持/对赌 | 国企专属 |
| **商业** | 主体无失信→付款合理→有追偿→退出机制合理 | 所有合同 |

**框架④：9 步法（结构化逐条审查）**

| 步骤 | 审查对象 | 关键检查点 |
|------|---------|-----------|
| Step 1 | 合同主体 | 营业执照/资质/信用/授权→穿透核查 |
| Step 2 | 鉴于条款 | 交易背景描述准确否？目的明确否？ |
| Step 3 | 合同标的 | 名称/规格/型号/数量和权属 |
| Step 4 | 权利义务 | 对等性、可操作性、陈述与保证 |
| Step 5 | 违约责任 | 情形全覆盖→违约金≤实际损失130% |
| Step 6 | 效力/生效 | 签章/条件成就→生效时间→有效期 |
| Step 7 | 解除/终止 | 约定解除权→解除程序→解除后果 |
| Step 8 | 争议解决 | 仲裁vs诉讼→唯一明确管辖→费用条款 |
| Step 9 | 附件附录 | 完整性→一致性→签署 |

**框架⑤：60 要点清单（风险逐项排查）**

分六大类逐项打勾：订立时 12 点、履行中 9 点、企业治理 10 点、劳动用工 14 点、知识产权 10 点、国际贸易 5 点。

#### A5：跨章交叉一致性检查（全量审核特有）

| 检查项 | 检查内容 | 常见问题 |
|--------|---------|---------|
| 术语一致性 | 同一概念在不同章节的表述 | 「交货期」vs「交付期限」vs「供货期」 |
| 权利一致性 | 同一角色的权限范围 | 甲方代表在签收章和变更章中权限不同 |
| 数据流一致性 | 金额/数量/期限在全文各处的引用 | 正文金额与附件清单不一致 |
| 救济闭环 | 每个义务条款是否有对应救济 | 交付义务有违约条款，验收义务无 |
| 缺失检查 | 行业惯例中应有的章节 | 买卖合同无验收条款 |

#### A6：风险定级

| 级别 | 标准 | 示例 |
|------|------|------|
| 🔴 高风险 | 可能导致条款无效、法定权利被剥夺、不可控损失 | 管辖不明、权利剥夺、违约金过高、无解约权 |
| 🟡 中风险 | 权利受损但可补救、商业条款不利但可协商 | 付款节点不合理、验收标准模糊、保密范围过宽 |
| 🟢 低风险 | 表述不规范但不影响效力、缺少非关键条款 | 错别字、缺少通知条款、合同份数未约定 |

#### A7：示范条款生成 ⭐核心

> 🔗 **外部增强可用**：对引用法律依据的示范条款，可调用 `legal-interpretation-argument` 做文义→体系→目的三阶段深度解释论证，然后调用 `argument-strength-evaluation` 对论证链做四维自评打分。说 `--skip-external` 可跳过。

每个风险条款和缺失条款，**必须同步输出两个版本**：

| 版本 | 定位 | 风格 | 适用场景 |
|------|------|------|---------|
| 📝 简洁版 | 最小修改，可直接替换原文 | 精炼、一句话说清、保留原条款结构 | 快速修改、对方接受度高 |
| 📋 全面版 | 完整法律保护，穷举场景 | 分款分项、带违约金和解约权、覆盖扩展风险 | 强势谈判、高风险条款 |

#### A7.1：示范条款完整性标准（协议锁级别强制规范）

> **以下标准优先级等同于协议锁**。不满足以下任意一条的「示范条款」视为未完成，用户有权要求重新审查。

**一、简洁版的硬性标准**

简洁版定位是「最小修改，可直接替换原文」，但**必须是一条完整的、可直接复制粘贴到合同中的条款**，不得是方向性建议或概括性描述。

| 要求 | 正确示例（可落地） | 错误反例（不可落地） |
|------|-------------------|---------------------|
| 含完整法律句式 | 「如乙方未按时交付，每逾期一日按合同总价的千分之一支付违约金。」 | 「建议约定逾期违约金，比例建议千分之一。」 |
| 可独立成条 | 「本合同项下产生的全部内容（包括但不限于直播画面、音频、文字及衍生剪辑）的知识产权归甲方独家所有。」 | 「知识产权应归属甲方。」 |
| 变量用占位符 | 「甲方应在收到乙方合格发票后`___`个工作日内支付。」 | 「付款时间要约定清楚。」 |
| 覆盖本条核心要件 | 至少包含：义务主体+行为标准+违约责任/后果 | 只写义务不写后果 |

**强制规则**：
- 简洁版必须以「本合同第 X 条……」或直接以条款正文开头（含完整法律句式）
- 禁止出现「建议补充」「建议约定」「应考虑」「可考虑加入」「需要约定」等方向性措辞——这些是**审查意见**，不是**示范条款**
- 如果该风险项是对缺失条款的补充，简洁版=该条款的完整最小版本（一条完整条款，含核心要件+基本违约责任）

**二、全面版的硬性标准**

全面版定位是「完整法律保护」，**必须是一条分款分项的标准合同条款**，格式对标正式合同文本。

| 要求 | 标准格式 |
|------|---------|
| 条款编号 | 「第 X 条 [条款名称]」 |
| 分款分项 | 至少 2 款，每款以「1.」「2.」编号 |
| 完整要素链 | 定义 → 义务 → 标准 → 程序 → 例外 → 违约责任 → 解约权（视需要） |
| 变量占位 | 具体数值/人名/日期用 `___` 占位，保留可填充性 |
| 可独立使用 | 将该条款单独抽出、放入任意同类合同，仍是一份完整的合同条款 |

**三、缺失条款的示范条款强制要求**

对于「漏缺提醒」或「建议补充的缺失条款」中列出的每一项缺失条款，**必须输出两个版本的完整示范条款**（格式与风险条款完全相同），**严禁**仅以「建议补充 XX 条款」「应考虑约定 XX」等方向性概括替代。

> 缺失条款的示范条款输出格式与风险条款完全一致：
> ```
> 📌 缺失条款：[条款名称]
>    缺失原因：[该条款的重要性/法律依据/行业惯例]
> 📝 简洁版示范条款：[完整条款文本，可直接使用]
> 📋 全面版示范条款：[分款分项完整条款文本，可直接使用]
> ```

**四、自检清单（生成每一条示范条款后必须逐项打勾）**

```
示范条款完整性自检：[条款编号/名称]
- [ ] 简洁版是完整法律句式（含主体+义务+后果）？不是方向性概括？
- [ ] 全面版是分款分项的标准合同条款格式？
- [ ] 两个版本都可以「复制粘贴即用」，无需律师再补充核心内容？
- [ ] 缺失条款也输出了完整双版本示范条款？
- [ ] 变量值用 ___ 占位？
- [ ] 📎 借鉴来源已标注（见「IMA 模板溯源与条款借鉴」章节）？
以上任一项为 ❌ = 该条示范条款视为未完成
```

#### A8：输出完整审核报告

> 🔗 **外部增强可用**：生成报告前，对高风险条款可调用 `argument-chain-construction` 增加完整论证段（法律规范→合同事实→推理→结论），对引用的所有法条调用 `legal-norm-validity-check` 核验现行有效性。说 `--skip-external` 可跳过。

```
📋 合同基本信息（类型、双方、金额、核心内容摘要）
📊 IMA 模板比对结果

🔴 高风险条款
  - 条款位置 → 原条款 → 风险描述 + 法律依据

## 审核问题台账机制（review-issues-contract.json）

### 设计目的

解决增量审核模式中的三大问题：**片段式摄入导致碎片化**、**前后审核结论不一致**、**问题缺少跟踪状态**。

### 文件位置

`{workspace}/.workbuddy/review-issues-contract.json`

### 文件结构

```json

  "document_version": "版本",
  "contract_type": "合同类型",
  "total_issues": 0,
  "sections_reviewed": ["已审章节列表"],
  "sections_pending": ["待审章节列表"],
  "sections_incomplete": ["部分审完待确认的章节"],
  "last_updated": "ISO 8601",
  "issues": [
    {
      "id": "ISSUE-001",
      "chapter": "第X章",
      "section": "条款名",
      "original_text": "原文",
      "finding": "发现的问题描述",
      "risk_level": "高/中/低",
      "priority": "P0/P1/P2",
      "status": "pending/confirmed/resolved/dismissed",
      "suggestion_type": "modify/add/delete",
      "needs_negotiation": false,
      "brief_suggestion": "一句话建议",
      "model_clause_simple": "简版示范条款",
      "model_clause_full": "全版示范条款",

  ],
  "new_sections_needed": [
    {
      "chapter": "建议新增章节",
      "section": "条款名",
      "reason": "缺失原因",
      "status": "pending_confirmation/confirmed"
    }
  ],
  "cross_cutting_concerns": ["跨章共性问题描述"]
}
```

### 使用规则

1. **每次增量审核前必须读取台账**：确认已审范围、待审范围、已知冲突
2. **每发现一个新问题即时写入台账**：增量追加，不覆盖已有问题
3. **检查冲突**：新问题写入前，检查是否与台账中已有问题冲突
4. **状态流转**：`pending` → `confirmed`（用户确认）/ `resolved`（已写入修订版）/ `dismissed`（用户拒绝）
5. **全量审核后一次性写入全部问题**
6. **台账禁止删除**：问题即使 dismissed 也保留记录，仅改状态

## 起草流程（Draft）

### ⚠️ 起草前置步骤（协议锁）

**开始前先执行规则 0 引用协议锁**。读取审查框架 + 风险模式文件、加载目标合同类型对应的 `legal_rules.json`、回顾会话中全部本地文件并按 P0-P4 分级、搜索全部 IMA 知识库（含大结果抽样 + 全面覆盖提炼）。只有输出完整的加载清单后，才能进入模式选择。

### 模式选择

> 「请选择起草模式：
> A. **深度定制** —— 逐章确认，含条款细节和风险预判（推荐，适合需要完整合同的场景）
> B. **快速生成** —— 一键生成完整框架，条款留占位符」

---

### 模式 A：深度定制

#### 步骤 A1：场景信息采集

通过结构化问答收集：

| 类别 | 信息项 | 用途 |
|------|--------|------|
| 基础信息 | 合同类型、双方全称、所在地、行业 | 确定合同框架和法律适用 |
| 立场定位 | 代表甲方还是乙方 | 决定条款倾向性 |
| 合同标的 | 标的物/服务的具体描述 | 填充核心条款 |
| 金额条款 | 合同总价、计价方式、付款节点偏好 | 构建金额结构 |
| 期限条款 | 合同期限、履行期、特殊时间要求 | 构建时间轴 |
| 特殊需求 | 保密要求、知识产权归属、竞业限制等 | 识别特殊条款需求 |

#### 步骤 A2：结构设计

根据合同类型 + IMA 全面覆盖提炼结果生成定制化大纲。

**标准章节结构**（基于多源提炼）：

1. 合同主体信息
2. 鉴于条款（交易背景与目的）
3. 合同标的（名称/规格/数量/质量标准）
4. 价款与支付方式
5. 双方权利义务
6. 交付/履行与验收
7. 违约责任
8. 保密条款
9. 知识产权（如涉及）
10. 不可抗力
11. 争议解决
12. 合同变更、解除与终止
13. 通知与送达
14. 附则（生效、份数、签章）

不同合同类型会增减章节：买卖合同→增加质保/售后，建设工程→增加工期/变更/验收，技术合同→增加成果归属/侵权责任，委托合同→增加转委托/竞业限制。

#### 步骤 A3：三层比选 + 逻辑审查 + 模板溯源

对 IMA 搜索到的多份模板做比选，确定各章节的最佳条款来源和表达方式。★★★★★ 来源的条款完整搬运，★★★★/★★★ 来源的独有条款补充注入。

比选合并后执行逻辑审查 6 项：
- 前后一致性、术语一致性、条款衔接性、场景适配性、法律合规性、结构完整性

> ⚠️ 起草模式同样受 A3.2「IMA 模板溯源与条款借鉴」约束：每个主要条款在终稿生成时必须标注 📎 借鉴来源（具体库名+条款名+借鉴方式）。起草过程中每章完成时应当记录该章节条款的借鉴来源，供终稿整理使用。

#### 步骤 A4：逐章起草

按确认的大纲逐章撰写。每章完成后暂停确认。每章起草时：
- 引用 IMA 全面覆盖提炼中的共性条款作为基础
- 注入特色条款（标注适配判断）
- 每个义务条款配对应违约责任

#### 步骤 A5：合规校验

起草完成后做全量合规校验：
1. 对照 `legal_rules.json` 逐条检查必备条款是否齐全
2. 对照 `risk-patterns/high-risk-clauses.md` + `risk-patterns/missing-clauses.md` 扫描风险
3. 重新搜索核心 IMA 知识库做最终对标验证
4. 输出 IMA 全面覆盖提炼报告（完整版）

#### 步骤 A6：终稿生成

- 统一格式排版
- 生成 Word 合同文件
- 附加「条款来源说明」页（标注各章节的引用来源和比选结果）

### 版本比对工作流

**步骤 1：确认版本身份**：要求用户指定哪个是旧版（A）、哪个是新版（B）。

**步骤 2：解析两版文档**：分别解析两份文件，提取全文段落结构，建立段落索引。

**步骤 3：差异分析**：逐段比对，将差异分为三类：

| 差异类型 | 描述 | 输出标识 |
|---------|------|---------|
| **新增** | B 版有而 A 版没有的段落 | 🟢 新增 |
| **删除** | A 版有而 B 版删掉的段落 | 🔴 删除 |
| **修改** | 同一位置内容发生变化 | 🟡 修改（标注变化词句） |

**步骤 4：变更合规审查 + 效力影响分析**：
- 对每项「新增」和「修改」内容执行合规检查
- 分析变更对条款效力的影响：新增→是否引入新风险？删除→是否造成保护真空？修改→原保护减弱还是增强？
- IMA 按需定向搜索（仅当变更涉及合规疑点时触发）

**步骤 5：输出比对报告**：包含版本概要、变更统计、逐条变更清单（含效力影响标注）、变更风险评估、总体建议。

## 修订流程（Revise）

修订模式依附于审核流程。审核完成后，用户可选择生成修订版。

### 四段式修订格式（协议锁级别强制格式）

与手册智囊完全一致的输出格式。**每条修改必须完整输出四段式，不得简化**：

```
═══ 修改项 #[序号] ═══

📌 标注
  所在位置：第[X]章 [章节名] / 第[X]条
  原文内容：[逐字引用原文]

📝 简版（最小改动，满足最低要求）：
  [仅修改问题点，保留其余结构]

📋 全版（推荐方案，含完整要素）：
  [重新撰写的完整条款，含定义→触发条件→操作流程→例外→救济]

📄 分析 + 理由
  修改原因：[违法风险 / 商业不利 / 缺失条款 / 行业对标差异 / 逻辑漏洞]
  法律依据：[法条 + 司法解释 / IMA 模板来源 / 判例参考]
  修改方向：[一句话概括要达到的目标]
```

**禁止简化条款优化输出**：不得以「建议改为XXX」代替完整四段式。不输出完整四段式（标注→简版→全版→分析+理由）= 该条修改视为未完成。

### 修订落痕分流规则（账本 → 落痕决策）

审核结论（四段式）告诉用户「改什么、为什么」，但**写进 Word 时到底哪些直接改、哪些只批注、哪些只进意见书**，必须按本规则分流。规则以 `review-issues-contract.json` 账本为唯一数据源，落痕前只认 `status=confirmed`。

**三种落痕通道**

| 通道 | 触发条件 | 落痕动作 | 产物 |
|------|---------|---------|------|
| 🟢 直接修订（revise） | `status=confirmed` 且非「需谈判」 | 原文件加 `<w:ins>/<w:del>` 原生修订 | 修订稿 docx |
| 🟡 仅批注（comment） | `status=confirmed` 但 `needs_negotiation=true`（高风险 / 商业取舍 / 改变交易结构） | 不写原文件，仅生成批注说明，汇入意见书 | 审核报告 / 意见书 |
| ⚪ 仅进意见书（opinion） | 用户选择「出正式意见书」或问题为提示性低风险 | 不触碰原文件 | 意见书 |

**edit_policy 三档（开头可声明，默认 balanced）**

- `revise-first`：能直接改的尽量直接改，仅把真正需谈判的转批注；用户追求「拿去就能用」
- `balanced`（默认）：低风险 / 中风险直接改，高风险且需谈判的转批注 + 进意见书
- `comment-first`：全部先批注，不落痕；用户逐条确认后再生成修订稿

**最小必要修改原则**：`replace` 时只改问题点、保留原文其余结构；不整段重写，除非用户明确选「全版示范条款」。

**落痕前置门禁**：`status≠confirmed` 一律不落痕；`pending/dismissed/resolved` 仅留在台账。

**确定性渲染（hybrid 架构）**：用户说「生成修订稿」时，调用 `scripts/ledger_to_revision.py`，把账本中 `confirmed` 问题收成结构化 render plan（补 `action` 类型 + 精确 `replace` 目标文本 + `needs_negotiation`），再一次性确定性应用到原 docx。此举保留「AI 直接看真实 XML 做四段式判断」的精度优势，同时获得「可复现、可归档、修订收敛」的工程收益——**不改为 contract-copilot 那种全量 plan-first**。

### 修订模式工作流

> ⚠️ **默认路径**：优先走步骤 5.5「确定性落痕」（调用 `scripts/ledger_to_revision.py`，以账本 `confirmed` 问题为数据源）。纯手工四段式插入（步骤 3）为兼容后备，**不再默认**。

**步骤 1：确认修改范围**：列出全部修改建议供用户勾选，默认全选。

**步骤 2：解析原文档**：使用 `python-docx` 读取原始合同，保留结构和格式。

**步骤 3：逐条四段式插入**：对每条修改，在原段落下方依次插入原条款块 → 简版修改块（红色 #CC0000）→ 全版修改块（红色 #CC0000）→ 分析+理由块（灰色 #888888）。

**步骤 4：添加修订说明页**：在文档开头插入修订日期、依据、条款清单。

**步骤 5：输出**：文件命名 `{原文件名}_修订版_{日期}.docx`。**文档末尾必须附加「参考文献」页（生成规范见「参考文献页生成规范」）**与「免责声明」（见「交付物免责声明」）。

**步骤 5.5：确定性落痕（推荐）**：优先调用 `scripts/ledger_to_revision.py`，以账本 `confirmed` 问题为数据源生成修订稿（见「修订落痕分流规则」）。脚本会输出 render plan（可复核）并归档执行日志。纯手工四段式插入仍可用，但不再默认。

> 生成后衔接：用户可说「原文件修订」把修订应用到原始 docx（即运行该脚本），或说「定稿学习」让我从最终定稿反推修改偏好。

### 参考文献页生成规范

修订模式步骤 5 与全量模式报告均要求附加「参考文献」页。本节定义其**数据来源**与**生成步骤**，避免空泛堆砌或编造条文。

**数据来源（仅列本次审查真实引用 / 依据的条目）**
1. **rule-pack 法条锚点**：已加载的 `references/rule-packs/{合同类型}/legal_rules.json` 中：
   - `civil_code_chapter` 字段（如「《民法典》第二十五章 中介合同（第961-966条）」）
   - `penalty_provisions[*].legal_basis`、`special_rules[*].legal_basis` 等含 `legal_basis` 的字段
2. **外部检索结果**：用户触发「查法条」「检索知识库」或协议锁命中的北大法宝 / WebSearch 结果，取实际引用到的条文与判例
3. **用户提供的资料**：对话中用户明确引用的合同模板、函件、在先裁定等

**生成步骤**
1. **汇总**：遍历本次审查输出的每条风险 / 修改，收集其引用的上述来源
2. **去重**：同一法规多条引用合并为一行（保留最具体的条号）
3. **归一化格式**（每条一行，按「法律法规 / 参考判例 / 用户资料」分组，组内编号）：
   - 法律法规：`[n] 《法规名》第X条 — 要点（来源：rule-pack 中介合同 / 北大法宝）`
   - 参考判例 / 模板：`[n] 案号或模板名 — 要旨（来源：IMA 知识库 / 用户提供）`
4. **附加**：在文档末尾插入分页符 + 标题「参考文献」+ 编号列表，作为独立页
5. **空源处理**：若本次审查未引用任何外部依据（仅依据通用法律常识），参考文献页仅列 rule-pack 的 `civil_code_chapter`，**不得编造条文**

**触发与位置**
- **修订模式**：步骤 5 输出时随免责声明一并附加
- **全量模式**：报告末尾可选附加——当用户触发过外部法条检索，或审查结论实质依赖了 rule-pack 法条锚点时附加；纯通用审查可不附

## DOCX 文件读取技术指南

### 段落和表格提取
```bash
python3 -c "
from docx import Document
doc = Document('合同文件路径.docx')
for p in doc.paragraphs:
    print(p.text)
for table in doc.tables:
    for row in table.rows:
        print([cell.text for cell in row.cells])
"
```

### Track Changes 修订标记提取
```bash
python3 -c "
from docx import Document
from lxml import etree
doc = Document('合同文件路径.docx')
body = doc.element.body
ns = {'w': 'http://schemas.openxmlformats.org/wordprocessingml/2006/main'}

# 提取新增内容
for ins in body.findall('.//w:ins', ns):
    text = ''.join(t.text or '' for t in ins.findall('.//w:t', ns))
    if text.strip(): print(f'INS: {text}')

# 提取删除内容
for d in body.findall('.//w:del', ns):
    text = ''.join(t.text or '' for t in d.findall('.//w:delText', ns))
    if text.strip(): print(f'DEL: {text}')
"
```

> ⚠️ python-docx 的 `.text` 属性不包含 Track Changes 中的修订内容，必须用 XML 解析 `<w:ins>` 和 `<w:del>` 元素才能获取完整修改。

## 定稿学习机制

**触发条件**：审核完成后，用户上传修改后的最终定稿版本，或说「上传定稿」「学习定稿」。

用户上传修改后的合同时，执行以下学习流程：

1. **XML 修订标记比对**：提取 `<w:ins>` 新增内容和 `<w:del>` 删除内容
2. **逐条对照审核建议**：将用户的修改与审核建议逐条匹配，记录：
   - 完全采纳的建议（用户偏好确认）
   - 部分采纳的建议（用户做了何种调整）
   - 未采纳的建议（可能的原因）
   - 用户自主新增的修改（补充到知识库）
3. **输出学习摘要**：告知用户已学习到的修改模式
4. **持久化闭环**：将本次采纳/驳回结果通过 `scripts/feedback_loop.py` 落盘（见「平台化增强能力 · 反馈闭环」），供同类合同下次审查调整默认置信度——形成「审查→定稿→反馈→更准」的飞轮

## 平台化增强能力：反馈闭环 / 批量组合审查 / 质控看板（v3.3.0）

> 这三项能力互相咬合，构成「越用越准、越用越省」的产品底座：反馈闭环产出误报率 → 质控看板消费误报率 → 批量/组合审查在常法规模化场景复用单合同审查资产。

### 一、反馈闭环（持久化学习）

在「定稿学习机制」基础上，把律师对每条审核结论的最终处置落盘为可复用的统计：

**触发**：用户上传定稿（含 Track Changes）或说「上传定稿」「学习定稿」时，运行：

```bash
python3 scripts/feedback_loop.py classify --ledger {workspace}/.workbuddy/review-issues-contract.json --final {定稿.docx} --out references/feedback/feedback-<合同>.json
python3 scripts/feedback_loop.py update-stats --feedback-dir references/feedback --out references/feedback/feedback_stats.jsonl
```

- `classify`：比对本合同原台账与定稿修订痕迹，逐条判定 `accepted`（原文删除且示范条款进入）/ `partial`（原文删除但示范条款未完整进入）/ `rejected`（原文保留=未采纳），并提取用户自主新增条款
- `update-stats`：累加为 `合同类型|章节` 维度的采纳/部分/驳回计数，写入 `references/feedback/feedback_stats.jsonl`
- `report`：打印各章节采纳分布与整体误报率

**反哺规则**：下次审查同类合同时，加载 `feedback_stats.jsonl`，对「驳回率 ≥ 50%」的章节：①默认风险定级下调一档并标注「历史常驳回，建议人工复核」；②在报告中提示该章节的高驳回背景，避免重复误报。

### 二、批量审查汇总

常法常遇到数十份同质合同（如 50 份员工劳动合同）。每份仍走单合同审查产出 `review-issues-<合同>.json`，随后聚合：

```bash
python3 scripts/batch_review.py --ledger-dir {台账目录} --out batch_report.md
```

输出：①各合同风险画像表；②跨合同共性高风险章节（同章节在 ≥2 合同为高风险）；③跨合同条款一致性提示（同章节在不同合同定级不一致，提示审查标准是否统一）。

### 三、组合一致性校验

主合同 + 补充协议 + 附件往往由不同人起草，易出现主体/金额/管辖矛盾。Agent 从各文件提取关键字段填入 manifest，再校验：

manifest 示例：

```json
{
  "main":         {"parties":["甲方","乙方"], "amount":"100万", "penalty":"...", "jurisdiction":"大连", "term":"1年"},

输出：主体与管辖冲突为 🔴 高风险，金额/期限/违约差异为 🟡 需结合交易结构判断。

## 输出规范

### Word 文档格式

使用 python-docx（与本 Skill 全部脚本一致，运行环境已预装）：

> ⚠️ **v3.4.1 字体规范强化（必读）**——下方"字体"行的核心要求是**每条 Run 都必须同时设置 Latin 字体（`font.name`）和 East Asian 字体（`font.east_asian`）**。**只设 `font.name = 'SimSun'` 不够**——Word 会按系统默认 East Asian 字体（如 PingFang SC / 微软雅黑）回退渲染中文，导致同一行内不同字符出现粗细/字形不一致（典型表现：少量汉字看上去被"自动加粗"、标点偏移、字距不均）。这是 v3.4.0 报告的实测 bug，已在本节修复。

**字体规范（v3.4.1 强制）**

| 用途 | 字体 | 字号 | 颜色 |
|------|------|------|------|
| 中文正文 | 宋体（east_asian = 'SimSun'） | 12pt | 黑 |
| 英文/数字 | 同上（latin = 'SimSun'） | 12pt | 黑 |
| 标题（一级） | 黑体（east_asian + latin = 'SimHei'） | 15pt | 黑 |
| 标题（二级） | 黑体（east_asian + latin = 'SimHei'） | 13pt | 黑 |
| 修订新增/修改 | 宋体（east_asian + latin = 'SimSun'） | 12pt | 红色 #CC0000 |
| 修订说明/借鉴来源 | 宋体（east_asian + latin = 'SimSun'） | 10.5pt | 灰色 #888888 |
| 高风险标识（🔴） | — | 12pt | 红色 #CC0000 |
| 中风险标识（🟡） | — | 12pt | 棕黄 #CC8800 |
| 低风险标识（🟢） | — | 12pt | 绿色 #006400 |

**排版规范**

- 行距：1.5 倍
- 页边距：上下 2.54 cm，左右 3.18 cm
- 段落间距：标题前后 6pt
- 加粗控制：仅用于"标题文字 / 关键标识 / 条款编号（如 R1、🔴）"，**禁止在段落中间做局部加粗**——这是产生"半行字粗细不一"最常见的原因

**辅助函数模板（必须在脚本顶部定义，不能直接 `add_paragraph()`）**

```python
from docx import Document
from docx.shared import Pt, Cm, RGBColor
from docx.oxml.ns import qn  # ← 关键：用于直接操作 OOXML 设置中文字体

doc = Document()

# 1. 页面设置
for section in doc.sections:
    section.top_margin = Cm(2.54)
    section.bottom_margin = Cm(2.54)
    section.left_margin = Cm(3.18)
    section.right_margin = Cm(3.18)

# 2. Normal 样式：同时设 Latin 和 East Asian
style = doc.styles['Normal']
style.font.name = 'SimSun'
style.font.size = Pt(12)
# 关键：直接改 OOXML 让 east_asian 也指向 SimSun
rpr = style.element.get_or_add_rPr()
rfonts = rpr.find(qn('w:rFonts'))
if rfonts is None:
    from docx.oxml import OxmlElement
    rfonts = OxmlElement('w:rFonts')
    rpr.append(rfonts)
rfonts.set(qn('w:eastAsia'), 'SimSun')
rfonts.set(qn('w:ascii'), 'SimSun')
rfonts.set(qn('w:hAnsi'), 'SimSun')

# 3. 通用辅助函数
def set_run_font(run, font_name='SimSun', size_pt=12, bold=False, color=None):
    """设置 Run 的 Latin + East Asian 字体（必须同时设）。"""
    run.font.name = font_name
    run.font.size = Pt(size_pt)
    if bold:
        run.font.bold = True
    if color:
        run.font.color.rgb = RGBColor(*color)
    # 关键设置：east_asian 通过 OOXML 写入
    rpr = run._element.get_or_add_rPr()
    rfonts = rpr.find(qn('w:rFonts'))
    if rfonts is None:
        rfonts = OxmlElement('w:rFonts')
        rpr.append(rfonts)
    rfonts.set(qn('w:eastAsia'), font_name)
    rfonts.set(qn('w:ascii'), font_name)
    rfonts.set(qn('w:hAnsi'), font_name)

def add_para(text, bold=False, color=None, size=12, font='SimSun'):
    """添加段落（统一字体处理）。"""
    p = doc.add_paragraph()
    run = p.add_run(text)
    set_run_font(run, font_name=font, size_pt=size, bold=bold, color=color)
    return p

def add_heading_cn(text, level=1):
    """添加中文标题（黑体）。"""
    sizes = {1: 15, 2: 13, 3: 12}
    p = doc.add_paragraph()
    run = p.add_run(text)
    set_run_font(run, font_name='SimHei', size_pt=sizes.get(level, 12), bold=True)
    return p

def add_red(text): return add_para(text, color=(0xCC, 0x00, 0x00))
def add_grey(text): return add_para(text, color=(0x88, 0x88, 0x88), size=10.5)
```

**常见错误与自检**

```
❌ 错误：run.font.name = 'SimSun' 后直接保存
   → Word 中"部分汉字变粗/变形"，这是 East Asian 字体未设置导致
✅ 正确：调用 set_run_font() 同时设置 Latin 与 East Asian

❌ 错误：段落正文里随意加粗（如对"迟到""擅自下架商品"等单独加粗）
   → 产生"半行字粗细不一致"，视觉极其杂乱
✅ 正确：仅在标题/编号/危险标识处加粗，正文不加粗

❌ 错误：用 doc.add_paragraph() 后直接 .add_run(text)
   → 同样会出现字体不一致
✅ 正确：所有 Run 通过 set_run_font() 统一处理
```

## 法条检索独立入口

「查法条」是高频独立需求，不必强制走完整审核流程。当用户说「查法条 [法条号 / 关键词]」「这条法律依据有效吗」「XX 条怎么规定的」时：

1. 优先 `mcp__pkulaw`（若已连接）检索现行法条全文 + 有效性
2. 其次 WebSearch 检索法条文本 + 最新修订 / 司法解释
3. 兜底检索本地 `references/rule-packs/{类型}/legal_rules.json` 中的法条锚点（civil_code_chapter / 各规则项的 legal_basis）
4. 输出：法条全文 + 生效状态 + 关联司法解释 + 在本案中的适用提示（一句话）

> 该入口与审核流程解耦：用户可随时调用，不影响正在进行的审核 / 起草会话。
