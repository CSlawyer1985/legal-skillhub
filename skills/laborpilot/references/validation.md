# 独立验证规则

> 废止复核（2026-09-07）：警示不等于获准采用；已知废止身份必须触发当前引用阻断。历史参考与正式法源分列，检查摘录、旧缓存及编译知识是否保留警示。

## 机器报告契约

- `record-validation --report` 只接受 JSON object，顶层必须包含 `status` 和 `findings` 数组。
- 验证结论为 `pass` 或 `escalate` 时必须提供上述 JSON 报告；仅在命令行自报状态而不附报告会被拒绝。
- Markdown 可作人读附件，但不得代替 JSON 状态记录。
- `findings` 至少保留问题 ID、严重程度、描述、处理方式和受影响节点。
- 对抗报告必须由 `scripts/adversarial_validation.py` 生成，`validator` 固定为 `laborpilot-adversarial-validator`，并包含报告版本、业务状态摘要、六项检查、事实冲突矩阵、程序完整性矩阵、逐争点挑战矩阵和问题清单。
- 工作流登记时按当前案件状态重新生成预期业务结果并逐字段比较，同时保存报告文件 SHA-256。业务状态变化、报告内容被修改、挑战矩阵为空或手工拼装报告时，验证记录不得通过节点。

## 确定性检查

- `case_state` 必填字段、ID 唯一性和引用完整性。
- 每个 `supported` 事实至少有一个材料来源。
- 事实冲突不得自引用或引用不存在的事实，关系及状态必须双向一致；未解决冲突必须写明说明和待核实行动，且不得将任一冲突事实静默标记为 `supported`。
- 争点路由按案件需要动态召回并覆盖相关争点；不输出完整知识卡正文、原始字段、内部卡号或案由门卡。
- `python3 scripts/domain_eval.py` 通过；数据集同时覆盖单一争点、复合争点、否定语境和非劳动争议，法律版本时间线无重叠、无空档且生效边界断言通过。评测数据不得含内部卡号或案由门字段。
- 争点发现结果只是 `to_review` 候选，不写入 `issues[]`。通过节点的正式争点必须为 `reviewed`，包含我方路径、构成要件、对方最强观点与回应、备选路径或无备选理由、失败后果。
- 构成要件和对方路径引用的 `fact_id`、`evidence_id` 和 `rule_id` 必须在案件状态中真实存在；非 `supported` 要件必须列明缺口。
- 每个争点构成要件必须有证据链或缺口链，不得以豁免、待复核骨架或只含 `evidence_id` 的占位记录代替。
- 证据链与构成要件、对方路径之间的 `evidence_ids` 必须双向一致；事实和材料引用必须真实存在。
- 单位掌握证据的链条必须记录劳动者初步举证、证据控制方、责任转移条件及举证不能后果。非充分证据必须列明缺口和行动；评估为充分时至少有一项已关联材料且真实性状态已明确的可用证据。
- 法源骨架和内置知识线索不得写入正式 `rules[]`。每个争点构成要件须关联至少一条已核验且明确适用的法源，不得豁免。
- 正式法源须具有完整条文及匹配的 SHA-256、官方来源或法律数据库 URL、检索时间、效力层级与起止日期、地域范围、本案相关日期和适用理由。地方规则与案件管辖地错配，或相关日期不在效力期间的，不得标记为适用。
- 法源与构成要件、对方路径之间的 `rule_ids` 必须双向一致。已修改、废止或失效规则须显式警示，不得静默当作现行规则采用。
- `VERSION`、Plugin 清单、根 Skill、子 Skill、知识统计清单、领域评测数据与 `CHANGELOG.md` 版本一致，`python3 scripts/sync_version.py --check` 通过。
- 每个请求／抗辩关联争点、事实、证据和法源。
- 金额型请求与计算记录通过 `claim_id`／`calculation_id` 双向关联，金额、状态、争点、法源和待确认项一致；金额节点不得豁免。
- 每个数值输入都具有已登记的来源 ID；公式输入和参数不得缺失、拼错或包含未使用字段。N、N＋1、2N 必须明确记录封顶是否适用，适用时须解析三倍社平工资封顶参数。
- 已解析参数须保存参数包路径、版本和匹配的 SHA-256，并覆盖本案相关日期与地域；参数来源须保存格式合法的官方来源 URL。
- 状态为 `calculated` 的记录须按当前公式版本重新计算，金额、算式、中间步骤、`ROUND_HALF_UP` 精确到分的舍入口径及内容摘要全部一致。状态为 `needs_confirmation` 时必须列明待确认输入，且不得生成金额、算式或步骤，也不得通过金额节点。
- 每个已复核争点均有程序分析，关联的 `claim_ids` 真实存在且属于该争点；时效、管辖、一裁终局、临时救济和后续救济路径字段完整。
- 程序分析引用的法源必须已核验、已采用、明确适用并属于对应争点；管辖记录与当前案件地域一致，程序分析日与当前案件分析日一致。
- 明确标记时效内或时效外时，起算日和截止日必须完整，且截止日与分析日的先后关系必须支持该结论。
- `procedure_digest` 必须与当前程序分析内容一致。存在 `pending_items` 时只能保留 `needs_confirmation`，不得通过 `reviewed_procedure_path`；该门禁不得豁免。
- 引用法源具有文档和条文锚点，废止或异常项未被静默采用。
- 内部产物和正式产物具有明确交付层级；正式产物具有业务来源摘要、直接上游、生成器、LaborPilot 版本、文件版本、哈希、生成者和生成时间。
- 正式 DOCX 重新打开后须通过 JLS 版式结构校验，覆盖字体、字号、固定 25 磅行距、段落对齐与缩进、页面、表格和落款；最终提交版还须阻断内部占位标记和行动清单。
- 原始材料具有来源哈希和页码定位；OCR 或其他派生结果具有本地路径与复核状态。
- 处理任何案件材料前，`task_context`、`representation` 和 `stage` 均已获得用户确认。
- 当前节点在工作图中存在，且没有尚未修复的上游 `return`、`failed`、`paused` 或 `escalated` 结果。
- `representation=undetermined` 或 `stage=undetermined` 时只能停留在 `task_intake`，不得处理材料或进入实体节点。
- 起草节点前存在起草授权与临时策略记录；用户明确请求特定文书时可以此作为授权，但互斥立场未决时仍必须暂停。交付前的独立验证必须绑定实际文件，律师审批必须绑定同一正式产物及其全部必需验证报告；最终提交版须直接派生自当前哈希已获批准的初稿，并作为新产物重新验证、重新审批；阶段结案时重新复算完整追溯链。

## 对抗性检查

1. 将我方最重要结论作为待证命题，寻找能推翻它的事实、证据和法律规则。
2. 检查对方最强观点是否被弱化或遗漏。
3. 检查主体、关系性质、仲裁前置、管辖、时效、终局裁决及救济路径。
4. 检查结论是否将当事人陈述或对方主张写成已证事实。
5. 说明当前分析最可能失败的边界条件。

上述检查必须在对抗报告中形成可重算业务结果：`opponent_case` 检查对方最强论证、引用、回应及待核实事项；`failure_boundaries` 检查失败后果与备选路径；`fact_layering` 检查已证事实与单方陈述、对方主张、争议或待核实事实是否混用；`fact_conflicts` 检查冲突关系、处理状态和待核实行动；`citation_consistency` 复核争点、证据、法源和金额之间的结构化引用；`procedure_completeness` 检查时效、管辖、一裁终局、临时救济、后续救济和程序摘要。事实或程序状态变化后，旧报告必须失效。不能只写一段“已完成对抗审查”的说明。

## 结果严重程度

- `blocker`：不得进入下一节点。
- `high`：原则上返回修复或升级律师。
- `medium`：允许带显式风险进入审批。
- `low`：记录后可继续。
