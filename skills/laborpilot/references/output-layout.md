# 案件工作区与交付物规范

## 两层目录

工作图可以有多个节点，但不得把每个节点都暴露为一份律师交付物。

```text
<case-root>/
├── 01_律师复核初稿/
│   ├── 02_<当前任务文书>_律师复核初稿_v1.docx
│   └── 04_待补材料与行动清单_律师复核稿_v1.docx
├── 02_最终提交版/
│   └── 02_<当前任务文书>_最终提交版_v1.docx
└── .casework/
    ├── case_state.json
    ├── history/
    ├── materials/
    ├── intake/
    ├── issue_analysis/
    ├── evidence_analysis/
    ├── authority/
    ├── drafting/
    ├── validation/
    ├── calculations/
    └── logs/
```

- 律师实际阅读的 `.docx` 按交付层级进入两个独立目录。`01_律师复核初稿/` 可保留待确认标记供复核；`02_最终提交版/` 只放已通过最终门禁的新文件。Markdown 只作内部工作稿，放入 `.casework/`；只有用户明确要求 Markdown 时，才可作为用户侧成果。
- OCR、分页图、材料索引、事实时间轴、争点候选、请求／抗辩矩阵、证据链骨架与正式证据／举证责任矩阵、法源核验任务与适用性矩阵、节点检查点、金额计算骨架与台账、验证报告一律进入 `.casework/`。
- 对原始案件文件保持只读；如果原件在案件根目录外，只在状态中登记路径和哈希，不为了“齐全”而复制。

金额骨架与正式台账位于 `.casework/calculations/`。骨架只供 Agent／律师确认公式与输入，不写入正式请求；`ledger.json` 是机器复算和产物哈希的依据，`ledger.md` 用于人工复核。动态参数可来自内置或外接版本化参数包，但台账必须保留参数包版本、路径、SHA-256、效力期间、地域和官方来源，不把年度数值只写成无法追溯的裸值。

文书生成时以案件根目录作为 `--output`，生成器再按 `--delivery-status` 选择 `.docx` 子目录；`.casework/drafting/` 保存 Markdown 和 JLS 版式验证报告。必须用 `--types` 明确指定本次文书，不得顺带生成未请求文件。Pandoc 转换或 JLS 版式校验失败时，内部文件可以保留供排障，但不能登记为已完成的用户侧文书产物。

起草输入 JSON 和内部 Markdown 使用 `internal_work_product` 登记；`01_律师复核初稿/` 中的 `.docx` 使用 `lawyer_review_draft` 登记。最终提交版必须直接派生自当前文件哈希已获律师批准的初稿，在 `02_最终提交版/` 新建文件和 `artifact_id`，再重新验证、重新审批；不得覆盖或改写初稿。正式产物通过 `source_refs[]` 关联事实、证据、法源、请求、计算和经确认决定，通过 `derived_from[]` 关联直接上游。完整规则见 [正式产物端到端追溯契约](artifact-traceability.md)。

## 单一案件状态

1. 首选状态路径是 `<case-root>/.casework/case_state.json`。
2. 每次转换就地更新该文件；更新前自动将旧状态存入 `.casework/history/`。
3. 不在根目录生成 `case_state_v2.json`、`case_state_intake_v1.json` 等节点快照。
4. 兼容旧案件时可读取根目录的 `case_state.json`，但下一次整理应迁入 `.casework/`。

## 整合式写作

- `intake`、`issue_analysis`、`evidence_analysis`、`authority_research` 和 `claims_procedure` 共同更新同一份《案件研判报告》的对应章节。
- 材料缺口、客户询问、补证、金额核对和程序节点统一收束到《待补材料与行动清单》。
- `drafting` 只产生用户明确要求的 `.docx` 文书，不顺带生成证据目录、质证意见等未请求文件。
- 生成器不覆盖任何已有目标。同一交付层级需修改时显式增加 `--version`，生成 `_v2`；从初稿进入最终提交版时使用独立目录和新产物记录。

## 用户明确要求文书时

“分析本案并写答辩状”等明确指令，同时表示用户授权在当前材料基础上生成 `.docx` “律师复核初稿”。不得为了形式化门禁再次追问“是否需要起草”。

仅当存在会实质改变文书立场的互斥策略、金额口径或关键事实选择时，才暂停并请用户确认。其他缺口使用 `【待确认：…】` 显式保留，不阻止初稿生成。

最终提交版不得含 `【】`、待确认、待核实、待补充或内部工作备注，不得包含《待补材料与行动清单》。生成最终提交版须记录作出提交决定的律师，但该参数不能替代产物生成后的独立验证和针对最终文件的律师审批。
