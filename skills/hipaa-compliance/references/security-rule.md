## 1. 范围与适用性

安全规则适用于**电子受保护健康信息（ePHI）**——即符合以下条件的受保护健康信息（PHI）：
- 以电子形式创建、接收、维护或传输
- 存储在任何电子介质上（服务器、工作站、笔记本电脑、移动设备、可移动介质、云）

**适用于：**
- 受保实体（CE）
- 业务伙伴（BA）——直接根据 HITECH（2009）

**不涵盖：**
- 纸质形式的 PHI（由隐私规则涵盖）
- 口头通信

## 2. 一般规则

### 三类保障措施
所有受保实体和业务伙伴必须实施：
1. **行政保障措施**——政策、程序、员工队伍管理
2. **物理保障措施**——设施访问、工作站、设备控制
3. **技术保障措施**——基于技术的 ePHI 保护

### 必需与可寻址
| 指定 | 含义 |
|------------|----------|
| **必需（Required）** | 必须实施——无灵活性 |
| **可寻址（Addressable）** | 必须评估其是否合理和适当；如是则实施；如否则记录原因并实施等效替代方案 |

> **常见误解**：“可寻址”并不意味着可选。你必须实施它，或正式记录为什么没有实施以及改做了什么。

### 灵活性原则（§164.306(b)）
实施可考虑：
- 受保实体/业务伙伴的规模、复杂性和能力
- 技术基础设施、硬件和软件安全能力
- 安全措施的成本
- 潜在风险的可能性和严重性

## 6. 组织要求
### §164.314

### 业务伙伴合同（§164.314(a)）：
BAA 必须要求业务伙伴：
- 实施行政、物理和技术保障措施
- 确保分包商同样执行（签署分包 BAA）
- 报告安全事件（包括成功和未成功的尝试）
- 授权受保实体在确定业务伙伴违反重大条款时终止合同

### 团体健康计划（§164.314(b)）：
计划文件必须要求计划发起人：
- 实施合理和适当的安全措施
- 除获准外不使用/披露 ePHI
- 向计划报告安全事件

## 7. 政策、程序与文档
### §164.316

### 政策与程序（§164.316(a)）：
- 必须实施合理和适当的政策以符合安全规则
- 必要时必须更新

### 文档要求（§164.316(b)）：
- 维护安全规则要求的书面（电子或纸质）政策、程序和记录
- **保留**：自创建之日起 6 年或最后生效之日起 6 年（以较晚者为准）
- 使文档可供负责实施程序的人员使用
- 定期审查文档并按需更新

## 8. 风险分析深入探讨

风险分析（§164.308(a)(1)(ii)(A)）是 HIPAA 安全合规的**基础**。HHS 强调它是执法行动中最常被引用的缺陷。

### 必需组成部分：
1. **范围**：所有创建、接收、维护或传输的 ePHI（不仅是电子病历——包括备份、电子邮件、移动设备）
2. **威胁识别**：识别对 ePHI 的潜在威胁（自然的、人为的、环境的）
3. **漏洞识别**：识别安全漏洞
4. **可能性评估**：评估每种威胁利用每个漏洞的概率
5. **影响评估**：评估威胁发生的潜在影响
6. **风险等级确定**：可能性 + 影响 = 风险等级（高/中/低）
7. **现有控制**：记录现有安全措施及其有效性

### 风险管理（§164.308(a)(1)(ii)(B)）：
- 实施足以将风险降至合理和适当水平的安全措施
- 按风险等级确定优先级
- 记录所有决定

### 常见风险分析错误（HHS 执法发现）：
- 仅分析电子病历系统（遗漏电子邮件、移动设备、备份、打印机）
- 只做一次然后从不更新
- 未记录分析
- 将风险分析与差距分析混淆
- 无方法论地分配风险等级

### NIST 框架对齐：
HHS 推荐使用 NIST SP 800-30 作为风险分析方法论。NIST SP 800-66 是 HIPAA 特定指南。

## 9. 云与现代化架构指导

### 云服务提供商（CSP）：
- 存储 ePHI 的云服务提供商是业务伙伴——**需要 BAA**
- AWS、Azure、GCP 均提供 BAA 下的 HIPAA 合格服务
- BAA 不转移合规责任——受保实体/业务伙伴必须正确配置

### 关键云考量：

**加密：**
- 静态：最低 AES-256（可寻址但为行业标准）
- 传输中：最低 TLS 1.2+；推荐 TLS 1.3
- 密钥管理：使用专用 KMS（AWS KMS、Azure Key Vault、GCP Cloud KMS）
- 更高敏感性优先使用客户管理密钥

**访问控制：**
- 实施遵循最小权限原则的 IAM
- 对所有可访问 ePHI 的账户使用 MFA
- 将服务账户与人类账户分开
- 定期审计和轮换凭据

**审计日志：**
- 启用 CloudTrail（AWS）、Activity Log（Azure）、Cloud Audit Logs（GCP）
- 记录：API 调用、数据访问、认证事件、配置更改
- 不可变日志存储（带 Object Lock 的 S3 等）
- 保留：HIPAA 记录至少 6 年
- 对异常访问模式发出警报

**网络安全：**
- ePHI 系统使用 VPC/私有网络
- 安全组/网络策略：默认拒绝
- ePHI 数据存储不得直接暴露于互联网
- 任何处理 ePHI 的公网应用使用 WAF

**移动与 BYOD：**
- 设备访问 ePHI 时需 MDM/EMM 解决方案
- 远程擦除能力
- 强制屏幕锁定
- 加密存储
- 如可能实施应用级控制（MAM）

### API 与应用安全：
- 认证：OAuth 2.0 + OIDC；健康应用考虑 SMART on FHIR
- 输入验证以防注入攻击
- URL 中不得含 ePHI（会出现在日志中）
- 错误消息中不得含 ePHI
- 处理 ePHI 的端点实施速率限制
- FHIR API：HL7 FHIR R4 配 SMART on FHIR 是现代标准

### DevOps / CI-CD：
- 开发/测试环境中不得使用真实 PHI（使用合成数据）
- 机密管理（绝不硬编码凭据）
- 流水线中进行 SAST/DAST 扫描
- 依赖漏洞扫描
- 基础设施即代码安全扫描

## 10. 实施检查清单

- [ ] 指定安全官员

- [ ] 实施带优先级修复的风险管理计划
- [ ] 对违规实施制裁政策
- [ ] 定期审查系统活动（审计日志）
- [ ] 建立员工队伍清关程序
- [ ] 实施访问授权流程
- [ ] 开展年度安全意识培训（并记录）
- [ ] 实施反恶意软件保护
- [ ] 监测失败的登录尝试
- [ ] 记录并实施密码/凭据政策
- [ ] 实施安全事件响应计划
- [ ] 制定数据备份计划（并测试）
- [ ] 制定灾难恢复计划（并测试）
- [ ] 制定应急模式运行计划
- [ ] 与所有处理 ePHI 的供应商签订 BAA
- [ ] 定期进行安全规则评估

### 物理
- [ ] 实施设施访问控制（门禁卡、键盘、锁）
- [ ] 制定并实施设施安全计划
- [ ] 记录工作站使用政策
- [ ] 实施工作站物理安全
- [ ] 实施介质处置程序（销毁证书）
- [ ] 实施介质重用程序（安全擦除）
- [ ] 跟踪硬件/介质移动

### 技术
- [ ] 分配唯一用户 ID（无共享账户）
- [ ] 实施基于角色的访问控制（RBAC）
- [ ] 对所有 ePHI 访问实施 MFA
- [ ] 实施自动会话超时
- [ ] 实施静态加密（AES-256）
- [ ] 实施传输中加密（TLS 1.2+）
- [ ] 启用并监测审计日志
- [ ] 实施完整性控制（校验和、数字签名）
- [ ] 实施实体认证机制
- [ ] 测试传输安全控制
