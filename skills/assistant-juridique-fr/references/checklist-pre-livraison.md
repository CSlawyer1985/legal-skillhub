# 交付前强制检查清单——反幻觉

<!-- NOYAU-ANTIHALLUCINATION v3 — 与 mandarinat 1.4.0 / assistant-juridique-fr 7.4.0 同步。两个 skill 共用的文件：任何修改都须以完全相同的方式同步（各编排中特有的“上文／下文”互见除外）。 -->

本检查清单构成一项**不可协商的控制步骤**，必须在**交付任何**包含判例引注、规范性文本引用（法典条文、法律、法令、命令、条例、规章、集体协议）或学说引用的交付物**之前**执行。

未经执行，不得宣称已完成。它必须以**显式**方式执行，采用**结构化表格**的形式（下文定义的强制工件），而非心里过一遍。其目的有二：

1. 防止交付严格意义上的幻觉引用——此类事故的学术和专业成本不成比例；
2. 防止交付**形式上可溯源但实质上不吻合**的引用（错误归属型幻觉）——即由会话中工具调用的引用，但返回的内容并不支撑它们本应支撑的主张。

## 何时执行检查清单

在**产出**交付物之后、**实际交付**给接收方（用户、学生、客户、评审团、委员会）**之前**执行。这是最后一道过滤器。

没有任何例外：检查清单适用于短交付物和长交付物、案例分析答案和科研论文、法律咨询意见和习题课讲义。

## 按环境确定的执行方式

### 在 COWORK 和 CHAT_CU 模式（有文件系统）

执行为**阻塞式**：只要检查清单未完整通过、结构化表格未产出，交付物就不予交付。

1. **依据引用日志生成核查表格**：`python3 scripts/reference_journal.py table --journal verification/journal-references.ndjson`（日志在每次工具调用时已实时写入——参见工作流第 8 步）。先核查其完整性：`python3 scripts/reference_journal.py check --journal verification/journal-references.ndjson`（只要有条目不完整，退出码即为 1）。由日志派生的表格禁止凭记忆填写“摘录”列。若无日志（遗忘），重新查阅会话中的工具调用以重建表格——绝不凭记忆。
2. 将交付物中出现的全部 Légifrance URL 汇编为一份中间 JSON 文件。
3. 执行 `scripts/verify_links.py --from-file urls.json --check-content`（`--check-content` 模式默认启用），并将每条引用返回的相关文本摘录填入表格第 3 列。
4. 检查输出：**任何失败的 URL**（pattern 无法识别、HTTP ≠ 200、内容不吻合）必须按下文“失败时的处理程序”一节处理，表格相应行随之标记为 ✗。
5. 仅当表格所有行均标 ✓ 且已显式说出收尾公式时，方可交付。

### 在 CHAT 模式（无文件系统）

执行为**显式**方式，逐条引用进行，采用结构化表格形式。`verify_links.py` 脚本无法执行，但必须应用同样的逻辑：

1. 在会话中产出核查表格（下文工件模板）。
2. 逐一列举交付物的每条引用并填入第 1 列。
3. 对每条引用，在会话中识别产生它的 OpenLegi（或其他检索工具）调用——第 2 列。
4. 阅读调用返回的内容（裁判理由、主文、条文款项）并将相关摘录填入第 3 列。
5. 将该摘录与引注所支撑的主张对照，填写第 4 列（✓／✗／改写）。
6. 若未作调用：交付前执行缺失的检索。若用户无法等待，将该引用标记为“待核查”并记入第 4 列。
7. 确认交付物中的 Légifrance 链接确实来自工具响应——而非凭记忆重建。
8. 交付交付物前，明确说出收尾公式。

## 条件降级（网络访问预检）

在 COWORK 和 CHAT_CU 模式，实际执行 `verify_links.py --check-content` 要求 Cowork 沙箱能够访问 `www.legifrance.gouv.fr`。该访问可能被组织的网络 allowlist 阻止。

**自动检测程序**——在第 4 步执行完整核查之前，先执行预检模式：

```bash
python3 scripts/verify_links.py --preflight
```

退出码：

| 退出码 | 状态 | 处理方式 |
|---|---|---|
| `0` | 网络可用 | 进行完整核查（`--check-content`）。 |
| `2` | 被 Cowork allowlist 阻止 | **切换至降级模式**（手工产出结构化表格，同 CHAT 模式）。向用户显示 allowlist 消息（见下文）。 |
| `3` | 其他网络错误 | 重试；若持续失败，切换至降级模式并向用户报告技术细节。 |
| `4` | 被 Cloudflare 反机器人挑战阻止 | **切换至 OpenLegi 通道**（见下文一节）。该阻止由 Légifrance 本身施加，与 Cowork 无关；用户无法采取任何行动解除。 |

**allowlist 阻止时向用户显示的消息**（须原文照录）：

> ⚠️ 本沙箱无法自动核查 Légifrance 链接：对 `www.legifrance.gouv.fr` 的网络访问被 Cowork allowlist 阻止。我切换到降级模式核查：逐条显式列举引用，并确认会话中每次工具调用的可溯源性。
>
> **如需启用自动核查**（这是额外的可靠性保证——例如可检测格式正确但指向无关判决的 URL），请在 *Settings → Capabilities → Network access* 中授权以下域名：
>
> - `www.legifrance.gouv.fr`
> - `www.conseil-constitutionnel.fr`
> - `hudoc.echr.coe.int`
> - `curia.europa.eu`
> - `eur-lex.europa.eu`
>
> 在 Team／Enterprise 上，联系组织管理员。授权生效后，自动核查将在下个会话自动恢复。

降级模式不是检查清单失败：它是一种优雅降级，与 CHAT 模式保持同等的实质严谨性，只是缺少 HTML 内容的自动双重核查。

### 切换至 OpenLegi 通道（退出码 4——反机器人挑战）

自 Légifrance 部署 Cloudflare 反机器人挑战以来，该服务器对所有来自 agent 沙箱的自动化请求一律返回 HTTP 403（带 `cf-mitigated: challenge` 响应头），*无论 Cowork allowlist 如何配置*。网络层是通的；是 Légifrance 拒绝了请求。

在此情况下，通过 `--check-content` 的直接 HTTP 核查对 Légifrance 域名无效，但对不实施此挑战的邻近域名（HUDOC、Curia、EUR-Lex、conseil-constitutionnel.fr）仍然有效。核查策略因此分为两个通道：

1. **对 Légifrance 标识符**（LEGIARTI、JURITEXT、CETATEXT、JORFTEXT、JORFARTI、LEGITEXT、CNILTEXT、KALITEXT）：**通过 OpenLegi 的 API 调用核查**，该 API 不经过 Cloudflare 前端，因此仍然可访问。脚本的 `--extract-ids` 模式识别交付物中的每个标识符并指明要调用的 OpenLegi 工具：

   ```bash
   python3 scripts/verify_links.py --extract-ids --from-file urls.json
   ```

   JSON 输出为每个标识符列出 `openlegi_tool` 字段（例如 JURITEXT 对应 `OpenLegi:get_decision_judiciaire`）、`openlegi_argument` 和 `openlegi_verification_instruction`（描述需核查什么：法院、日期、案号、文本的法律状态、生效日期等）。随后 agent 为每个标识符调用 OpenLegi，并将响应与引注对照。

2. **对非 Légifrance 域名**（HUDOC、Curia、EUR-Lex、conseil-constitutionnel.fr）：`--check-content` 的 HTTP 核查可正常使用。

此切换比 HTTP 核查*更严格*，而非更宽松：OpenLegi 除标识符存在性外，还返回文本的法律状态和被引用版本文本的生效日期——这直接覆盖第 5 步规则 (c)“强制时间核查”。

**反机器人阻止时向用户显示的消息**（须原文照录）：

> ℹ️ 通过 HTTP 请求自动核查 Légifrance 链接已不可行：Légifrance 现以 Cloudflare 反机器人挑战阻止来自 agent 沙箱的自动化请求。网络层是通的（其他域名可访问），但 Légifrance 服务器拒绝请求。我切换到 OpenLegi API 调用核查，该通道不受此阻止影响，并且还提供所引用文本的法律状态和生效日期核查。您无需采取任何行动。

## 强制结构化表格——核查工件

自版本 1.3.0／7.3.0 起，“心里枚举”被禁止：检查清单采用**在有效交付前产出并记入会话的结构化表格**形式（在 COWORK 模式，它也可以作为单独交付物保存）。表格是证明检查清单已完整通过的实体工件。

**文档中每一条实际引注占一行。** 同一引用在交付物中多处出现时，按被引用次数计行——每次出现都必须与其在各自语境中所支撑的主张对照。

**四列**（最高法院审查中为五列，含陈述声部）：

| 文档中写成的引注 | 工具＋标识符（CID/JURITEXT/CETATEXT/JORFTEXT/DOI/HAL） | 工具返回的相关文本摘录 | 声部（最高法院） | 支撑该主张？（✓／✗／改写） |

**大型交付物的优先级排序（规模化处理）**：

“每次出现一行”的规则适用于短交付物（答案、习题课讲义、简短咨询意见）。对包含数十条引注的完整课程或著作，该规则会变得难以管理，并存在执行被截断的风险。此时应用：

- **P1**——支撑核心论证、在引言／结论中被引用、或重复超过三次的引用：按**出现次数**核查（在每个语境中进行内容匹配）。
- **P2**——被引用一至三次的示例性引用：按**引用**核查（单次内容匹配）。
- **P3**——仅出现在参考文献中的引用：核查存在性和标识符，不做主张的内容匹配。

表格骨架可通过 `scripts/extract_references.py --file [交付物]` 预填充，该脚本检测引用及其位置（并可根据出现次数分配 P1／P2／P3 优先级）。

**使用规则**：

- 表格在有效交付前产出并记入会话（或在 COWORK 模式作为单独交付物）。
- 进度标准是二元的：只要某行带 ✗ 或“需改写”标注，交付即**被阻塞**。对这些行，应用内容匹配的三种结果之一——(i) 更换引用，(ii) 改写表述使其与真实内容相符，(iii) 切换为无人称表述——然后更新该行。
- 遗漏表格等同于遗漏检查清单：没有表格，交付不能宣布为合规。
- 只有第 3 列所载摘录确实（而非近似）支撑交付物对应主张时，该行才可标记 ✓。

### 可复制的模板工件

下面的骨架为每个交付物复制一份。其写法使其可以直接复制粘贴（CHAT 模式）或写入单独文件 `tableau-verification-pre-livraison.md`（COWORK／CHAT_CU 模式）。

```markdown
# 交付前核查表格

**所涉交付物**：[文档标题]
**日期**：[AAAA-MM-JJ]
**模式**：[CHAT / CHAT_CU / COWORK]
**`verify_links.py` 预检**：[退出码 0 / 2 / 3 / 4——CHAT 模式下不适用]

| # | 文档中写成的引注 | 工具＋标识符（CID/JURITEXT/CETATEXT/JORFTEXT/DOI/HAL） | 工具返回的相关文本摘录 | 声部（最高法院） | 支撑该主张？（✓／✗／改写） |
|---|---|---|---|---|---|
| 1 | [交付物中所写的引注] | [例如 `OpenLegi:rechercher_code` — LEGIARTI000006437058] | “[裁判理由／条文文本摘录或忠实摘要]” | — | ✓ |
| 2 | [引注] | [工具＋标识符] | “[摘录]” | — | ✗ → 已完成改写 → 第 2bis 行 |
| 2bis | [新的无人称表述或新引用] | [工具＋标识符或“无人称表述”] | “[摘录，如有]” | — | ✓ |
| 3 | [最高法院判决摘录] | [`Themia:...`＋`OpenLegi:...`（Légifrance 链接）] | “[最高法院自己的裁判理由]” | voix_cour | ✓ |
| … | … | … | … | … | … |

**汇总**：
- 已核查行数：X
- 已完成改写数：Y
- 残留未溯源引用：0（必须为 0）

**收尾公式**：

> “核查表格已产出；已核查 X 行；已完成 Y 处改写；不存在任何未溯源的引用。允许交付。”
```

### 显式收尾公式

检查清单结束时——且仅当表格所有行均标 ✓——skill 在会话中明确说出以下公式（将变量 `X` 和 `Y` 相应代入）：

> “核查表格已产出；已核查 X 行；已完成 Y 处改写；不存在任何未溯源的引用。允许交付。”

没有明确说出该公式，**并且**没有相应的表格工件，交付**不得被宣布**。有公式而无表格同样严重：公式是表格已产出的证明，而非其替代品。

## 五个强制步骤

以下五个步骤对应填充结构化表格各列的操作。

### 第 1 步——穷尽列举被引用的引用

列出文档中引用的**全部**引用，分三个不同类别：

**(a) 判例引注**——对每一条，记录：法院、日期、上诉／申请／案件编号、Légifrance 链接。在最高法院审查（Themia）中，记录所引任何摘录的**陈述声部**。

**(b) 对具体规范性文本的引用**——对每一项，记录：文本或法典名称、条文号、适用版本（被引用文本版本的生效日期）、Légifrance 链接。

**(c) 学说引用**——对每一项，记录：作者、标题、载体（期刊／著作／学位论文）、年份，以及**可核查标识符**（DOI、HAL 标识符或公认数据库的 URL）。无核查标识符的学说引用按“未核查”处理（参见“失败时的处理程序”）。

清单必须穷尽：交付物中存在的任何引用都须列入，包括 skill 认为“显而易见”或“经典到极点”的引用（如《民法典》第 1240 条、Costedoat 判决等）。恰恰是这些引用需要最高度警惕。

### 第 2 步——核查每条引用的可溯源性（表格第 2 列）

对第 1 步列出的每条引用，核查当前会话中**确实存在针对该条特定引用**的检索工具调用（OpenLegi、LegalDataHunter、针对官方来源的 web_search），并将工具＋标识符记入表格第 2 列。

可溯源性不可推定：若引用无法关联到可识别的工具调用，在相反证明之前**推定其为幻觉**。

### 第 3 步——内容匹配：将返回内容与主张对照（第 3 列和第 4 列）

这是防止错误归属型幻觉的步骤。对第 2 步已溯源的每条引用：

1. **阅读工具返回的实际内容**——判决的裁判理由和主文、条文的准确款项、OpenLegi 卡片页的文本内容。仅元数据卡片不足以证明。
2. **将相关文本摘录记入第 3 列**（判决裁判理由、条文款项等）。
3. **将该摘录与引用本应支撑的主张对照**。填写“支撑该主张？”列：
   - **✓**：返回内容确实支撑该主张。
   - **✗**：返回内容不支撑该主张（错误归属）。
   - **改写**：通过改写表述使其贴合实际内容来消除偏差。
4. **在最高法院审查（Themia）中**：填写“声部”列并核查陈述归属的一致性——作为最高法院立场呈现的摘录必须来自 `passage_voix_cour`／`passage_visas`／`passage_chapeau`（tag `voix:cour_cassation`），而非 `passage_motifs_ca`（上诉法院）或 `passage_moyens`（当事方）。陈述归属错误即视为 ✗。
5. **对学说**：核查标识符（DOI／HAL／URL）确实解析到所声明的引用，且归于作者的论点与实际内容（摘要、确实发表的言论）相符——而非貌似合理的重建。

对任何非 ✓ 的行，应用内容匹配的三种结果之一：

1. **更换引用**——重新检索以识别真正支撑该主张的文本。创建表格新行（或子编号 `nbis`）反映替换。
2. **改写表述**，使其符合引用的实际内容。新表述记入第 1 列；第 4 列随即变为“改写”。
3. **切换为无人称表述**——将引注替换为诸如“一惯判例认为……”／“侵权责任一般法规定……”之类的表述，不带具体编号或日期。数字引用从交付物中消失。

只要某行带 ✗ 或“需改写”标注，交付即被阻塞。

对此外**未溯源**的引用（第 2 步失败），应用严格并列的三种解决方案：

1. **立即核查**——执行缺失的检索。若其确认引用且内容支撑主张，保留并进入第 4 步。否则，采用下述两条路径之一。
2. **删除**——将引用从交付物中彻底移除。论证必要时可不用它改写（无人称表述、改用另一条已核查引用）。
3. **转换为无人称表述**。

第四条路径应谨慎使用：保留引用但在交付物和表格第 4 列中明确标注“待核查”。该路径仅在用户明确同意接收未核查引用时允许（这始终应优于静默交付不确定的引用）。

### 第 4 步——核查官方链接／可核查标识符的存在与有效性

对每条**判例和规范性**引用，核查：

1. 交付物中存在 Légifrance 链接；
2. 链接符合已识别的 Légifrance pattern（`JURITEXT`、`CETATEXT`、`JORFTEXT`、`JORFARTI`、`LEGIARTI`、`LEGITEXT`、`CNILTEXT`、`KALITEXT`）；
3. 所引标识符在实质上确实对应交付物中的引用。核查通道取决于预检结果（参见上文“条件降级”一节）：
   - **退出码 0**（网络可用）：执行 `verify_links.py --check-content`，它抓取 HTML 页面并将预期的编号／关键词与内容对照。
   - **退出码 4**（Cloudflare 反机器人阻止——2026 年以来沙箱中最常见的情况）：执行 `verify_links.py --extract-ids`，它为每个 Légifrance 标识符产出要调用的 OpenLegi 工具名称。随后 agent 为每个标识符调用 OpenLegi，并核查响应确认引注。对非 Légifrance 域名（HUDOC、Curia、EUR-Lex、conseil-constitutionnel.fr），保留仍然有效的 `--check-content` HTTP 核查。
   - **退出码 2**（被 Cowork allowlist 阻止）：逐行核查，通过阅读相应的 OpenLegi 卡片页（降级模式），同 CHAT 模式。

对每条**学说**引用，核查存在**可核查标识符**（DOI、HAL 标识符或公认数据库的 URL）且其解析到所声明的引用。无核查标识符的学说引用按第 3 步程序处理（未核查→标注或删除）。

任何无链接或无效标识符的引用按第 3 步程序处理。

### 第 5 步——核查规范性文本的适用文本版本

对每条被引用的规范性文本（法典条文、法律、法令等），核查：

1. 所引文本版本确为**相关日期时有效**的版本：对案例分析或判决评注，是**题干事实（或所评案件事实）的日期**，而非当日日期；对前瞻性咨询意见或讲授现行法的课程，是当日日期。枢纽日期须显式确定，若题干未作说明，则按显式标注的假设确定；
2. 当文本最近经历过可能影响推理的修改时，须明确注明适用版本。预期标注示例：“《民法典》第 1242 条第 4 款，按 2025 年 6 月 23 日第 2025-568 号法律修改后的文本”。

## 失败时的处理程序

任何未通过上述五个步骤之一的引用，只能适用**以下三种结果之一**——绝无其他：

1. **迟到的成功核查**——引用经检索*事后*溯源并获确认。保留。
2. **删除**——引用被移除。论证必要时可不用它改写（无人称表述、改用另一条已核查引用）。
3. **显式“待核查”标注**——引用保留但在交付物中以显式标注提示，并告知用户。

不作为（明知失败仍交付交付物）**被禁止**。

### 示例 B——因缺乏可溯源性而失败的检查清单及其修正

一份案例分析答案提到“最高法院第二民事庭，2004 年 7 月 8 日，第 03-12.244 号”。

在第 2 步，skill 发现会话中没有针对该引用的 `OpenLegi:rechercher_jurisprudence_judiciaire` 调用。表格第 2 列留空；第 4 列因缺乏可溯源性变为 ✗。

在第 3 步，skill 执行 `OpenLegi:rechercher_jurisprudence_judiciaire`，参数为 `champ: "NUM_AFFAIRE"`、`type_recherche: "EXACTE"`、`search: "03-12.244"`。响应返回一份涉及司法管理人、与物件责任无关的判决：该引用在**实质上被推翻**。第 3 列——“摘录”——记载判决的真实裁判理由，其不支撑该主张；第 4 列因此保持 ✗。

skill 随即应用第三种结果（无人称表述）并改写相关段落：“第二民事庭的一惯判例认为，照管意味着对物的实际控制”。数字引用从交付物中消失，表格行变为“改写”。

交付物已修正，表格重新通过，收尾公式已说出：

> “核查表格已产出；已核查 1 行；已完成 1 处改写；不存在任何未溯源的引用。允许交付。”

### 示例 C——错误归属型幻觉（形式上已溯源但被内容推翻）

一份民事责任案例分析答案提到“明知对车辆解限速违反《公路法典》第 R. 412-43-3 条仍驾驶该车”。

在第 2 步，skill 发现会话中确实执行过针对该条文的 `OpenLegi:rechercher_code` 调用：形式可溯源性得到满足，第 2 列已填写（`OpenLegi:rechercher_code` — 标识 R. 412-43-3 条的 CID）。

在第 3 步（内容匹配），skill **阅读 OpenLegi 返回的内容**并记入第 3 列：第 R. 412-43-3 条规定驾驶个人机动代步工具（EDPM）的最低年龄为十四周岁，并要求夜间佩戴反光装备。与主张（驾驶解限速车辆）对照，它并不支撑：第 4 列变为 ✗。

skill 应用结果 (i)（更换引用）：就 EDPM 的设计限速进行补充检索；OpenLegi 返回《公路法典》第 R. 311-1 条第 6.15 项，其内容恰好规定设计限速为 25 km/h。表格已更新：新行第 4 列变为 ✓。

> “核查表格已产出；已核查 1 行；已完成 1 处改写／替换；不存在任何未溯源的引用。允许交付。”

此示例说明 1.3.0／7.3.0 版覆盖的新场景：形式可溯源性核查（第 2 步）并不充分；只有第 3 步的内容匹配能防止此类幻觉。
