# NIST AI RMF 1.0——完整类别与子类别参考

来源：NIST AI 100-1（2023 年 1 月）和 AI RMF 操作手册（NIST AI 100-1 Playbook）

---

## 治理（GOVERN）功能（6 个类别，21 个子类别）

治理（GOVERN）确立支撑所有其他功能的组织文化、政策、问责制和风险容忍度。应首先处理并持续重新审视。

### GV-1：政策、流程、程序与实践到位

**目的：** 确保组织在整个人工智能生命周期内对人工智能风险管理有正式化的政策和流程。

| 子类别 | 描述 |
|-------------|-------------|
| GV-1.1 | 人工智能风险管理已整合到组织更广泛的企业风险管理（ERM）流程中 |
| GV-1.2 | 可信人工智能的特征已整合到组织政策、流程和实践中 |
| GV-1.3 | 组织对人工智能的风险容忍度已确立、传达并反映在人工智能政策中 |
| GV-1.4 | 组织团队致力于风险意识和持续改进的文化 |
| GV-1.5 | 组织的人工智能风险管理政策按定期节奏审查和更新 |
| GV-1.6 | 已确立遵守适用人工智能法律、法规和标准的政策 |
| GV-1.7 | 已确立定期审查人工智能风险政策以纳入新兴人工智能风险的流程 |

**建议行动：**
- 发布由高级领导层签署的组织级《人工智能风险管理政策》
- 定义人工智能风险偏好声明（如可接受的误报率、偏见阈值）
- 将人工智能风险纳入现有 ERM 委员会议程和季度审查
- 建立政策审查周期（至少年度），并指定人工智能风险负责人

---

### GV-2：问责结构

**目的：** 在组织层面明确分配人工智能风险管理决策的所有权。

| 子类别 | 描述 |
|-------------|-------------|
| GV-2.1 | 跨组织层级的人工智能风险管理角色和职责已记录在案 |
| GV-2.2 | 组织指定对人工智能风险结果负责的高级官员 |
| GV-2.3 | 高管层理解人工智能风险并培育问责文化 |

**建议行动：**
- 任命向董事会汇报的人工智能风险负责人或首席人工智能官
- 为人工智能开发、部署和监控决策定义 RACI
- 将人工智能风险纳入高管绩效目标和领导层仪表盘

---

### GV-3：角色与职责

**目的：** 识别并定义参与人工智能设计、开发、部署和评估的所有角色。

| 子类别 | 描述 |
|-------------|-------------|
| GV-3.1 | 人工智能风险管理角色涵盖从设计到退役的整个人工智能生命周期 |
| GV-3.2 | 为开发团队、运营人员和部署者定义人工智能风险职责 |
| GV-3.3 | 人工智能风险职责分配给技术性和非技术性角色 |

**建议行动：**
- 创建人工智能角色登记册，将每个生命周期阶段映射到负责团队/个人
- 确保业务负责人（而不仅仅是工程师）对已部署的人工智能结果负责
- 为外部人工智能供应商和第三方模型提供者定义职责

---

### GV-4：跨职能团队协作

**目的：** 确保人工智能风险管理涉及组织内多元化的视角。

| 子类别 | 描述 |
|-------------|-------------|
| GV-4.1 | 跨职能人工智能风险团队包括人工智能/机器学习、法律、隐私、安全、人力资源和伦理职能 |
| GV-4.2 | 团队之间沟通人工智能风险的流程已记录在案 |
| GV-4.3 | 已建立升级人工智能风险关切的机制 |

**建议行动：**
- 建立人工智能风险工作组，进行季度跨职能审查
- 创建从开发团队到高管层的人工智能风险升级路径
- 在人工智能系统设计审查中纳入隐私、法律和安全代表

---

### GV-5：组织对人工智能的风险容忍度

**目的：** 传达人工智能风险容忍度并将其与运营决策挂钩。

| 子类别 | 描述 |
|-------------|-------------|
| GV-5.1 | 人工智能风险容忍度已定义并反映组织价值观 |
| GV-5.2 | 在部署新人工智能系统或情境变化时审查人工智能风险容忍度 |
| GV-5.3 | 风险容忍度声明为人工智能系统部署的放行/不放行（go/no-go）决策提供信息 |

**建议行动：**
- 按人工智能系统类别定义风险容忍度（如低风险推荐与影响个人的高风险决策）
- 创建部署检查清单，在启动前对照声明的风险容忍度验证人工智能系统
- 将风险容忍度与测试要求中的特定偏见和准确性阈值挂钩

---

### GV-6：人工智能风险与法律、法规和原则保持一致

**目的：** 确保人工智能风险和风险管理实践与适用的法律、伦理原则和行业标准保持一致。

| 子类别 | 描述 |
|-------------|-------------|
| GV-6.1 | 识别并跟踪人工智能的法律和监管要求 |
| GV-6.2 | 人工智能风险管理流程与适用的伦理原则保持一致 |
| GV-6.3 | 组织以主动方式参与新兴人工智能法规 |

**建议行动：**
- 维护适用人工智能法律（欧盟人工智能法、州级人工智能法律、部门特定要求）的监管登记册
- 将人工智能风险政策与 NIST AI 100-1、ISO/IEC 42001 以及相关行业框架（FINRA、HIPAA 等）对齐
- 在人工智能治理委员会指定法律/合规代表

---

## 映射（MAP）功能（5 个类别，20 个子类别）

映射（MAP）在风险被测量或管理之前建立情境。执行良好的 MAP 可防止将资源投入错误的风险处理。

### MP-1：情境已确立

**目的：** 理解每个人工智能系统的预期用途、运行环境和受影响人群。

| 子类别 | 描述 |
|-------------|-------------|
| MP-1.1 | 组织与人工智能相关的使命和目标已记录在案 |
| MP-1.2 | 人工智能系统的预期用途已记录并有边界 |
| MP-1.3 | 人工智能系统的运行环境和约束已定义 |
| MP-1.4 | 已识别受影响的个人、群体、社区和组织 |
| MP-1.5 | 潜在的损害、滥用和意外用途已界定范围 |
| MP-1.6 | 已识别法律、监管和合同约束 |

**建议行动：**
- 为每个已部署系统编制《人工智能系统描述文件》，涵盖：目的、输入、输出、决策权、操作者与用户角色
- 在设计开始时——而非部署时——识别受影响人群
- 明确记录禁止的使用案例

---

### MP-2：运用科学理解

**目的：** 将当前对人工智能能力和局限性的科学理解应用于设计和风险评估。

| 子类别 | 描述 |
|-------------|-------------|
| MP-2.1 | 针对特定系统类型记录人工智能和机器学习的能力与局限性 |
| MP-2.2 | 记录人工智能系统训练数据的假设和约束 |
| MP-2.3 | 表征人工智能输出的不确定性和变异性 |

**建议行动：**
- 记录模型卡或系统卡信息，包括训练数据来源、已知偏见和性能边界
- 在适用处量化输出不确定性（置信区间、校准指标）
- 审查关于所用模型架构已知失效模式的相关文献

---

### MP-3：风险与收益映射到利益相关方

**目的：** 识别谁从人工智能系统中受益、谁承担其风险——这些往往是不同的群体。

| 子类别 | 描述 |
|-------------|-------------|
| MP-3.1 | 为每个已识别的利益相关方群体记录收益和风险 |
| MP-3.2 | 在可行处让受影响社区参与，以理解其感知到的风险和收益 |
| MP-3.3 | 评估跨利益相关方群体的收益与风险分配 |
| MP-3.4 | 为受影响个人建立报告损害的回馈机制 |

**建议行动：**
- 创建利益相关方风险/收益矩阵：行 = 利益相关方群体，列 = 风险类型、收益类型
- 实施回馈渠道（如投诉表、审计日志审查），供用户报告意外结果
- 进行公平性分析：哪些群体受错误影响不成比例？

---

### MP-4：风险优先排序

**目的：** 对已识别风险进行优先排序，以有效聚焦测量（MEASURE）和管理（MANAGE）资源。

| 子类别 | 描述 |
|-------------|-------------|
| MP-4.1 | 已建立风险优先排序标准（如严重程度、广度、可逆性） |
| MP-4.2 | 风险已在人工智能风险登记册中排序并记录 |
| MP-4.3 | 最高优先风险升级至治理（GOVERN）以进行风险容忍度审查 |

**建议行动：**
- 使用严重程度 × 广度 × 可逆性评分模型进行优先排序
- 将任何影响受保护类别、产生法律敞口或不可逆的风险标记为高优先
- 在每次模型版本更新或重大情境变化时审查优先排序

---

### MP-5：可能性与影响表征

**目的：** 表征已识别损害的概率和潜在严重程度。

| 子类别 | 描述 |
|-------------|-------------|
| MP-5.1 | 使用历史数据、专家判断或红队测试估计损害的可能性 |
| MP-5.2 | 从身体、心理、财务和声誉维度评估潜在影响 |
| MP-5.3 | 考虑累积性和系统性风险（如广泛部署的社会影响） |

**建议行动：**
- 进行红队演练和对抗性测试以估计真实世界的失败率
- 跨损害维度评估影响：身体安全、财务、心理、声誉、社会
- 对于大规模部署，建模总体社会影响（如自动化招聘工具对劳动力市场的影响）

---

## 测量（MEASURE）功能（4 个类别，16 个子类别）

测量（MEASURE）采用定量和定性工具评估在映射（MAP）中识别的人工智能风险。

### MS-1：识别测量方法

**目的：** 识别用于测量人工智能风险的适当方法和工具。

| 子类别 | 描述 |
|-------------|-------------|
| MS-1.1 | 为每个已识别风险定义指标（技术、运营和社会） |
| MS-1.2 | 测量方法适合人工智能系统类型和部署情境 |
| MS-1.3 | 测量能力的缺口已记录并加以解决 |

**建议行动：**
- 为每个可信赖性属性定义指标：准确性、公平性（人口统计均等、机会均等）、稳健性（对抗性准确性）、可解释性（LIME/SHAP 分数）、隐私（差分隐私 ε）
- 记录测量工具及其已知局限性
- 确定何处需要人工评估代替（或补充）自动化指标

---

### MS-2：评估人工智能系统的可信赖性

**目的：** 在整个生命周期内对照可信赖性属性评估人工智能系统。

| 子类别 | 描述 |
|-------------|-------------|
| MS-2.1 | 人工智能系统在部署前评估技术性能和安全性 |
| MS-2.2 | 跨人口统计群体进行偏见和公平性测试 |
| MS-2.3 | 可解释性和可理解性要求已测试并记录 |
| MS-2.4 | 评估人工智能系统的安全和隐私 |
| MS-2.5 | 人工监督机制已测试和验证 |
| MS-2.6 | 评估结果已记录并共享给相关利益相关方 |

**建议行动：**
- 要求部署前评估报告涵盖全部七项可信赖性属性
- 跨人口统计亚组（年龄、性别、种族、地域）运行分解性能测试
- 使用与模型类型相关的标准基准数据集测试对抗性稳健性
- 为影响高风险个人决策的模型记录 SHAP/LIME 解释

---

### MS-3：随时间跟踪人工智能风险

**目的：** 部署后持续监控人工智能风险，以检测漂移、性能退化或新的损害。

| 子类别 | 描述 |
|-------------|-------------|
| MS-3.1 | 部署后已定义并实施持续监控指标 |
| MS-3.2 | 检测模型漂移和性能退化并触发审查 |
| MS-3.3 | 部署后识别的新风险回馈至映射（MAP） |
| MS-3.4 | 外部信号（监管更新、学术发现、媒体报道）为监控提供信息 |

**建议行动：**
- 实施模型监控仪表盘，跟踪准确性、公平性指标和输入数据分布
- 设置触发人工审查的警报阈值（如准确性下降超过 5%、人口统计均等差距超过阈值）
- 指定模型负责人负责月度监控审查
- 订阅 NIST NVD 和相关人工智能安全/偏见研究动态

---

### MS-4：回馈为管理（MANAGE）提供信息

**目的：** 确保测量结果直接为管理（MANAGE）中的风险处理决策提供信息。

| 子类别 | 描述 |
|-------------|-------------|
| MS-4.1 | 测量输出传达给负责管理（MANAGE）的决策者 |
| MS-4.2 | 测量局限性和不确定性随结果一并传达 |
| MS-4.3 | 测量结果用于更新人工智能风险登记册和处理计划 |

**建议行动：**
- 创建测量到行动协议：定义哪些测量发现触发哪些管理（MANAGE）行动
- 在所有人工智能风险报告中包含测量不确定性注意事项
- 在可行处从监控仪表盘自动更新风险登记册

---

## 管理（MANAGE）功能（4 个类别，18 个子类别）

管理（MANAGE）通过处理、监控和改进来应对已识别的人工智能风险。

### MG-1：风险优先排序并记录

**目的：** 确保影响最大的人工智能风险首先获得处理资源。

| 子类别 | 描述 |
|-------------|-------------|
| MG-1.1 | 人工智能风险登记册条目已优先排序并分配处理负责人 |
| MG-1.2 | 风险优先排序反映组织风险容忍度（治理 GV-1.3） |
| MG-1.3 | 处理后的剩余风险已记录并由适当权限接受 |

**建议行动：**
- 为每个风险登记册条目分配处理负责人、目标日期和处理方法
- 要求接受超出已定义风险容忍度阈值的剩余风险须经高级管理层批准
- 每年或在发生重大系统变更时审查剩余风险接受

---

### MG-2：策略已规划并执行

**目的：** 制定并执行将人工智能风险降低到可接受水平的风险处理策略。

| 子类别 | 描述 |
|-------------|-------------|
| MG-2.1 | 已识别风险处理选项（缓解、转移、规避、接受） |
| MG-2.2 | 处理策略已配置资源并实施 |
| MG-2.3 | 为关键故障定义应急干预措施（如系统关闭） |
| MG-2.4 | 在降低风险的同时保留人工智能系统的收益 |

**建议行动：**
- 为每个高优先风险识别一个或多个处理选项：技术（重新训练、约束、增加人工审查）、运营（限制使用案例）、合同（赔偿）或规避（退役）
- 为影响安全的人工智能系统定义"终止开关"或紧急关闭程序
- 为任何被接受的风险记录收益-风险权衡

---

### MG-3：监控并调整风险响应

**目的：** 确保风险处理随时间保持有效并适应变化的条件。

| 子类别 | 描述 |
|-------------|-------------|
| MG-3.1 | 使用定义指标监控风险处理的有效性 |
| MG-3.2 | 人工智能事件已记录、报告和调查 |
| MG-3.3 | 从事件中吸取的教训应用于未来的风险管理 |
| MG-3.4 | 重大人工智能风险或事件已通知利益相关方 |

**建议行动：**
- 实施带严重程度分类（低/中/高/严重）的人工智能事件日志
- 定义通知阈值：内部升级、外部客户通知、监管披露
- 进行事件后审查并更新风险登记册和治理（GOVERN）政策
- 在适当处与行业分享匿名化的事件经验教训（如人工智能事件数据库）

---

### MG-4：审查并改进风险处理

**目的：** 闭环——将处理结果回馈至治理（GOVERN）和映射（MAP）以实现持续改进。

| 子类别 | 描述 |
|-------------|-------------|
| MG-4.1 | 定期审查人工智能风险管理流程的有效性 |
| MG-4.2 | 已识别并实施对人工智能风险管理的改进 |
| MG-4.3 | 经验教训为组织人工智能风险政策的更新提供信息 |
| MG-4.4 | 发生重大变化时审查组织的人工智能风险状况 |

**建议行动：**
- 安排季度人工智能风险计划审查，涵盖全部四项功能
- 每 1-2 年使用外部评估或第三方审计验证计划有效性
- 在每次重大事件或模型更新后更新治理（GOVERN）政策和映射（MAP）情境文件
