## 类型选择

在确定管辖地之后，将以下问题作为**第一个问题**询问用户：

> "您需要哪种类型的隐私通知？"

| 类型 | 典型触发短语 |
|---|---|
| **网站/App** | "website（网站）"、"app"、"online service（在线服务）"、"landing page（落地页）"、"SaaS"、"platform（平台）" |
| **应聘者** | "Bewerber"、"applicant（应聘者）"、"recruiting（招聘）"、"career page（招聘页）"、"candidat"、"Bewerbungsverfahren" |
| **员工** | "Mitarbeiter"、"employee（员工）"、"HR（人力资源）"、"salarié"、"Beschäftigte"、"workforce（员工队伍）" |
| **商业伙伴** | "B2B"、"vendor（供应商）"、"supplier（供货商）"、"business partner（商业伙伴）"、"Geschäftspartner"、"partenaire" |
| **B2C 客户** | "customer（客户）"、"Kunde"、"client（客户）"、"loyalty（忠诚度）"、"CRM"、"retail（零售）"、"e-commerce（电子商务）" |

如果用户需要多种类型→见[合并通知](#合并通知)。

以下每种类型画像定义：
- **章节映射**：13 个标准章节中应包含、跳过或调整哪些
- **可能的数据类别**：预填建议以加快信息收集
- **可能的合法依据**：需与用户确认的默认假设
- **类型特定的信息收集问题**：标准 A–F 组之外的问题
- **类型特定的法律考量**：依管辖地而异的规则
- **保留期默认值**：该类型的常见保留期限

### 子类型与数据画像

**宣传册/公司网站**（数据最少）：
- 身份：姓名、电子邮箱（仅联系表单）
- 技术：IP、浏览器/操作系统、访问日志
- Cookie：分析、可能有社交插件嵌入
- 合法依据：合法利益（分析、安全）、同意（营销 Cookie）

**电子商务**：
- 宣传册全部数据 PLUS：账户数据、收货地址、支付（通过服务商）、订单历史、退货、心愿单
- 合法依据：合同（订单、账户）、法定义务（发票）、同意（通讯、营销）、合法利益（防欺诈）

**SaaS/Web 应用**：
- 宣传册全部数据 PLUS：账户、使用/功能日志、API 使用、协作数据、上传的内容、设置
- 合法依据：合同（提供服务）、合法利益（产品改进、安全）

**移动 App**：
- Web 应用全部数据 PLUS：设备 ID、推送令牌、设备权限（相机、定位、麦克风、通讯录）、App 使用指标、崩溃日志
- 必须披露每个权限及其用途

**市场/平台**：
- 双重数据主体（买家 + 卖家）、评分/评论、消息、支付托管、卖家验证文件
- 考虑为每个用户角色设置单独的小节

### 类型特定的信息收集问题
1. 网站上有哪些表单？（联系、注册、结账、通讯）
2. 是否有用户账户创建？哪些数据是必填 vs 可选？
3. 使用哪些分析工具？（GA4、Matomo、Plausible、Mixpanel）
4. 是否有第三方嵌入？（YouTube、Google 地图、社交按钮、聊天小部件）
5. 是否有 A/B 测试或个性化工具？
6. 网站是否使用 CDN？（Cloudflare、Fastly——可能涉及数据传输）
7. 是否有带评论的博客？
8. 是否有用户生成内容？

### 保留期默认值
| 数据 | 期限 | 依据 |
|---|---|---|
| 联系表单提交 | 问题解决后 6–12 个月 | 第 6 条第(1)款(f)项 |
| 活跃账户 | 关系存续期间 | 第 6 条第(1)款(b)项 |
| 不活跃账户 | 最后活动后 2–3 年 | 业务开拓时效限制 |
| 服务器日志 | 7–30 天 | 第 6 条第(1)款(f)项安全 |
| Cookie | 最长 13 个月（法国）/ 基于会话或按声明 | TDDDG 第 25 条 / CNIL |
| 发票 | 6–10 年，视管辖地而定 | HGB/AO/《商法典》 |

### 示例条款模式

**分析同意行**（目的表）：
```
| Web 分析 | 了解访问者如何使用我们的网站以改善用户体验 | 第 6 条第(1)款(a)项 GDPR——您通过我们的 Cookie 横幅给予的同意 | 匿名化：无限期；假名化：[13 个月 / 26 个月] |
```

**第三方嵌入披露**：
```
我们的网站嵌入了第三方服务的内容（[YouTube / Google 地图 / 社交媒体插件]）。当您访问包含此类内容的页面时，会与提供商的服务器建立连接，该服务器可能设置 Cookie 并收集您的 IP 地址。合法依据：第 6 条第(1)款(a)项 GDPR——您的同意。您可以随时通过我们的同意工具管理您的偏好。
```

**软性选择加入条款**（既有客户）：
```
如果您此前曾向我们购买过[商品/服务]，我们可能会通过电子邮件向您发送有关类似[商品/服务]的信息。这基于[《反不正当竞争法》第 7 条第(3)款（德国）/《邮政与电子通信法典》第 L.34-5 条（法国）/《隐私和电子通信条例》第 22 条（英国）]。您可以随时使用每封邮件中的链接或联系我们退订。
```

**通讯同意**：
```
| 通讯与营销邮件 | 向您发送有关[产品/服务/优惠]的信息 | 第 6 条第(1)款(a)项 GDPR——您的同意 | 直至您撤回同意 |
```

**联系表单**：
```
| 回应您的咨询 | 处理并回应您的联系表单提交 | 第 6 条第(1)款(f)项 GDPR——我们对回应咨询的合法利益 / 如与合同有关则第 6 条第(1)款(b)项 GDPR | 您的咨询解决后 6 个月 |
```

## 应聘者/招聘

### 章节映射

| 章节 | 是否包含？ | 说明 |
|---|---|---|
| 1. 控制者 | ✅ 始终 | |
| 2. 收集的数据 | ✅ 始终 | 可能包含敏感数据（健康、残疾、照片） |
| 3. 目的与依据 | ✅ 始终 | 德国以《联邦数据保护法》第 26 条为核心 |
| 4. 接收方 | ✅ 始终 | 招聘平台、背景调查服务商、集团企业 |
| 5. 跨境传输 | ✅ 如适用 | 云端 HR 工具（Workday、SAP SuccessFactors、Greenhouse） |
| 6. 保留期 | ✅ **关键** | 拒绝后短期保留是关键合规点 |
| 7. 权利 | ✅ 始终 | |
| 8. Cookie 与追踪 | ⚠️ 仅当招聘页有自己的 Cookie | 通常很少，或由主站通知处理 |
| 9. AI 与自动化 | ✅ 如适用 | 简历筛选、AI 匹配、自动初选 |
| 10. 安全 | ✅ 始终 | 强调申请的保密性 |
| 11. 儿童 | ❌ 通常跳过 | 除非有面向未成年人的实习项目 |
| 12. 变更 | ✅ 始终 | |
| 13. 联系 | ✅ 始终 | |

### 可能的数据类别
- **身份**：全名、出生日期、国籍、照片（如提交）、性别
- **联系**：地址、电子邮箱、电话
- **职业**：简历/CV、求职信、工作经历、教育背景、证书、推荐信
- **评估**：面试记录、评估结果、测试分数
- **敏感数据（第 9 条）**：残疾状态（为工作场所便利/重度残疾身份）、健康（入职前体检）、有时包括宗教（德国的教会税）
- **技术**：如使用在线申请门户则为 IP/日志
- **AI 衍生**：匹配分数、自动筛选结果（如适用）

### 可能的合法依据
| 目的 | 德国 | 法国 | 通用欧盟 |
|---|---|---|---|
| 申请处理 | 《联邦数据保护法》第 26 条第 1 款 | 第 6 条第(1)款(b)项缔约前 | 第 6 条第(1)款(b)项 |
| 人才库（未来职位） | 同意（《联邦数据保护法》第 26 条第 2 款） | 同意 第 6 条第(1)款(a)项 | 同意 |
| 背景调查 | 《联邦数据保护法》第 26 条第 1 款（如必要） | 第 6 条第(1)款(b)项 + 比例原则 | 第 6 条第(1)款(b)项或(f)项 |
| 残疾/重度残疾 | 《联邦数据保护法》第 26 条第 3 款 | 第 9 条第(2)款(b)项劳动法 | 第 9 条第(2)款(b)项 |
| 平等机会监测 | 第 9 条第(2)款(b)项劳动法 | 第 9 条第(2)款(b)项 | 第 9 条第(2)款(b)项 |
| 基于 AI 的筛选 | 《联邦数据保护法》第 26 条 + GDPR 第 22 条 | 第 6 条第(1)款(b)项 + RGPD 第 22 条 | GDPR 第 22 条 |

### 类型特定的信息收集问题
1. 是否有应聘者追踪系统（ATS）？哪一个？（Personio、Workday、Greenhouse、SAP SF、BambooHR）
2. 是否使用 AI 进行简历筛选或候选人匹配？
3. 是否将申请存入人才库以备未来职位？保留多久？是否经同意？
4. 是否进行背景调查或推荐人核查？
5. 招聘过程中是否有工会委员会（Betriebsrat）参与？
6. 是否收集残疾状态（重度残疾身份）？
7. 是否有外部招聘机构或猎头参与（共同/独立控制者）？
8. 招聘页在主网站还是独立平台？
9. 是否在集团公司内部处理应聘者数据？

### 保留期默认值
| 数据 | 期限 | 依据 |
|---|---|---|
| 被拒应聘者——标准 | 拒绝后 6 个月 | AGG 时效期限（德国）、合理期限（欧盟） |
| 被拒应聘者——延长（经同意） | 最长 24 个月 | 人才库同意 |
| 录用 → 员工 | 转入员工档案 | 《联邦数据保护法》第 26 条 / 雇佣关系 |
| 评估结果 | 随申请一并删除 | 与申请相同 |
| 背景调查结果 | 决策后立即 | 数据最小化 |

### 类型特定的法律考量
- **德国**：《联邦数据保护法》（BDSG）第 26 条是主要合法依据，而非第 6 条第(1)款(b)项。GDPR 第 88 条 + BDSG 第 26 条构成特定制度。工会委员会协议（Betriebsvereinbarung）可作为合法依据。
- **法国**：适用 CNIL《招聘指引》（2023）。简历照片：不得要求提供。犯罪记录检查：仅限于特定岗位。
- **AI 筛选**：如作出对应聘者有重大影响的完全自动化决策，适用 GDPR 第 22 条。必须披露逻辑、意义、后果。要求人工复核。

### 示例条款模式

**人才库同意**：
```
经您另行同意，我们将您的申请文件存入人才库，以便在将来出现合适职位时考虑您。合法依据：第 6 条第(1)款(a)项 GDPR——您的同意 [德国：BDSG 第 26 条第 2 款]。您的数据将保留 [12/24] 个月。您可以随时通过联系 [联系方] 撤回同意。
```

**拒绝后保留**：
```
如果您的申请未获成功，我们将在通知拒绝后保留您的申请数据 [6 个月（德国）/ 最长 2 年（法国）]。这是为了在可能的法律程序（如依据 AGG《平等待遇法》/《劳动法典》）中保护我们的合法利益。合法依据：第 6 条第(1)款(f)项 GDPR [德国：BDSG 第 26 条第 1 款]。此期限后，您的数据将被删除，除非您已同意纳入我们的人才库。
```

**AI 筛选披露**：
```
我们使用 [系统名称] 支持我们的候选人遴选流程。该系统 [分析简历进行关键词匹配 / 根据资质对候选人排序]。结果仅作为参考因素之一，任何决策作出前均会由我们的招聘团队复核。合法依据：第 6 条第(1)款(b)项 GDPR [德国：BDSG 第 26 条第 1 款]。您有权获得人工干预、表达您的观点并对决策提出异议。
```

**外部招聘机构 / 第 14 条来源**：
```
如果您的数据由招聘机构或猎头提供给我们，您的数据来源为 [机构名称 / 类别："外部招聘机构"]。我们收到了以下类别的数据：[姓名、联系方式、简历、专业资质]。我们将最迟在首次联系时告知您此项处理。
```

## 员工

### 章节映射

| 章节 | 是否包含？ | 说明 |
|---|---|---|
| 1. 控制者 | ✅ 始终 | 雇主为控制者 |
| 2. 收集的数据 | ✅ 始终 | 范围很广——薪资、健康、绩效、IT 监控 |
| 3. 目的与依据 | ✅ 始终 | 多种依据：BDSG 第 26 条、法定义务、工会委员会协议 |
| 4. 接收方 | ✅ 始终 | 薪资服务商、税务机关、社保机构、养老金、集团企业 |
| 5. 跨境传输 | ✅ 如适用 | 全球 HR 平台、境外集团企业 |
| 6. 保留期 | ✅ **关键** | 复杂的多重保留期 |
| 7. 权利 | ✅ 始终 | 注意：某些权利在雇佣语境中受限 |
| 8. Cookie 与追踪 | ⚠️ 仅当内网/员工工具有 | 改为 IT 监控章节 |
| 9. AI 与自动化 | ✅ 如适用 | 绩效评分、员工队伍分析、HR 工具中的 AI |
| 10. 安全 | ✅ 始终 | |
| 11. 儿童 | ❌ 跳过 | 除非有面向未成年人的学徒制 |
| 12. 变更 | ✅ 始终 | |
| 13. 联系 | ✅ 始终 | |

### 附加章节（员工特定）
- **IT 监控 / BYOD**：互联网使用、邮件监控、设备管理政策
- **视频监控**：《联邦数据保护法》第 4 条、工会委员会共同决定权
- **GPS / 车辆追踪**：如追踪公司车辆
- **举报**：HinSchG（德国）/ Loi Sapin II（法国）数据处理
- **工会委员会访问**：与工会委员会共享哪些数据

### 可能的数据类别
- **主数据**：姓名、地址、出生日期、税号、社保号、银行信息
- **合同**：雇佣合同、职位、薪资、工时、起止日期
- **薪资**：工资、奖金、税级、扣减、福利
- **考勤**：工时、加班、休假、病假
- **绩效**：评估、目标、培训、证书
- **健康**：病假证明（AU 证明）、职业健康、BEM 记录
- **IT**：登录数据、电子邮箱（如被监控）、互联网使用日志、门禁卡
- **敏感**：残疾（重度残疾状态）、宗教（教会税）、工会会员身份（如与薪资相关）

### 保留期默认值（德国）
| 数据 | 期限 | 依据 |
|---|---|---|
| 薪资记录 | 雇佣关系结束后 6 年 | 《商法典》第 257 条 |
| 税务记录 | 10 年 | 《税收通则》第 147 条 |
| 社保记录 | 至 67 岁 + 6 年 | 《社会保障法典》第四编 |
| 人事档案（一般） | 终止后 3 年 | 一般时效《民法典》第 195、199 条 |
| 病假证明 | 年度结束后 1 年 | 数据最小化 |
| BEM 记录 | BEM 结束后 3 年 | 劳动法院先例 |
| 工会委员会选举记录 | 5 年 | 《企业宪法法》 |

### 类型特定的信息收集问题
1. 使用什么 HR/薪资系统？（Personio、SAP HCM、DATEV、Workday）
2. 是否有 IT 监控？（邮件、互联网、屏幕监控）
3. 场所内是否有视频监控？
4. 是否追踪公司车辆（GPS）？
5. BYOD 政策？移动设备管理？
6. 是否有工会委员会？相关 Betriebsvereinbarungen（工会委员会协议）？
7. 公司是否属于集团？集团内数据共享？
8. 是否设有举报渠道？
9. 职业健康管理（BEM）？
10. HR 流程中是否有 AI？（人员分析、绩效评分）

### 示例条款模式

**IT 监控披露**：
```
我们监控公司 IT 系统（电子邮件、互联网、应用程序）的使用情况，以确保 IT 安全、防止数据泄露并履行法律义务。监控仅限于元数据（发件人/收件人、时间戳、数据量），不包括内容监控。合法依据：第 6 条第(1)款(f)项 GDPR [德国：BDSG 第 26 条第 1 款]。[如存在工会委员会协议：处理还基于 [日期] 的工会委员会协议，依据 BDSG 第 26 条第 4 款。]
```

**教会税条款**（德国）：
```
| 教会税处理 | 按法律规定计算并代缴教会税 | 第 6 条第(1)款(c)项 GDPR + 第 9 条第(2)款(b)项 GDPR、BDSG 第 26 条第 3 款、《所得税法》第 51a 条 | 雇佣期间 + 6 年（《商法典》第 257 条） |
```

**病假处理**：
```
我们处理病假证明（AU 证明 / 病假条）用于继续支付工资的权利和缺勤管理。我们仅接收无劳动能力期间的信息，不接收诊断信息。合法依据：第 6 条第(1)款(c)项 GDPR + 第 9 条第(2)款(b)项 GDPR [德国：BDSG 第 26 条第 3 款 + 《工资继续支付法》第 5 条]。保留期：[日历年结束后 1 年（德国）/ 期间 + 5 年（法国）]。
```

**BYOD 条款**：
```
如果您将个人设备用于工作目的（BYOD），我们通过移动设备管理（MDM）解决方案 [名称] 处理设备标识符和使用数据，以保护公司数据并确保 IT 安全。我们不会访问您设备上的个人内容。合法依据：第 6 条第(1)款(f)项 GDPR——我们对 IT 安全的合法利益 [德国：BDSG 第 26 条第 1 款]。
```

## 商业伙伴（B2B）

### 章节映射

| 章节 | 是否包含？ | 说明 |
|---|---|---|
| 1. 控制者 | ✅ 始终 | |
| 2. 收集的数据 | ✅ 始终 | 最少——联系人，而非公司 |
| 3. 目的与依据 | ✅ 始终 | 合法利益占主导 |
| 4. 接收方 | ✅ 始终 | CRM、ERP、集团企业 |
| 5. 跨境传输 | ✅ 如适用 | CRM/ERP 往往设于美国 |
| 6. 保留期 | ✅ 始终 | 与商业保留义务挂钩 |
| 7. 权利 | ✅ 始终 | |
| 8. Cookie 与追踪 | ❌ 通常跳过 | 除非有带登录的 B2B 门户 |
| 9. AI 与自动化 | ⚠️ 罕见 | 仅当有信用评分或采购中的 AI |
| 10. 安全 | ✅ 始终 | |
| 11. 儿童 | ❌ 跳过 | 不适用 |
| 12. 变更 | ✅ 始终 | |
| 13. 联系 | ✅ 始终 | |

### 关键区分：第 13 条 vs 第 14 条
商业伙伴通知常涉及**第 14 条**（数据并非直接从数据主体收集）：
- 商业伙伴的联系人可能未直接提供其数据
- 其信息可能来自公司本身、公开登记簿、LinkedIn、展会
- 第 14 条要求披露数据的**来源**和**类别**
- 必须在获取数据后 **1 个月内**或在首次沟通时提供

### 可能的数据类别
- **商务联系**：姓名、职位/头衔、商务邮箱、商务电话、公司名称
- **合同**：签署人信息、授权代表
- **财务**：公司银行信息、信用信息（用于 B2B 信用核查）
- **沟通**：商务往来信函、会议记录
- **来源**：联系方式的获取途径（直接、网站、展会、公开登记簿、转介）

### 可能的合法依据
| 目的 | 合法依据 | 说明 |
|---|---|---|
| 合同管理 | 如数据主体为缔约方则第 6 条第(1)款(b)项；如为伙伴公司联系人则第 6 条第(1)款(f)项 | 联系人 ≠ 缔约实体 |
| 缔约前措施 | 第 6 条第(1)款(b)项或(f)项 | 询价、提案、谈判 |
| B2B 业务开拓 | 第 6 条第(1)款(f)项 | 合法利益——需利益衡量测试 |
| 会计与开票 | 第 6 条第(1)款(c)项——税法/商法 | HGB、AO、《商法典》 |
| CRM 管理 | 第 6 条第(1)款(f)项 | 关系管理 |
| 合规 / KYC | 第 6 条第(1)款(c)项——反洗钱、制裁 | 如适用 |
| 信用核查 | 第 6 条第(1)款(f)项或(b)项 | 如涉及评分则德国 BDSG 第 31 条 |

### 类型特定的信息收集问题
1. 您如何获取商务联系数据？（直接、展会、LinkedIn、购买名单、转介）
2. 是否有 B2B 门户或客户登录？
3. 是否对商业伙伴进行信用核查？
4. 使用什么 CRM/ERP？（Salesforce、HubSpot、SAP、Microsoft Dynamics）
5. 是否在企业集团内共享数据？
6. 是否有合规/KYC 要求？（反洗钱、制裁筛查）
7. 商务联系是否用于营销？如何（邮件、电话、活动）？

### 保留期默认值
| 数据 | 期限 | 依据 |
|---|---|---|
| 活跃商务关系 | 关系存续期间 | 第 6 条第(1)款(b)/(f)项 |
| 终止后（合同） | 3 年（一般时效）→ 最长 10 年（税务） | BGB/HGB/AO |
| 发票与会计 | 6–10 年 | 《商法典》第 257 条 / 《税收通则》第 147 条 |
| 开拓联系（无关系） | 3 年无互动 | 合法利益衡量 |
| KYC/反洗钱记录 | 关系结束后 5 年 | 《反洗钱法》第 8 条 |

### 示例条款模式

**第 14 条来源披露**：
```
我们可能从以下来源获取您的商务联系数据：您的雇主或您所代表的公司、公开可访问的企业登记簿（如 Handelsregister 商业登记簿、Registre du Commerce 商业登记簿）、职业网络（如 LinkedIn）、展会与行业活动，或商务转介。获取的数据类别：姓名、职业头衔、商务邮箱、商务电话、公司名称。
```

**B2B 业务开拓合法利益**：
```
| 业务拓展 / B2B 业务开拓 | 就与其专业活动相关的[产品/服务]联系潜在商业伙伴 | 第 6 条第(1)款(f)项 GDPR——我们发展业务关系的合法利益 | 自最后一次互动起 3 年 |
```

**CRM 管理**：
```
我们将您的商务联系数据存储在我们的 CRM 系统（[Salesforce / HubSpot / Microsoft Dynamics]）中，以管理我们的业务关系、协调沟通并确保服务质量。合法依据：第 6 条第(1)款(f)项 GDPR——我们对高效关系管理的合法利益。
```

**信用核查条款**（B2B）：
```
在建立业务关系之前，我们可能从 [Creditreform / SCHUFA / Coface / Euler Hermes] 获取有关贵公司的资信信息。这包括评分数据和信用评级。合法依据：第 6 条第(1)款(f)项 GDPR——我们评估信用风险的合法利益 [德国：BDSG 第 31 条]。您有权反对此项处理。
```

### 章节映射

| 章节 | 是否包含？ | 说明 |
|---|---|---|
| 1. 控制者 | ✅ 始终 | |
| 2. 收集的数据 | ✅ 始终 | 范围广——账户、购买、支付、偏好 |
| 3. 目的与依据 | ✅ 始终 | 合同 + 同意 + 合法利益混合 |
| 4. 接收方 | ✅ 始终 | 支付、配送、营销工具 |
| 5. 跨境传输 | ✅ 始终 | 支付处理商、营销工具往往设于美国 |
| 6. 保留期 | ✅ 始终 | |
| 7. 权利 | ✅ 始终 | 直接营销的反对权是关键 |
| 8. Cookie 与追踪 | ✅ 如在线 | 与网站通知交叉引用或整合 |
| 9. AI 与自动化 | ✅ 如适用 | 推荐、评分、个性化、欺诈检测 |
| 10. 安全 | ✅ 始终 | 支付安全尤其相关 |
| 11. 儿童 | ✅ 如产品或服务面向未成年人 | 玩具店、游戏、教育 |
| 12. 变更 | ✅ 始终 | |
| 13. 联系 | ✅ 始终 | |

### 背景：线上 vs 线下 B2C
该类型涵盖可能纯线下（零售店）、纯线上（电子商务——与网站类型重叠）或混合的客户关系。对于纯电子商务，将本画像与网站/App 画像合并。

### 可能的数据类别
- **身份**：姓名、电子邮箱、电话、地址、出生日期（年龄验证、生日优惠）
- **账户**：凭证、偏好、心愿单、已存地址
- **购买**：订单历史、产品偏好、退货、保修索赔
- **支付**：支付方式（通过处理商）、账单地址、分期数据
- **营销**：通讯同意、活动互动、促销使用
- **忠诚度**：积分、等级状态、计划参与
- **沟通**：支持工单、评论、投诉、聊天记录
- **画像**：购买模式、细分归属、流失预测、终身价值

| 目的 | 合法依据 | 说明 |
|---|---|---|
| 订单履行 | 第 6 条第(1)款(b)项 | 合同履行 |
| 账户管理 | 第 6 条第(1)款(b)项 | |
| 支付处理 | 第 6 条第(1)款(b)项 | 通过处理商（Stripe、PayPal 等） |

1. 这是用于线上、线下（零售）还是全渠道？

## 合并通知

如果用户需要涵盖多种类型的通知（例如，一家同时有应聘者门户和 B2B 伙伴板块的公司网站）：

### 方案 A：单一综合通知（推荐中小企业）
- 合并所有相关章节映射
- 在章节内使用小标题区分受众
- 示例：第 3 节有子节"3.1 网站访客"、"3.2 应聘者"、"3.3 商业伙伴"
- 风险：文档变长、难以导航

### 方案 B：独立通知（推荐大型/复杂机构）
- 每个受众/数据主体类别一份通知
- 从集中的隐私中心页面链接
- 更易于维护和更新
- 更适合每个受众处理活动不同的复杂组织
- 德国最佳实践：独立的"应聘者数据保护通知"非常普遍

### 方案 C：分层方法
- 一份简短的一般通知（1–2 页），涵盖共同要素（控制者、权利、安全、联系）
- 每种类型单独的详细附件
- 适合数据主体类别较多的组织

**建议**：询问用户偏好哪种方法。对于大多数中小企业，带清晰小标题的方案 A 可行。对于大型组织或涉及敏感处理的组织（如员工 + 应聘者），方案 B 更安全、更易维护。
