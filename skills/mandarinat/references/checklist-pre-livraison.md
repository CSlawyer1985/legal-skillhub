# 交付前强制性核查清单——反幻觉

<!-- NOYAU-ANTIHALLUCINATION v3 —— 与 mandarinat 1.4.0 / assistant-juridique-fr 7.4.0 同步。两个 skill 共用本文件：任何修改必须原样同步（各版本自身特有的「上文/下文」引用除外）。 -->

本核查清单构成**不可协商的检查环节**，须在**任何**包含判例引用、规范性文本引用（法典条文、法律、条例、法令、规章、集体协议）或学说引用的交付物**交付之前**执行。

未实际执行不得声称已完成。必须以**结构化表格**形式（下文定义的强制性工件）**明示**执行，而非心中一带而过。其目的有二：

1. 防止交付严格意义上的幻觉引用——此类事故的学术和专业代价不成比例；
2. 防止交付**形式上可追溯但实质上不吻合**的引用（错误归因型幻觉）——即会话中由工具调出的引用，但其返回内容并不支持它们本应奠基的论断。

## 何时执行核查清单

应在交付物**产出之后**、**实际交付给接收方**（用户、学生、客户、评审团、委员会）**之前**执行。这是最后一道过滤。

无任何例外：核查清单适用于短交付物和长交付物、案例题参考答案和研究论文、法律咨询意见和作业卡片。

## 依环境的执行方式

### 在 COWORK 和 CHAT_CU 模式（有文件系统）

执行为**阻塞式**：只要核查清单未完整通过且未产出结构化表格，交付物即不得交付。

1. **从引用日志生成核查表格**：`python3 scripts/reference_journal.py table --journal verification/journal-references.ndjson`（日志已在每次工具调用时实时记录——见工作流第 8 步）。先核验其完整性：`python3 scripts/reference_journal.py check --journal verification/journal-references.ndjson`（只要有一条记录不完整即退出码 1）。从日志派生的表格禁止凭记忆填写「摘录」列。如无日志（遗漏），通过重新查阅会话中的工具调用重建表格——绝不可凭记忆。
2. 将交付物中出现的全部 Légifrance URL 汇总到一个中间 JSON 文件。
3. 执行 `scripts/verify_links.py --from-file urls.json --check-content`（`--check-content` 模式默认启用），并在表格第 3 列中记录每项引用返回的相关文本摘录。
4. 检查输出：**任何失败的 URL**（模式无法识别、HTTP ≠ 200、内容不吻合）必须按下方「失败时的处理」一节处理，表格对应行随即标记为 ✗。
5. 只有当表格所有行均标记 ✓ 且已明确说出结束语时，方可交付。

### 在 CHAT 模式（无文件系统）

执行为**明示式**，逐条引用进行，采用结构化表格形式。`verify_links.py` 脚本不可执行，但必须应用同样的逻辑：

1. 在会话中生成核查表格（下方模板工件）。
2. 逐一列出交付物中的每项引用并记入第 1 列。
3. 对每一项，在会话中找出产生该引用的 OpenLegi（或其他检索工具）调用——第 2 列。
4. 阅读调用返回的内容（判决理由、判项、条文款项）并在第 3 列记录相关摘录。
5. 将该摘录与引用所奠基的论断对照，填写第 4 列（✓ / ✗ / 改写）。
6. 如未执行调用：在交付前补做缺失的检索。如用户无法等待，将该引用标注为「待核实」并记入第 4 列。
7. 确认交付物中的 Légifrance 链接确实来自工具响应——而非凭记忆重建。
8. 在交付交付物之前说出明确的结束语。

## 条件性降级（网络访问预检）

在 COWORK 和 CHAT_CU 模式下，实际执行 `verify_links.py --check-content` 要求 Cowork 沙箱能够访问 `www.legifrance.gouv.fr`。该访问可能被组织的网络白名单阻止。

**自动检测程序**——在第 4 步执行完整核验之前，先执行预检模式：

```bash
python3 scripts/verify_links.py --preflight
```

返回码：

| 退出码 | 状态 | 处理方式 |
|---|---|---|
| `0` | 网络正常 | 继续完整核验（`--check-content`）。 |
| `2` | 被 Cowork 白名单阻止 | **切换至降级模式**（手工生成结构化表格，如 CHAT 模式）。向用户显示白名单消息（见下）。 |
| `3` | 其他网络错误 | 重试；如持续失败，切换至降级模式并向用户报告技术细节。 |
| `4` | 被 Cloudflare 反机器人验证阻止 | **切换至 OpenLegi 通道**（见下文）。该阻止由 Légifrance 自身施加，与 Cowork 无关；用户无法解除。 |

**白名单阻止时向用户显示的消息**（须逐字复现）：

> ⚠️ 本沙箱无法进行 Légifrance 链接的自动核验：对 `www.legifrance.gouv.fr` 的网络访问被 Cowork 白名单阻止。我切换至降级核验模式：逐条明示枚举引用，确认会话中每次工具调用的可追溯性。
>
> **如需启用自动核验**（这是额外可靠性保证——可检测格式正确但指向无关判决的 URL，例如），请在 *Settings → Capabilities → Network access* 中授权以下域名：
>
> - `www.legifrance.gouv.fr`
> - `www.conseil-constitutionnel.fr`
> - `hudoc.echr.coe.int`
> - `curia.europa.eu`
> - `eur-lex.europa.eu`
>
> 在 Team / Enterprise 版中，请联系组织管理员。授权生效后，自动核验将在下次会话自动恢复。

降级模式不是核查清单的失败：这是一种正常降级，与 CHAT 模式遵循相同的实质严谨性，只是没有 HTML 内容的双重自动核验。

### 切换至 OpenLegi 通道（退出码 4——反机器人验证）

自 Légifrance 部署 Cloudflare 反机器人验证以来，服务器对所有来自代理沙箱的自动化请求一律返回 HTTP 403（带 `cf-mitigated: challenge` 响应头），*无论 Cowork 白名单如何配置*。网络层正常；是 Légifrance 拒绝请求。

在此情况下，通过 `--check-content` 的直接 HTTP 核验对 Légifrance 域名无效，但对不实施该验证的相邻域名（HUDOC、Curia、EUR-Lex、conseil-constitutionnel.fr）仍然有效。核验策略因此分为两个通道：

1. **对 Légifrance 标识符**（LEGIARTI、JURITEXT、CETATEXT、JORFTEXT、JORFARTI、LEGITEXT、CNILTEXT、KALITEXT）：**通过 OpenLegi 的 API 调用核验**，该通道不经过 Cloudflare 前端，因此仍可访问。脚本的 `--extract-ids` 模式识别交付物中的每个标识符，并指示要调用的 OpenLegi 工具：

   ```bash
   python3 scripts/verify_links.py --extract-ids --from-file urls.json
   ```

   输出 JSON 为每个标识符列出 `openlegi_tool` 字段（例如 JURITEXT 对应 `OpenLegi:get_decision_judiciaire`）、`openlegi_argument` 和 `openlegi_verification_instruction`（描述须核验什么：法院、日期、案件号、文本的法律状态、生效日期等）。随后代理对每个标识符调用 OpenLegi，并将响应与引用对照。

2. **对非 Légifrance 域名**（HUDOC、Curia、EUR-Lex、conseil-constitutionnel.fr）：`--check-content` 的 HTTP 核验照常可用。

这一切换*比 HTTP 核验更严格*，而非更宽松：OpenLegi 除标识符存在性外，还返回文本的法律状态和被引用版本的有效日期——直接覆盖第 5 步规则 (c)「强制性时间核验」。

**反机器人阻止时向用户显示的消息**（须逐字复现）：

> ℹ️ 通过 HTTP 请求对 Légifrance 链接的自动核验已不可行：Légifrance 现以 Cloudflare 反机器人验证阻止代理沙箱的自动化请求。网络层正常（其他域名可访问），但 Légifrance 服务器拒绝请求。我切换至 OpenLegi API 调用核验，该通道不受此阻止影响，并且额外带来被引用文本法律状态与生效日期的核验。无需您采取任何操作。


## 强制性结构化表格——核验工件

自 1.3.0 / 7.3.0 版起，「心中枚举」被禁止：核查清单采取**在有效交付前生成并写入会话**的**结构化表格**形式（在 COWORK 模式下，也可作为独立交付物保存）。表格是证明核查清单已完整执行的实体工件。

**文档中每一条实际引用占一行。** 一项引用在交付物中多处被调用时，按其被引用的次数计——每次出现都必须在各自语境中与它所奠基的论断对照。

**四列**（最高法院判例为五列，加陈述主体列）：

| 文档中所写引用 | 工具 + 标识符（CID/JURITEXT/CETATEXT/JORFTEXT/DOI/HAL） | 工具返回的相关文本摘录 | 陈述主体（最高法院判例） | 是否支持论断？（✓ / ✗ / 改写） |

**大体积交付物的优先级（规模化）**：

「每次出现一行」的规则适用于短交付物（参考答案、作业卡片、简短咨询）。对包含数十条引用的完整课程或专著，该规则将难以管理，并带来执行不完整的风险。此时适用：

- **P1**——奠基大前提、在引言/结论中被引用、或重复出现三次以上的引用：按**出现**核验（在每一语境中进行内容匹配）。
- **P2**——被引用一至三次的示例性引用：按**引用**核验（单一内容匹配）。
- **P3**——仅出现在参考文献中的引用：核验存在性与标识符，不做论断内容匹配。

表格骨架可通过 `scripts/extract_references.py --file [交付物]` 预填，该脚本检测引用及其位置（并可根据出现次数分配 P1/P2/P3 优先级）。

**使用规则**：

- 表格在有效交付前生成并写入会话（或在 COWORK 模式作为独立交付物）。
- 进度标准是二元的：只要有一行标记 ✗ 或「待改写」，交付即被**阻止**。对这些行，适用内容匹配三种出路之一——(i) 更换引用，(ii) 改写论断使之符合实际内容，(iii) 切换为无人称表述——然后更新该行。
- 省略表格等同于省略核查清单：没有表格，交付不得被宣布为合规。
- 只有当第 3 列所载摘录确实（而非近似地）奠基交付物对应论断时，该行方可标记 ✓。

### 可复制的模板工件

以下骨架为每个交付物复制一份。其撰写方式使其可复制粘贴（CHAT 模式）或写入单独文件 `tableau-verification-pre-livraison.md`（COWORK / CHAT_CU 模式）。

**相关交付物**：[文档标题]
**日期**：[年-月-日]
**模式**：[CHAT / CHAT_CU / COWORK]
**`verify_links.py` 预检**：[退出码 0 / 2 / 3 / 4——CHAT 模式不适用]

| # | 文档中所写引用 | 工具 + 标识符（CID/JURITEXT/CETATEXT/JORFTEXT/DOI/HAL） | 工具返回的相关文本摘录 | 陈述主体（最高法院判例） | 是否支持论断？（✓ / ✗ / 改写） |
|---|---|---|---|---|---|
| 1 | [交付物中所载引用] | [如 `OpenLegi:rechercher_code` — LEGIARTI000006437058] | 「[文本摘录或对理由/条文的忠实概括]」 | — | ✓ |

| 2bis | [新的无人称表述或新引用] | [工具 + 标识符或「无人称表述」] | 「[摘录，如有]」 | — | ✓ |
| 3 | [最高法院判例摘录] | [`Themia:...` + `OpenLegi:...`（Légifrance 链接）] | 「[最高法院自己的判决理由]」 | 法院主体 | ✓ |
| … | … | … | … | … | … |

**汇总**：
- 已核验行数：X
- 已改写次数：Y
- 残留未追溯引用：0（必须为零）

**结束语**：

> 「核查表格已生成；已核验 X 行；已改写 Y 处；无任何未追溯引用残留。准予交付。」

### 明确的结束语

在核查清单结束时——且仅在表格所有行均标记 ✓ 时——skill 在会话中明确说出以下话语（相应调整变量 `X` 和 `Y`）：

> 「核查表格已生成；已核验 X 行；已改写 Y 处；无任何未追溯引用残留。准予交付。」

未明确说出此结束语，**且**没有相应表格工件，交付**不得**被宣布。有结束语而无对应表格与两者皆无同样严重：结束语是表格已生成的证明，而非其替代品。

## 五个强制性步骤

以下五步对应于充实结构化表格各列的操作。

### 第 1 步——穷尽列出所引用的全部引用

列出文档中引用的**所有**引用，分三个不同类别：

**(a) 判例引用**——对每一项，登记：法院、日期、上诉/申请/案件编号、Légifrance 链接。在最高法院判例（Themia）中，记录任何所引摘录的**陈述主体**。

**(b) 特定规范性文本引用**——对每一项，登记：文本或法典名称、条文号、适用版本（被引用版本的生效日期）、Légifrance 链接。

**(c) 学说引用**——对每一项，登记：作者、标题、载体（期刊/著作/论文）、年份，以及**可核验标识符**（DOI、HAL 标识符或公认数据库的 URL）。无可用标识符的学说引用按「未核验」处理（见「失败时的处理」）。

清单必须穷尽：交付物中出现的每一项引用都应在其中，包括 skill 可能认为「显而易见」或「超级经典」的引用（《民法典》第 1240 条、Costedoat 判决等）。恰恰是这些引用需要最大限度的警惕。

### 第 2 步——核验每项引用的可追溯性（表格第 2 列）

对第 1 步清点出的每项引用，核验当前会话中**确实存在针对该具体引用**的检索工具调用（OpenLegi、LegalDataHunter、针对官方来源的 web_search），并在表格第 2 列记录工具 + 标识符。

可追溯性不可推定：如引用无法关联到可识别的工具调用，在证明相反之前**推定其为幻觉**。

### 第 3 步——内容匹配：将返回内容与论断对照（第 3 列和第 4 列）

此步防止错误归因型幻觉。对第 2 步追溯到的每项引用：

1. **阅读工具返回的实际内容**——判决的理由与判项、条文的准确款项、OpenLegi 卡片的文本内容。仅有元数据卡片不够。
2. **在第 3 列记录**相关文本摘录（判决理由、条文款项等）。
3. **将该摘录与引用本应奠基的论断对照**。填写「是否支持论断？」列：
   - **✓**：返回内容确实支持论断。
   - **✗**：返回内容不支持论断（错误归因）。
   - **改写**：通过改写论断使其贴合实际内容来消除差距。
4. **在最高法院判例（Themia）中**：填写「陈述主体」列，核验陈述归属的一致性——被呈现为最高法院立场的摘录必须来自 `passage_voix_cour` / `passage_visas` / `passage_chapeau`（标记 `voix:cour_cassation`），而非 `passage_motifs_ca`（上诉法院）或 `passage_moyens`（当事人）。陈述归属错误计为 ✗。
5. **对学说**：核验标识符（DOI/HAL/URL）确实解析到所宣称的引用，且归予作者的观点与内容实际相符（摘要、实际发表的言论）——而非合理重构。

对任何非 ✓ 行，适用内容匹配三种出路之一：

1. **更换引用**——重新检索以识别确实支持论断的文本。创建表格新行（或子编号 `nbis`）反映替换。
2. **改写论断**，使其符合引用的实际内容。新表述写入第 1 列；第 4 列随即改为「改写」。
3. **切换为无人称表述**——以「既有判例一贯认为……」/「责任之一般法规定……」之类的表述替换引用，不带具体编号或日期。数字引用从交付物中消失。

只要有一行标记 ✗ 或「待改写」，交付即被阻止。

对任何**未追溯**的引用（第 2 步失败），适用三条严格并行的出路：

1. **立即核验**——执行缺失的检索。如检索确认该引用且内容支持论断，保留并进入第 4 步。否则，遵循以下两条途径之一。
2. **删除**——将引用径直从交付物中移除。
3. **转为无人称表述**。

第四条途径应谨慎使用：保留引用但在交付物和表格第 4 列中明确标注为「待核实」。此途径仅在用户明确同意接收未核验引用时方可使用（这始终优于静默交付不确定的引用）。

### 第 4 步——核验官方链接/可核验标识符的存在与有效性

对每项**判例和规范性**引用，核验：

1. 交付物中包含 Légifrance 链接；
2. 链接符合公认的 Légifrance 模式（`JURITEXT`、`CETATEXT`、`JORFTEXT`、`JORFARTI`、`LEGIARTI`、`LEGITEXT`、`CNILTEXT`、`KALITEXT`）；
3. 所引标识符在实质上确实对应交付物中的引用。核验通道取决于预检结果（见上文「条件性降级」一节）：
   - **退出码 0**（网络正常）：执行 `verify_links.py --check-content`，获取 HTML 页面并将预期编号/关键词与内容对照。
   - **退出码 4**（Cloudflare 反机器人阻止——2026 年以来沙箱中最常见情形）：执行 `verify_links.py --extract-ids`，为每个 Légifrance 标识符生成要调用的 OpenLegi 工具名称。代理随后对每个标识符调用 OpenLegi，核验响应确认该引用。对非 Légifrance 域名（HUDOC、Curia、EUR-Lex、conseil-constitutionnel.fr），保留仍然有效的 `--check-content` HTTP 核验。
   - **退出码 2**（被 Cowork 白名单阻止）：如 CHAT 模式，逐行读取相应 OpenLegi 卡片核验（降级模式）。

对每项**学说**引用，核验存在**可核验标识符**（DOI、HAL 标识符或公认数据库 URL）且解析到所宣称的引用。无可核验标识符的学说引用按第 3 步程序处理（未核验 → 标注或删除）。

任何无链接或无效标识符的引用按第 3 步程序处理。

### 第 5 步——核验规范性文本的适用版本

对每个被引用的规范性文本（法典条文、法律、法令等），核验：

1. 所引版本确为**相关日期有效**的版本：对案例题或判决评注，为**案情（或所评注案件）事实发生之日**，而非当前日期；对前瞻性咨询或讲授现行法的课程，为当前日期。基准日期须明确确定，如题干未明示，则按所标示的假设确定；
2. 当文本有近期修改且可能影响推理时，明确说明适用版本。预期标注示例：「《民法典》第 1242 条第 4 款，依 2025 年 6 月 23 日第 2025-568 号法律修订的版本」。

## 失败时的处理

任何未通过上述五步之一的引用，落入**以下三种出路之一**——别无其他：

1. **迟延核验成功**——引用通过检索*事后*追溯并确认。保留。
2. **删除**——移除引用。推理必要时在不带该引用的情形下改写（无人称表述、援用另一条已核验引用）。
3. **明确标注「待核实」**——保留引用但在交付物中予以明确标注，并告知用户。

不作为（尽管失败仍交付交付物）是**被禁止的**。

### 示例 C——错误归因型幻觉（形式上可追溯但被内容否定）
