# 工作流：REVIEW_QUICK

以 Art. 28(3)(a)–(h) 为基准的快速合规审查，用于签署/不签署决策。目标周期：30–45 分钟。

**本工作流针对的问题是“这份 DPA 是否足够合规、我可以签署吗？”**——而非谈判策略。如果用户想知道应当对哪些内容提出异议或如何修订，改用 `review-negotiation.md`。

## 第 1 步——确认范围并加载参考文件

- 与用户确认：这是为签署/不签署决策做的快速审查（而非深度谈判）。
- 确认视角（控制人 / 处理人）。
- 加载 `references/art28-3-checklist.md`（强制）。
- 如源文件提及传输、SCC、第三国、Drittland：另加载 `references/sccs-module-guide.md`。

## 第 2 步——角色筛查（≤ 5 分钟）

应用 `references/art26-joint-controller.md` 中的筛查测试。如出现 3 个及以上“共同控制”指标，**停止审查**——向用户揭示错误归类，并建议切换到 `joint-controller.md`。对错误归类的文件做“合规”快速审查属于类别错误。

## 第 3 步——走查序言部分（C1–C7）

找到附件 1（或等效描述）。对每个序言要素，标记：

| 代码 | 要素 | 判定 |
|---|---|---|
| C1 | 处理事项 |  |
| C2 | 期限 |  |
| C3 | 性质 |  |
| C4 | 目的 |  |
| C5 | 个人数据类型 |  |
| C6 | 数据主体类别 |  |
| C7 | 控制人的权利与义务 |  |

判定 = `通过` / `薄弱` / `缺口` / `缺陷`。

如附件 1 仅为“主协议所载的服务”（缺陷 D1.1），立即将 C3、C4、C5、C6 全部标记为 `缺陷` 并继续。

## 第 4 步——走查 (a)–(h)

对每项义务，定位正文中的相关条款并标记：

| 代码 | 义务 | 判定 |
|---|---|---|
| (a) | 仅按书面指示处理 |  |
| (b) | 获授权人员的保密义务 |  |
| (c) | 安全（第 32 条）+ 附件 2 |  |
| (d) | 子处理人（制度 + 附件 3） |  |
| (e) | 数据主体权利协助 |  |
| (f) | 泄露 / DPIA / 协商协助 |  |
| (g) | 终止时删除 / 返还 |  |
| (h) | 审计与检查 |  |

快速测试（每项 ≤ 3 分钟）：
- 找到该条款。
- 与 `references/art28-3-checklist.md` 中的规范表述比对。
- 标记判定。
- 如为 `薄弱` / `缺口` / `缺陷`，记录*一个*最实质的问题。

## 第 5 步——跨条款检查

- **子处理人清单（附件 3）**：为空、已填写，还是“签署时无”？如为空但已知处理人使用子处理人，标记 `缺陷`。
- **TOMs（附件 2）**：存在且具体（`通过`）；存在但笼统/“行业标准”表述（`薄弱`）；缺失（`缺陷`）。
- **传输**：
  - 传输是否在范围内？
  - 如为是，机制是否已识别（SCC / DPF / 充分性认定）？
  - 如为 SCC：模块正确吗？附件 I.A/I.B/I.C/II/III 是否填写？
  - 如为 DPF：认证状态如何（注意：认证可能失效，建议设置回退）？
  - 是否引用 TIA（对 SCC 为强制性）？

## 第 6 步——头条问题

从所有 `缺口` 和 `缺陷` 标记中，按影响识别**前 3 项**。这些是决定建议的问题。

## 第 7 步——建议

根据判定模式：

| 模式 | 建议 |
|---|---|
| 序言部分和 (a)–(h) 全部 `通过`；传输已处理；无特殊类别处理 | **签署** |
| 大部分 `通过`，仅 1–2 项 `薄弱`；无 `缺陷` | **在记录剩余风险的情况下签署**（建议用户在内部记录接受事项） |
| 1 项及以上 `薄弱` + 1 项不阻碍签署的 `缺口` | **附随函签署**（随函处理该 `缺口`） |
| 序言部分或 (a)、(c)、(d) 子处理人制度或 (g) 控制人选择中出现任何 `缺陷` | **不修改则不签署** |
| 关键领域 3 项及以上为 `薄弱` 或更差，或传输无机制，或附件 2 为空 | **升级为 REVIEW_NEG** |

## 第 8 步——输出组装

按以下精确结构产出输出（不得偏离）：

```markdown
# DPA 快速审查——[相对方名称]

## 执行摘要
[3–5 句。陈述整体状况（合规 / 有缺口 / 有缺陷）。陈述头条问题。陈述建议。]

## 范围
- 角色：[控制人 / 处理人——确认]
- 视角：[控制人侧 / 处理人侧]
- 源文件日期：[date]
- 范围内传输：[是 / 否]
- 特殊类别 / 第 10 条数据：[是 / 否]

## 序言部分（附件 1 / 处理描述）

| 代码 | 要素 | 判定 | 证据（条款引用 + 逐字引述或“缺失”） | 备注 |
|---|---|---|---|---|
| C1 | 处理事项 | | | |
| ... | | | | |

## Art. 28(3)(a)–(h) 覆盖

| 代码 | 义务 | 判定 | 证据（条款引用 + 逐字引述或“缺失”） | 备注 |
|---|---|---|---|---|
| (a) | 书面指示 | | | |
| ... | | | | |

## SCC / 传输充分性
[无传输时跳过。否则：模块、附件、TIA、回退。]

## 需要修复的前 3 大问题

## 执业备注
```

## 交付前的质量门禁

- [ ] 开头确认角色。
- [ ] 序言部分所有要素均已处理（无跳过的行）。
- [ ] 所有 (a)–(h) 均已处理（无跳过的行）。
- [ ] 如涉及传输：SCC 充分性章节存在。
- [ ] 前 3 大问题确为影响最大的事项（而非最容易发现的事项）。
- [ ] 建议与判定模式匹配（关键领域存在任何 `缺陷` 时不得说“签署”）。
- [ ] 以执业备注结尾。

## 时间预算护栏

如审查超过 60 分钟，停止并询问用户是否希望升级为 `REVIEW_NEG`。耗时 90 分钟的快速审查属于范围设定错误。
