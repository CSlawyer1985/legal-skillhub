# 质量自检清单与禁止行为（SUB Agent 检查规范）

> 本文件供 Step 6.4 SUB Agent 读取并执行质量检查。SUB Agent 必须严格按照本文件定义的检查项、判定标准和输出格式执行检查，不得自行增减检查项或修改判定标准。

## 一、SUB Agent 检查流程

### 执行步骤

1. **读取本文件**：SUB Agent 启动后首先读取本文件的完整内容
2. **接收检查输入**：从主 Agent 接收以下输入数据：
   - 要素分解表（Step 3 输出）
   - 逐要素技术描述（Step 6.2 输出）
   - 整体技术方案描述（Step 6.3 输出）
   - 权利要求原文
   - 说明书关键段落
3. **逐项执行检查**：按照"二、检查项清单"中的每一项进行检查
4. **输出检查结果**：按照"四、输出格式"输出结构化检查结果
5. **禁止事项**：⛔⛔⛔ 禁止向用户提问、禁止要求用户提供任何信息、禁止因任何原因暂停处理流程

### 检查原则

- **严格判定**：每项检查只有"通过"和"未通过"两种判定，不存在"部分通过"
- **证据支撑**：每个"未通过"判定必须指出具体的问题位置和内容
- **修正建议**：每个"未通过"项必须给出可操作的修正建议

---

## 二、检查项清单

### 检查项 1：要素完整性

**检查目标**：确认每个权利要求要素都有对应的技术描述，无遗漏

**检查方法**：
1. 从要素分解表（Step 3 输出）中提取所有要素的序号和描述
2. 逐一在逐要素技术描述（Step 6.2 输出）中查找对应的技术描述
3. 确认要素数量完全一致，无遗漏、无多余

**判定标准**：
- 通过：要素分解表中的每个要素在技术描述中都有对应项，且数量一致
- 未通过：存在要素分解表中有但技术描述中缺失的要素，或数量不一致

**未通过时的输出要求**：列出所有遗漏要素的序号和原文描述

### 检查项 2：原文记载完整性

**检查目标**：确认保护范围解读中每项权利要求都包含"原文记载"子标题及完整原文引用

**检查方法**：
1. 在整体技术方案描述（Step 6.3 输出）中，检查每项权利要求是否都有"#### 权利要求X的原文记载"子标题
2. 检查每个"原文记载"子标题下是否完整引用了该权利要求的原文（使用引用块格式 `>`）
3. 确认原文为逐字引用，无意译、概括或省略
4. 确认"原文记载"子标题后紧接"#### 权利要求X的保护范围"子标题

**判定标准**：
- 通过：每项权利要求都有完整的"原文记载"+"保护范围"子标题结构，原文逐字引用
- 未通过：存在缺少"原文记载"子标题的权利要求，或原文引用不完整

**未通过时的输出要求**：列出缺少原文记载的权利要求编号

### 检查项 3：引用链消除

**检查目标**：确认技术描述中消除了所有"所述"引用链，可独立阅读

**检查方法**：
1. 在逐要素技术描述中搜索"所述"关键词
2. 检查每个"所述"是否已被还原为完整的技术对象名称
3. 确认技术描述可以脱离权利要求原文独立阅读理解

**判定标准**：
- 通过：技术描述中无"所述"引用链，或所有"所述"均已还原为完整名称
- 未通过：技术描述中仍存在未还原的"所述"引用链

**未通过时的输出要求**：列出所有未消除的"所述"引用链及其所在要素序号

### 检查项 4：功能性限定展开

**检查目标**：确认所有功能性限定都已基于说明书展开

**检查方法**：
1. 在权利要求原文中识别所有功能性限定（"用于…的装置""配置为…""适于…"等）
2. 检查每个功能性限定在技术描述中是否已展开为具体结构/手段
3. 展开内容是否基于说明书公开的实施例

**判定标准**：
- 通过：所有功能性限定均已展开，且展开内容有说明书依据
- 未通过：存在未展开的功能性限定，或展开内容无说明书依据

**特殊处理**：如说明书也未公开具体实施方式，判定为"未通过"，但在说明中标注"说明书未公开具体实施方式，保护范围存在争议"

**未通过时的输出要求**：列出所有未展开的功能性限定及其所在要素序号

### 检查项 5：禁止添加

**检查目标**：确认技术描述未添加权利要求和说明书中均未出现的技术特征

**检查方法**：
1. 将技术描述中的每个技术特征与权利要求原文和说明书关键段落进行比对
2. 识别技术描述中出现但权利要求和说明书中均未提及的技术特征
3. 排除"展开"功能性限定时还原的说明书已公开内容

**判定标准**：
- 通过：技术描述中的所有技术特征均可追溯到权利要求原文或说明书
- 未通过：技术描述中存在权利要求和说明书中均未出现的技术特征

**未通过时的输出要求**：列出所有添加的未出现技术特征及其所在要素序号

### 检查项 6：过渡词语义

**检查目标**：确认开放式/封闭式过渡词的语义在技术描述中正确体现

**检查方法**：
1. 在权利要求原文中识别所有过渡词（"包括""包含""由…组成""基本上由…组成"等）
2. 检查技术描述中是否正确体现了过渡词的语义：
   - 开放式（"包括""包含""含有"）→ 技术描述应体现"至少包含，不排除其他"
   - 封闭式（"由…组成""仅由"）→ 技术描述应体现"仅由以下组成，不含其他"
   - 半开放式（"基本上由…组成"）→ 技术描述应体现"排除改变本质的要素"

**判定标准**：
- 通过：所有过渡词的语义在技术描述中均正确体现
- 未通过：存在过渡词语义在技术描述中未正确体现的情况

**未通过时的输出要求**：列出语义错误的过渡词、其所在要素序号、以及正确的语义要求

### 检查项 7：依据溯源

**检查目标**：确认每条技术描述都标注了改写依据（说明书/审查历史）

**检查方法**：
1. 检查每条逐要素技术描述是否包含"改写依据"字段
2. 验证改写依据是否指向具体的说明书段落或审查历史页码
3. 确认无"合理推测"等无依据的表述

**判定标准**：
- 通过：每条技术描述均有具体的改写依据（说明书段落号/审查历史页码）
- 未通过：存在缺少改写依据或依据不具体的技术描述

**未通过时的输出要求**：列出缺少依据的技术描述及其要素序号

### 检查项 8：置信度标注

**检查目标**：确认整体描述标注了 `confidence: LEGAL-OPINION`

**检查方法**：
1. 检查整体技术方案描述（Step 6.3 输出）中是否包含 `confidence: LEGAL-OPINION` 标注
2. 检查是否附注"⚠️ 初步法律分析，需专利律师确认"

**判定标准**：
- 通过：整体描述已标注 `confidence: LEGAL-OPINION` 并附注律师确认提示
- 未通过：缺少置信度标注或律师确认提示

**未通过时的输出要求**：指出缺失的标注项

## 三、质量要求（主 Agent 参考用）

### 必须满足

1. **原文可溯**：每个要素分解必须可追溯到权利要求原文的具体位置，不得凭记忆或概括
2. **解释一致**：本步骤确定的权利要求解释，在报告内各章节之间必须保持一致
3. **置信度标注**：
   - 权利要求原文要素分解 → `EXTRACTED`
   - 保护范围解读 → `LEGAL-OPINION`
   - 等同范围预判 → `LEGAL-OPINION`
   - 审查历史限制分析 → `INFERRED`（有审查历史时）或 `UNVERIFIED`（无审查历史时）
   - 同族差异 → `INFERRED`
4. **法律分析标注**：所有 `LEGAL-OPINION` 内容必须附注"⚠️ 初步法律分析，需专利律师确认"
5. **保密等级**：权利要求解析页面默认 `classification: 内部`
6. **审查历史优先**：当说明书解释与审查历史限制冲突时，以审查历史限制为准

### 禁止行为

1. 不得意译或概括权利要求原文，必须逐字引用
2. 不得将 LEGAL-OPINION 内容标注为 EXTRACTED
3. 不得编造不在原始素材中的审查历史信息
4. 不得忽略审查历史中的限缩性修改
5. 不得在保护范围解读中使用模糊的法律术语替代具体技术描述
6. 不得对授权前专利和授权后专利采用相同的解释原则（授权前：最宽合理解释；授权后：结合审查历史限缩解释）
7. 不得跳过任何步骤，即使某些步骤暂无数据（无数据时标注"缺失"并建议补充）

## 四、输出格式

SUB Agent 必须严格按照以下格式输出检查结果：

```markdown

| 检查项 | 判定 | 说明 |
|--------|------|------|
| 要素完整性 | 通过/未通过 | [具体说明，未通过时指出遗漏要素] |
| 原文记载完整性 | 通过/未通过 | [具体说明，未通过时指出缺少原文记载的权利要求编号] |
| 引用链消除 | 通过/未通过 | [具体说明，未通过时指出未消除的引用链] |
| 功能性限定展开 | 通过/未通过 | [具体说明，未通过时指出未展开的功能性限定] |
| 禁止添加 | 通过/未通过 | [具体说明，未通过时指出添加的未出现技术特征] |
| 过渡词语义 | 通过/未通过 | [具体说明，未通过时指出语义错误的过渡词] |
| 依据溯源 | 通过/未通过 | [具体说明，未通过时指出缺少依据的技术描述] |
| 置信度标注 | 通过/未通过 | [具体说明，未通过时指出缺失的标注] |

**总体判定**：全部通过 / 存在未通过项

**未通过项修正建议**：
- [针对每个未通过项，给出具体的修正建议]
```

## 五、保护范围解读的三条核心约束

1. **一一对应约束**：技术描述的要素数量必须与权利要求要素分解表（Step 3 的输出）完全一致，不得增删
2. **依据溯源约束**：每条技术描述必须标注出处（说明书段落/审查历史页码），禁止无依据的"合理推测"
3. **禁止添加约束**：技术描述不得引入权利要求和说明书中均未出现的技术特征——"展开"功能性限定是还原说明书已公开的内容，不是发明新内容

这三条约束解决 Agent 最常见的两种错误：
- **过度泛化**：把保护范围描述得比实际更宽
- **过度具体化**：把保护范围描述得比实际更窄
