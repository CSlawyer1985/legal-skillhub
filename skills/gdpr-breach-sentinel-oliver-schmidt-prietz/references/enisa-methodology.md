# ENISA 严重性评估方法论

**公式：** `SE = (DPC × EI) + CB`

> **本方法论的角色：** ENISA 评分是结构化的**决策支持**。它为第 33(1) 条（「不太可能造成风险」）和第 34(1) 条（「可能造成高风险」）的法定测试提供信息——但绝不替代。每个评分都必须桥接到书面的第 33/34 条结论（见 §4a）。

---

## 0. 快速定向树（常见简单场景）

供有经验的 DPO 在完整工作流之前快速初步检查：

```
加密设备丢失
├── 加密为现行算法（如 AES-256）？→ 否 → 需要完整评估
├── 密钥安全且分开存放？→ 否 → 需要完整评估
├── 存在备份？→ 否 → 可用性泄露——进一步评估
└── 全部为是 → 可能 LOW（仅内部日志）。如涉及 >100 名主体，以完整评估确认。

误投邮件（单一收件人）
├── 在阅读前已撤回/删除？→ 是，已确认 → 可能 LOW（内部日志）
├── 含第 9 条数据？→ 是 → 需要完整评估（可能 HIGH）
├── 含财务数据？→ 是 → 需要完整评估（可能 HIGH）
└── 仅为简单联系数据 → 可能 LOW-MEDIUM。记录并评估。

勒索软件
├── 有外泄证据？→ 是 → 需要完整评估（可能 HIGH/VERY HIGH）
├── 备份在 24 小时内恢复？→ 是，无外泄 → 评估可用性影响
└── 无备份 / 长时间停机 → 需要完整评估（可能 HIGH）

钓鱼（凭证泄露）
├── 范围限于单一账户？→ 评估该账户访问了哪些数据
├── 受损账户已启用 MFA？→ 是 → 风险降低，仍需评估
└── 管理员/特权账户？→ 立即需要完整评估
```

**注：** 决策树仅提供初步定向。务必完成完整 ENISA 评估加上第 33/34 条法律桥接，以确定最终分类和记录。

## 1. 数据处理情境（DPC）：1-4

### 按类别的基础分

| 类别 | 基础分 | 示例 |
|----------|------|----------|
| **简单数据** | 1 | 姓名、联系方式、履历数据、教育背景、职业经历 |
| **行为数据** | 2 | 位置、流量数据、浏览历史、偏好、习惯 |
| **财务数据** | 3 | 收入、银行对账单、信用卡、投资、交易 |
| **敏感数据（第 9 条）** | 4 | 健康、政治观点、宗教信仰、性取向、生物识别、基因、犯罪记录 |

### 情境调整（±1-3，上限为最终 DPC 范围 1-4）

| 因素 | 方向 | 示例 |
|--------|-----------|----------|
| 每名个人的数据量 | ↑ +1 至 +2 | 1 年流量数据 vs. 1 周 |
| 控制者的特征 | ↑ +1 至 +2 | 网上药店客户名单 → 健康推断 |
| 弱势数据主体 | ↑ +1 至 +3 | 未成年人、受保护证人、虐待受害者 |
| 数据失效/年代 | ↓ -1 至 -2 | 10 多年前过期的信用卡 |
| 公开可得性 | ↓ -1 至 -2 | 数据已在公共目录中 |
| 性质揭示少于类别 | ↓ -1 | 通用健康证明 vs. 诊断 |

**重要：** 应用所有调整后，最终 DPC 分数必须**上限为 4.0**（封顶）且**下限为 1.0**（最低）。如调整会使分数超出 4.0，将超出因素在战略咨询部分记为**定性加重情节**——它们强化严重性等级，但不改变 DPC 数字分数。

### 调整示例

| 场景 | 基础分 | 调整 | 最终 DPC |
|----------|------|------------|-----------|
| 超市客户名单（姓名、电话） | 1 | 无 | 1 |
| 豪车经销商客户名单 | 1 | +1（财务状况推断） | 2 |
| 网上药店客户名单 | 1 | +2（健康状况推断） | 3 |
| 卧底警察名单 | 1 | +3（重大安全风险） | 4 |
| 约会网站用户名单（仅姓名） | 2 | 无 | 2 |
| 含性偏好的约会网站 | 4 | 无 | 4 |
| 10 年前的过期信用卡 | 3 | -2（数据失效） | 1 |

## 2. 识别难易度（EI）：0.25-1.00

### 评分等级

| 分数 | 等级 | 说明 |
|-------|-------|-------------|
| **0.25** | 可忽略 | 将数据与个人匹配极其困难；仅在特定条件下可能 |
| **0.50** | 有限 | 识别需要重大努力或访问额外来源 |
| **0.75** | 显著 | 以中等努力或常见可得信息即可实现识别 |
| **1.00** | 最大 | 仅凭泄露数据即可直接识别；无需特别研究 |

### 按标识符类型的 EI

| 标识符 | EI = 0.25 | EI = 0.50 | EI = 0.75 | EI = 1.00 |
|------------|-----------|-----------|-----------|-----------|
| **全名** | 常见姓名，人口众多 | 全国同名人少 | 小城市同名人少 | + 出生日期 + 电子邮件 |
| **身份证/护照/社保号** | 仅号码，无参考库访问 | — | + 揭示出生日期 + 电子邮件 | + 从参考库得到姓名 |
| **电话/地址** | 不在公共登记册 | 非公开，小城市 | — | 在公共登记册 |
| **电子邮件** | 无姓名，网上不可检索 | — | 在社交网络可检索 | 含姓名且可检索 |
| **照片** | 模糊/远处图像 | 模糊 + 位置线索 | 清晰照片，无其他信息 | 清晰 + 关联到位置/群体 |
| **代码/别名** | 无参考库无法关联 | — | 别名揭示名字 + 电子邮件 | 揭示全名或可访问库 |

## 3. 泄露情境（CB）：0-2（可累加）

分数**可累加**——多种情境可同时适用。

### 保密性丧失

| 分数 | 情境 |
|-------|--------------|
| 0 | 数据暴露于风险但无访问证据 |
| +0.25 | 数据披露给有限的已知接收者 |
| +0.50 | 数据披露给数量未知的接收者或公开披露 |

### 完整性丧失

| 分数 | 情境 |
|-------|--------------|
| 0 | 数据被更改但在使用前已恢复原件 |
| +0.25 | 数据被更改，可能被错误使用，可恢复 |
| +0.50 | 数据被更改，可能被错误使用，不可恢复 |

### 可用性丧失

| 分数 | 情境 |
|-------|--------------|
| 0 | 数据无困难即可恢复（存在备份） |
| +0.25 | 暂时不可用（恢复需要努力/时间） |
| +0.50 | 永久不可用（无法恢复） |

### 恶意意图

| 分数 | 情境 |
|-------|--------------|
| 0 | 意外（人为错误、技术故障、配置错误） |
| +0.50 | 故意（盗窃、黑客攻击、内部攻击、数据出售） |

## 4. 严重性计算与判定

### 计算：`SE = (DPC × EI) + CB`

| SE 分数 | 等级 | 影响描述 | 推定行动（以第 33/34 条法律测试为准） |
|----------|-------|--------------------|--------------------------------------------------------|
| **< 2** | LOW | 轻微不便（重新输入信息的时间、烦扰） | 推定：仅内部日志（第 33(5) 条） |
| **2 – < 3** | MEDIUM | 需费力克服的显著不便（额外成本、服务被拒、压力） | 推定：通知监管机构（第 33 条） |
| **3 – < 4** | HIGH | 造成严重困难的重大后果（盗用、列入黑名单、财产损失、失业） | 推定：通知监管机构 + 数据主体（第 33 和 34 条） |
| **≥ 4** | VERY HIGH | 重大/不可逆后果（财务困境、长期伤害、死亡风险） | 推定：通知监管机构 + 主体 + 考虑公开沟通 |

分数产生**推定或建议，而非自动法律义务**。法定触发条件仍是第 33(1) 条和第 34(1) 条。

## 4a. 法律桥接（分数 → 事实 → 结论）

每项评估都必须将分数书面转化为法律测试：

```
法律桥接
ENISA 分数：      [SE 值 + 等级]
关键事实：        [发生了什么、涉及谁的数据、规模多大]
保障措施：        [泄露前已到位 / 泄露后已应用]
可能影响：        [对个人后果的可能性和严重性]
→ 第 33(1) 条：     [通知监管机构 / 否——不太可能造成风险，因为……]
→ 第 34(1) 条：     [通知主体 / 否——无高风险，因为…… /
                   否——适用第 34(3)(a)/(b)/(c) 条例外，因为……]
```

**桥接示例演练**（承接示例 1，带备份勒索软件，SE = 3.75 HIGH）：

> ENISA 分数：3.75（HIGH）——推定：通知监管机构 + 主体。
> 关键事实：医院遭勒索软件攻击；5000 名患者的健康数据被攻击者加密；备份在 24 小时内恢复；迄今无外泄证据，但取证审查未完成。
> 保障措施：离线备份（有效）；静态数据未加密（缺口）。
> 可能影响：暂时不可用已实际发生（护理可能延迟）；保密性影响未确认但鉴于攻击者访问，具有可能性——对第 9 条数据，可能披露不能排除为「不太可能」。
> → 第 33(1) 条：通知监管机构——在外泄未被排除且可用性已丧失 24 小时的情况下，不能得出「不太可能造成风险」的结论。
> → 第 34(1) 条：通知主体——如披露已发生，高风险很可能；鉴于第 9 条数据和持续中的取证，现在即沟通并补充，而非等待。无第 34(3) 条例外：数据静态未加密 (a)，无后续措施消除披露风险 (b)，个别沟通可行 (c)。

**分歧规则：** 如法律结论偏离分数的推定——无论哪个方向——理由必须在桥接中说明并记入内部合规日志。LOW 分数在涉及弱势主体和可信威胁情境时仍可能要求通知；MEDIUM 分数在经取证排除访问时可能以书面记录证明不通知的正当性。

## 4b. 边界分数指引

接近阈值的分数需要额外审查：

| 分数范围 | 指引 |
|-------------|----------|
| **1.8 – 2.0** | 充分记录为何你认为 LOW 有理由；监管机构可能不同意 |
| **2.8 – 3.0** | 考虑是否有任何未捕获因素将推入 HIGH；倾向保守 |
| **3.8 – 4.0** | 评估即使在 4.0 阈值以下，公开沟通是否仍有必要 |

当分数距阈值 0.25 以内时，在评估中明确注明，并建议用户与其 DPO 或法律顾问讨论边界分类。

## 5. 加密评估

### 逻辑树

```
如果 已加密 + 算法现行 + 密钥安全 + 密钥分开存放 + 存在备份：
    → 保密性风险 = 极小
    → 第 34 条例外：可能可用（高置信度）
    → 但仍要评估：可用性是否受影响？多长时间？

如果 已加密 + 算法现行 + 密钥安全 + 存在备份：
    → 保密性风险 = 低
    → 第 34 条例外：可能可用（中置信度）
    → 标记：密钥存储分离未确认

如果 已加密 + 密钥受损 或 密钥与数据同存：
    → 按未加密数据处理
    → 第 34 条例外：不可用
    → 需要完整风险评估

如果 已加密 + 无备份：
    → 无论加密与否，可用性泄露均已发生
    → 尽管有加密，仍可能要求通知
    → 第 34 条例外不适用于可用性丧失
```

### 需要询问的问题

1. 数据是否使用最先进算法（如 AES-256）静态加密？
2. 加密密钥是否受损或可能可访问？
3. 密钥是否与加密数据分开存放？
4. 密钥的生成方式是否使其无法通过现有技术手段获知？
5. 攻击者可能访问了多长时间？（与暴力破解风险相关）

**关键告诫：** 加密仅可能免除*数据主体*通知（第 34 条）。你可能仍须通知*监管机构*（第 33 条），且必须始终内部记录（第 33(5) 条）。

## 6. 演练示例

### 示例 1：带备份的勒索软件
- **场景：** 医院遭勒索软件，5000 名患者，健康数据被加密，备份在 24 小时内恢复
- **DPC：** 4（健康数据）
- **EI：** 0.75（姓名 + 患者 ID）
- **CB：** 0.25（暂时不可用）+ 0.50（恶意）= 0.75
- **SE：** (4 × 0.75) + 0.75 = 3.75 → **HIGH**
- **推定判定（通过第 33/34 条桥接确认——见 §4a）：** 通知监管机构 + 主体

### 示例 2：误投邮件
- **场景：** 含薪资信息的单封邮件误发给错误员工，1 小时内撤回
- **DPC：** 3（财务）
- **EI：** 1.00（全名 + 薪资）
- **CB：** 0.25（有限的已知接收者）+ 0（意外）= 0.25
- **SE：** (3 × 1.00) + 0.25 = 3.25 → **HIGH**
- **推定判定（通过第 33/34 条桥接确认）：** 通知监管机构 + 主体——但如披露经可核验地得到控制，桥接可能证明较轻处理有理由（参见 EDPB 误邮案件）

### 示例 3：加密笔记本电脑丢失
- **场景：** 含 200 条客户记录的笔记本电脑，全盘加密，密钥未受损
- **DPC：** 1（联系数据）
- **EI：** 0.25（加密使识别可忽略）
- **CB：** 0（数据实际未被访问）
- **SE：** (1 × 0.25) + 0 = 0.25 → **LOW**
- **推定判定（通过第 33/34 条桥接确认）：** 仅内部日志

## 7. 边界分数演练示例

这些示例说明接近严重性阈值、最需要判断力的情形。

### 示例 4：接近 LOW/MEDIUM 阈值（SE = 1.75 – 2.0）
- **场景：** 营销机构向 150 名收件人发送通讯，所有电子邮件地址在 CC 中可见（而非 BCC）
- **DPC：** 1（仅电子邮件地址——简单联系数据）
- **EI：** 1.00（电子邮件地址是直接标识符）
- **CB：** 0.25（披露给有限的已知接收者——其他订阅者）+ 0（意外）= 0.25
- **SE：** (1 × 1.00) + 0.25 = 1.25 → **LOW**
- **但需考虑：** 如通讯主题揭示敏感信息（如心理健康通讯的订阅者），DPC 应向上调整（+1 至 +2），可能将 SE 推至 2.25-3.25 → MEDIUM 或 HIGH
- **教训：** 邮件列表的性质对 DPC 调整影响极大

### 示例 5：接近 MEDIUM/HIGH 阈值（SE = 2.75 – 3.0）
- **场景：** HR SaaS 提供商（处理者）遭受泄露；3 家客户公司的员工记录被暴露。数据包括姓名、薪资和绩效评级。500 名员工受影响。经配置错误的 API 端点意外暴露，12 小时内发现。
- **DPC：** 3（薪资 = 财务数据）
- **EI：** 1.00（全名 + 员工 ID）
- **CB：** 0.25（经 API 暴露，不清楚是否有人访问）+ 0（意外）= 0.25
- **SE：** (3 × 1.00) + 0.25 = 3.25 → **HIGH**
- **支持 MEDIUM 的理由：** 如访问日志确认暴露窗口期内零外部访问，可主张 CB 应为 0（暴露于风险但无访问证据），得出 SE = 3.0——恰在边界上
- **建议：** 在此边界上，倾向 HIGH（通知主体）。绩效评级与薪资并列造成工作场所伤害的可能性，足以证明保守做法

### 示例 6：接近 HIGH/VERY HIGH 阈值（SE = 3.75 – 4.0）
- **场景：** 保险公司数据被外部攻击者窃取。2000 名客户的健康数据（诊断 + 理赔历史）被盗。数据包括姓名、保单号和 ICD-10 诊断代码。确认外泄至外部服务器。
- **DPC：** 4（健康数据——第 9 条）
- **EI：** 1.00（全名 + 保单号）
- **CB：** 0.50（披露给未知接收者）+ 0.50（恶意意图）= 1.00
- **SE：** (4 × 1.00) + 1.00 = 5.00 → **VERY HIGH**
- **注：** 这明显是 VERY HIGH。但考虑一个变体：同一泄露但仅涉及 15 名个人，且 ICD-10 代码为常见病症（流感、常规体检）。此处可主张 DPC 调整 -1（性质揭示少于类别所示），得出 SE = (3 × 1.00) + 1.00 = 4.00——恰在 VERY HIGH 阈值。此时，规模小可能证明停留在 HIGH 有理由，但恶意外泄主张 VERY HIGH。两种分析都记录。
