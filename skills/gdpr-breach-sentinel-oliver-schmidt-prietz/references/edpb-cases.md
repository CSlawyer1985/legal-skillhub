# EDPB 案例匹配参考

基于 EDPB《指南 01/2021——数据泄露通知示例》。

---

## 勒索软件案例（01-04）

### 案例 01：有适当备份的勒索软件
**情景：** 小型制造公司，勒索软件加密员工数据（30 名员工），数小时内从备份恢复，无数据外泄证据。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 否 |
| 通知数据主体 | 否 |
| 理由 | 无保密性侵犯，可用性影响极小，有备份可用 |

**关键区分因素：** 如果备份不可用或疑似外泄 → 升级为案例 02/03。

---

### 案例 02：无适当备份的勒索软件
**情景：** 农业公司，勒索软件加密包括客户/供应商信息在内的业务数据，无备份，数据丢失。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 永久性可用性损失，业务关系受影响 |

**关键区分因素：** 如果仅涉及内部数据（无第三方数据）→ 可能减少主体通知。

---

### 案例 03：医院勒索软件伴数据外泄
**情景：** 医院遭勒索软件攻击，健康数据在加密前被外泄，影响 5000 多名患者。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 高风险数据（健康）、保密性侵犯已确认、规模大 |

**关键区分因素：** 这是严重案例——始终需要全面通知。

---

### 案例 04：医院勒索软件无外泄
**情景：** 医院遭勒索软件攻击，无外泄证据，备份已恢复，服务中断 2 天。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 视影响而定 |
| 理由 | 健康数据 + 可用性损失需通知监管机构；主体通知取决于对护理的实际影响 |

**关键区分因素：** 如果患者护理受到影响 → 通知主体。

---

## 数据外泄案例（05-07）

### 案例 05：哈希密码外泄
**情景：** 网络托管服务，含用户名和哈希密码的数据库被盗，120 万用户。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 规模 + 凭据数据；即使是哈希密码也构成风险 |

**关键区分因素：** 强哈希（bcrypt、Argon2）可能降低紧迫性，但不能免除通知。

---

### 案例 06：未加密凭据外泄
**情景：** 在线市场，未加密密码 + 个人数据被盗，1500 名用户。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是（紧急） |
| 理由 | 账户被入侵和身份盗窃的即时风险 |

**关键区分因素：** 紧迫性最高；建议强制立即重置密码。

---

### 案例 07：敏感数据外泄
**情景：** 保险公司，健康数据（诊断、索赔）外泄，2000 名客户。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 第 9 条特殊类别数据，歧视/损害风险高 |

**关键区分因素：** 健康 + 财务数据结合 = 风险极高。

---

## 内部人员风险案例（08-09）

### 案例 08：员工外泄
**情景：** 离职员工将客户数据库（2000 条记录）复制到个人设备。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 可能是 |
| 理由 | 故意行为，数据用途不明 |

**关键区分因素：** 如果数据已追回且员工确认未使用/未共享 → 可能减少主体通知。

---

### 案例 09：数据意外传输
**情景：** 员工意外将含 89 名学生成绩的电子表格发送到错误的班级群组。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 未成年人（弱势群体），教育数据披露给已知接收人 |

**关键区分因素：** 已知接收人 + 快速删除行动可能降低严重性评估。

---

## 丢失/被盗设备（10-12）

### 案例 10：被盗设备含加密数据
**情景：** 公司笔记本电脑被盗，全盘加密（AES-256），强密码，无密钥泄露。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 否 |
| 通知数据主体 | 否 |
| 理由 | 加密使数据不可理解 |

**关键区分因素：** 如果加密较弱或密钥可能泄露 → 按案例 11 处理。

---

### 案例 11：被盗设备无加密
**情景：** 未加密 U 盘丢失，内含 500 条客户记录，含联系方式和财务数据。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 财务数据可访问，不知设备在谁手中 |

**关键区分因素：** 仅联系方式数据 → 可能不需要通知主体。

---

### 案例 12：纸质文件被盗
**情景：** 公文包被盗，内含 20 名客户税务记录的纸质文件。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 财务数据，纸质文件无法进行技术保护 |

**关键区分因素：** 纸质 = 始终未加密；按敏感处理。

---

## 误投递案例（13-16）

### 案例 13：邮寄至错误地址
**情景：** 含健康数据的保险文件寄往错误地址，原封未动退回。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 否 |
| 通知数据主体 | 否 |
| 理由 | 原封退回 = 无实际披露 |

**关键区分因素：** 如果被拆封或未退回 → 升级为案例 14/15。

---

### 案例 14：邮寄件被拆封
**情景：** 银行对账单寄往错误地址，接收人在退回前拆封并阅读了内容。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 财务数据披露给已知第三方 |

**关键区分因素：** 单一接收人，恶意意图可能较低 → 可记录并监测。

---

### 案例 15：敏感医疗结果误投
**情景：** 化验结果（HIV 检测）被错误发送给另一位患者。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是（双方） |
| 理由 | 高度敏感的健康数据，错误接收人知悉正确接收人的数据 |

**关键区分因素：** HIV/精神健康/基因 = 最高敏感类别。

---

### 案例 16：批量邮寄错误
**情景：** 15,000 张发票寄往错误的收件人地址（每个人都收到了他人的发票）。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 规模 + 每张发票均披露财务关系 |

**关键区分因素：** 大规模系统性增加风险。

---

## 社会工程案例（17-18）

### 案例 17：身份盗窃/冒充
**情景：** 来电者冒充客户，获取其账户详情（地址、后 4 位数字、交易记录）。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是（被冒充的个人） |
| 理由 | 定向攻击，特定个人面临风险 |

**关键区分因素：** 通知受害者，而非攻击者（显然）。

---

### 案例 18：通过钓鱼邮件外泄
**情景：** 员工落入钓鱼陷阱，攻击者访问电子邮件 3 周，100 多个联系人暴露。

| 因素 | 评估 |
|--------|------------|
| 通知监管机构（SA） | 是 |
| 通知数据主体 | 是 |
| 理由 | 访问期间长，不知已阅读/复制了什么 |

**关键区分因素：** 访问持续时间增加严重性；如果在数小时内发现访问 → 可能降低。

## 使用本参考

### 类比警告（匹配前阅读）

- 《指南 01/2021》的案例是**说明性类比，而非有约束力的决定**。它们展示了 EDPB 如何在类型化事实上推理——它们不决定您的案件。
- **事实差异很重要。** 类比永远不能替代对实际事实适用第 33/34 条法律测试（参见 SKILL.md 中的法律桥接）。
- **ENISA 和 EDPB 的示例可能分歧。** 在冲突时，记录两者并采取保守立场（参见下文"案例与 ENISA 冲突时"）。
- **渠道很重要：** 误投的*电子邮件*只是被*类比*到邮寄案例（13–16）和案例 09——并非直接由其涵盖。明确说明差异：电子邮件可撤回，已读回执和服务器日志可证明（未）访问，数字副本会以纸质不会的方式持续存在和转发。
- 如果示例建议不通知但您的案情不确定，请以书面形式保留保守的推理，而非采纳示例的结果。

### 匹配过程

1. 识别**类别**（勒索软件、外泄、人员风险、设备丢失、误投递、社会工程）
2. 在该类别中找到**最接近的案例**
3. 记下该案例的 **EDPB 建议**
4. 识别您的场景与案例之间的**关键差异**
5. 评估差异**增加还是降低**风险
6. 与您的 **ENISA 计算**比较——它们应一致

### 输出格式

> "此场景最接近 **EDPB 案例 [XX]：[简要描述]**——作为类比，而非有约束力的先例。
>
> EDPB 在该案例中的建议：监管机构通知 [是/否]，主体通知 [是/否]
>
> 您的情况不同之处在于：[关键差异]
>
> 类比的局限：[例如，渠道/媒介不同、规模、数据类别、访问证据]
>
> 此比较 [支持 / 建议重新考虑] 您计算的严重性结论 [等级]。基于您事实的第 33/34 条法律桥接仍然具有决定性。"

### 案例与 ENISA 冲突时

如果 EDPB 案例与 ENISA 计算建议不同结果：
- 记录两种评估
- 倾向更保守（更高级别通知）的方法
- 在内部合规日志中注明差异
- 考虑咨询法律顾问
