# 上诉文本生成

## 目的

让律师在**二审阶段**用一次对话拿到全套可直接使用的文本：一份**以上诉请求为核心、逐条挂靠判决书原文与法条原文**的民事上诉状，加上随附的证据清单、法条与类案检索报告、委托手续与工作文书。

**本技能不做一审的事。** 一审是从零构建主张（起诉状）；二审是**评价一份已经作出的裁判**——以民诉法为尺子，审查原审判决错在哪里、能撬动二审的哪一种处理方式。两者不是同一个物种，所以本技能独立存在。

**本技能也不做"诉讼策略"。** 案由定了，法律适用路线就大体定了；剩下的"改判还是发回重审、打全部还是打一部分"，本质就是上诉请求怎么写。本技能只做两件事：**把上诉人能打的点找全，把上诉请求写好。**

---

## 三项铁律（不可违背）

**铁律一 · 事实由当事人指认，不由 AI 推断。**
判决书认定的事实是否错误，只有当事人知道。律师看的是卷宗里"被记录下来"的部分，判决书恰恰可能错在**没被记下来的地方**。因此生成前**必须**做一次事实核对互动（H1）——但它是"必做的互动"，**不是"必须做完的闸门"**：当事人一时联系不上、不便逐条过判决书时，照常生成，只是事实类上诉理由必须标注「待当事人确认」，并在交付时标红提示。

**铁律二 · 法律由律师定性，AI 只做检索与核验。**
法律说理由律师结合生效判决的说理进行；元典连接器负责把**更贴合的法条**迅速找出来并核验效力、检索类案。判断"哪条最贴合"是执业判断，不可外包。

**铁律三 · 一切论述必须挂靠文书原文。**
- 事实主张 → 指向「判决书某段／庭审笔录某页／某证据名称」
- 法律主张 → 指向「法条名称＋条号＋**原文**」
- 对一审的批评 → 指向「判决书某段的说理」

**脱离文书原文的论述，一律不得进入上诉状。** 这是防幻觉、防"空泛抗议型"上诉状的最后一道闸。

## 适用场景

- 用户说「帮我写上诉状」「准备上诉材料」「这个判决能不能上诉」「评估上诉前景」
- 案件类型：**民商事案件**（不适用刑事、行政案件）
- 前置条件：用户提供**一审判决书或裁定书**（.pdf/.docx/图片均可）

**两种模式**

| 模式 | 触发 | 产出 |
|---|---|---|
| `full` | 「帮我写上诉状」「准备上诉材料」 | 走完五道闸门 + 全部产出（见「生成清单」） |
| `scan` | 「这份判决能不能上诉」「评估上诉前景」 | ①《一审判决漏洞清单》②《上诉可行性与胜算分档评估》③《上诉费测算》④《诉请—判项对照表》——**不出全套文书** |

`scan` 模式同样跑 H1 三问（成本就是问律师三句话），但不强制事实核对完成，评估结论按 H1 分支表自动标注可信度。

## 前置检查（必须执行）

### 1. 法律数据库连接器

本技能的核心检索引擎是 **`yuandian-mcp`（华宇元典）**：法规时效性核验、找更贴合法条、类案检索、企业信息补全。

- **已连接** → 按 `references/元典检索姿势.md` 的四步调用，产出《支持上诉请求的法条与类案检索报告》
- **未连接** → 不阻断生成，按降级模式运行：所有法条引用标注 `⚠️ 未经法规库核验，须执业律师逐条复核`，《检索报告》降级为「法条线索清单」并在交付回复中提示

### 2. 模型推荐

推荐使用最新版 **DeepSeek** 模型运行本技能，以获得最佳的法律推理与文书撰写效果。

### 3. 上游材料

不上传《委托代理合同》不阻断，但**建议主动提醒**：有已签署的合同（.docx/.pdf/图片）可自动提取代理律师姓名、执业机构、联系电话、律所地址、委托事项与代理权限，省去手动填写。

### 4. 二进制模板还原（仅从 SkillHub 安装时需要）

SkillHub 服务端不接受 .docx 等二进制 Office 模板（报 `400 不允许的文件类型`），故 4 份 .docx 模板（上诉状母版、风险告知书、工作反馈卡、委托代理合同）以 base64 文本载体 `references/templates-b64.json` 随包分发，安装后需还原一次（幂等）：

```bash
python3 scripts/restore_templates.py check     # 列出缺失/不一致
python3 scripts/restore_templates.py unpack    # 还原并逐文件校验 md5，已存在则跳过
```

`unpack` 遇到文件已存在且 md5 不一致时**中止并提示**，不覆盖本地模板；确要覆盖加 `--force`。**本机开发副本（含 .docx 原件）无需执行此步。**

⚠️ **二进制模板必须放顶层 `assets/`**：Skill 包只允许「根目录 / 二级目录 / 文件」两级结构，在 references 下再建 assets 子目录会被平台判为「目录层级超限」而解析失败。

## 生成前的五道闸门（顺序不可颠倒）

单轮提问 **≤5 个**；**凡是能从判决书自动提取的一律不问**（案号、法院、当事人、判项、诉请——先提后确认，让律师改而不是让律师填）。

### G0 期限闸（最先，先于一切）

必须问清：**判决还是裁定？送达日期是哪天？**（区分直接／邮寄／公告／电子送达）**我方是原审原告还是原审被告？委托人是自然人还是法人？**——**以及决定产出清单的那一问：一审是否本所（本律师）代理？**

最后一问的答案直接决定本次生成哪些文书：**续办二审（情形 A）不生成授权委托书、风险告知书、律师工作反馈卡、二审接待笔录**（详见「生成清单」A 表）。**这一问不问清，就会多生成四份用不上的文书、多让当事人签一次字。**

计算上诉期：

```bash
python3 scripts/deadline_check.py --served <送达日 YYYY-MM-DD> --type <判决|裁定>
```

- 判决 **15 日**、裁定 **10 日**，自送达之日起（民诉法第171条；期间计算规则见第85条）
- **剩余 ≤3 天 → 紧急模式**：先出上诉状保期限，其余材料在期限内后补（见 `references/当事人事实核对清单.md` 第四节）
- 期限已过 → **终止**，提示评估再审／申诉路径（本技能不生成再审文书）
- 脚本只自动处理周六周日；**法定节假日与调休必须人工核对**并提示律师复核

### G1 材料闸

按四档要材料，并明确告知"缺哪份会降级到什么分析深度"：

| 档位 | 材料 | 缺档后果 |
|---|---|---|
| **L0 硬门槛** | ① 一审判决书／裁定书**全文**（含送达日期、审判人员署名）② 委托人身份信息 ③ 承办律师信息 | 缺任一 → **终止**，提示补件 |
| **L1 上诉状必需** | ④ 一审起诉状 ⑤ 一审答辩状 ⑥ **一审诉讼请求逐项清单** | 缺 ⑥ → 射程校验做不了，上诉请求只能保守写并标注 |
| **L2 质量档** | ⑦ 一审证据目录＋证据材料 ⑧ **庭审笔录** ⑨ 一审代理词／质证意见 | 缺 → 降级为"仅判决书说理审查"，交付时标注「未做案卷级比对」 |
| **L3 加分档** | ⑩ 新证据线索 ⑪ 诉讼目的（拖延／减损／商誉／经济利益） | 缺 → 不能打"新事实／新证据／新理由"牌，影响**是否开庭** |

另可接受：**格式母版**（法院／律所自有上诉状模板 .docx，替代内置母版）。

### H1 事实核对互动（必做，但不阻断生成）

**形式上是一次"问律师"，不是"必须开成会"。** 三问，措辞必须反复强调**要有证据**：

> 1. **您是否已与当事人逐条确认过一审判决书中的事实认定错误？**（是／否／部分确认）
> 2. **当事人有没有新的事实或证据？** —— 只登记**有证据支撑**的：无证据支撑的单方陈述写进上诉状不但没用，还可能反噬。
> 3. 如有，请提供：**证据名称 · 持有情况 · 一审是否已提交 · 拟证明的事实**。

四分支处理（**任何一支都继续生成**）：

| 律师答复 | 动作 | 对上诉状的影响 |
|---|---|---|
| 已确认＋有新证据 | 正常推进，新证据入 L3 | 可打"新证据"牌 → 争取开庭 |
| 已确认＋无新证据 | 正常推进 | 事实攻击点限于**在案证据**与**认定逻辑矛盾** |
| 未确认／部分确认 | **继续生成**；事实类理由标注「待当事人确认」；清单与回复标红 | 律师须在递交前自行补齐 |
| 称有错但拿不出证据 | **不写进上诉状**（铁律三），记入《待取证线索表》 | 先取证，再决定是否上诉 |

同时生成 **《待确认事实清单》**（Word）——把判决书「本院查明」逐条拆条，律师有空就当面过、没空就直接发微信让当事人勾。详见 `references/当事人事实核对清单.md`。

```bash
python3 scripts/build_pending_facts_docx.py <payload.json> "<输出目录>/待确认事实清单.docx"
```

### G2 定请求闸（分析完成、动笔之前）

1. AI 输出《一审判决漏洞清单》（六诊结果，表格式，带"是否主张"勾选列）
2. **律师勾选**要主张的漏洞（未勾的不写进上诉状）
3. AI 出**上诉请求草案**（撤销哪一项判项、改判事项、主位／备位、一审二审诉讼费负担）
4. **律师确认或修改上诉请求 → 才允许写正文**

> **顺序不可颠倒**：上诉请求是全案天花板，写错（写少、写错、超射程）事后无法补救。**请求先于理由定稿。**

上诉请求三档写法（详见 `references/民诉法审查尺子表.md`）：

| 档位 | 写法 | 适用 |
|---|---|---|
| 主位改判 | 撤销原判，改判〔具体改判事项〕 | 事实清楚、证据充分 |
| **主位改判＋备位发回** | 撤销原判，改判〔…〕；或撤销原判决，发回重审 | **实务最常用** |
| 主位发回 | 撤销原判决，发回重审 | 遗漏当事人、违法缺席、基本事实不清等硬伤 |

### G3 回填闸（落盘前）

落款日期、签章位置、副本份数（对方当事人数＋2）、上诉费金额与预交提示、文件清单与实际产出逐格一致。

## 分析层：六诊

规则见 **`references/判决书解剖清单.md`**（总输出格式、六诊检查项、三条流水线），法条映射见 **`references/民诉法审查尺子表.md`**。

| 诊断 | 检查 | 产出 |
|---|---|---|
| ① 期限诊 | 裁判类型、送达日、剩余天数 | 期限闸门 |
| ② 主体·程序诊 | 遗漏当事人、违法缺席、送达瑕疵、审判组织、程序申请未处理、违反专属管辖、判决书内部矛盾 | 发回重审／撤销原裁判理由 |
| ③ 诉请·判项比对诊 | 判如所请／部分支持／**漏判**／**超裁**／判如所请但理由错误 | 《诉请—判项对照表》，定上诉请求边界 |
| ④ 三段论诊 | 大前提（法条时效／适用／漏引／请求权基础）、小前提（事实—证据比对四步、举证责任、证明标准）、涵摄、结论唯一性 | 改判理由（主战场） |
| ⑤ 说理诊 | 判而不理、说理与判项脱节、同一证据矛盾评价、对质证意见未评判、争议焦点漂移 | 改判辅助理由 |
| ⑥ 新要素诊 | 新证据／新事实／新理由、逾期举证正当理由 | 决定是否开庭 |

**每一条漏洞必须填满九列**（编号／类型／一审定位／**一审原话摘录**／违反的法律依据＋原文／支撑依据／对应二审处理方式／我方受损后果／可信度与是否主张）。**摘不出判决书原话、给不出具体依据的，该条不得进入上诉状。**

**映射不到二审法定处理方式（民诉法第177条）的，直接剔除。**

**先定情形，再定清单。** G0 闸门必须先问清「一审是否本所代理」——**续办二审（情形 A）与新接二审（情形 B）的产出完全不同**：续办时一审已经办过的委托手续类文书一律不再重复生成。

### C. 情形 A 的材料清单 `--skip` 参数

续办二审时未生成的行必须从清单剔除——**清单只列本次真正要当事人签字/盖章的材料**：

```bash
python3 scripts/generate_file_list.py references/文件清单及盖章指引模板.md \
  "<输出目录>/00 二审上诉材料清单及盖章指引.docx" \
  --case "案件：[上诉人]与[被上诉人][案由]二审上诉案" \
  --counterparties <对方当事人人数> \
  --skip "04,05-1,05-2,06,07,08,09,12,13"
```

序号以实际产出逐项核对为准，不要机械照抄上面这串。生成后核对脚本输出的 `self_check` 结果。

### D. 不出（任何情形）

- 起诉状（二审不写起诉状）
- **二审利息计算表**（二审一般不做）
- 一审已生成且在二审无变化的材料
- **"诉讼策略"类文件**（本技能不做策略）

### E. 委托手续三情形（G0 必须问到）

| 情形 | 委托代理合同 | 授权委托书 | 所函 | 风险告知书 / 反馈卡 / 接待笔录 |
|---|---|---|---|---|
| **A. 一审本所代理，续办二审** | **不签**（一审合同已约定二审阶段）；仅当律师明确要求时才出《二审阶段补充协议》 | ❌ **不出** | **仍需出具**（出具给二审法院） | ❌ **不出** |
| **B. 一审非本所，二审新接** | 全套新签 | 新出具 | 新出具 | 全部新出 |
| **C. 只代书上诉状，不代理二审** | 改签《法律文书代书委托书》 | 视需要 | 视需要 | ❌ |

## 工作流程

### 第一步 · 闸门与期限

G0 → G1 → H1（见上文）。期限与上诉费先行测算，两者都是**不可逆**事项：

```bash
python3 scripts/deadline_check.py --served 2026-09-10 --type 判决
python3 scripts/appeal_fee_calc.py --amount 800000 --counterparties 1
```

上诉费要点（诉讼费用交纳办法第17条、第22条第2款）：财产案件按**不服一审判决部分**的上诉请求数额计收；上诉费原则上**提交上诉状时预交**，上诉期内未预交的法院通知后 **7 日内**预交，**逾期视为撤回上诉**。

### 第二步 · 六诊与检索

按 `references/判决书解剖清单.md` 逐诊执行，产出《一审判决漏洞清单》《诉请—判项对照表》。法律线按 `references/元典检索姿势.md` 四步调用元典，**必须先读 `references/yuandian_tools_guide.md`** 再调用，避免参数试错。

### 第三步 · G2 定请求

律师勾选漏洞 → AI 出上诉请求草案 → **律师确认后才写正文**。

### 第四步 · 生成全部文本

**上诉状**（格式母版填充，格式逐项保留）：

```bash
python3 scripts/fill_appeal_docx.py assets/民事上诉状-脱敏模板.docx \
  "上诉文本_[上诉人简称]_[日期]/01-1 民事上诉状.docx" payload.json
```

payload 结构见 `references/上诉状填充字段表.md`。**脚本自检会拦截残留的 `〔〕` 占位符，不通过不落盘。**

**其余文书**（Markdown 模板 → docx）：

```bash
python3 scripts/render_docx.py references/所函模板.md "上诉文本_.../05-3 所函（指派函）.docx" --vars '<JSON>'
```

变量优先取 `private/lawyer-profile.json`，其次 `--vars`。

**固定文书原件直出**：

```bash
cp "assets/06-风险告知书.docx" "上诉文本_[上诉人简称]_[日期]/06 风险告知书.docx"
cp "assets/07-律师工作反馈卡.docx" "上诉文本_[上诉人简称]_[日期]/07 律师工作反馈卡.docx"
```

**必须 `md5` 核验**复制件与源文件一致；**不得**用 md 渲染方式重做这两份。

### 第五步 · 输出与交付

1. 全部文件输出到 `上诉文本_[上诉人简称]_[日期]/`
2. 生成文件清单（**份数按对方当事人人数，不是被告人数**）：

```bash
python3 scripts/generate_file_list.py references/文件清单及盖章指引模板.md \
  "上诉文本_.../00 二审上诉材料清单及盖章指引.docx" \
  --case "案件：[上诉人]与[被上诉人][案由]二审上诉案" --counterparties <对方当事人人数>
```

3. **清单与实际产出一致（强制）**：**先按情形裁剪**——情形 A 续办时用 `--skip` 剔除授权委托书、风险告知书、工作反馈卡、接待笔录、委托代理合同等本次未生成的行（见「生成清单」C 节）；内部工作底稿（01-2 漏洞清单、待确认事实清单）**不进清单**；脚本内置 `self_check`，不通过不落盘
4. 文件名编号必须与清单「序号」列完全一致
5. 使用 `present_files` 展示全部生成文件
6. 交付回复中必须提示：**上诉期届满日、上诉费预交义务、法定节假日需复核、未确认事实的标注位置**

## 核心规则与禁止项

### 上诉状

- **格式母版不可改动**：`assets/民事上诉状-脱敏模板.docx` 是格式基准，脚本只替换文字、不动版式。需要改版式时改母版本身，不要改脚本
- **必须包含民诉法第172条的六项内容要件**：当事人姓名／法人名称及法定代表人／其他组织名称及主要负责人、原审法院名称、案件编号、案由、上诉请求、上诉理由
- 事实与理由按 **「错误之一／之二／之三」** 编号，每个错误独立成段，按「引判决书原文 → 陈述真实情况 → 指明依据 → 推翻一审认定」四步展开
- 「事实上」后面的依据**不限于当事人陈述**，也可以是**在案证据或二审新证据**，但必须能指出具体依据
- **不得**在模板正文中使用 Markdown 行内加粗（`**`）——渲染引擎不解析，会原样印在文书上

### 上诉请求

- **不得超出一审诉请射程**（民诉法解释第326条）
- **不得遗漏有上诉利益的判项**——二审只审查上诉请求有关的事实与法律（民诉法第175条）
- 改判与发回重审可写**递进式**（改判为主、发回备位），**不得**写成两套互斥主张并列

### 副本与份数

- 上诉状按**对方当事人或者代表人的人数**提副本（民诉法第173条）：我方 1 ＋ 对方 N ＋ 法院 1
- **不是一审的「被告数＋2」**

### 私有配置（发布物零个人信息）

- **真实值存放**：`private/lawyer-profile.json`（已写入 `.gitignore`，发布副本自动排除）
- **模板里只有 `[占位符]`**，由脚本按优先级回填：`--vars` > `private/lawyer-profile.json` > 保留占位符并告警
- 换律所／换律师使用：填 `private/lawyer-profile.json` 即可
- ⚠️ **发布前必查**：`private/` 不得随发布物出现；`assets/*.docx` 与 `references/*.md` 全文不得含真实姓名／身份证号／手机号／客户名／案号

### 与其他技能的分工

- `case-file-review`（阅卷）→ 案卷 → 证据链，是二审证据清单的上游；本技能不重做阅卷
- `litigation-hub` → 上诉期与缴费期算出来后**交给它设三线提醒**，本技能不另建提醒系统
- `element-complaint-filler` → 仅法院要求要素式时联动
- 元典 MCP → 本技能的核心检索引擎（法规＋类案＋企业信息）
