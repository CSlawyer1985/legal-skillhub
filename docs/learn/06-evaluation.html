06 · 评测和迭代

法律人最容易接受的一个观点是："写完"不等于"能用"——通过评测才算写完。这一讲把"我觉得这个 Skill 不错"变成"我知道这个 Skill 好多少"。

一、一个反直觉的事实

很多看起来写得很好的 Skill，在评测中相对于"什么都不装"的基础模型没有任何提升，甚至因为塞了太多规则而表现更差。所以请记住这个公式：

Skill 的价值 = 相对基础模型的可测量增量——不在于你写了多少规则，而在于它让输出变好了多少。

二、一个最小评测集的结构

给自己的 Skill 建一个 evals/ 目录，至少包含以下用例：

用例类型数量作用法律 Skill 示例
正常用例3典型场景能不能做好一份标准买卖合同，要求审查
边界用例2极端情况会不会崩只有 2 页的合同；中英文混排合同
不应触发2防止误调用用户只是问"什么叫违约金"（理论咨询，不该启动审查流程）
对抗用例1压力测试合同里埋一个虚构法条引用，看 Skill 会不会跟着编

每个用例四要素：真实用户 Prompt + 必要的输入文件 + 预期输出 + 可验证的断言（Assertions）。断言要具体："输出必须包含风险等级分级""每个风险点必须定位到条款编号""不得出现'建议加强沟通'这类空话"。

contract-review/
├── SKILL.md
└── evals/
    ├── evals.json        ← 用例与断言
    └── files/            ← 输入材料（虚构的测试合同）

三、怎么跑评测

每个用例跑两遍：装 Skill 一遍，不装 Skill（基线） 一遍。比较四个指标：

  1. 断言通过率——装 Skill 的版本到底多过了几条断言？
  2. 任务完成质量——结构、深度、口径是否符合输出契约？
  3. Token 消耗——提升值不值这个成本？
  4. 执行时间——律师等不等得起？
干净上下文纪律：每次评测必须从全新会话启动。写 Skill 时残留的对话上下文会掩盖 Skill 本身的缺陷——你以为是 Skill 会了，其实是它"记得"。

四、版本迭代：评测驱动修改

评测暴露问题后，修改遵循"对症下药"：

评测发现病因改法
该触发不触发description 缺触发词把用户原话写进 description
不该触发乱触发没写不触发场景补"不适用于……"
输出结构不稳输出契约太粗把"每个风险点必须含四要素"写死
分析太浅自由度过高把判断标准从形容词改成口径（"超过 X 视为过高"）
经常跑题/漏步骤正文太长太散拆附属文件，正文只留导航（渐进式披露）
偶尔编法条缺验证动作加"引用前必须检索原文"的强制步骤

每改一版，重跑整个评测集——新旧两版盲测对比，提升才合并。这就是"一次版本改进记录"，是你的 Skill 走向成熟的证据链。

五、法律 Skill 特有的评测点

  • 虚构检测：输出中的法条引用逐条抽查是否真实存在；
  • 时效检测：引用已修订法条的旧版本内容，看 Skill 是否发现；
  • 法域检测：给一个香港法域的问题，看它是否拒绝用大陆法回答；
  • 保密检测：检查示例和输出模板里有没有残留真实客户信息。
