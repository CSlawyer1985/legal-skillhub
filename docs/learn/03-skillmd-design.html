03 · 编写 SKILL.md

SKILL.md 只有两部分：frontmatter（名片区）和正文（操作区）。写好的诀窍在于先理解 AI 怎么用它们——frontmatter 决定"会不会被调用"，正文决定"调用后做得好不好"。

一、描述就是路由器

AI 面对几百个 Skill 时，只看每个 Skill 的 name 和 description 来决定调用谁。description 不是产品简介，是调用条件。它必须同时回答两个问题：做什么 和 什么时候用。

写法示例评价
坏"一个合同审查助手"AI 不知道什么场景该调用，也不会知道不该调用
一般"审查合同风险"有动作无场景，容易误触发（用户只是聊聊合同理论也会被触发）
好"中国法律框架下的施工合同风险审查。当用户上传施工合同、EPC 合同，或要求审查工程价款、工期、变更、结算、违约条款时使用。不适用于商品房买卖合同审查。"做什么 + 何时用 + 何时不用，三个要素齐全

三个写作纪律：

  • 用第三人称（"审查……"而不是"我来帮你审查……"）；
  • 写进具体触发词（用户嘴里会说的词：起诉状、尽调、批注、N+1——这些词直接决定召回率）；
  • 写不触发场景（"不适用于……"和触发条件同样重要，能避免一半的误用）。

对比两个站内实例：construction-contract-review（边界清晰）与 contract-review-assistant（边界宽泛）——把它们的 description 放在一起读，你会立刻理解路由器写法的差别。

二、正文的九个标准件

正文没有法定格式，但成熟的法律 Skill 几乎都包含以下部件中的大部分：

  1. Intake（事实收集）——先收集信息，再开始分析。好的法律 Skill 绝不直接跳到结论。例如要求先确认：合同类型、我方立场、交易背景、重点关注。站内 家事尽调 把 Intake 做到了极致（结构化要素采集清单）。
  2. Workflow（工作流程）——分几个阶段、每个阶段做什么。阶段顺序就是专业判断的固化。
  3. Decision Points（判断节点）——在哪些地方必须停下来判断、依据什么判断。这是律师经验和 AI 执行的分界面。
  4. Guardrails（护栏）——不许做什么：不虚构法条、不替客户做最终决策、不确定就标注。
  5. Output Contract（输出契约）——交付物的结构、格式、粒度。写清"每个风险点必须定位条款+说明理由+给出建议"。
  6. Verification（验证）——输出前自检什么：法条是否现行有效？引用条款编号是否与原文一致？
  7. 异常处理——材料缺失、语言不符、超范围时怎么办。
  8. 触发/不触发场景——与 description 呼应的正文级细化。
  9. 示例——一个输入输出的样例，胜过三段抽象描述。

三、任务自由度：法律 Skill 最核心的设计决策

同一项法律任务，可以写成三种"硬度"——这叫任务自由度，是法律 Skill 设计里最微妙的判断：

自由度写法适合的法律任务风险
高（只给原则和判断标准）"审查违约责任是否对等，综合考虑……"法律分析、策略研判输出不稳定，深浅不一
中（给模板、伪代码、参数化流程）"按以下六步审查；违约金口径默认 LPR 4 倍，可调整参数 X"合同审查、尽调、检索覆盖不全时容易教条
低（给固定脚本、固定步骤、强制校验）"必须调用 search_law.py 检索，输出必须包含条款编号+原文+来源，缺一项判不合格"计算、格式处理、文书要素填充、合规检查僵硬，遇例外就错

法律分析不能全部写成刚性流程，也不能全部留给模型自由发挥。实务中的黄金分割是：流程刚性 + 判断弹性——"必须走完这六步"（刚性），"每一步里怎么判断，给你标准和空间"（弹性）。站内两个典型对照：complaint-drafter（极低自由度：在最高法 67 类官方模板上"填空而非重写"，连字体和留空都强制）与 civil-litigation-mindset（高自由度：只给诉讼思维框架）。

四、渐进式披露：SKILL.md 只做导航

SKILL.md 正文建议控制在 500 行以内。超出的内容按性质拆到附属文件，正文只留链接：

内容放哪原因
触发条件、总流程、输出契约SKILL.md每次必用，必须在主文件
法规依据、审查标准、内部口径references/体量大，按需加载一层，不要多层嵌套
合同范本、文书样式assets/ 或 templates/调用时才读取
检索/计算/格式处理脚本scripts/可执行工具，附使用说明
输入输出示例examples/ 或正文末尾少量即可
测试用例evals/见第 06 讲
一层原则：附属文件直接从 SKILL.md 链接，references 里的文件不要再链向更深层的文件。每多一层，AI 漏读的概率就高一截。

站内知识库型的标杆：ad-compliance-consumer-rights-review-plus（SKILL.md 做导航，78 个附属文件分层承载法答网问答、标签合规锚点、理论库）——它的文件树就是"渐进式披露"的完整教案。

五、自检清单

写完 SKILL.md 后，逐条问自己：

  • description 能让一个外行 AI 在 100 个 Skill 里准确选中它吗？
  • 有没有写明"什么时候不要用"？
  • Intake 是否先于分析？还是直接跳到了结论？
  • 判断标准写的是可操作口径（"超过 X 视为过高"），还是正确的废话（"注意合理性"）？
  • 输出契约是否具体到"每个风险点必须包含哪几个要素"？
  • 正文是否超过 500 行？超出的部分拆了吗？
  • 有没有"不写 AI 也知道"的内容（法条原文、常识）？

六、元技能推荐：让 AI 来写 SKILL.md

前五节是徒手写 SKILL.md 的方法。实际动手时更快的路径是装一个元技能（制作 Skill 的 Skill）——把"把这个流程做成一个 Skill"这句话直接交给 AI，由它完成调研、起草、评测、发布的全流程。推荐三个，按工程化程度递进：

1. Anthropic 官方 skill-creator —— 官方口径的基线

anthropics/skills 仓库中的官方元技能：负责意图澄清、起草 SKILL.md、生成测试用例、打包发布。它定义了 Anthropic 对 Skill 结构的官方理解（frontmatter + 正文 + references 分层），本讲前五节的规则大多源自它。三个中最轻，适合第一次接触元技能、想先理解官方口径的人。

2. qiaomu-meta-skill —— 先研究再创造

乔木元技能（joeseesun）的核心差异是"先研究再创造"：动手写之前先在 skills.sh、SkillsMP 检索同类 Skill，回到 GitHub 核验来源、维护状态与许可证，对每个候选记录 keep / adapt / reject / invent 决策，避免拼贴抄袭。产出按原型等级控制复杂度——个人试验走轻量 Scaffold，公开发布才启用完整 Governed 门禁；配触发评测（应触发/不应触发/近邻场景）、质量门禁（目录结构、版本一致性、上下文预算）、密钥泄漏扫描和一键开源发布（功能分支 → PR → 合并 → Release → npx skills add 安装验证）。作者自述已用此流程产出 28 个 Skill。安装（需 Node.js 18+）：

npx skills add joeseesun/qiaomu-meta-skill

3. yao-meta-skill —— 把 Skill 当软件工程来管

YAO 元技能（yaojingang）自称"Skill OS"，是三个中工程化最重的一个：先用平台中立的"技能 IR"（意图、触发器、输入输出、边界）建模，再编译到 Claude、OpenAI、Codex、VS Code 多平台；配 Output Eval Lab（输出断言、盲审 A/B 包）、Review Studio 单页审查门户、发布治理（安装模拟、权限探测、证据账本）和 SkillOps 持续迭代循环（采纳漂移检测、每日看护报告）。作者自评 91.5/100（对比官方 skill-creator 67.5、OpenAI 50.5），但仅有一次人工盲审，属自评参考。安装（需 Python 3.11+）：

npx -y skills add yaojingang/yao-meta-skill -a codex -g -y
选型提示：三个的差别本质是第 3 节的"任务自由度"——官方版最低（固定流程），乔木版是"流程刚性 + 判断弹性"的折中，YAO 版自由度最高、工程化最重。个人法律 Skill 起步用官方版或乔木版即可；需要跨平台分发、持续迭代治理的团队级资产，再上 YAO。
